Servers and deployment

Shop service

The Shop is an optional .NET service that runs the in-game premium shop: the catalog, the premium balances of every account, purchases and gifts, and real-money payments. This page covers how it fits with the rest, its catalog file, every endpoint and setting, payments, and how to run it locally and in production.

For the player side (the shop window, premium currencies) see Cash shop. For editing offers in the editor see Shop page.

#How it fits

  • Separate and optional. Central knows nothing about the Shop. Without it the game runs normally and the shop button doesn't show.
  • Online only. Single player games have no shop.
  • Players never reach it. The shop window asks the map server; the map server calls the Shop's internal API with its key (X-Shop-Key). Only payment webhooks come from outside, through Caddy.
  • Same database. It uses the database Login and Central use. Login must have started once so the items catalog is filled.
  • Purchases travel by mail. A buy writes the charge and a letter with the bought items in one transaction. Map servers take shop letters into the bag at once (unless Shop Auto Take (shopAutoTake) is off in Game Settings); if the bag and the bank are full, the letter waits in the mailbox and the player is told.
Who Talks to the Shop with Over
Map servers Internal API, X-Shop-Key HTTP on the private network, port 5300
Payment providers Webhooks, signed HTTPS through Caddy on the Login domain
You and the editor Admin API, X-Admin-Key HTTP on 127.0.0.1:5300, or an SSH tunnel

#Running it

#On your computer, from the editor

Open the Shop page of the KitARPG window, turn the shop on and press Start the shop. The editor runs the launcher with --headless --shop-only, with keys made for this computer and the catalog in UserSettings/KitARPG/shop-conf.json. Maps in Play find it on their own. See Shop page.

#With the launcher

Tick Premium shop in the launcher window, or set ShopEnabled and ShopAutoStart in launcher.json. The Shop starts with Login and Central on port ShopPort (5300), and the maps Central starts get its address and key. See Launcher.

#By hand, for development

cd Services
ASPNETCORE_ENVIRONMENT=Development \
Database__ConnectionString="Data Source=/full/path/to/kitarpg.db" \
dotnet run --project Shop          # http://localhost:5300

In Development the map key is dev-shop-key and the admin key dev-shop-admin-key (appsettings.Development.json). Point it at the same SQLite file as Login and Central.

#In Docker Compose

docker compose --profile shop up --build -d

Set KITARPG_SHOP_KEY and KITARPG_SHOP_ADMIN_KEY in Deploy/.env first. See Docker.

#How map servers find it

Map server reads What it is
-shop <url> or KITARPG_SHOP_URL The Shop's address, for example http://shop:5300
-shopKey <key> or KITARPG_SHOP_KEY One of the Shop's map keys

In the editor, a map in Play without these uses the Shop page's settings (UserSettings/KitARPG/launcher.json). A built map server refuses a plain http:// address on a public IP, since the key would cross the internet readable: use https:// or a private address.

#The catalog file

shop-conf.json, at Shop:CatalogPath (relative to the service's folder unless absolute). A sample ships next to the service; if the configured file is missing, the first start copies the sample there.

{
  "mailSender": "Shop",
  "mailDays": 30,
  "products": [ { "id": "gems_500", "currency": "gems", "amount": 550 } ],
  "offers": [
    {
      "id": "potion_bundle", "name": "Potion Bundle", "description": "Twenty of each.",
      "category": "Supplies", "icon": "", "image": "", "banner": "", "badge": "Sale", "order": 0,
      "currency": "gems", "price": 60,
      "items": [ { "itemId": "health_potion", "amount": 20 }, { "itemId": "mana_potion", "amount": 20 } ],
      "startsAt": "", "endsAt": "2026-12-31T23:59:59Z", "perAccount": 0, "giftable": true, "hidden": false
    }
  ]
}

#Top level

Field What it does Default
mailSender Sender name on purchase letters Shop
mailDays Days a purchase letter stays in the mailbox 30
products What each real-money product gives (below) Empty
offers What the shop sells for premium currency (below) Empty

#Offers

Field What it does Default
id Unique id, up to 64 characters. Never change it once sold: buy limits and history use it Required
name, description What players read Empty
category The entry it shows under on the shop's left side Featured
icon Item whose icon the card shows. Empty uses the first item's Empty
image Key of the card and detail picture in the game's Shop Art. Empty draws the icon Empty
banner Key of a wide picture. Offers with one take turns at the top of the shop Empty
badge Ribbon on the card, such as New or Sale, up to 24 characters Empty
order Lower comes first when sorted by relevance 0
currency The premium currency it costs Required
price Price, above 0 and up to 1,000,000,000,000 Required
items itemId and amount of each item it gives. At least one Required
startsAt, endsAt UTC, ISO 8601 (2026-12-01T00:00:00Z). Empty is always Empty
perAccount Times one account can buy it. 0 is no limit 0
giftable Can be bought as a gift for another character true
hidden Kept for history but no longer sold false

#Products

Each real-money product id (the one your payment provider sends) gives an amount of one currency.

Field What it does
id Product id, unique, up to 64 characters
currency The premium currency it gives
amount How much, from 1 to 1,000,000,000,000

#Checks and reloading

  • Each offer and product is checked: id, currency, price, dates (ISO 8601, ending after starting), badge and picture key lengths, at least one item with an amount, no repeated ids, and every item present and not retired in the items table.
  • A bad offer or product is logged and left out. It never stops the service. If the items table is empty, the item check is skipped with a warning.
  • The file is read again half a second after it changes, and on POST /api/shop/admin/reload. A file that can't be parsed keeps the last good catalog.
  • The catalog has a version, a short hash of the offers on sale, so maps know when to fetch it again.

#How buying works

  1. The player picks an offer in the shop window. The map server makes the item copies (with their random bonuses) and sends them with the offer id to /api/shop/internal/buy.
  2. The Shop charges the price from its own catalog, never one from the map, and checks the copies against the offer: same items, same amounts, unique ids, known to the item catalog.
  3. It checks the offer is on sale, the per-account limit and the balance.
  4. In one transaction, one buy at a time, it writes the charge to currency_ledger and a letter with the copies, from mailSender, marked Kind = shop, with the subject From the shop: <offer> (or A gift from <buyer>).
  5. The map takes the letter into the bag; Central deletes a shop letter once it is taken.
  6. The buy is written to game_logs as shop.premium_buy or shop.premium_gift.

Refusals (not enough currency, limit reached, not on sale, wrong copies) come back as a normal answer with ok: false and a message for the player.

  • Gifts. The offer must be giftable. The recipient is found by character name and can't be the buyer.
  • Grants. GM commands (/currency gems 100 Name) and game rewards use the internal grant. A reference sent by a map is stored as map:<reference>; without one it becomes grant:<guid>, so grants never collide with payments.

#The ledger

Every change to a balance is a row of currency_ledger: account, currency, change, reason, offer, detail and a unique reference. The balance is the sum of the rows. The unique reference makes a retried payment, grant or webhook count once.

Reason When
shop.buy A buy or gift
premium.topup A paid webhook
premium.refund A refund webhook
gm.grant A GM grant or an admin grant
game.reward A game reward, such as a quest

#Internal API

For map servers. Header X-Shop-Key with one of Shop:MapKeys or KITARPG_SHOP_KEY. Bodies and answers are the shared classes in ShopMessages.cs.

Method Route Body → answer
GET /api/shop/internal/catalog ShopCatalog: the version and every offer that isn't hidden. The client filters by date
POST /api/shop/internal/state ShopStateRequest (characterId) → ShopState: balances of every catalog currency and any the account holds, buys per offer, catalog version. 404 for an unknown character
POST /api/shop/internal/buy ShopBuyRequest (characterId, offerId, items, giftTo) → ShopResult (mailedTo is the character who got the letter, state the buyer's)
POST /api/shop/internal/grant ShopGrantRequest → ShopResult (changed is the target character)

#Admin API

Header X-Admin-Key with Shop:AdminKey. Empty AdminKey turns the admin API off. Caddy doesn't forward it: call it from the server itself (127.0.0.1:5300) or through an SSH tunnel.

Method Route What it does
GET /api/shop/admin/catalog The whole file as a ShopConfig, including hidden offers and ones that fail the checks. 409 if it can't be parsed
PUT /api/shop/admin/catalog Publishes a whole ShopConfig (at most 2 MB, 2,000 offers and 500 products). All or nothing: with any problem nothing is written and the answer is 400 with one line per problem (Offer witch_hat: gives no items). Otherwise 200 with ok, the new version and the number of offers
GET /api/shop/admin/offers Every offer in use, hidden ones too, and the products
PUT /api/shop/admin/offers/{id} Adds or replaces one offer, checked like the file. The rest of the file stays; comments in it are lost
DELETE /api/shop/admin/offers/{id} Removes the offer from the file. Its buys stay in the ledger
POST /api/shop/admin/reload Reads the file again. 409 if it can't be parsed
POST /api/shop/admin/grant { username or accountId, currency, amount, reason?, reference?, detail? }. A negative amount takes. The same reference twice applies once. Answers applied and the new balance
GET /api/shop/admin/balance/{username} Every currency the account has
GET /api/shop/admin/history/{username}?take=50 The latest ledger rows, at most 500

The editor's Publish to server and Pull from server use the catalog routes. From a terminal:

curl -H "X-Admin-Key: $KEY" http://127.0.0.1:5300/api/shop/admin/balance/alice
curl -X POST -H "X-Admin-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"username":"alice","currency":"gems","amount":500,"reason":"support","reference":"ticket-1234"}' \
  http://127.0.0.1:5300/api/shop/admin/grant

Writes replace the file by writing it aside and renaming it over the old one. In Docker the Deploy/shop folder must be writable by the container user (sudo chown 1654 shop).

#Payments

Webhooks arrive at POST /api/shop/webhooks/{provider}, which Caddy forwards from https://<login domain>/api/shop/webhooks/....

  • A paid event adds amount × quantity of its product (premium.topup). A refund takes it back (premium.refund). A balance can go below zero; the player then can't buy until it is back above the price.
  • An event already applied answers 200 with "status": "duplicate". An unknown account or product answers 422 and is logged. A bad signature answers 400.
  • At most Shop:MaxQuantity (100) units of a product per payment.

#Stripe

Set Shop:Stripe:WebhookSecret (KITARPG_STRIPE_WEBHOOK_SECRET) to the endpoint's signing secret from the Stripe dashboard. The Shop checks Stripe-Signature itself (HMAC-SHA256 of {t}.{body}, at most ToleranceSeconds old), without the Stripe SDK.

  1. In Stripe, add a webhook endpoint https://login.mygame.com/api/shop/webhooks/stripe for checkout.session.completed, checkout.session.async_payment_succeeded and charge.refunded.
  2. Create Checkout Sessions from your website with client_reference_id (the account id or username), or metadata.account_id / metadata.username, plus metadata.product (a product id from the catalog) and metadata.quantity when it isn't 1.
  3. Completed sessions count once paid. The reference is stripe:<payment_intent>.
  4. charge.refunded counts once the charge is refunded in full and takes back exactly what that payment gave. Handle partial refunds with the admin grant.

#Your own web shop

Set Shop:Signed:Secret (KITARPG_SHOP_SIGNED_SECRET) and have your shop post to /api/shop/webhooks/signed:

  • Header X-KitARPG-Signature: sha256=<hex HMAC-SHA256 of the raw body with the secret>.
  • Body { "id", "kind": "paid" | "refunded", "accountId" or "username", "product", "quantity", "refundOf" }. A refund with refundOf (the id of the paid order) takes back exactly what that order gave.

#Another provider

Implement IPaymentProvider in the Shop project:

  • Name is the {provider} in the URL.
  • Read checks the signature and returns a PaymentEvent, null for events to ignore, or throws PaymentRejectedException for forged ones.
  • Register it in Shop/Program.cs: builder.Services.AddSingleton<IPaymentProvider, MyProvider>();.

Consoles and mobile stores need their own payment systems.

#Settings

Setting What it does Default
Shop:CatalogPath The catalog file shop-conf.json
Shop:MapKeys Keys map servers send as X-Shop-Key. KITARPG_SHOP_KEY adds one more. Several allow rotating them Empty (dev-shop-key in Development)
Shop:AdminKey Key for the admin API. Empty turns it off Empty (dev-shop-admin-key in Development)
Shop:Stripe:WebhookSecret Stripe endpoint secret (whsec_...). Empty turns Stripe off Empty
Shop:Stripe:ToleranceSeconds How old a Stripe event may be 300
Shop:Signed:Secret Secret shared with your web shop. Empty turns it off Empty
Shop:InternalPerMinute Internal API requests per client address and minute 1200
Shop:WebhooksPerMinute Webhook requests per client address and minute 120
Shop:AdminPerMinute Admin API requests per client address and minute 30
Shop:MaxQuantity Most units of a product in one payment 100
Shop:MaxItemsPerBuy Most item copies one buy may carry 100

It also reads Database, Proxy and Logs like the other services. See Configuration.

#Security

  • Outside Development the Shop refuses to start without a map key, or with a map key, admin key or provider secret that is empty, short or a sample value. An empty provider secret only turns that provider off.
  • Keys and signatures are compared in constant time. Every endpoint group has its own rate limit per client address.
  • The internal and admin APIs stay off the internet. Map servers on other machines reach the Shop over a private network or a WireGuard tunnel.
  • Run a single Shop per database: buys are serialized by a lock in its process. The Shop only adds new item rows inside new letters; moving copies stays with Central.

#Common mistakes

  • The shop button doesn't show. The Shop isn't running, the map has no -shop/-shopKey, or the In-game shop module is off.
  • An offer is missing in the game. It failed a check (the Shop's log names it), it is hidden, or its dates exclude today.
  • Publishing from the editor fails with 401. The admin key on the Shop page doesn't match Shop:AdminKey.
  • Admin edits fail in Docker. The shop folder isn't writable by uid 1654.
  • A payment didn't arrive. Look for the webhook in the Shop's log: 400 is a wrong secret, 422 an unknown account or product id.
