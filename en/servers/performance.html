Servers and deployment

Performance

The performance targets KitARPG is designed for, what has been measured, the settings that decide how much a map server can carry (tick rate, visibility grid, connections, saves) and how to watch and plan the capacity of your own servers.

#Targets

These are the design targets for one map server. Measure your own game against them: your maps, monsters and skills change the numbers.

Metric Target
Players on one open map (a town) 200
Players in one dungeon copy 1 to 4, several copies in the same map server
Server simulation 30 ticks per second
Server upload per player Under 10 KB/s on average
Memory per map server process Under 1 GB
Character saves Every 60 seconds, on leaving and on changing maps
Login response Under 300 ms
Client 60 FPS on a mid-range PC

#What has been measured

The load test uses a map server with 300 monsters and headless bots that connect, walk at random and use an area skill every few seconds, with the same server build and Mirror settings the kit uses.

Test Bots Ticks per second KB/s per player Memory Notes
Local, Mac 50 for 75 s 30, steady 0.8 to 0.9 Bot process: about 175 MB Server and bots on the same computer, 300 monsters
Docker on a Mac (x86 emulated) 50 for 90 s 28 to 29 0.9 Server: 243 MB Checks the image; ticks aren't representative under emulation

The KB/s figures are Mirror's payload, without KCP, UDP and IP headers. Measure real traffic with docker stats or your host's network graphs.

#How the work is split

Knowing where the load goes tells you what to scale.

Piece Load grows with Scales by
Map server Players and monsters on that map, how many see each other, skills and effects One process per map. Move busy maps to their own machine
Dungeon copies Copies open at once, each a full copy of the scene They share their map server's process; an empty copy unloads after emptyMinutes (5)
Central Saves, map changes, chat, guild, mail and market traffic One instance. Its database queries are the main cost
Login Sign ins (Argon2id uses 19 MiB and some CPU per attempt) Several instances behind the proxy
Database Saves from every map, item moves, logs PostgreSQL on fast disks; a bigger instance

#The server tick

The map server runs Mirror's loop at Send Rate (sendRate) on KitNetworkManager, 30 per second in the kit. A headless server runs one frame per tick, so this is both the simulation rate and the network update rate.

  • The sign of overload is the tick rate dropping below 30. Frame times near 33 ms are normal at 30 ticks: they include the wait for the next tick.
  • Raising it makes movement smoother and costs CPU and bandwidth in proportion. Lowering it to 20 saves both at the cost of responsiveness. Keep the client and server on the same value (both read the same prefab).

#Interest management

KitInterestManagement, on the KitNetwork prefab, decides what each player receives. It is Mirror's spatial hashing grid with the kit's rules on top:

  • the world is split into square cells of half visRange (20 meters with the kit's 40), and each player gets what is in their cell and the eight cells around it;
  • invisible enemies (the stealth status) are hidden from their foes;
  • event monsters brought for one player are sent to that player only.
Field What it does Kit value
visRange Meters a player sees. The grid's cells are half this size 40
rebuildInterval Seconds between visibility rebuilds 1

Bandwidth grows with how many entities each player sees, not with the players on the map. A town of 200 players spread out costs far less than 200 players in one square.

  • Lower visRange to send less in crowded maps. The camera must not show farther than this, or players see things pop in.
  • Raise rebuildInterval to spend less CPU on rebuilds; new things then appear a little later.

The same rules decide what a player can target: the server never accepts a target the connection doesn't see.

#Connections per map

Max Connections (maxConnections) on KitNetworkManager is the most players one map server accepts. The kit ships it at 100. To reach the 200 player target on a map, raise it on the KitNetwork prefab and rebuild the map servers, then load test.

#Transport

The kit uses KCP over UDP with these values on KcpTransport:

Field Kit value What it does
NoDelay On Sends at once instead of waiting to batch
Interval 10 ms KCP's internal update interval
Timeout 10000 ms A silent connection is dropped after this
SendWindowSize, ReceiveWindowSize 4096 Packets in flight; enough for a busy map
MaxRetransmit 40 Retries before a connection is considered dead
MaximizeSocketBuffers On Asks the OS for large socket buffers

Leave them unless a load test points at them.

#Saves

  • Each player is saved every Save Interval Seconds (saveIntervalSeconds on MapServer), 60, plus when they leave and when they change maps. Central also writes at once for anything it handles itself: trades, mail, the market, guild storage.
  • One save per character is in flight at a time; a newer one waits for it.
  • A longer interval lowers database writes; a crash then loses up to that many seconds of progress (experience, loot picked up). A shorter one is safer and costs more writes.

#Command limits

Every client command counts against a budget of 30 per second with bursts of 60; a client far above that is disconnected as flooding. Commands that go on to Central get 2 per second with bursts of 10. These protect the server from modified clients and keep one player from using everyone's CPU. They are fixed in code (CommandPacing).

#Planning capacity

Concurrent users (CCU) for the whole game are the sum over maps. Work it out map by map:

  1. List your maps and where players gather. Towns and event areas hold most players; field maps fewer; dungeons only their parties.
  2. Load test the busiest map on the machine you will rent, with your monsters and skills. Raise players until the tick rate drops below 30, then keep a margin below that.
  3. Add the dungeon load to its map server: each open copy costs like a small map with its monsters.
  4. Give each busy map its own machine when one machine can't hold them all, connected to Central over a private network. See Docker.
  5. Check the database. With many players, saves every 60 seconds and the game log add up; watch PostgreSQL's CPU and disk.

#Watching your servers

What Where
Players per map GET /api/maps on Central: curl http://127.0.0.1:5200/api/maps on the server
CPU, memory, network per container docker stats
A map server's log docker compose logs map-town, or data/logs/map-<id>.log from the launcher
Service health GET /health on Login, Central and the Shop
Slow or failed saves Central's log (Save of character ... refused) and the map log (... was not saved)
Game activity /logs in game, or the game_logs table

#Tips

  • Load test on the same kind of machine you will run on. A laptop, or x86 emulated on Apple silicon, tells you little about a VPS.
  • The Linux map server is built with IL2CPP: native code costs less CPU per tick than Mono.
  • Spread NPCs, vendors and spawn points so players don't all stand in one grid cell.
  • Many monsters awake far from players cost CPU for nothing; place spawners where players go.
  • Keep Logs:Days reasonable on busy servers; the game log grows with every action.
