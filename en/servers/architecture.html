Servers and deployment

Architecture

How an online KitARPG game is put together: the client, the Login, Central and Shop services, the map servers and the database, what each one owns, the ports and protocols between them, and what happens from sign in to changing maps.

#The pieces

An online (MMO) game is five kinds of programs. A single player game is one: the client hosts its own map and saves to a local file (see Single player).

Piece What it is Made with Owns
Client The game players install Unity, Mirror Nothing. It only asks; the servers decide
Login Web service for accounts and characters .NET 10, ASP.NET Core Accounts, passwords, access tokens, "Remember me" tokens, character creation and deletion, the item and skill catalog in the database
Central Web service plus a UDP link for the map servers .NET 10, ASP.NET Core, LiteNetLib Sessions (one per account), map tickets, the list of running maps, character saves, chat between maps, friends, parties, guilds, alliances, mail, the market, tax collectors, reports, GM audit, every move of an item between owners
Map servers One Unity server per map, without graphics Unity, Mirror with KCP The live world of its map: players, monsters, combat, loot, NPCs, dungeon copies. It never touches the database
Shop (optional) Web service for the premium shop .NET 10, ASP.NET Core The shop catalog, premium balances, premium purchases and gifts, real-money payment webhooks
Database SQLite file or PostgreSQL EF Core Everything that lasts. Login, Central and the Shop share one database

All three services and the map servers are separate processes. On your computer the launcher starts them for you (Launcher); on a server Docker Compose does (Docker).

#How they talk

From To Protocol Default port What travels Who can reach it
Client Login HTTP (HTTPS in production) 5100 locally, 443 behind Caddy Register, sign in, "Remember me", character list, create, delete Everyone
Client Central HTTP (HTTPS in production) 5200 locally, 443 behind Caddy POST /api/play: which map, its address and a one-use ticket Everyone
Client Map server Mirror over KCP (UDP) 7777 town, 7778 forest, 7779 crypt, 7780 guild_hall The game itself: the ticket first, then input, world state, chat, windows Everyone
Map server Central LiteNetLib (UDP), key in the connection request 7700 Registration, heartbeats, ticket checks, character saves, map changes, chat, social, guild, mail, market, GM audit, game log Only map servers. Never the internet
Map server Shop HTTP with the X-Shop-Key header 5300 Catalog, balances, buys, grants Only map servers. Never the internet
Payment provider Shop HTTPS through Caddy 443 Signed webhooks on /api/shop/webhooks/{provider} Everyone, checked by signature
Editor or operator Shop HTTP with the X-Admin-Key header 5300 Admin API: publish the catalog, grant, balances, history The server itself only (127.0.0.1)
Login, Central, Shop Database SQLite file or PostgreSQL protocol 5432 for PostgreSQL All lasting data The services only

During play the client holds a single network connection: the one with its map server. Chat, friends, parties and guild messages go through the map, which forwards them to Central over the map link. The client never talks to the Shop: shop windows ask the map, and the map asks the Shop.

#The picture, in words

Read it from top to bottom:

  1. At the top is the client. It has two HTTPS lines going up-left to Login and Central, and one UDP line going right to its map server.
  2. In the middle row sit Login, Central and the map servers. Central and each map server are joined by a two-way UDP line, the map link, on port 7700. The map servers also have an HTTP line to the Shop, which sits next to Central.
  3. At the bottom is one database. Login, Central and the Shop each have a line down to it. The map servers have none.
  4. In production a Caddy box sits in front of Login, Central and the Shop's webhook route, turning HTTPS from the internet into plain HTTP on the private network.

#What each piece owns

Each kind of data has one owner, so two programs never fight over it.

Data Owner Notes
Accounts and passwords Login Argon2id hashes. Bans are read by every service on each request
Access tokens (JWT) Login signs, Central validates Same signing keys in both. 30 minutes by default
Characters (creation, deletion) Login Start values come from gamedata.json, exported from your Game Database
Characters (everything after creation) Central Saved by the map that holds the character, through Central. A version number refuses old saves
Sessions and tickets Central, in memory One session per account. Lost if Central restarts, which ends every session
Parties Central, in memory Rebuilt by players after a Central restart
Item copies changing owner Central (ItemLedger) Bag, bank, guild storage, letters, collectors and market lots are all rows of one table with exactly one owner
Item and skill catalog Login Copied from gamedata.json at every start. Manual edits are overwritten
Live world state Map server Monsters, positions, combat, buffs, dungeon copies. Saved characters are the only part that lasts
Premium currency and shop buys Shop A ledger of rows in currency_ledger; the balance is their sum
Game log, GM audit, reports Central (and Login, Shop for their own lines) Tables game_logs, gm_audit, reports

Details per table are in Database.

#From sign in to playing

  1. Sign in. The client sends the username and password to Login over HTTPS (POST /api/auth/login). Login checks the Argon2id hash and answers with an access token that lives Auth:TokenMinutes (30) and, with "Remember me", a one-use remember token.
  2. Pick a character. The client lists characters (GET /api/characters) and can create one (POST /api/characters). Login creates it with the class, start map, position, health, mana and start items from gamedata.json.
  3. Ask to play. The client sends the access token and the character id to Central (POST /api/play). Central:
    • checks that the character belongs to the account and that the account isn't banned;
    • if the account is already in a map, tells that map to save and drop the character, and waits up to Central:KickWaitSeconds (5) for the save (see Logging in twice);
    • makes sure the character's map runs: a running map is used, a map with an executable is launched and waited for up to Central:LaunchTimeoutSeconds (60), and a map without one (Docker, the editor) gets 3 seconds to register;
    • opens a session and answers with the map's address, port and a random ticket that expires after Central:TicketSeconds (30).
  4. Join the map. The client connects to the map server with Mirror and presents the ticket, its network version and its control mode. The map server sends the ticket to Central over the map link. Central redeems it once, loads the character from the database and sends it back. The map refuses a client built from different network code (version_mismatch) or with another control mode (mode_mismatch).
  5. Play. The client sends requests; the map server validates and applies them. The map saves each character every 60 seconds (MapServer.saveIntervalSeconds), when they leave and when they change maps. Each character has one save in flight at a time, and Central refuses a save from a map that doesn't hold the character or with an old version.
  6. Change maps. When a player takes a portal, the map saves the character with its destination and sends a transfer request to Central. Central checks the session, starts the target map if needed, saves the new position and returns a ticket for the target. The client shows the loading screen and joins the new map with that ticket.
  7. Leave. The map saves the character with leaving set and Central closes the session. If the map server stops or loses Central, every session on it ends and the players go back to the title.

#Logging in twice

There is one session per account. When an account asks to play while its character is still in a map:

  • Central sends that map a kick with the reason logged_in_elsewhere. The map saves the character and drops it.
  • Central waits up to Central:KickWaitSeconds (5) for the save to arrive.
  • If it arrives, Central reads the character again and hands out the new ticket.
  • If it hasn't, /api/play answers HTTP 503 with session_busy and no ticket. The client tries again a moment later. Handing out a ticket before the save lands would load the character from before it, and anything the old session moved (gold, items) would exist twice.
  • If the old map is gone, the session is dropped at once.

#Scaling model

  • One process per map. Each map id runs in exactly one map server. Central refuses a second registration of the same map id while the first is connected. More players means more maps (or bigger hardware for a busy map), not copies of the same map.
  • Dungeons run inside their map server. An instanced map (MapData.instanced) gives each party, or each player alone, its own copy of the scene, loaded again inside the same process and moved instanceSpacing (1000) meters away from the others. An empty copy is unloaded after emptyMinutes (5). See Dungeons.
  • Map servers can run on other machines. They register with Central over the map link from anywhere Central allows (Central:MapNetworks). The link isn't encrypted, so other machines reach it over a private network or a WireGuard tunnel. See Docker.
  • Exactly one Central per database. Sessions, tickets, parties and the item lock live in its memory. Two Centrals on one database could hand out the same item twice.
  • Exactly one Shop per database. Buys are serialized by a lock in its process.
  • Login can run several times behind the proxy, but each copy keeps its own rate limits and failed-login counters.

Targets and tuning are in Performance.

#When something stops

What stops What players see What happens
A map server Everyone on it is disconnected Central ends their sessions. The last save stands (at most 60 seconds old by default, newer if they traded, changed map or did something Central handles). Central launches the map again on the next player who needs it, if it has an executable
Central Players stay on their map, but nobody new can get a ticket, and map changes, saves, chat between maps, mail, guilds and the market fail Maps retry the link every 3 seconds (CentralLink.retrySeconds). GM commands of level 2 or more don't run while Central can't record them. Game log lines wait in the map (up to 5,000). Sessions and parties live in Central's memory, so after a restart Central refuses the saves of players who were already on a map until they sign in again. Restart Central only with players out
Login Nobody can sign in or create characters Players already in a map keep playing
Shop The shop window says it can't reach the service Everything else keeps working
Database Services answer errors Map servers keep the world running but saves fail until it is back

#Single player

A single player game uses the same map code with none of the services:

  • The client starts a Mirror host for the map (MapServer.Host) that takes no outside connections.
  • The KitARPG.Local assembly replaces Login and Central with a local backend that saves to a SQLite file in the player's persistent data folder (KitSettings.saveFile, savegame.db by default).
  • Each map change restarts the host with the new map, using the same ticket and transfer flow as the MMO.
  • There is no shop, no mail between players, no guilds across players and no market.

The mode is chosen in KitARPG > Play and Servers and stored in Assets/Settings/Resources/KitARPGSettings.asset. See Play & Servers.
