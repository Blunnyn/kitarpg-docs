Servers and deployment

Services

Login, Central and the Shop are .NET 10 web services that run next to your map servers. This page covers what each one does, every endpoint, the map link messages and the shared pieces they are built on.

#Where they are

The services are a .NET solution, KitARPG.Services.slnx, with these projects:

Project What it does
Shared Compiles the contracts and rules in Assets/Blunnyn/KitARPG/Runtime/Shared/, so the services and Unity use the same code
Data EF Core: the tables, one database context per provider (SQLite and PostgreSQL) and their migrations. See Database
Hosting What every service shares: token checks, JSON, request size limits, proxy headers, refusing sample secrets, the game log writer, ban checks
Modules The contract and loader for your own Login and Central modules. See Service modules
Login Accounts and characters
Central Sessions, tickets, the map link and everything shared between maps
Shop The optional premium shop. See Shop service
Launcher Starts everything with one button or one command. See Launcher
Examples/Bounties An example Central module with its own table
Tests Tests for the rules, Login, Central (with a fake map server), the Shop and modules, on SQLite

In the Asset Store package they come as Assets/Blunnyn/KitARPG/Services.zip. The editor unpacks them to Assets/Blunnyn/KitARPG/Services~ the first time it opens, and again when a kit update brings a new zip. Unity doesn't import folders whose name ends in ~. KitARPG > Play and Servers builds them for you; from a terminal:

cd Assets/Blunnyn/KitARPG/Services~
dotnet build
dotnet test

#What every service shares

  • JSON. Requests and answers are JSON with camelCase names. The shared contracts use public fields so Unity's JsonUtility reads them too.
  • Errors. A refused request answers { "code": "...", "message": "..." }. The codes are in ErrorCodes in the shared code, for example wrong_credentials, login_locked, account_banned, session_busy, map_unavailable, character_limit.
  • Body size. Requests over 64 KB are refused. The Shop's catalog publish has its own limit of 2 MB.
  • Health. GET /health answers ok on Login, Central and the Shop. Use it for load balancers and monitoring.
  • Migrations. With Database:MigrateOnStartup on (the default), each service brings the database schema up to date when it starts.
  • Sample secrets. Outside the Development environment a service refuses to start while a key or the database password is empty, short or a sample value. See Security.
  • Game log. Each service writes its own lines to game_logs in batches, off the request path. Lines older than Logs:Days (180) are deleted once an hour; 0 keeps them.

#Login

Login owns accounts and characters. Clients reach it over HTTPS in production.

#Endpoints

Method Route Needs What it does
POST /api/auth/register Nothing Creates an account: username, password, email (optional). 201, or 409 username_taken
POST /api/auth/login Nothing username, password, remember. Answers token, expiresAt (Unix seconds), accountId, username and, with remember, a rememberToken
POST /api/auth/resume A remember token Trades the remember token for a new access token and the next remember token
POST /api/auth/forget A remember token Deletes that token's family (sign out on this computer)
POST /api/auth/forget-all Access token Deletes every remember token of the account (sign out everywhere)
GET /api/characters Access token The account's characters and maxCharacters
POST /api/characters Access token Creates a character: name, classId, appearance
DELETE /api/characters/{id} Access token Deletes one of the account's characters and everything it holds
GET /health Nothing ok

Every /api/auth/* route counts against the rate limit below.

#Passwords

Passwords are hashed with Argon2id: 19 MiB of memory, 2 passes, 16-byte salt, 32-byte hash. The parameters are stored inside each hash, so they can be raised later without breaking existing accounts. When a username doesn't exist, Login still hashes a dummy password, so a wrong username takes as long as a wrong password.

#Access tokens

  • A JWT signed with HMAC-SHA256 with the first key of Auth:SigningKeys (or Auth:SigningKey).
  • Lives Auth:TokenMinutes (30). Issuer and audience are Auth:Issuer (kitarpg).
  • Carries the account id (sub), the username and the GM level.
  • Central validates it with the same keys. A banned or deleted account loses access within Auth:BanCheckSeconds (5), with HTTP 403 account_banned.

#Remember me

  • With remember: true, sign in returns a random 32-byte token. The database keeps only its SHA-256 in remember_tokens, with the account, the address and an expiry of Auth:RememberDays (30).
  • POST /api/auth/resume uses the token once and returns the next one of the same family.
  • A spent token that comes back means someone copied it. Login deletes the whole family, so both the owner and the copier must sign in with the password again. The line remember token reused goes to the game log.
  • An account keeps at most 10 remembered computers; signing in on one more drops the oldest.
  • The client stores the username, the check boxes and the token, never the password.

#Rate limits

Limit Setting Default
Requests to /api/auth/* per client and minute Auth:AttemptsPerMinute 10
Wrong passwords per username before it is locked Auth:FailedLoginsPerAccount 5
Lock length, in minutes Auth:FailedLoginMinutes 15
  • Clients are counted by IPv4 address, or by the /64 of an IPv6 address.
  • A locked username answers HTTP 429 login_locked. Unknown usernames are counted the same way, so the answer never says whether an account exists. A correct password clears the count.
  • The counters live in memory: a restart forgets them, and each Login copy counts on its own.
  • Behind a reverse proxy, turn on the Proxy settings, or every player looks like the proxy's address. See Security.

#Characters and gamedata.json

Login creates characters from gamedata.json, a file exported from your Game Database: the player models, the classes each model can take, each class's start map, position, health, mana and start items, the item and skill catalog, and the most characters per account (maxCharactersPerAccount in the Game Database, 6 by default).

  • Characters:GameDataFile says where it is (gamedata.json next to the service by default).
  • KitARPG > Play and Servers exports it each time it starts the services, to UserSettings/KitARPG/gamedata.json.
  • KitARPG > Export Game Data for Services writes it to Services/Login/gamedata.json, so a build or a Docker image of Login carries it. Run it before building Login for a server.
  • Without the file, Login logs an error and nobody can create characters.
  • A character can only take a class its model offers. Names are unique across the game.

At every start Login copies the items and skills from the file into the items and skills tables. A removed item isn't deleted: it is marked retired, since copies may still point to it. If the file has no items, the catalog is left as it was.

#Central

Central is the hub of the online world. Clients call it once per map entry; map servers stay connected to it the whole time.

#HTTP endpoints

Method Route Needs What it does
POST /api/play Access token characterId. Answers mapId, address, port and a one-use ticket. 404 character_not_found, 403 account_banned, 503 map_unavailable or session_busy
GET /api/maps Nothing The registered maps and the players on each: [{ "mapId": "town", "players": 3 }]
GET /health Nothing ok

Modules add their own endpoints. See Talking to Central.

#Tickets and sessions

  • /api/play opens a session for the account in the Pending state with a random 24-byte ticket. It expires after Central:TicketSeconds (30).
  • The map server sends the ticket to Central; Central redeems it once, for that map only, and the session becomes InMap.
  • Only the map holding the session may save the character or ask to move it.
  • Logging in again while playing kicks the old session first. See Logging in twice.

#Starting map servers

Central knows the maps from Central:Maps. For each map:

  • With an Executable, Central starts it with Arguments when a player needs it, or at startup with AutoStart, and waits up to Central:LaunchTimeoutSeconds (60) for it to register. The map key goes to the process in the KITARPG_CENTRAL_KEY environment variable.
  • Without one, the map is started by someone else (Docker, the editor in Play, a service manager). Central waits 3 seconds for it to register.
  • A map that registers but isn't listed still works while it runs; listing it lets Central wait for it.
  • Stopping Central kills the map servers it started.

See Configuration for every field.

#The map link

Map servers connect to Central on UDP Central:MapLinkPort (7700) with LiteNetLib. The connection request must carry Central:MapKey, and the sender's address must be in Central:MapNetworks when that list isn't empty. Each message is its class name followed by a JSON body, sent reliable and ordered.

Message from the map What Central does
MapRegister Adds the map with its id, public address and port. Refused if another server already holds that map id
MapHeartbeat Updates the player count (every 5 seconds)
TicketCheck Redeems a ticket and sends the character
CharacterSave Saves the character if this map holds it and the version matches; ends the session when the player leaves
TransferRequest Saves the new position, starts the target map if needed and returns a ticket for it
ChatRelay, FriendCommand, PartyCommand, CharacterLevel Chat between maps, friends, parties, level changes
GuildCommand, AllianceCommand, GuildExperience, GuildStorageCommand Guilds, alliances, guild levels and the guild bank
MailSend, MailCommand Mail
MarketCommand The market between players
CollectorCommand Tax collectors
BanRequest, RoleChange, GmAuditBatch, RatesChange GM actions; audit lines are confirmed only once stored
PlayerReport, ReportCommand Player reports
GameLogBatch Game log lines, stamped with the sender's map id
Any other class name Handed to a module that registered it, or logged as unknown

Central checks that a message about a player comes from the map that player is on, so a map can only speak for its own players.

#Items move through one ledger

Every copy of an item is one row of item_instances with exactly one owner: a character, an account bank, a guild, a letter, a tax collector or a market lot. Central's ItemLedger changes owners one move at a time, inside a transaction:

  • A move only happens if the copy is where the sender says it is. A copy held by someone else is refused and logged.
  • An item the catalog doesn't know never reaches the database. The map keeps it and tries again after Login has the new export.
  • Market, mail, guild storage and collectors raise the character's Deliveries counter in the same transaction. The map records the last delivery it applied, so a save made before a delivery can't erase it.

This is why there must be exactly one Central per database: the lock lives in its process.

#Limits Central enforces

Central's own settings (friends, party and guild sizes, mail and market rules) are listed in Configuration. Some limits are fixed in code:

Limit Value
Gold or postage in one letter 1,000,000,000,000,000
Price of one market lot 1,000,000,000,000
Reports one player can send per day 10
GM audit lines per batch from a map 500

#Shop

The Shop is optional and separate: Central doesn't know it exists. Map servers call its internal API with a key; payment providers call its webhooks; you manage it with the admin API. Everything about it is in Shop service.

#Running a service by hand

The launcher is the easy way. To run one service on its own, for debugging:

cd Services
ASPNETCORE_ENVIRONMENT=Development \
ASPNETCORE_URLS=http://127.0.0.1:5100 \
Database__ConnectionString="Data Source=$PWD/kitarpg.db" \
dotnet run --project Login
  • Development uses the test keys in appsettings.Development.json. Never use it on a server.
  • Without ASPNETCORE_URLS, dotnet run uses the ports in the project's Properties/launchSettings.json (5022 for Login, 5091 for Central, 5300 for the Shop), not the 5100 and 5200 the client expects.
  • With SQLite, give every service the same absolute file. The default Data Source=kitarpg.db is relative to each service's folder, so Login and Central would each make their own database.
  • Central started this way has the maps from appsettings.json without executables: start the map servers yourself with -central 127.0.0.1:7700 and the development map key.

#Common mistakes

  • Nobody can create characters. Login didn't find gamedata.json. Its log says where it looked. Export it and restart Login.
  • "Map ... is not running." The map isn't registered: the map server build is missing, its executable path is wrong, it crashed (see its log), or its key or address isn't allowed. Central logs Refused a map link and Map registration refused with the reason.
  • Players get session_busy. The old map didn't confirm the save within KickWaitSeconds. It usually clears in a few seconds. If it keeps happening, look at that map's log.
  • Tokens fail between Login and Central. Both must have the same signing keys and issuer.
