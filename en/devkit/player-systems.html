Player systems

How to add a system of your own to every player: a NetworkBehaviour on the player model prefabs with synced state, commands the owner sends, replies, saving, and the rules that keep it correct online.

#When you need one

The kit's player features are components on the player prefab: PlayerInventory, PlayerSkills, PlayerQuests, PlayerProgress, PlayerChat, PlayerGuild, PlayerMail and the rest. Add a component of your own when your feature needs:

  • state that other code reads often, on the server or on the client (a reputation value, a pet, a crafting queue),
  • synced values that the interface shows, or that other players see,
  • requests from the owner with their own rules.

If you only need a request and an answer, without state on the player, network messages are lighter and need no prefab change. If you only need to save a few numbers, character flags need no code at all.

Where the file goes: the Game assembly. The same component runs on the server and the clients.

#Start from the template

Create > KitARPG > Scripts > Player System makes PlayerNewSystem. The full code is on Templates. It shows the pieces every player system has:

Piece What it is for
[RequireComponent(typeof(PlayerCharacter))] It only makes sense on a player.
[SyncVar] public int points A value the server sets and clients receive.
static event Action<int> Changed Tells the owner's interface when the value changes.
static PlayerNewSystem Local The local player's copy, for windows. Set in OnStartAuthority.
ResetStatics in SubsystemRegistration Clears the statics between Plays without domain reload.
OnStartServer Loads saved state when the player spawns on the server.
public void Earn() => CmdEarn() The client-side method windows call.
[Command] void CmdEarn() The request, run on the server. Spends from the connection's budget with CommandPacing.Allow, then checks everything.
[TargetRpc] void TargetTold(string) An answer to the owner only.
OnPointsChanged hook Raises Changed on the owner's client.

#Adding it to the player prefabs

Every player model has its own prefab, listed in the game database (KitARPG > Game Database > Models, field GameDatabase.playerModels). Add your component to every one of them:

  1. Open KitARPG > Game Database > Models and pick a model. Its page links its prefab.
  2. Open the prefab and add your component.
  3. Repeat for every model.

A model added later with + New player model gets the kit's systems but not yours. To add your component to every model automatically, and to models made later, ship a kit update that adds it where it is missing. That page has the full code for it.

Warning

Mirror matches network components by their order on the object. Client and server builds must have exactly the same NetworkBehaviours on each player prefab. Never add your component at runtime, or only in one kind of build.

#Synced state

Tool Reaches Use for
[SyncVar] on a field Clients that see the player (or only the owner, see below) Single values
SyncList<T>, SyncDictionary<K,V>, SyncHashSet<T> (as readonly fields) Same Collections
[TargetRpc] The owner only One-off answers and events
[ClientRpc] Every client that sees the player Effects others must see

Each NetworkBehaviour has a Sync Mode: Observers (everyone who sees the player gets the values) or Owner (only the owner does). The kit's private systems (PlayerQuests, PlayerProgress, PlayerInventory bag contents) set Owner in Reset():

void Reset() => syncMode = SyncMode.Owner;

Reset runs when you add the component in the editor. Pick Owner for anything other players shouldn't read: a hacked client can read every value it receives.

Who sees a player is decided by the kit's interest management (a spatial grid). Players far away, or in another copy of a dungeon, don't receive your values or [ClientRpc]s.

#Commands: the owner asks

A [Command] runs on the server with the caller's identity known: only the owner's client can call commands on its own player. Inside a command:

  1. Spend from the connection's budget. CommandPacing.Allow(connectionToClient) gives each connection 30 commands a second with a burst of 60, shared by every component, and disconnects floods. Use CommandPacing.AllowCentral for commands that end up as work for Central (2 a second, burst 10).
  2. Validate every argument. Lengths, ranges, finite numbers, ids that exist in the database.
  3. Check the player's state. Alive, loaded (player.State != null), not busy, in range of what they act on.
  4. Change state through the kit's systems. Items and gold through PlayerInventory, flags through PlayerProgress, quests through PlayerQuests.

#A complete example: reputation

A reputation value per faction, earned from kills, shown in a window, and spent at an NPC. It saves itself with PlayerData through IPlayerSave and syncs only to the owner.

using System;
using System.Collections.Generic;
using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Shared.Characters;
using Mirror;
using UnityEngine;

namespace Game
{
    [RequireComponent(typeof(PlayerCharacter))]
    public class PlayerReputation : NetworkBehaviour, IPlayerSave
    {
        const string Key = "mygame.reputation";
        public const int Max = 100000;

        [Serializable]
        class Saved
        {
            public List<string> factions = new List<string>();
            public List<int> values = new List<int>();
        }

        /// <summary>Faction id to reputation. Owner only.</summary>
        public readonly SyncDictionary<string, int> standing = new SyncDictionary<string, int>();

        /// <summary>Owner's client: something changed.</summary>
        public event Action Changed;

        /// <summary>Owner's client: a message for the reputation window.</summary>
        public static event Action<string> Told;

        public static PlayerReputation Local { get; private set; }

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            Local = null;
            Told = null;
        }

        void Reset() => syncMode = SyncMode.Owner;

        PlayerCharacter player;

        protected virtual void Awake()
        {
            player = GetComponent<PlayerCharacter>();
            standing.OnChange += (_, __, ___) => Changed?.Invoke();
        }

        public override void OnStartAuthority() => Local = this;

        public override void OnStopAuthority()
        {
            if (Local == this) Local = null;
        }

        public int Of(string faction) => standing.TryGetValue(faction, out int v) ? v : 0;

        // Saving: loaded as the character enters a map, written before every save.

        public void ServerLoad(PlayerCharacter owner, CharacterState state)
        {
            standing.Clear();
            Saved saved = PlayerData.Get<Saved>(owner, Key);
            for (int i = 0; i < saved.factions.Count && i < saved.values.Count; i++)
                standing[saved.factions[i]] = saved.values[i];
        }

        public void WriteTo(PlayerCharacter owner, CharacterState state)
        {
            var saved = new Saved();
            foreach (KeyValuePair<string, int> pair in standing)
            {
                saved.factions.Add(pair.Key);
                saved.values.Add(pair.Value);
            }
            PlayerData.Set(owner, Key, saved);
        }

        /// <summary>Server only. Called by your own rules, never from a client's word.</summary>
        [Server]
        public void ServerAdd(string faction, int amount)
        {
            if (string.IsNullOrEmpty(faction) || amount == 0) return;
            standing[faction] = Mathf.Clamp(Of(faction) + amount, -Max, Max);
        }

        // Spending: the owner asks, the server checks everything.

        public void Spend(string npcId, string faction, int amount) => CmdSpend(npcId, faction, amount);

        [Command]
        void CmdSpend(string npcId, string faction, int amount)
        {
            if (!CommandPacing.Allow(connectionToClient)) return;
            if (player.State == null || player.IsDead) return;
            if (string.IsNullOrEmpty(faction) || faction.Length > 32 || amount <= 0 || amount > Max) return;
            if (!Npc.TryFind(npcId, out Npc npc) || !npc.InReach(transform.position)) return;
            if (Of(faction) < amount)
            {
                TargetTold("Not enough reputation.");
                return;
            }
            standing[faction] = Of(faction) - amount;
            GameLog.Write("mygame.reputation_spent", player, amount: amount, detail: $"{faction} at {npc.Id}");
            TargetTold($"Spent {amount} reputation with {faction}.");
        }

        // Runs on the owner's client: hand it to the interface.
        [TargetRpc]
        void TargetTold(string text) => Told?.Invoke(text);
    }
}

A window of yours subscribes to PlayerReputation.Told and to PlayerReputation.Local.Changed, and calls PlayerReputation.Local.Spend(...) from its button.

And the server rule that earns reputation, anywhere in the Game assembly:

public static class ReputationRules
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]
    static void Hook()
    {
        Monster.ServerKilled -= OnKilled;
        Monster.ServerKilled += OnKilled;
    }

    static void OnKilled(Monster monster, PlayerCharacter killer)
    {
        if (killer == null || monster.Data == null) return;
        if (killer.TryGetComponent(out PlayerReputation reputation)) reputation.ServerAdd("forest_wardens", 5);
    }
}

#Loading and saving

Way How it loads When it saves Seen by clients
Character flags (PlayerProgress.SetFlag, IPlayerActor.SetFlag) With the character, before spawn With the character The owner, synced
PlayerData with IPlayerSave Your ServerLoad, before spawn Your WriteTo, before every save Never; sync what you need

The order on the map server when a character enters:

  1. The player prefab is instantiated.
  2. PlayerCharacter.ServerSetup loads the kit's systems (inventory, bank, skills, progress with its flags, quests), then calls ServerLoad on every IPlayerSave component.
  3. The player is spawned: OnStartServer runs on every component, then PlayerCharacter.ServerSpawned is raised.

So OnStartServer can read flags, as the template does. In ServerLoad the object isn't spawned yet: isServer is still false, so PlayerData.Set refuses and [Server] methods log a warning there. Read in ServerLoad; write later.

Saves happen every Save Interval Seconds (saveIntervalSeconds, 60 on the map server), when the player leaves or changes map, and when the server stops. See Saving data.

#Turning your system off with a module

GameInstance.Has(KitModule.X) tells whether one of the kit's modules is on. For a switch of your own, add a field to an asset of yours and check it on the server in every command. Never remove the component instead: the prefab must keep the same network components in every build.

#Overriding instead of adding

To change one of the kit's player systems rather than add a new one, subclass it and swap the component on the prefabs. See Overriding kit behaviour.

#Server and client

Server Owner's client Other clients
[Command] body Runs Calls it No
[TargetRpc] body Calls it Runs No
[ClientRpc] body Calls it Runs Runs if they see the player
[SyncVar] (Observers) Sets Receives Receive
[SyncVar] (Owner) Sets Receives No
OnStartServer, IPlayerSave Runs No No
OnStartAuthority, OnStartLocalPlayer No Runs No

In single player the host is server and owner at once: commands run in the same process, CommandPacing lets the host's own connection through, and both OnStartServer and OnStartAuthority run on the same object.

#Common mistakes

  • No CommandPacing in a [Command]. A modified client can call it thousands of times a second.
  • Trusting an argument because the button that sends it is hidden. Clients can send anything.
  • Different components in client and server builds. Mirror reads the wrong component and the connection breaks.
  • Statics without a reset. Local from the last Play points at a destroyed object. See Play without domain reload.
  • Observers sync mode for private data. Every nearby client receives it.
  • Writing PlayerData in ServerLoad. The player isn't spawned yet; the write is refused.
