Play without domain reload

Why static state in your code must be reset by hand, when each startup method runs, and the patterns the kit uses so that every Play starts clean.

#What domain reload is

When you press Play, Unity can reload the scripting domain: throw away every loaded assembly and every static value, and load them again. That makes each Play start clean, and it takes many seconds in a project the size of KitARPG.

The kit's project turns it off: Project Settings > Editor > Enter Play Mode Settings has Reload Domain off (scenes are still reloaded). Play then starts in a second or two. The price is that static fields keep their values from the last Play:

  • a static list still holds the entries added last time,
  • a static event still has last Play's subscribers, which point at destroyed objects,
  • a static Local still points at the previous local player,
  • a static counter keeps counting.

Builds always start clean. These problems only show in the editor, and only on the second Play and after, which makes them easy to miss. Your project may have Reload Domain on; write your code so it works either way.

#The startup moments

[RuntimeInitializeOnLoadMethod] runs a static method at a fixed moment of each Play (and each build launch):

Load type When Use it to
SubsystemRegistration First, before anything else Clear your own statics.
AfterAssembliesLoaded After all assemblies are loaded Subscribe to other classes' static events; add menu entries and options.
BeforeSplashScreen Before the splash screen (rarely needed)
BeforeSceneLoad Before the first scene loads Install formulas and other replacements.
AfterSceneLoad After the first scene loaded Things that need scene objects: KitNetworkManager.Instance, GM commands.

Within one load type, Unity doesn't define the order between methods of different classes. The kit's rules come from that.

#The kit's rules

  1. Every class clears its own statics in SubsystemRegistration. Fields, events, collections and caches that hold state go back to their starting values in a method usually called ResetStatics.
  2. Subscribe to another class's static events in AfterAssembliesLoaded or later. That class clears them in SubsystemRegistration; if you subscribed in the same phase, your subscription might be cleared after you made it.
  3. Lists the kit fills with its own entries are rebuilt in SubsystemRegistration (ItemMenu.Entries, PlayerMenu.Entries, ClientOptions.All, the GM commands). Add yours later.
  4. The kit's formulas go back to its own in SubsystemRegistration (GameInstance.Formula, GameInstance.Combat). Install yours in BeforeSceneLoad.
  5. A class that registers something of its own in SubsystemRegistration clears and registers in the same method, so the order with other classes doesn't matter (GmCommands).
  6. Work buffers emptied on every use and caches that stay valid are not cleared. A static List used as scratch space, or a computed value that can't change during the session, can stay.

The game mode tables (GameModes) are an exception: they are never cleared, so mode assemblies can register from SubsystemRegistration in any order.

#The pattern for your code

using System;
using System.Collections.Generic;
using Blunnyn.KitARPG.Net;
using UnityEngine;

namespace Game
{
    public static class Kills
    {
        // State of this class.
        static readonly Dictionary<long, int> counts = new Dictionary<long, int>();
        public static event Action<PlayerCharacter, int> ServerCounted;

        // 1. Clear own state first.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            counts.Clear();
            ServerCounted = null;
        }

        // 2. Subscribe to the kit's events after the kit cleared them.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]
        static void Hook()
        {
            Monster.ServerKilled -= OnKilled;
            Monster.ServerKilled += OnKilled;
        }

        static void OnKilled(Monster monster, PlayerCharacter killer)
        {
            if (killer == null || killer.State == null) return;
            counts.TryGetValue(killer.State.id, out int n);
            counts[killer.State.id] = ++n;
            ServerCounted?.Invoke(killer, n);
        }
    }
}

-= before += makes the subscription safe even if the method runs twice. Named methods (not lambdas) make -= possible.

#Statics on components

A NetworkBehaviour or MonoBehaviour with static members follows the same rule:

public class PlayerPet : NetworkBehaviour
{
    public static PlayerPet Local { get; private set; }
    public static event Action<string> Told;

    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    static void ResetStatics()
    {
        Local = null;
        Told = null;
    }

    public override void OnStartAuthority() => Local = this;

    public override void OnStopAuthority()
    {
        if (Local == this) Local = null;
    }
}

The templates for player systems and saved data already do this.

#Things that live on scene objects

Events on objects that are created again on each Play (the network manager, a window in the HUD) don't need clearing: the old object is gone with its subscribers. That is why the kit's templates subscribe to KitNetworkManager.ServerStarted in AfterSceneLoad without unsubscribing.

#Lazy caches

static AttributeData toughness;

public static AttributeData Toughness
{
    get
    {
        if (toughness == null && GameInstance.Database != null) GameInstance.Database.TryGet("toughness", out toughness);
        return toughness;
    }
}

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
static void ResetStatics() => toughness = null;

A cache of an asset survives Play harmlessly if the asset can't change, but clearing it costs nothing and covers edits made between Plays.

#Checklist

For every static in your code, ask:

It is Do
A value that changes during play (a counter, a Local, a dictionary of players) Reset in SubsystemRegistration.
A static event of your class Set to null in SubsystemRegistration.
A subscription to someone else's static event Make it in AfterAssembliesLoaded or later, with -= first.
An entry in a kit list (menus, options, commands, validator checks in the editor) Add it after the kit filled the list.
A const or static readonly value that never changes Nothing.
A scratch buffer cleared before each use Nothing.

Editor-only statics (validator checks, pages) follow the editor's own lifetime, not Play: register them from [InitializeOnLoadMethod] and remove before adding (see Editor extensions).

#Testing it

  1. Press Play, do what your feature does, stop.
  2. Press Play again and do it again.
  3. Watch for doubled messages, events firing twice, counts that didn't start at zero, and MissingReferenceException from destroyed objects.

The kit itself was tested this way: two Plays in a row in single player give the same subscribers, commands and menu entries.

#Common mistakes

  • Subscribing in SubsystemRegistration. The kit may clear the event after you. Subscribe in AfterAssembliesLoaded or later.
  • Clearing someone else's event. Each class clears only its own.
  • Clearing your event in one startup method and subscribing to it in another of the same type. The order is undefined: clear in SubsystemRegistration, subscribe in a later phase.
  • Lambdas in += that run every Play on an event that isn't cleared.
  • Static references to scene objects without a reset: they become destroyed objects that compare equal to null but still hold memory.
