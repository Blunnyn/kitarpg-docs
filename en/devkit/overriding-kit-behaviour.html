Overriding kit behaviour

How to change what one of the kit's components does, without editing it: subclass the window, player system, monster or NPC component, override its virtual methods, and swap the component on the prefab.

#When to override

Most changes need less than this. Before overriding, check:

  • a setting in Game Settings or on the component,
  • an event to react to (Events),
  • a formula (Formulas),
  • an effect, condition, action, objective or NPC option of your own.

Override when the kit's own flow must go differently: a window that reads its text from your localization, a monster with its own way of taking damage, a mail system that refuses letters with links.

Where the file goes: the Game assembly, since the component lives on prefabs that every build loads.

#What can be overridden

The kit keeps these open for subclasses:

In What is virtual
Windows and HUD parts (KitARPG.Client) Unity methods (Awake, OnEnable, OnDisable, Update, OnDestroy) are protected virtual, plus methods meant to change, such as ShopWindow.Describe (error text)
Player systems (PlayerInventory, PlayerSkills, PlayerQuests, PlayerMail and the rest) Unity methods protected virtual; server methods Server... public virtual (or protected virtual for internal steps, such as PlayerMail.ServerAnnounce(MailList))
Monster Unity methods, ServerSetup, ServerDamage, ServerHeal, ServerAddBuff, ServerRemoveBuffs, ServerKnock, ServerRevive, ServerDespawn, Think, TryCast, RunPhase, and more
PlayerCharacter ServerSetup, ServerHeal, ServerAddExperience, ServerTryAttack, ServerAnnounce(string, Color) and other server methods

The API reference in Assets/Blunnyn/KitARPG/Documentation/API/ lists every virtual member. Methods that aren't virtual are not meant to change; read the class to find the virtual step that covers what you need.

#How to swap a component

  1. Write your subclass and let it compile.

  2. Open the prefab that holds the kit's component:

    Component Prefab
    Player systems, PlayerCharacter Every player model prefab (KitARPG > Game Database > Models)
    Windows and HUD parts The HUD prefab (GameInstance.hudPrefab, in Game Settings > Interface)
    Monster Each monster's prefab (the Prefab field of the monster in the Game Database)
    Npc The NPC object in its scene

  3. On the kit's component, open the menu (the three dots) and pick Copy Component.

  4. Add your component. On it, pick Paste Component Values: every field the kit's component had is copied, since your class inherits them.

  5. Remove the kit's component.

  6. Save the prefab. For player systems, repeat on every player model prefab.

Kit code finds components with GetComponent<PlayerMail>() and similar calls, which return your subclass too. Nothing else needs to change.

Warning

On networked prefabs (players, monsters), the position of the component in the list matters to Mirror. Replacing a component moves the new one to the end, which is fine as long as client and server builds use the same prefab. Never swap components at runtime or in one build only.

#Example: the template

Create > KitARPG > Scripts > Player System Override makes a subclass of PlayerMail:

using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Shared.Central;

namespace Game
{
    /// <summary>
    /// Changes how one of the kit's player systems behaves, here the mail, without editing the kit.
    /// On every player model prefab, remove the kit's component and add this one in its place
    /// (Copy Component, then Paste Component Values, keeps the settings).
    /// </summary>
    public class MyPlayerMail : PlayerMail
    {
        // Server methods decide for every player; call base for whatever you keep.
        protected override void ServerAnnounce(MailList list)
        {
            base.ServerAnnounce(list);
        }

        // Unity methods are protected virtual too.
        protected override void Awake()
        {
            base.Awake();
        }
    }
}

#Example: a monster that halves damage

using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;
using UnityEngine;

namespace Game
{
    /// <summary>A monster with armor: every hit is reduced before it lands.</summary>
    public class ArmoredMonster : Monster
    {
        [Range(0, 1)] public float reduction = 0.5f;

        public override void ServerDamage(Hit hit, IFighter source)
        {
            hit.amount = Mathf.Max(1, Mathf.RoundToInt(hit.amount * (1 - reduction)));
            base.ServerDamage(hit, source);
        }
    }
}

Swap Monster for ArmoredMonster on that monster's prefab. Other monsters keep the kit's component.

#Example: localized shop messages

ShopWindow.Describe turns error codes into sentences and is meant to be overridden:

using Blunnyn.KitARPG.Client;
using Blunnyn.KitARPG.Net;

namespace Game
{
    public class MyShopWindow : ShopWindow
    {
        protected override string Describe(string code)
        {
            switch (code)
            {
                case NpcErrors.NotEnoughMoney: return Localize("shop.no_money");
                case NpcErrors.OutOfStock: return Localize("shop.sold_out");
                default: return base.Describe(code);
            }
        }

        static string Localize(string key) => key; // your localization lookup
    }
}

Swap it on the HUD prefab, under its Windows group.

#Example: a rule on every item use

PlayerInventory.UseItem is the server step that makes an item do its thing. False keeps the item:

using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;

public class MyPlayerInventory : PlayerInventory
{
    protected override bool UseItem(IUsable item)
    {
        // No potions inside the arena maps.
        if (item.CooldownGroup == "potion" && gameObject.scene.name.StartsWith("Arena")) return false;
        return base.UseItem(item);
    }
}

#Example: a mailbox that opens from a level

PlayerMail.ServerOpen runs when a mailbox NPC opens the mail for a player:

using Blunnyn.KitARPG.Net;
using UnityEngine;

public class LevelGatedMail : PlayerMail
{
    public int minLevel = 5;

    public override string ServerOpen(Npc npc)
    {
        if (TryGetComponent(out PlayerCharacter player) && player.level < minLevel)
        {
            player.ServerAnnounce($"The mailbox opens at level {minLevel}.", new Color(1f, 0.5f, 0.45f));
            return null;
        }
        return base.ServerOpen(npc);
    }
}

The same rule could be a condition on the mailbox NPC's option, with no code. Overriding is for rules that must hold wherever the system is reached from.

Server methods decide for every player. Read the base method before overriding it, and call base for every step you keep.

#Server and client overrides

Override Effect
A Server... method Changes the rule for every player on that map server. Online, the map server build is what counts.
A Unity method or a window method Changes what that player sees and how they ask. A modified client can undo it, so never rely on it for rules.

Anything a client-side override sends to the server must be checked again on the server, by the kit or by a server override of yours.

#Statics in the base class

Player systems set statics such as PlayerMail.Local in their own OnStartAuthority. If you override OnStartAuthority, OnStopAuthority, Awake or any Unity method, call base first, or those statics stay empty and the kit's windows stop finding your component.

#Kit updates and your subclasses

Kit updates check for the kit's components with GetComponent too, so a prefab with your subclass counts as having the component: the update doesn't add a second one. Updates that add fields to a kit component reach your subclass as well, since it inherits them.

When a kit release changes a virtual method you override (new parameters, a method removed), your code stops compiling and the changelog says what changed. Keep overrides small and call base so new behaviour in the kit reaches your game.

#Common mistakes

  • Not calling base in Unity methods. Statics, subscriptions and synced collections set up by the base class are missing.
  • Copying a whole kit class instead of subclassing. Updates no longer reach it.
  • Forgetting a player model. Each model is its own prefab; one with the kit's component behaves differently.
  • Client overrides that enforce rules. Do it on the server.
