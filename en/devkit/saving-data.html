Saving data

Where to keep your game's own data so it is saved with the character in single player and online: character flags, PlayerData, components with IPlayerSave, tables in a Central module, and data assets.

#Pick a place

What you keep Where Seen by the client Saved
Small whole numbers per character: story marks, counters, a day stamp Character flags The owner, synced With the character
Structured values per character: a list, a pet with stats, a history PlayerData Never With the character
The same, owned by a component of yours that loads and writes it IPlayerSave + PlayerData What you sync yourself With the character
Data you query across characters: rankings, world events, counters for the whole server A table in a Central module What you send In your own table
Content designers edit: recipes, boards, drop lists A ScriptableObject or GameData asset Both builds load it It is an asset

Never put game state in PlayerPrefs: it lives on the player's computer, never reaches the server and can be edited by the player. PlayerPrefs is for client settings (see Menus and settings options).

#Character flags

Flags are named integers on the character, kept by PlayerProgress. Designers already use them through SetFlagAction and FlagCondition, and so can you.

Where Read Write
Conditions and actions facts.Flag(key) actor.SetFlag(key, value) (server)
Server code player.Facts.Flag(key) or progress.Flag(key) player.Facts.SetFlag(key, value) or progress.SetFlag(key, value)
Owner's client PlayerProgress.Local.Flag(key) Never
  • A value of 0 removes the flag. Flag returns 0 for flags never set.
  • Flags are synced to the owner (PlayerProgress uses Owner sync), so the owner's interface and conditions can read them. Other players never see them.
  • PlayerProgress.ServerFlagChanged (PlayerCharacter, string key, int value) is raised on the server when one changes.
  • Online, Central keeps them in characters.extra under flags; in single player they go in the local save.

The bounty example keeps its hunt progress in flags (bounty.board, bounty.index, bounty.kills, bounty.day, bounty.done). Each character's last hunts are a list of names, which doesn't fit in a flag, so they go in PlayerData (see below).

Flags hold int. A day number, a count or an id hash fits; text and lists don't.

#PlayerData

PlayerData (namespace Blunnyn.KitARPG.Net) stores JSON under keys of your own on the character. Server only.

Member What it does
T Get<T>(PlayerCharacter player, string key) The value, or a new T when there is none or it can't be read.
bool Set<T>(PlayerCharacter player, string key, T value) Stores it. Null removes the key. False when a limit would break; nothing changes then.
bool Has(PlayerCharacter player, string key) Whether the key has a value.
void Remove(PlayerCharacter player, string key) Removes it.
string GetJson(...), bool SetJson(...) The same with raw JSON.

Values are [Serializable] classes read and written with Unity's JsonUtility:

[Serializable]
public class PetSave
{
    public string petId;
    public int level = 1;
    public long experience;
    public List<string> tricks = new List<string>();
}

// On the server:
PetSave pet = PlayerData.Get<PetSave>(player, "mygame.pet");
pet.experience += 50;
if (!PlayerData.Set(player, "mygame.pet", pet)) Debug.LogWarning("Pet data too big.");

#Limits

CharacterDataRules (namespace Blunnyn.KitARPG.Shared.Characters) applies the same limits on the map, in Central and in the local save:

Limit Value
Keys per character (MaxKeys) 64
Key length (MaxKeyLength) 64 characters
Key characters Letters, digits, ., - and _
All values together (MaxBytes) 32 KB of UTF-8

Prefix every key with your game's name (mygame.pet), so it never meets another package's.

#Where it is stored

Online, Central keeps the values in characters.extra under game, as one JSON object ({ "mygame.pet": { ... } }), readable in the database and with no table migration. A save whose data breaks the limits, or holds a value that isn't valid JSON, keeps the stored data, logs a warning and saves the rest of the character. In single player the same data goes into the local save (savegame.db under the player's persistent data folder, set by Save File in KitSettings).

#What JsonUtility can and can't do

  • Public fields and [SerializeField] private fields. Not properties.
  • int, long, float, bool, string, enums, arrays, List<T>, nested [Serializable] classes.
  • No dictionaries. Store two parallel lists, or a list of key-value classes.
  • No polymorphism, no null for nested classes (they come back empty).

#Components with IPlayerSave

When a component of yours owns its data, implement IPlayerSave and let the kit call you:

Method When
void ServerLoad(PlayerCharacter player, CharacterState state) As the character enters a map, after the kit's systems loaded, before the player spawns.
void WriteTo(PlayerCharacter player, CharacterState state) Before every save. 
[RequireComponent(typeof(PlayerCharacter))]
public class PlayerPet : NetworkBehaviour, IPlayerSave
{
    const string Key = "mygame.pet";

    PetSave pet = new PetSave();

    [SyncVar] public string petId;
    [SyncVar] public int petLevel;

    public void ServerLoad(PlayerCharacter player, CharacterState state)
    {
        pet = PlayerData.Get<PetSave>(player, Key);
        petId = pet.petId;
        petLevel = pet.level;
    }

    public void WriteTo(PlayerCharacter player, CharacterState state) => PlayerData.Set(player, Key, pet);
}

The Saved Player Data template makes one of these (see Templates).

Warning

In ServerLoad the player isn't spawned yet, so isServer is false and PlayerData.Set refuses. Read there; write from WriteTo or later.

#When saves happen

On the map server, a character is saved:

  • every Save Interval Seconds (saveIntervalSeconds on the map server, 60),
  • when the player disconnects or changes map,
  • when the server stops.

Each save calls WriteTo on every IPlayerSave. Online the state goes to Central, which writes it to the database; in single player it goes to the local save. Values set with PlayerData.Set between saves live on the character in memory and go with the next save. A crash between two saves loses what changed since the last one, as it does for the kit's own data.

Items and gold that move between characters (trades, mail, market, guild bank) use transactions in Central instead of the periodic save; never model an exchange between players with PlayerData.

#Changing the format later

Saved JSON outlives your code. Plan for old data:

  • New fields get their default when old data is read; give them sensible defaults.
  • Removed fields are ignored.
  • For bigger changes, put a version number in the class and convert in ServerLoad.
  • Renaming a key loses the old data. Read the old key once, write the new one, and Remove the old.

#Tables in a Central module

For data you query across characters (the best hunters, a server-wide counter, auction history of your own), a module adds tables to the kit's database next to the kit's own, with its own migrations. Map servers reach it with CentralMessages. See Talking to Central and Service modules. Single player has no Central: keep a per-character fallback, as the bounty example does with its PlayerData history.

#Data assets

Content (recipes, drop lists, board definitions) belongs in assets, not saves:

  • A plain ScriptableObject with [CreateAssetMenu] when only your code points at it. The bounty example's BountyBoardData is one.
  • A GameData subclass when saves or messages must point at it by id. A GameData has an Id (made from its name, saved with characters), a display name, a description and an icon, and GameInstance.Database.TryGet<T>(id, out T) finds it. It must be reachable from the game database: listed in one of its arrays, or handed over by a Visit method of something that is. Project Check lists GameData assets the database can't reach.

#Common mistakes

  • Saving in PlayerPrefs. It never reaches the server.
  • Reading PlayerData on the client. It is never sent. Sync what the interface needs.
  • Keys without a prefix. Another package can overwrite them.
  • Dictionaries in saved classes. JsonUtility drops them silently.
  • Ignoring Set's answer. Over the limits, nothing is stored.
  • Changing a GameData id. Saves point at the old id.
