DevKit

DevKit overview

The DevKit is the set of extension points, templates and examples that let you build any feature on top of KitARPG without editing the kit's code. This page explains the rules, where your code runs, and which page to read for each kind of change.

#Why you never edit the kit

Everything under Assets/Blunnyn/KitARPG/ belongs to the kit. When you install a new version, those files are replaced. Any line you changed there is lost, and a merge between your change and the new version is your problem to solve by hand.

The kit is built so you never need to touch it:

  • Data assets (items, skills, monsters, quests) are yours. They live wherever you save them and the kit never rebuilds them.
  • Behaviour comes in small polymorphic pieces (skill effects, item effects, conditions, actions, quest objectives, NPC options). You add new kinds by writing a class; the inspector lists it next to the kit's own.
  • Systems raise static events and expose virtual methods, so you can react to them or replace them from your own assembly.
  • Rules that decide numbers (damage, experience, stats) are objects you can swap at startup.
  • The services (Login and Central) load your own .NET modules, with their own database tables.

Your code goes in assemblies of your own, in a folder of your own, for example Assets/Game. Kit updates never touch that folder.

#The layers of the kit

The kit is organised in layers. Each layer only knows the ones below it.

Layer Assembly What lives there
Shared rules KitARPG.Shared Plain C# with no Unity references: inventory rules, character state, messages to Central, the log format. The .NET services compile the same files.
Data KitARPG.Data ScriptableObject assets and pure rules: items, skills, monsters, quests, conditions, actions, formulas, GameInstance.
Network entities KitARPG.Net Everything that lives on the network with Mirror: players, monsters, NPCs, chat, guilds, the game log. Server logic for those entities runs here.
Server only KitARPG.Server The map server: loot payouts, the link to Central, GM commands. Never in an online client build.
Client KitARPG.Client HUD, windows, camera helpers, title screen, settings, input.
Game modes KitARPG.Modes.* How each control mode moves and fights. Each has a client half and a .Server half.
Editor KitARPG.Editor The KitARPG window, the validator, the templates.

The Assemblies page lists every assembly, what it references and which builds carry it.

#Where your code runs

KitARPG has two ways to play, and the same game code runs in both:

Single player MMO
Who is the server The game itself is the host: it runs the map server and the client in one process. A separate map server process (a headless Linux build, or the editor in Play) runs each map.
Saving A local save on the player's computer (KitARPG.Local). Central saves characters in PostgreSQL or SQLite.
Central None. CentralMessages.Online is false. Central links all map servers; Login handles accounts.
Server-only assemblies Included (the build defines KITARPG_SERVER). Only in the map server build.
GM commands Every player is admin when Single Player Commands (singlePlayerCommands) is on in Game Settings. The account's role decides.

Because of this, every piece of code you write belongs to one of three places:

  • Server code decides what happens: damage, items, gold, quest progress, saving. It runs on the map server online, and on the host in single player. Methods named Server... and [Command] handlers are server code.
  • Client code shows things and asks the server: windows, menus, sounds, the camera, input. It runs on each player's machine, and in single player on the same machine as the server.
  • Shared code runs on both, such as a condition's Met, which the server checks and the client uses to grey out a locked line.

The Security rules page explains why the server always checks again what a client asks for.

Before writing a new system, check whether a smaller extension point does the job.

Effects, conditions, actions, objectives and NPC options need no registration. They are [Serializable] classes held in [SerializeReference] fields marked [PickType]: once your class compiles, it shows up in the type menu of every list of that kind in the inspector.

#Your first five minutes

  1. In the Project window, make a folder Assets/Game.
  2. Right click it and pick Create > KitARPG > Scripts > Game Assembly. A Game.asmdef appears. Scripts in this folder now see the kit and get the Game namespace.
  3. Right click the folder again and pick Create > KitARPG > Scripts > Skill Effect. Name the file PoisonDart.cs.
  4. Open any skill in KitARPG > Game Database > Skills. In its effect list, press + and pick PoisonDart from the type menu.
  5. Press Play and cast the skill.

The Templates page documents every template with its full code.

#The example

Assets/Blunnyn/KitARPG/DevKit/Example/Bounties is a complete feature built only with these tools: a bounty board that hands out one hunt a day, counts kills, shows progress on the HUD, pays rewards and keeps a ranking in Central. The Example: bounty board page walks through it file by file. Read it once before starting a large feature.

#Rules that apply everywhere

  • Never edit files under Assets/Blunnyn/KitARPG/. Subclass, subscribe or swap instead.
  • The server decides. Clients ask. Check every request again on the server. See Security rules.
  • Server-only code goes in a server-only assembly (Game.Server), so online clients never carry it. See Assemblies.
  • Static state is reset by you. The kit's project plays without domain reload, so static fields keep their values between Plays. See Play without domain reload.
  • Prefix your keys and names with your game's name (mygame.pets, mygame.bounty_done), so they never meet the kit's or another package's.

#API reference

Every public type and member of the kit is listed in the API reference that ships with the package, in Assets/Blunnyn/KitARPG/Documentation/API/, one file per assembly. It is generated from the code, so it always matches the version you have installed.
