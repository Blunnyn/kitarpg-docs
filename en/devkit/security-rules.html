Security rules

The rules that keep an online game built on KitARPG safe from modified clients, and how to follow them in your own code: server authority, pacing, identity, validation, items and currencies, what clients receive, what builds carry, and the services.

#Assume the client is hostile

Online, players run your client on their own machines. Anyone can modify it, or write a program that speaks your network protocol. Such a client can:

  • call any [Command] and send any network message, with any arguments, as often as its connection allows,
  • read every value your server sends it,
  • skip every check your client code makes,
  • change its own memory: health bars, cooldown timers, buttons that were hidden.

It can't change what the server decides. That is the whole model: the client asks, the server decides. Every rule below follows from it.

Single player has no other players to protect, but the same code runs there, so following the rules costs nothing.

#1. The server decides everything that matters

Damage, healing, items, gold, experience, quest progress, cooldowns, positions, who can see what: all of it is decided by server code (map server online, host in single player). Client code shows results and sends requests.

Belongs on the server Belongs on the client
Server... methods, [Command] bodies, message handlers on NetworkServer Windows, menus, camera, input, sounds, effects
Skill effects' Apply, item effects' Use, actions' Run, NPC options' Run Tooltips (Describe), labels
Formulas Settings in PlayerPrefs

A check the client makes (greying out a button, a range circle) is a courtesy to the player. Make it again on the server.

#2. Pace every request

CommandPacing (namespace Blunnyn.KitARPG.Net) gives each connection one budget shared by every component and handler: 30 requests a second with a burst of 60. A connection far over it is disconnected with KickReasons.Flooding. Requests that make work for Central (mail, guild, friends, reports and anything of yours that ends in CentralMessages.Send) also spend from a stricter budget: 2 a second, burst 10.

[Command]
void CmdDoThing(int value)
{
    if (!CommandPacing.Allow(connectionToClient)) return;
    ...
}

static void OnRequest(NetworkConnectionToClient conn, MyRequest message)
{
    if (!CommandPacing.AllowCentral(conn)) return;   // this one reaches Central
    ...
}

Refused requests still count, so a client that keeps pushing sinks until it is kicked. The host's own connection in single player is never limited.

#3. Identity comes from the connection

The server knows who sent a request: the connection's player object (conn.identity, or the component's own player inside a [Command]). Never put "who I am" in a request.

// Wrong: any client can claim any id.
public struct GiftRequest : NetworkMessage { public long fromCharacterId; public string toName; }

// Right: the sender is the connection's player.
public struct GiftRequest : NetworkMessage { public string toName; }

static void OnGift(NetworkConnectionToClient conn, GiftRequest message)
{
    if (conn.identity == null || !conn.identity.TryGetComponent(out PlayerCharacter from)) return;
    ...
}

The same goes for Central modules: a message carries a character id, and the module checks m.Hosts(characterId) so a map can only speak for players it holds.

#4. Validate every argument

Argument Check
Strings Not null, length limits, PlayerText.Clean before storing or showing to others
Integers Ranges, never negative where it makes no sense, long.MinValue and overflow (compare against limits without adding first)
Floats and vectors float.IsFinite on every component, distances clamped
Ids of game data Exist in the database (GameInstance.Database.TryGet)
Slots and indices Inside the container; the slot holds what the client says
Things in the world Resolved on the server and in reach (see below)
Arrays Length limits before looping

Overflow is a real risk: the kit once had a bug where a large gold amount plus the postage wrapped around to a small number. Compare amount > limit - fee, not amount + fee > limit.

#5. Resolve the world on the server

The client names Resolve with Then check
A monster or player (by netId) Fighters.TargetFor(conn, player, netId): null for anything out of that client's view, invisible enemies, event monsters spawned for someone else Fighters.Enemies, distance, Sight.Clear
An NPC (by id) Npc.TryFind(id, out npc) npc.InReach(player.transform.position)
A drop Rewards.Instance.Pickup(player, id) (checks reach itself)
A player by name PlayerCharacter.ServerFind(name) (this map) Distance, consent, rules
A point on the ground Clamp the distance, NavMesh.SamplePosition, Sight.Clear

#6. Move items and currencies through the kit

Items have a single owner at all times and every move between owners is a transaction in Central. Your code keeps that true by going through the kit:

  • Bag and gear: PlayerInventory (Give, GiveOrBank, ServerReceive, ServerReceiveGold, AddGold, AddCurrency), or IPlayerActor (GiveItem, TakeItem, AddCurrency).
  • Between players: the kit's trade, mail and market. Don't build your own transfer with two separate saves; a crash between them duplicates or loses items.
  • Premium currencies belong to the account and are spent only at the in-game shop, whose service checks the balance. AddCurrency with a premium currency grants it through the shop service; taking it is refused.
  • Log what support will need with GameLog.Write("mygame.kind", player, ...). Lines go to the game_logs table and moderators read them with /logs.

#7. Send clients only what they may know

  • A NetworkBehaviour with Sync Mode Observers sends its synced values to every client that sees the player. Use Owner for private data (bags, quests, flags, your own systems).
  • [ClientRpc] reaches every observer; [TargetRpc] only the owner.
  • PlayerData never leaves the server. Sync only what the interface needs.
  • Don't send positions, health or stats of things a client can't see; the kit's interest management already limits what each client receives.
  • Text written by players is shown with PlayerText.NoTags (or cleaned with PlayerText.Clean on the server), so nobody can inject TextMeshPro tags into other players' screens.

#8. Keep server code out of client builds

Server-only code goes in assemblies with the UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER constraint (Game.Server). Online clients then don't carry GM commands, Central messages or your server rules, so they can't be read or called.

Before every build, BuildSeparation stops a client build that would carry server code, the single player save or test tools. Release clients are built with IL2CPP (the check requires it), which makes them much harder to read. Never put keys, passwords or connection strings in anything a client build includes: the map server reads the Central key from KITARPG_CENTRAL_KEY, and the shop key from KITARPG_SHOP_KEY.

See Assemblies and Builds.

#9. Staff commands are audited

GM commands live in server-only assemblies, check the player's level before running, and every staff-level use (level 2 or more) is written to the GM audit and the game log. When the audit can't be written, staff commands pause. Your commands get all of this from GmCommands.Register. Cap what they hand out with GmCommands.MaxItems, MaxGold and the other limits. See GM commands in code.

#10. The services

  • Central modules handle what maps send for their players: validate every field, check m.Hosts(characterId), and log refusals with the map id.
  • HTTP endpoints in modules are public unless they call RequireAuthorization(). Read the account from the token's sub claim, never from a parameter.
  • Modules run with the service's full rights. Only the server operator installs them; Modules:Allow limits which dlls may load. See Service modules.
  • Never change the kit's tables from a module.

#A review checklist

Before shipping a feature, go through each request a client can send:

  • [ ] It is paced with CommandPacing.Allow (or AllowCentral).
  • [ ] The sender comes from the connection, not the message.
  • [ ] Every string, number, vector and array is checked.
  • [ ] Every id is looked up on the server; every world object is resolved with the kit's helpers and checked for reach and sight.
  • [ ] Items, gold and currencies move through PlayerInventory or IPlayerActor.
  • [ ] The answer and any synced values reveal nothing the player shouldn't know.
  • [ ] Server-only code is in a .Server assembly.
  • [ ] Anything support will ask about is in the game log.
