Talking to Central

How map servers exchange messages of your own with a module in Central, for features that span maps or characters: rankings, world events, server-wide counters. This page covers the map side (CentralMessages); the Central side is on Service modules.

#When you need Central

Online, each map runs in its own server process and never touches the database. Central links all of them, keeps sessions and writes to the database. Anything a single map can't know needs Central:

  • a ranking across every character (the bounty example's hunters board),
  • an event that starts on every map at once,
  • a counter for the whole server,
  • data about characters who aren't online.

Per-character data that travels with the character doesn't need Central: use flags or PlayerData (see Saving data).

In single player there is no Central. Every feature that uses it needs a fallback, even if the fallback is "only online".

#How a message travels

Map server (Unity)                       Central (.NET)
CentralMessages.Send(new BountyFinished)  ->  module handler for BountyFinished
                                               m.Reply(new BountyBoardList)
CentralMessages.On<BountyBoardList>(...)  <-   (to the map that asked)
  1. On the map, CentralMessages.Send writes the message's class name and its JSON (Unity's JsonUtility) over the map's authenticated link to Central (LiteNetLib, reliable and ordered).
  2. Central looks up which module registered that class name and hands it the message, deserialized with System.Text.Json, together with which map sent it.
  3. The module answers the map that asked (Reply), the map a character is on (SendToCharacter), one map by id (Send) or every map (Broadcast).
  4. On the map, CentralMessages.On<T> handlers run on the main thread.

#CentralMessages

CentralMessages lives in KitARPG.Server (namespace Blunnyn.KitARPG.Server), so the code that uses it goes in a server-only assembly such as Game.Server.

Member What it does
static bool Online The map is registered with Central. False in single player and while Central is away.
static bool Send<T>(T message) Sends to Central's modules. False when Central can't be reached; nothing is queued. Throws for a kit message name.
static void On<T>(Action<T> handler) Calls handler on the main thread for each T Central sends. One handler per type: a second call replaces the first; null removes it. Throws for a kit message name.

Handlers are cleared at the start of every Play; register them in AfterSceneLoad (or AfterAssembliesLoaded). An exception inside a handler is logged and doesn't stop the link.

#Writing the messages

Messages are plain C# classes, compiled by Unity and by your Central module from the same file:

using System;

namespace Game
{
    /// <summary>Map to Central: a character finished a bounty.</summary>
    [Serializable]
    public class BountyFinished
    {
        public long characterId;
        public string name;
        public string monster;
    }

    /// <summary>Central to the map the asking character is on.</summary>
    [Serializable]
    public class BountyBoardList
    {
        public long characterId;
        public BountyHunter[] top = new BountyHunter[0];
        public int mine;
    }

    [Serializable]
    public class BountyHunter
    {
        public string name;
        public int bounties;
    }
}

Rules, because two different JSON libraries read them:

  • [Serializable] classes with public fields. No properties, no constructors with parameters, no dictionaries.
  • Field names in lowerCamelCase. Central writes JSON in camelCase; Unity's JsonUtility matches names exactly, so a field named CharacterId would come back empty on the map.
  • Types both sides read: int, long, float, double, bool, string, enums (as numbers), arrays and lists of those and of other message classes.
  • No Unity types (Vector3, Color). Send numbers.
  • Names of your own. Messages travel by class name only (no namespace). The kit's names are refused on both sides: on the map, Send and On throw; in Central, the module fails to start. Prefix them (BountyFinished, not Finished).

Keep the file in an assembly with no engine references (noEngineReferences: true) so nothing Unity-only slips in, and link it from the module's .csproj. The example keeps it in DevKit/Example/Bounties/Shared/BountyBoardMessages.cs, assembly Game.Bounties.Shared. See Assemblies.

#Sending

// Offline the board just misses this one; the character's own history still has it.
CentralMessages.Send(new BountyFinished { characterId = player.State.id, name = player.characterName, monster = monster.Id });

player.State.id is the character's database id. Central checks that this map really hosts that character before acting on it (MapMessage.Hosts), so a map can only speak for its own players.

Send returns false when the map isn't connected. Nothing is kept for later: if the data must not be lost, keep it on the character too (PlayerData) and send it again when Online comes back, or design the module to accept a full state instead of increments.

#Receiving

using System.Text;
using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Server;
using UnityEngine;

namespace Game
{
    public static class HuntersBoard
    {
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
        static void Register()
        {
            CentralMessages.On<BountyBoardList>(OnBoard);
        }

        static void OnBoard(BountyBoardList board)
        {
            var text = new StringBuilder("Best bounty hunters:");
            int rank = 1;
            foreach (BountyHunter hunter in board.top ?? new BountyHunter[0])
                text.Append($"\n{rank++}. {PlayerText.NoTags(hunter.name)}: {hunter.bounties}");
            if (rank == 1) text.Append("\nNobody yet.");
            text.Append($"\nYou: {board.mine}");
            SocialHub.Notice(board.characterId, text.ToString());
        }
    }
}
  • An answer about a character carries its id, and the map finds the player with PlayerCharacter.ServerFind(characterId) or shows a system line with SocialHub.Notice(characterId, text). Either does nothing if the character left meanwhile.
  • Text that came from players (names, notes) is shown with PlayerText.NoTags, so it can't open rich text tags on other screens.
  • Arrays can arrive null from JSON; guard with ?? new T[0].

#A complete example: a world event on every map

A moderator starts a "double gold" hour on every map. The module keeps it and broadcasts it; each map applies it to its own players.

Shared messages (in Game.Shared, linked by the module):

[Serializable]
public class GoldHourStart
{
    public long characterId;   // who asked, so Central can check the map hosts them
    public int minutes;
}

[Serializable]
public class GoldHourState
{
    public long endsUnixSeconds;   // 0 when none
}

Map side (in Game.Server):

using System;
using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Server;
using UnityEngine;

namespace Game
{
    public static class GoldHour
    {
        static long endsAt;

        public static bool Active => DateTimeOffset.UtcNow.ToUnixTimeSeconds() < endsAt;

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics() => endsAt = 0;

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
        static void Register()
        {
            CentralMessages.On<GoldHourState>(state => endsAt = state.endsUnixSeconds);
            GmCommands.Register(new GmCommand
            {
                name = "goldhour", rank = GmRank.GameMaster, usage = "goldhour minutes", description = "Double gold on every map.",
                run = c =>
                {
                    int minutes = Mathf.Clamp(c.Int(0, 60), 1, 24 * 60);
                    if (!CentralMessages.Send(new GoldHourStart { characterId = c.player.State.id, minutes = minutes }))
                        return "Only online.";
                    return $"Starting a {minutes} minute gold hour everywhere.";
                },
            });
        }
    }
}

Central side (in the module, see Service modules):

public void OnMapLink(IMapLink link)
{
    link.On<GoldHourStart>(m =>
    {
        if (!m.Hosts(m.Message.characterId) || m.Message.minutes < 1 || m.Message.minutes > 1440) return Task.CompletedTask;
        long ends = DateTimeOffset.UtcNow.AddMinutes(m.Message.minutes).ToUnixTimeSeconds();
        link.Broadcast(new GoldHourState { endsUnixSeconds = ends });
        return Task.CompletedTask;
    });
}

Your own reward code reads GoldHour.Active. For the kit's own experience, loot and gold rates you don't need any of this: the /rates command already starts timed rate events that Central hands to every map.

The GM command already checked the level on the map, and the audit recorded it. A map that joins later doesn't know about the event; send the state to maps as they ask, or keep it in the module and answer a GoldHourAsk from each map on startup.

#Single player

CentralMessages.Online is false and Send returns false. Decide per feature:

  • Only online: say so to the player, as /hunters does ("The hunters board is kept online").
  • Local fallback: keep a per-character version with PlayerData, as the example keeps each character's last hunts.

#Common mistakes

  • Using CentralMessages from the Game assembly. It lives in KitARPG.Server; the code goes in Game.Server.
  • PascalCase fields. Answers from Central come back empty on the map.
  • Trusting a character id on the Central side without m.Hosts(id).
  • Expecting Send to queue. It doesn't; plan for Central being away.
  • Registering two handlers for one type. The second replaces the first.
