Mensajes de red

Cómo hacer que el cliente y el servidor se hablen con mensajes de red de Mirror, sin agregar un componente al prefab del jugador: definir mensajes, registrar manejadores en el momento correcto, validar en el servidor y enviar a un jugador, a los jugadores cercanos o a todos.

#Mensajes o un sistema del jugador

Mensajes de red Un sistema del jugador (NetworkBehaviour)
Cambio en el prefab Ninguno Se agrega a cada prefab de modelo de jugador
Estado sincronizado Ninguno; envías lo que cambia [SyncVar] y colecciones sincronizadas
Quién lo envió conn.identity en el servidor El propio jugador del componente
Sirve para Pedidos y respuestas, avisos, funciones que quieres poder borrar quitando una carpeta Estado que la interfaz lee todo el tiempo

El ejemplo de recompensas usa mensajes: el cliente pide su recompensa cuando aparece, y el servidor envía la recompensa cada vez que cambia. Consulta Sistemas del jugador para la otra opción.

Dónde va el archivo: el ensamblado Game. Los dos lados necesitan los tipos de mensaje y sus manejadores.

#Definir un mensaje

Un mensaje es un struct que implementa Mirror.NetworkMessage, con campos públicos de tipos que Mirror sabe escribir: números, bool, string, Vector3, enums, arreglos y listas de esos, y otros structs hechos de ellos.

using Mirror;

public struct CraftRequest : NetworkMessage
{
    public string recipeId;
    public int amount;
}

public struct CraftResult : NetworkMessage
{
    public bool ok;
    public string text;
}

El weaver de Mirror genera el código que los lee y los escribe, en tu ensamblado, al compilar.

#Registrar manejadores

Los manejadores se registran en el servidor cuando arranca y en el cliente cuando se conecta. KitNetworkManager lanza eventos para los dos:

Evento Cuándo
ServerStarted Arranca un servidor o un host. En un jugador el host se reinicia en cada cambio de mapa, así que se vuelve a lanzar cada vez.
ServerStopping Antes de que se detenga el servidor.
ServerDisconnecting (NetworkConnectionToClient) Antes de que se destruya el jugador de una conexión.
ClientConnected El cliente se conectó a un mapa.
ClientDisconnected El cliente salió de un mapa.

KitNetworkManager.Instance es el manager, en el objeto KitNetwork de la escena Title (clientes y un jugador) y de la escena Server (servidores de mapa), las escenas desde las que arranca un juego. Sobrevive a los cambios de escena, así que engánchate en AfterSceneLoad, cuando la primera escena ya lo cargó:

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
static void Hook()
{
    KitNetworkManager manager = KitNetworkManager.Instance;
    if (manager == null) return;
    manager.ServerStarted += () => NetworkServer.ReplaceHandler<CraftRequest>(OnCraft);
    manager.ClientConnected += () => NetworkClient.ReplaceHandler<CraftResult>(OnResult);
}

static void OnResult(CraftResult result) => Debug.Log(result.text);

Usa ReplaceHandler, no RegisterHandler: no se queja cuando el mismo manejador se registra otra vez en el siguiente arranque. Los manejadores del servidor solo aceptan mensajes de conexiones autenticadas (jugadores que presentaron un ticket válido).

#Atender un pedido en el servidor

static void OnCraft(NetworkConnectionToClient conn, CraftRequest message)
{
    // 1. Spend from this connection's budget; floods get disconnected.
    if (!CommandPacing.Allow(conn)) return;

    // 2. Who sent it comes from the connection, never from the message.
    if (conn.identity == null || !conn.identity.TryGetComponent(out PlayerCharacter player)) return;
    if (player.State == null || player.IsDead) return;

    // 3. Validate every field.
    if (string.IsNullOrEmpty(message.recipeId) || message.recipeId.Length > 64) return;
    if (message.amount < 1 || message.amount > 99) return;
    if (!GameInstance.Database.TryGet(message.recipeId, out RecipeData recipe)) return;

    // 4. Do it through the kit's systems, then answer.
    string why = Crafting.ServerCraft(player, recipe, message.amount);
    conn.Send(new CraftResult { ok = why == null, text = why ?? $"Crafted {recipe.DisplayName}." });
}

(RecipeData y Crafting representan tu propio tipo de datos y tus reglas.)

Los cuatro pasos se aplican a todo manejador:

  1. Ritmo. CommandPacing.Allow(conn) comparte un presupuesto por conexión con todos los [Command] del juego (30 por segundo, ráfaga de 60). Muy por encima de eso, la conexión se expulsa con KickReasons.Flooding. Usa CommandPacing.AllowCentral(conn) para los pedidos que generan trabajo para Central (2 por segundo, ráfaga de 10).
  2. Identidad. conn.identity es el objeto del jugador de la conexión que lo envió. Nunca pongas un id de personaje, un id de cuenta ni un nombre de jugador en un pedido para actuar según él.
  3. Validación. Los textos tienen largos, los números tienen rangos y deben ser finitos (float.IsFinite), los ids deben existir en la base de datos, y las referencias a cosas del mundo (un NPC, un monstruo, un botín) deben estar cerca y ser visibles para ese jugador.
  4. Sistemas del kit. Cambia ítems, oro y progreso mediante PlayerInventory, IPlayerActor, PlayerQuests y PlayerProgress.

#Nombrar cosas del mundo

Para nombrar un monstruo o un jugador, envía su netId y resuélvelo en el servidor con Fighters.TargetFor, que devuelve null para todo lo que esa conexión no debería ver (fuera de su vista, un enemigo invisible, un monstruo de evento creado para otro):

ICombatant target = Fighters.TargetFor(conn, player, message.targetNetId);
if (target == null) return;

Para nombrar un NPC, envía su id y revisa la distancia:

if (!Npc.TryFind(message.npcId, out Npc npc) || !npc.InReach(player.transform.position)) return;

#Enviar desde el servidor

A Cómo
Un jugador player.connectionToClient.Send(message) (o conn.Send en un manejador)
Todos los que ven a un jugador NetworkServer.SendToReadyObservers(player.netIdentity, message)
Todos en este servidor de mapa NetworkServer.SendToAll(message)
Todos en todos los mapas Mediante Central: consulta Hablar con Central

connectionToClient es null en los objetos sin dueño y puede ser null mientras un jugador se va; usa ?.Send. Los mapas instanciados (mazmorras, casas de gremio) corren sus copias dentro del mismo proceso del servidor de mapa, así que SendToAll llega a todas las copias. Para limitar un aviso a una copia, recorre PlayerCharacter.ServerAll() y compara gameObject.scene.

#Enviar desde el cliente

public static void Craft(string recipeId, int amount) =>
    NetworkClient.Send(new CraftRequest { recipeId = recipeId, amount = amount });

Envía solo mientras estés conectado (NetworkClient.isConnected). Los mensajes enviados antes de que apareciera el jugador llegan con conn.identity en null, y el manejador de arriba los ignora.

#Pedir cuando aparece el jugador

El cliente sabe que su jugador existe cuando se lanza PlayerCharacter.LocalSpawned. El ejemplo de recompensas pide su estado ahí:

PlayerCharacter.LocalSpawned -= AskOnSpawn;
PlayerCharacter.LocalSpawned += AskOnSpawn;

static void AskOnSpawn(PlayerCharacter _) => NetworkClient.Send(new BountyAsk());

#Un ejemplo completo: un tablón de avisos del mundo

Los jugadores leen un mensaje del día para todo el servidor, y los moderadores lo cambian con un comando de GM. El aviso se guarda en el servidor de mapa.

using Blunnyn.KitARPG.Net;
using Mirror;
using UnityEngine;

namespace Game
{
    public struct NoticeAsk : NetworkMessage { }

    public struct NoticeText : NetworkMessage
    {
        public string text;
    }

    public static class NoticeBoard
    {
        public const int MaxLength = 300;

        /// <summary>Server: the current notice.</summary>
        public static string Current { get; private set; } = "";

        /// <summary>Client: the notice arrived.</summary>
        public static event System.Action<string> Received;

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            Current = "";
            Received = null;
        }

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
        static void Hook()
        {
            PlayerCharacter.LocalSpawned -= AskOnSpawn;
            PlayerCharacter.LocalSpawned += AskOnSpawn;
            KitNetworkManager manager = KitNetworkManager.Instance;
            if (manager == null) return;
            manager.ServerStarted += () => NetworkServer.ReplaceHandler<NoticeAsk>(OnAsk);
            manager.ClientConnected += () => NetworkClient.ReplaceHandler<NoticeText>(OnText);
        }

        static void OnText(NoticeText message) => Received?.Invoke(message.text);

        static void AskOnSpawn(PlayerCharacter _) => NetworkClient.Send(new NoticeAsk());

        static void OnAsk(NetworkConnectionToClient conn, NoticeAsk _)
        {
            if (!CommandPacing.Allow(conn) || conn.identity == null) return;
            conn.Send(new NoticeText { text = Current });
        }

        /// <summary>Server only. Sets the notice and shows it to everyone on this map server.</summary>
        public static void ServerSet(string text)
        {
            Current = PlayerText.Clean(text ?? "", MaxLength);
            NetworkServer.SendToAll(new NoticeText { text = Current });
        }
    }
}

Hook sigue Play sin recarga de dominio: el evento estático PlayerCharacter.LocalSpawned lleva -= antes de +=, y va antes de revisar el manager, así que se engancha aunque la escena no tenga network manager. Los eventos del propio manager no necesitan -=: el manager se vuelve a crear en cada Play, y el viejo desaparece con sus suscriptores.

El comando de GM, en el ensamblado Game.Server:

GmCommands.Register(new GmCommand
{
    name = "notice", rank = GmRank.Moderator, usage = "notice text", description = "Sets the notice board.",
    run = c =>
    {
        NoticeBoard.ServerSet(c.rest);
        return "Notice set.";
    },
});

PlayerText.Clean recorta el texto, quita los caracteres de control, lo corta a un largo y rompe las etiquetas de texto enriquecido, así un aviso no puede inyectar marcado de TextMeshPro en las pantallas de otros jugadores. Para ponerlo en todos los mapas a la vez, envíalo mediante Central (consulta Hablar con Central).

#Versión de red

El kit calcula un hash de cada mensaje de red y de cada campo sincronizado del proyecto, los tuyos incluidos (NetworkVersion). El cliente envía el hash con su ticket y un servidor de mapa compilado con otro código lo rechaza con version_mismatch. Después de agregar o cambiar un mensaje, vuelve a compilar tanto el cliente como el servidor de mapa. En el editor el valor se calcula a partir del código actual, así que el Play siempre coincide consigo mismo.

#Un jugador y MMO

Los mensajes funcionan igual en los dos. En un jugador el cliente y el host corren en un mismo proceso: NetworkClient.Send llega al manejador del host por una conexión local, que CommandPacing nunca limita. Como el host se reinicia en cada cambio de mapa, los manejadores registrados desde ServerStarted se vuelven a registrar cada vez, y por eso se usa ReplaceHandler.

#Errores comunes

  • Confiar en un id del mensaje. Un jugador envía el nombre o el id de otro y el servidor actúa en nombre de ese otro. Usa conn.identity.
  • Sin control de ritmo. Todo manejador que un cliente pueda activar debe llamar a CommandPacing.Allow.
  • Registrar una sola vez al arrancar. El host de un jugador se reinicia; registra en ServerStarted y ClientConnected.
  • Enviar datos privados a los observadores. SendToReadyObservers llega a todos los que están cerca.
  • Textos y arreglos sin límite. Revisa los largos antes de usarlos, y antes de guardarlos o reenviarlos.
  • Olvidar volver a compilar el servidor de mapa después de cambiar un mensaje.
