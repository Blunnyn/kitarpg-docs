Guardar datos

Dónde guardar los datos propios de tu juego para que se guarden con el personaje en un jugador y online: marcas del personaje, PlayerData, componentes con IPlayerSave, tablas en un módulo de Central y assets de datos.

#Elige un lugar

Qué guardas Dónde Lo ve el cliente Se guarda
Números enteros pequeños por personaje: marcas de historia, contadores, un sello de día Marcas del personaje El dueño, sincronizado Con el personaje
Valores con estructura por personaje: una lista, una mascota con stats, un historial PlayerData Nunca Con el personaje
Lo mismo, pero de un componente tuyo que lo carga y lo escribe IPlayerSave + PlayerData Lo que sincronices tú Con el personaje
Datos que consultas entre personajes: clasificaciones, eventos del mundo, contadores de todo el servidor Una tabla en un módulo de Central Lo que envíes En tu propia tabla
Lo que editan los diseñadores de contenido: recetas, tablones, listas de botín Un asset ScriptableObject o GameData Ambos builds lo cargan Es un asset

Nunca pongas estado del juego en PlayerPrefs: vive en la computadora del jugador, nunca llega al servidor y el jugador puede editarlo. PlayerPrefs es para los ajustes del cliente (consulta Opciones de menús y ajustes).

#Marcas del personaje

Las marcas son enteros con nombre en el personaje, que guarda PlayerProgress. Los diseñadores ya las usan con SetFlagAction y FlagCondition, y tú también puedes.

Dónde Leer Escribir
Condiciones y acciones facts.Flag(key) actor.SetFlag(key, value) (servidor)
Código de servidor player.Facts.Flag(key) o progress.Flag(key) player.Facts.SetFlag(key, value) o progress.SetFlag(key, value)
Cliente del dueño PlayerProgress.Local.Flag(key) Nunca
  • Un valor de 0 quita la marca. Flag devuelve 0 para las marcas que nunca se pusieron.
  • Las marcas se sincronizan con el dueño (PlayerProgress usa sincronización Owner), así que la interfaz y las condiciones del dueño pueden leerlas. Los demás jugadores nunca las ven.
  • PlayerProgress.ServerFlagChanged (PlayerCharacter, string key, int value) se lanza en el servidor cuando una cambia.
  • Online, Central las guarda en characters.extra bajo flags; en un jugador van en el guardado local.

El ejemplo de recompensas guarda el progreso de la cacería en marcas (bounty.board, bounty.index, bounty.kills, bounty.day, bounty.done). Las últimas cacerías de cada personaje son una lista de nombres, que no cabe en una marca, así que van en PlayerData (ver abajo).

Las marcas guardan int. Un número de día, una cuenta o un hash de un id caben; el texto y las listas no.

#PlayerData

PlayerData (namespace Blunnyn.KitARPG.Net) guarda JSON bajo claves propias en el personaje. Solo en el servidor.

Miembro Qué hace
T Get<T>(PlayerCharacter player, string key) El valor, o un T nuevo cuando no hay ninguno o no se puede leer.
bool Set<T>(PlayerCharacter player, string key, T value) Lo guarda. Null quita la clave. False cuando se rompería un límite; en ese caso no cambia nada.
bool Has(PlayerCharacter player, string key) Si la clave tiene un valor.
void Remove(PlayerCharacter player, string key) Lo quita.
string GetJson(...), bool SetJson(...) Lo mismo con JSON en crudo.

Los valores son clases [Serializable] que se leen y escriben con JsonUtility de Unity:

[Serializable]
public class PetSave
{
    public string petId;
    public int level = 1;
    public long experience;
    public List<string> tricks = new List<string>();
}

// On the server:
PetSave pet = PlayerData.Get<PetSave>(player, "mygame.pet");
pet.experience += 50;
if (!PlayerData.Set(player, "mygame.pet", pet)) Debug.LogWarning("Pet data too big.");

#Límites

CharacterDataRules (namespace Blunnyn.KitARPG.Shared.Characters) aplica los mismos límites en el mapa, en Central y en el guardado local:

Límite Valor
Claves por personaje (MaxKeys) 64
Largo de la clave (MaxKeyLength) 64 caracteres
Caracteres de la clave Letras, dígitos, ., - y _
Todos los valores juntos (MaxBytes) 32 KB de UTF-8

Pon el nombre de tu juego como prefijo de cada clave (mygame.pet), para que nunca choque con la de otro paquete.

#Dónde se guarda

Online, Central guarda los valores en characters.extra bajo game, como un solo objeto JSON ({ "mygame.pet": { ... } }), legible en la base de datos y sin migración de tablas. Un guardado cuyos datos rompen los límites, o que tiene un valor que no es JSON válido, conserva los datos guardados, registra una advertencia y guarda el resto del personaje. En un jugador los mismos datos van al guardado local (savegame.db en la carpeta de datos persistentes del jugador, definido por Save File en KitSettings).

#Lo que JsonUtility puede y no puede hacer

  • Campos públicos y campos privados [SerializeField]. No propiedades.
  • int, long, float, bool, string, enums, arrays, List<T>, clases [Serializable] anidadas.
  • Sin diccionarios. Guarda dos listas paralelas, o una lista de clases clave-valor.
  • Sin polimorfismo, sin null para clases anidadas (vuelven vacías).

#Componentes con IPlayerSave

Cuando un componente tuyo es dueño de sus datos, implementa IPlayerSave y deja que el kit te llame:

Método Cuándo
void ServerLoad(PlayerCharacter player, CharacterState state) Cuando el personaje entra a un mapa, después de que cargaron los sistemas del kit, antes de que aparezca el jugador.
void WriteTo(PlayerCharacter player, CharacterState state) Antes de cada guardado. 
[RequireComponent(typeof(PlayerCharacter))]
public class PlayerPet : NetworkBehaviour, IPlayerSave
{
    const string Key = "mygame.pet";

    PetSave pet = new PetSave();

    [SyncVar] public string petId;
    [SyncVar] public int petLevel;

    public void ServerLoad(PlayerCharacter player, CharacterState state)
    {
        pet = PlayerData.Get<PetSave>(player, Key);
        petId = pet.petId;
        petLevel = pet.level;
    }

    public void WriteTo(PlayerCharacter player, CharacterState state) => PlayerData.Set(player, Key, pet);
}

La plantilla Saved Player Data crea uno de estos (consulta Plantillas).

Atención

En ServerLoad el jugador todavía no apareció, así que isServer es false y PlayerData.Set lo rechaza. Lee ahí; escribe desde WriteTo o después.

#Cuándo se guarda

En el servidor de mapa, un personaje se guarda:

  • cada Save Interval Seconds (saveIntervalSeconds en el servidor de mapa, 60),
  • cuando el jugador se desconecta o cambia de mapa,
  • cuando el servidor se detiene.

Cada guardado llama WriteTo en cada IPlayerSave. Online el estado va a Central, que lo escribe en la base de datos; en un jugador va al guardado local. Los valores puestos con PlayerData.Set entre guardados viven en el personaje en memoria y van con el siguiente guardado. Una caída entre dos guardados pierde lo que cambió desde el último, igual que con los datos del propio kit.

Los ítems y el oro que se mueven entre personajes (intercambios, correo, mercado, banco del gremio) usan transacciones en Central en lugar del guardado periódico; nunca modeles un intercambio entre jugadores con PlayerData.

#Cambiar el formato después

El JSON guardado dura más que tu código. Planifica para los datos viejos:

  • Los campos nuevos reciben su valor por defecto cuando se leen datos viejos; dales valores por defecto razonables.
  • Los campos quitados se ignoran.
  • Para cambios más grandes, pon un número de versión en la clase y convierte en ServerLoad.
  • Cambiarle el nombre a una clave pierde los datos viejos. Lee la clave vieja una vez, escribe la nueva y haz Remove de la vieja.

#Tablas en un módulo de Central

Para datos que consultas entre personajes (los mejores cazadores, un contador de todo el servidor, un historial de subastas propio), un módulo agrega tablas a la base de datos del kit junto a las del kit, con sus propias migraciones. Los servidores de mapa llegan a él con CentralMessages. Consulta Hablar con Central y Módulos de servicio. En un jugador no hay Central: guarda un respaldo por personaje, como hace el ejemplo de recompensas con su historial en PlayerData.

#Assets de datos

El contenido (recetas, listas de botín, definiciones de tablones) va en assets, no en guardados:

  • Un ScriptableObject simple con [CreateAssetMenu] cuando solo tu código lo referencia. El BountyBoardData del ejemplo de recompensas es uno.
  • Una subclase de GameData cuando los guardados o los mensajes deben apuntarle por id. Un GameData tiene un Id (hecho a partir de su nombre, guardado con los personajes), un nombre para mostrar, una descripción y un ícono, y GameInstance.Database.TryGet<T>(id, out T) lo encuentra. Tiene que poder alcanzarse desde la base de datos del juego: listado en uno de sus arrays, o entregado por un método Visit de algo que sí lo esté. Project Check lista los assets GameData que la base de datos no alcanza.

#Errores comunes

  • Guardar en PlayerPrefs. Nunca llega al servidor.
  • Leer PlayerData en el cliente. Nunca se envía. Sincroniza lo que necesita la interfaz.
  • Claves sin prefijo. Otro paquete puede sobrescribirlas.
  • Diccionarios en clases guardadas. JsonUtility los descarta sin avisar.
  • Ignorar la respuesta de Set. Pasados los límites, no se guarda nada.
  • Cambiar el id de un GameData. Los guardados apuntan al id viejo.
