Play sin recarga de dominio

Por qué el estado estático de tu código hay que reiniciarlo a mano, cuándo corre cada método de inicio y los patrones que usa el kit para que cada Play empiece limpio.

#Qué es la recarga de dominio

Cuando presionas Play, Unity puede recargar el dominio de scripts: descartar todos los ensamblados cargados y todos los valores estáticos, y volver a cargarlos. Así cada Play empieza limpio, y en un proyecto del tamaño de KitARPG eso tarda muchos segundos.

El proyecto del kit la apaga: Project Settings > Editor > Enter Play Mode Settings tiene Reload Domain apagado (las escenas sí se recargan). Así Play arranca en uno o dos segundos. El precio es que los campos estáticos conservan sus valores del Play anterior:

  • una lista estática todavía tiene las entradas que se agregaron la última vez,
  • un evento estático todavía tiene los suscriptores del Play anterior, que apuntan a objetos destruidos,
  • un Local estático todavía apunta al jugador local anterior,
  • un contador estático sigue contando.

Las builds siempre empiezan limpias. Estos problemas solo aparecen en el editor, y solo desde el segundo Play, por eso es fácil pasarlos por alto. Tu proyecto puede tener Reload Domain encendido; escribe tu código para que funcione de las dos formas.

#Los momentos de inicio

[RuntimeInitializeOnLoadMethod] corre un método estático en un momento fijo de cada Play (y de cada arranque de una build):

Tipo de carga Cuándo Úsalo para
SubsystemRegistration Primero, antes que todo Limpiar tus propios estáticos.
AfterAssembliesLoaded Después de cargar todos los ensamblados Suscribirte a eventos estáticos de otras clases; agregar entradas de menú y opciones.
BeforeSplashScreen Antes de la pantalla de presentación (casi nunca hace falta)
BeforeSceneLoad Antes de cargar la primera escena Instalar fórmulas y otros reemplazos.
AfterSceneLoad Después de cargar la primera escena Lo que necesita objetos de la escena: KitNetworkManager.Instance, comandos de GM.

Dentro de un mismo tipo de carga, Unity no define el orden entre métodos de clases distintas. De ahí salen las reglas del kit.

#Las reglas del kit

  1. Cada clase limpia sus propios estáticos en SubsystemRegistration. Los campos, eventos, colecciones y cachés que guardan estado vuelven a sus valores iniciales en un método que suele llamarse ResetStatics.
  2. Suscríbete a los eventos estáticos de otra clase en AfterAssembliesLoaded o después. Esa clase los limpia en SubsystemRegistration; si te suscribieras en la misma fase, tu suscripción podría borrarse después de hacerla.
  3. Las listas que el kit llena con sus propias entradas se rearman en SubsystemRegistration (ItemMenu.Entries, PlayerMenu.Entries, ClientOptions.All, los comandos de GM). Agrega las tuyas después.
  4. Las fórmulas del kit vuelven a las suyas en SubsystemRegistration (GameInstance.Formula, GameInstance.Combat). Instala las tuyas en BeforeSceneLoad.
  5. Una clase que registra algo propio en SubsystemRegistration limpia y registra en el mismo método, así el orden con otras clases no importa (GmCommands).
  6. Los búferes de trabajo que se vacían en cada uso y las cachés que siguen siendo válidas no se limpian. Una List estática usada como espacio de trabajo, o un valor calculado que no puede cambiar durante la sesión, pueden quedarse.

Las tablas de modos de juego (GameModes) son una excepción: nunca se limpian, así los ensamblados de los modos pueden registrarse desde SubsystemRegistration en cualquier orden.

#El patrón para tu código

using System;
using System.Collections.Generic;
using Blunnyn.KitARPG.Net;
using UnityEngine;

namespace Game
{
    public static class Kills
    {
        // State of this class.
        static readonly Dictionary<long, int> counts = new Dictionary<long, int>();
        public static event Action<PlayerCharacter, int> ServerCounted;

        // 1. Clear own state first.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            counts.Clear();
            ServerCounted = null;
        }

        // 2. Subscribe to the kit's events after the kit cleared them.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]
        static void Hook()
        {
            Monster.ServerKilled -= OnKilled;
            Monster.ServerKilled += OnKilled;
        }

        static void OnKilled(Monster monster, PlayerCharacter killer)
        {
            if (killer == null || killer.State == null) return;
            counts.TryGetValue(killer.State.id, out int n);
            counts[killer.State.id] = ++n;
            ServerCounted?.Invoke(killer, n);
        }
    }
}

-= antes de += hace que la suscripción sea segura aunque el método corra dos veces. Los métodos con nombre (no lambdas) hacen posible el -=.

#Estáticos en componentes

Un NetworkBehaviour o MonoBehaviour con miembros estáticos sigue la misma regla:

public class PlayerPet : NetworkBehaviour
{
    public static PlayerPet Local { get; private set; }
    public static event Action<string> Told;

    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    static void ResetStatics()
    {
        Local = null;
        Told = null;
    }

    public override void OnStartAuthority() => Local = this;

    public override void OnStopAuthority()
    {
        if (Local == this) Local = null;
    }
}

Las plantillas de sistemas del jugador y de datos guardados ya lo hacen.

#Lo que vive en objetos de la escena

Los eventos de objetos que se crean de nuevo en cada Play (el network manager, una ventana del HUD) no necesitan limpiarse: el objeto viejo desaparece con sus suscriptores. Por eso las plantillas del kit se suscriben a KitNetworkManager.ServerStarted en AfterSceneLoad sin desuscribirse.

#Cachés perezosas

static AttributeData toughness;

public static AttributeData Toughness
{
    get
    {
        if (toughness == null && GameInstance.Database != null) GameInstance.Database.TryGet("toughness", out toughness);
        return toughness;
    }
}

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
static void ResetStatics() => toughness = null;

Una caché de un asset sobrevive al Play sin daño si el asset no puede cambiar, pero limpiarla no cuesta nada y cubre los cambios hechos entre un Play y otro.

#Lista de revisión

Para cada static de tu código, pregúntate:

Es Haz
Un valor que cambia durante el juego (un contador, un Local, un diccionario de jugadores) Reinícialo en SubsystemRegistration.
Un evento estático de tu clase Ponlo en null en SubsystemRegistration.
Una suscripción al evento estático de otro Hazla en AfterAssembliesLoaded o después, con -= primero.
Una entrada en una lista del kit (menús, opciones, comandos, revisiones del validador en el editor) Agrégala después de que el kit llenó la lista.
Un valor const o static readonly que nunca cambia Nada.
Un búfer de trabajo que se vacía antes de cada uso Nada.

Los estáticos solo del editor (revisiones del validador, páginas) siguen la vida del editor, no la del Play: regístralos desde [InitializeOnLoadMethod] y quítalos antes de agregarlos (consulta Extensiones del editor).

#Cómo probarlo

  1. Presiona Play, haz lo que hace tu función y detente.
  2. Presiona Play otra vez y hazlo de nuevo.
  3. Fíjate si hay mensajes duplicados, eventos que se disparan dos veces, contadores que no empezaron en cero y MissingReferenceException por objetos destruidos.

El kit mismo se probó así: dos Play seguidos en un jugador dan los mismos suscriptores, comandos y entradas de menú.

#Errores comunes

  • Suscribirse en SubsystemRegistration. El kit puede limpiar el evento después de ti. Suscríbete en AfterAssembliesLoaded o después.
  • Limpiar el evento de otro. Cada clase limpia solo los suyos.
  • Limpiar tu evento en un método de inicio y suscribirte a él en otro del mismo tipo. El orden no está definido: limpia en SubsystemRegistration y suscríbete en una fase posterior.
  • Lambdas en += que corren en cada Play sobre un evento que no se limpia.
  • Referencias estáticas a objetos de la escena sin reinicio: se vuelven objetos destruidos que comparan igual a null pero siguen ocupando memoria.
