Cambiar el comportamiento del kit

Cómo cambiar lo que hace uno de los componentes del kit sin editarlo: hereda de la ventana, el sistema del jugador, el monstruo o el componente de NPC, sobrescribe sus métodos virtuales y cambia el componente en el prefab.

#Cuándo sobrescribir

La mayoría de los cambios necesitan menos que esto. Antes de sobrescribir, revisa:

  • un ajuste en Game Settings o en el componente,
  • un evento al que reaccionar (Eventos),
  • una fórmula (Fórmulas),
  • un efecto, condición, acción, objetivo u opción de NPC propios.

Sobrescribe cuando el flujo propio del kit tiene que ir de otra forma: una ventana que lee su texto de tu localización, un monstruo con su propia forma de recibir daño, un sistema de correo que rechaza cartas con enlaces.

Dónde va el archivo: el ensamblado Game, porque el componente vive en prefabs que carga cada build.

#Qué se puede sobrescribir

El kit deja esto abierto a subclases:

En Qué es virtual
Ventanas y piezas del HUD (KitARPG.Client) Los métodos de Unity (Awake, OnEnable, OnDisable, Update, OnDestroy) son protected virtual, más los métodos pensados para cambiar, como ShopWindow.Describe (texto de error)
Sistemas del jugador (PlayerInventory, PlayerSkills, PlayerQuests, PlayerMail y los demás) Métodos de Unity protected virtual; métodos de servidor Server... public virtual (o protected virtual para pasos internos, como PlayerMail.ServerAnnounce(MailList))
Monster Métodos de Unity, ServerSetup, ServerDamage, ServerHeal, ServerAddBuff, ServerRemoveBuffs, ServerKnock, ServerRevive, ServerDespawn, Think, TryCast, RunPhase y más
PlayerCharacter ServerSetup, ServerHeal, ServerAddExperience, ServerTryAttack, ServerAnnounce(string, Color) y otros métodos de servidor

La referencia de la API en Assets/Blunnyn/KitARPG/Documentation/API/ lista cada miembro virtual. Los métodos que no son virtuales no están pensados para cambiar; lee la clase para encontrar el paso virtual que cubre lo que necesitas.

#Cómo cambiar un componente

  1. Escribe tu subclase y deja que compile.

  2. Abre el prefab que tiene el componente del kit:

    Componente Prefab
    Sistemas del jugador, PlayerCharacter Cada prefab de modelo de jugador (KitARPG > Game Database > Models)
    Ventanas y piezas del HUD El prefab del HUD (GameInstance.hudPrefab, en Game Settings > Interface)
    Monster El prefab de cada monstruo (el campo Prefab del monstruo en la Game Database)
    Npc El objeto del NPC en su escena

  3. En el componente del kit, abre el menú (los tres puntos) y elige Copy Component.

  4. Agrega tu componente. En él, elige Paste Component Values: se copian todos los campos que tenía el componente del kit, porque tu clase los hereda.

  5. Quita el componente del kit.

  6. Guarda el prefab. Para los sistemas del jugador, repítelo en cada prefab de modelo de jugador.

El código del kit encuentra los componentes con GetComponent<PlayerMail>() y llamadas parecidas, que también devuelven tu subclase. No hace falta cambiar nada más.

Atención

En prefabs en red (jugadores, monstruos), la posición del componente en la lista le importa a Mirror. Reemplazar un componente mueve el nuevo al final, lo que está bien mientras las builds de cliente y servidor usen el mismo prefab. Nunca cambies componentes en tiempo de ejecución ni en una sola build.

#Ejemplo: la plantilla

Create > KitARPG > Scripts > Player System Override crea una subclase de PlayerMail:

using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Shared.Central;

namespace Game
{
    /// <summary>
    /// Changes how one of the kit's player systems behaves, here the mail, without editing the kit.
    /// On every player model prefab, remove the kit's component and add this one in its place
    /// (Copy Component, then Paste Component Values, keeps the settings).
    /// </summary>
    public class MyPlayerMail : PlayerMail
    {
        // Server methods decide for every player; call base for whatever you keep.
        protected override void ServerAnnounce(MailList list)
        {
            base.ServerAnnounce(list);
        }

        // Unity methods are protected virtual too.
        protected override void Awake()
        {
            base.Awake();
        }
    }
}

#Ejemplo: un monstruo que recibe la mitad del daño

using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;
using UnityEngine;

namespace Game
{
    /// <summary>A monster with armor: every hit is reduced before it lands.</summary>
    public class ArmoredMonster : Monster
    {
        [Range(0, 1)] public float reduction = 0.5f;

        public override void ServerDamage(Hit hit, IFighter source)
        {
            hit.amount = Mathf.Max(1, Mathf.RoundToInt(hit.amount * (1 - reduction)));
            base.ServerDamage(hit, source);
        }
    }
}

Cambia Monster por ArmoredMonster en el prefab de ese monstruo. Los demás monstruos conservan el componente del kit.

#Ejemplo: mensajes de tienda localizados

ShopWindow.Describe convierte códigos de error en frases y está pensado para sobrescribirse:

using Blunnyn.KitARPG.Client;
using Blunnyn.KitARPG.Net;

namespace Game
{
    public class MyShopWindow : ShopWindow
    {
        protected override string Describe(string code)
        {
            switch (code)
            {
                case NpcErrors.NotEnoughMoney: return Localize("shop.no_money");
                case NpcErrors.OutOfStock: return Localize("shop.sold_out");
                default: return base.Describe(code);
            }
        }

        static string Localize(string key) => key; // your localization lookup
    }
}

Cámbialo en el prefab del HUD, dentro de su grupo Windows.

#Ejemplo: una regla en cada uso de ítem

PlayerInventory.UseItem es el paso del servidor que hace que un ítem cumpla su función. False conserva el ítem:

using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;

public class MyPlayerInventory : PlayerInventory
{
    protected override bool UseItem(IUsable item)
    {
        // No potions inside the arena maps.
        if (item.CooldownGroup == "potion" && gameObject.scene.name.StartsWith("Arena")) return false;
        return base.UseItem(item);
    }
}

#Ejemplo: un buzón que se abre desde cierto nivel

PlayerMail.ServerOpen corre cuando un NPC de buzón abre el correo para un jugador:

using Blunnyn.KitARPG.Net;
using UnityEngine;

public class LevelGatedMail : PlayerMail
{
    public int minLevel = 5;

    public override string ServerOpen(Npc npc)
    {
        if (TryGetComponent(out PlayerCharacter player) && player.level < minLevel)
        {
            player.ServerAnnounce($"The mailbox opens at level {minLevel}.", new Color(1f, 0.5f, 0.45f));
            return null;
        }
        return base.ServerOpen(npc);
    }
}

La misma regla podría ser una condición en la opción del NPC del buzón, sin código. Sobrescribir sirve para reglas que deben cumplirse desde dondequiera que se llegue al sistema.

Los métodos de servidor deciden por cada jugador. Lee el método base antes de sobrescribirlo y llama a base en cada paso que conserves.

#Sobrescrituras de servidor y de cliente

Sobrescritura Efecto
Un método Server... Cambia la regla para cada jugador en ese servidor de mapa. En línea, lo que cuenta es la build del servidor de mapa.
Un método de Unity o de una ventana Cambia lo que ve ese jugador y cómo pide las cosas. Un cliente modificado puede deshacerlo, así que nunca dependas de esto para las reglas.

Todo lo que una sobrescritura del lado del cliente envíe al servidor debe revisarse otra vez en el servidor, por el kit o por una sobrescritura de servidor tuya.

#Estáticos en la clase base

Los sistemas del jugador ponen estáticos como PlayerMail.Local en su propio OnStartAuthority. Si sobrescribes OnStartAuthority, OnStopAuthority, Awake o cualquier método de Unity, llama primero a base; si no, esos estáticos quedan vacíos y las ventanas del kit dejan de encontrar tu componente.

#Actualizaciones del kit y tus subclases

Las actualizaciones del kit también buscan los componentes del kit con GetComponent, así que un prefab con tu subclase cuenta como que tiene el componente: la actualización no agrega un segundo. Las actualizaciones que agregan campos a un componente del kit también llegan a tu subclase, porque los hereda.

Cuando una versión del kit cambia un método virtual que sobrescribes (parámetros nuevos, un método eliminado), tu código deja de compilar y el registro de cambios dice qué cambió. Mantén las sobrescrituras pequeñas y llama a base para que el comportamiento nuevo del kit llegue a tu juego.

#Errores comunes

  • No llamar a base en los métodos de Unity. Faltan los estáticos, las suscripciones y las colecciones sincronizadas que prepara la clase base.
  • Copiar una clase entera del kit en vez de heredar de ella. Las actualizaciones ya no le llegan.
  • Olvidar un modelo de jugador. Cada modelo es su propio prefab; uno con el componente del kit se comporta distinto.
  • Sobrescrituras de cliente que imponen reglas. Hazlo en el servidor.
