Servidores y despliegue

Seguridad

Cómo mantiene KitARPG seguro un juego en línea, lo que debes configurar antes de abrirlo a los jugadores, cómo rotar las claves y una lista de revisión para recorrer antes del lanzamiento.

#El modelo

  • El servidor decide. El cliente solo pide. Movimiento, combate, botín, intercambios, el banco, la forja, la tienda: el servidor de mapa revisa cada petición y la aplica. Un cliente modificado puede enviar cualquier cosa; no puede hacer que el servidor la acepte.
  • Los jugadores nunca llegan a la base de datos. Los servidores de mapa tampoco: cargan y guardan a través de Central.
  • Tickets. Un cliente entra a un mapa solo con un ticket de un solo uso de Central, válido 30 segundos, solo para ese mapa. Nadie se salta el inicio de sesión ni juega con el personaje de otro.
  • Una sesión por cuenta. Volver a iniciar sesión cierra primero la sesión vieja, después de que guarda su mapa.
  • Los objetos tienen un dueño. Cada copia es una fila de la base de datos con exactamente un dueño, y cada movimiento pasa por un bloqueo y una transacción. Consulta Servicios.
  • Los clientes no llevan código de servidor. La separación de builds mantiene la lógica del servidor, los comandos de GM, las claves y las cadenas de conexión fuera del cliente que publicas. Consulta Builds.

El resto de esta página es lo que configuras para que ese modelo se cumpla en tus servidores.

#Secretos

Secreto Dónde vive Quién debe tenerlo
Clave de firma de tokens Auth:SigningKey / KITARPG_SIGNING_KEY Login y Central
Clave del mapa Central:MapKey / KITARPG_MAP_KEY, KITARPG_CENTRAL_KEY en los mapas Central y cada servidor de mapa
Clave del mapa para Shop Shop:MapKeys / KITARPG_SHOP_KEY Shop y cada servidor de mapa
Clave de administración de Shop Shop:AdminKey / KITARPG_SHOP_ADMIN_KEY Shop y quien publique el catálogo
Secretos de pago Shop:Stripe:WebhookSecret, Shop:Signed:Secret Shop y tu proveedor de pagos
Contraseña de la base de datos Database:ConnectionString / POSTGRES_PASSWORD Login, Central, Shop, PostgreSQL

Fuera de Development, los servicios se niegan a arrancar mientras alguno de estos esté vacío, tenga menos de 16 caracteres o sea un valor de ejemplo del repositorio (cualquier cosa que contenga change-me o kitarpg-dev, o que empiece con development- o dev-). La clave de firma además debe tener al menos 32 bytes. La contraseña de la base de datos no puede ser kitarpg, postgres, password, admin, root ni secret. Se permite una cadena de conexión sin contraseña en absoluto, para archivos de contraseñas y conexiones locales de confianza.

El lanzador y Play & Servers generan claves aleatorias por computadora y las guardan en launcher.json (UserSettings/KitARPG/ desde el editor). Docker las lee de Deploy/.env. Mantén ambos fuera del control de versiones y nunca pongas un secreto en una build de cliente.

Importante

Cualquiera con la clave del mapa puede hacerse pasar por un servidor de mapa y guardar cualquier personaje. Cualquiera con la clave de firma puede iniciar sesión como cualquier cuenta. Trata ambas como la contraseña de la base de datos.

#TLS y el proxy inverso

Login, Central y Shop hablan HTTP simple. En producción, Caddy está delante de ellos (el archivo compose lo arranca):

  • Caddy sirve https://<login domain> y https://<central domain> y reenvía a los servicios en la red privada de compose. Obtiene y renueva los certificados solo una vez que los dominios apuntan al servidor y los puertos 80 y 443 están abiertos.
  • Los puertos 5100, 5200 y 5300 se publican solo en 127.0.0.1, para revisiones de salud y la API de administración de Shop desde el servidor mismo. No los publiques en otras interfaces.
  • De Shop, Caddy reenvía solo /api/shop/webhooks/*, en el dominio de Login.
  • Los clientes de release se niegan a compilar con direcciones HTTP simples para Login o Central (salvo esta computadora), e ignoran -login, -centralUrl y -mode, así un acceso directo malicioso no puede enviar una contraseña a otro lado.

#Proxy inverso

Detrás de un proxy, cada petición viene de la dirección del proxy, así que los límites de ritmo por dirección meterían a todos los jugadores en la misma bolsa. Los servicios leen X-Forwarded-For y X-Forwarded-Proto solo cuando se permite:

Opción Qué hace Predeterminado
Proxy:Enabled Cree en las cabeceras reenviadas false
Proxy:KnownProxies Direcciones de los proxies cuyas cabeceras se creen (loopback siempre) Vacío
Proxy:KnownNetworks Redes en formato CIDR, para proxies sin dirección fija Vacío
Proxy:ForwardLimit Proxies en la cadena 1

El archivo compose le da a Caddy una dirección fija (KITARPG_PROXY_ADDRESS, 172.28.0.10) y confía solo en esa.

Atención

Nunca actives Proxy:Enabled sin un proxy conocido delante. Los clientes podrían escribir su propio X-Forwarded-For y esquivar los límites de ritmo.

#Cuentas y tokens

  • Las contraseñas se hashean con Argon2id (19 MiB, 2 pasadas). Los nombres de usuario desconocidos tardan lo mismo que las contraseñas incorrectas.
  • Límites de ritmo. /api/auth/* permite Auth:AttemptsPerMinute (10) peticiones por cliente y minuto, contando las direcciones IPv4 de a una y las direcciones IPv6 por /64.
  • Bloqueo de cuenta. Auth:FailedLoginsPerAccount (5) contraseñas incorrectas bloquean ese nombre de usuario durante Auth:FailedLoginMinutes (15) con login_locked, exista la cuenta o no.
  • Los tokens de acceso viven Auth:TokenMinutes (30). Una cuenta baneada o borrada pierde el acceso dentro de Auth:BanCheckSeconds (5).
  • Los tokens de Remember me se guardan solo como SHA-256, se usan una vez y se cambian por el siguiente de su familia. Un token reutilizado borra toda la familia. POST /api/auth/forget-all cierra la sesión de una cuenta en todos lados.

Estos contadores viven en memoria, por proceso de Login: un reinicio los olvida, y varias copias de Login cuentan cada una por su lado.

#El enlace del mapa

  • Los servidores de mapa se conectan a Central por UDP en Central:MapLinkPort (7700) y deben presentar Central:MapKey.
  • Central:MapNetworks lista las direcciones o redes que pueden abrir el enlace. Vacío permite cualquiera. El archivo compose permite solo su propia red.
  • Central les pasa la clave a los mapas que lanza en la variable de entorno KITARPG_CENTRAL_KEY, que los demás usuarios de la máquina no pueden leer como sí pueden leer una línea de comandos.
  • Un mapa solo puede hablar por los jugadores de ese mapa: Central revisa el remitente de cada mensaje sobre un jugador.
  • El enlace no está cifrado. Los mapas en otras máquinas alcanzan a Central por una red privada o un túnel WireGuard. Publica UDP 7700 solo en la dirección de esa interfaz y agrega la red a Central:MapNetworks. Nunca lo publiques en internet.

#Shop

  • Los servidores de mapa se autentican con X-Shop-Key, la API de administración con X-Admin-Key. Ambas se comparan en tiempo constante.
  • Las API interna y de administración quedan fuera de internet: solo los webhooks pasan por Caddy, y el puerto 5300 se publica solo en loopback.
  • Cada grupo de endpoints tiene su propio límite de ritmo por dirección de cliente.
  • Los webhooks se aceptan solo con una firma válida; cada pago cuenta una vez.
  • Un servidor de mapa rechaza una dirección de Shop con http:// simple en una IP pública, porque su clave cruzaría internet legible.

Consulta Servicio Shop.

#Lo que revisa el servidor de mapa

Una lista corta de lo que te protege de los clientes modificados, todo en el código de servidor del kit:

  • Ritmo de comandos. Cada comando del cliente cuenta contra 30 por segundo con ráfagas de 60; muy por encima de eso la conexión se corta por inundar. Los comandos que llegan a Central (correo, gremio, amigos, grupo, reportes) tienen 2 por segundo con ráfagas de 10. Las solicitudes de intercambio y de duelo se limitan a una cada 2 segundos.
  • Objetivos. Un jugador solo puede apuntar a lo que ve su conexión, nunca a un enemigo invisible.
  • Texto de jugadores. El chat, el correo, las notas, los nombres de gremio y los roles se limpian para que no puedan abrir etiquetas de TextMeshPro.
  • Cantidades. Las cantidades de oro y objetos negativas, enormes o que desbordan se rechazan en el banco, el correo, el intercambio y el mercado.
  • Entregas. Un guardado hecho antes de que Central entregara un objeto (mercado, correo, banco del gremio, recaudadores) no puede borrar la entrega.
  • Los comandos de GM corren solo para cuentas con el nivel correcto, y cada comando de nivel 2 o más se escribe primero en gm_audit. Si Central no puede registrarlo, el comando no corre. Consulta Herramientas de GM.

Tu propio código sigue las mismas reglas. Consulta Reglas de seguridad para tu código.

#Builds

  • Los clientes de release son solo IL2CPP. La build se detiene si un cliente de release usa Mono.
  • Un cliente MMO nunca lleva ensamblados de servidor, el guardado local, herramientas de prueba, claves ni cadenas de conexión. La build se detiene si los llevaría.
  • Las herramientas de prueba (KITARPG_DEV) están solo en el cliente de prueba. Nunca les des el cliente de prueba a los jugadores.
  • Guarda la carpeta de símbolos de IL2CPP (*_BackUpThisFolder_ButDontShipItWithYourGame) para los reportes de fallos y fuera de lo que publicas.

#Correr los servicios

  • Exactamente un Central por base de datos. Las sesiones, los tickets, los grupos y el bloqueo de objetos viven en su memoria. Dos entregarían los mismos objetos dos veces.
  • Exactamente un Shop por base de datos. Las compras se ordenan con un bloqueo en su proceso.
  • Login puede correr varias veces detrás del proxy, pero cada copia suma su propio margen de límite de ritmo.
  • Los módulos corren con todos los permisos del servicio. Instala solo módulos en los que confíes, lístalos en Modules:Allow y mantén las carpetas de módulos en solo lectura (el archivo compose las monta así). El archivo y el SHA-256 de cada módulo se registran al arrancar.
  • Corre sin root. Las imágenes de Docker corren los servicios como el usuario app y los servidores de mapa como kit.

#Rotar claves

Rota una clave cuando se va alguien que la conocía, cuando puede haberse filtrado o según un calendario.

#Clave de firma de tokens (sin tiempo de inactividad)

Auth:SigningKeys es una lista. La primera clave firma; cada clave de la lista, más Auth:SigningKey, se acepta.

  1. Crea una clave nueva: openssl rand -hex 32.

  2. En ambos, Login y Central, pon la clave nueva primero y conserva la vieja:

    Auth__SigningKeys__0=<new key>
Auth__SigningKeys__1=<old key>

    En Docker Compose, agrega ambas líneas al bloque &service-env del servicio login, que comparte Central, y corre docker compose up -d login central.

  3. Espera al menos Auth:TokenMinutes (30 minutos), para que cada token firmado con la clave vieja haya vencido.

  4. Quita la clave vieja: pon KITARPG_SIGNING_KEY en la clave nueva y elimina las líneas SigningKeys, luego reinicia otra vez.

Los tokens de "Remember me" no se firman con esta clave, así que los jugadores siguen recordados.

#Clave del mapa (mantenimiento corto)

Central acepta una clave de mapa a la vez.

  1. Crea una clave nueva y ponla en KITARPG_MAP_KEY (o Central__MapKey y el KITARPG_CENTRAL_KEY de cada mapa).
  2. Sin jugadores dentro, reinicia Central y cada servidor de mapa juntos: docker compose up -d central map-town map-forest map-crypt map-guild-hall.

Los mapas que siguen con la clave vieja se rechazan hasta que se reinician con la nueva.

#Clave del mapa para Shop (sin tiempo de inactividad)

Shop acepta cada clave de Shop:MapKeys más KITARPG_SHOP_KEY.

  1. Agrega la clave nueva a Shop como Shop__MapKeys__0 junto a la vieja y reinicia Shop.
  2. Dales a los servidores de mapa el nuevo KITARPG_SHOP_KEY y reinícialos.
  3. Quita la clave vieja de Shop y reinícialo.

#Clave de administración de Shop

Cambia KITARPG_SHOP_ADMIN_KEY, reinicia Shop y actualiza la clave de administración en la página Shop del editor.

#Secretos de pago

Cambia el secreto del webhook en el panel de tu proveedor (Stripe) o en tu tienda web, pon el nuevo valor en .env y reinicia Shop. Los webhooks firmados con el secreto viejo se rechazan desde entonces.

#Contraseña de la base de datos

  1. En PostgreSQL: ALTER USER kitarpg PASSWORD '<new password>';
  2. Cambia POSTGRES_PASSWORD en .env (el archivo compose arma las cadenas de conexión con ella).
  3. docker compose up -d login central shop.

POSTGRES_PASSWORD solo define la contraseña cuando se crea por primera vez el volumen pgdata; después, solo ALTER USER la cambia.

#Lista de revisión antes del lanzamiento

Secretos

  • [ ] Cada valor de .env cambiado respecto de la muestra, cada uno creado con openssl rand -hex 32.
  • [ ] .env y launcher.json están fuera del control de versiones y las copias de seguridad se guardan en un lugar seguro.
  • [ ] Ningún servicio corre con ASPNETCORE_ENVIRONMENT=Development.

Red

  • [ ] Firewall abierto solo para 22/tcp, 80/tcp, 443/tcp y udp, y los puertos UDP de los mapas.
  • [ ] 5100, 5200, 5300, 5432 y 7700 no se pueden alcanzar desde internet.
  • [ ] Ambos dominios resuelven y sirven HTTPS con un certificado válido.
  • [ ] KITARPG_PUBLIC_ADDRESS es la dirección pública del servidor.
  • [ ] Los servidores de mapa en otras máquinas usan una red privada o WireGuard, listada en Central:MapNetworks.

Builds

  • [ ] El cliente se compiló con Build Mac Client o Build Windows Client (IL2CPP), con Login Url y Central Url en HTTPS.
  • [ ] KitARPG > Check Build Separation no muestra código de servidor en el cliente.
  • [ ] El cliente de prueba no está en ningún lugar donde los jugadores puedan conseguirlo.
  • [ ] Cliente y servidores de mapa compilados con el mismo código.

Servicios

  • [ ] Un Central y como máximo un Shop por base de datos.
  • [ ] Las opciones Proxy confían solo en la dirección de Caddy.
  • [ ] Modules:Allow lista tus módulos, si usas alguno.
  • [ ] El primer admin está nombrado, y los niveles de GM en Game Settings > Commands son los que quieres.

Datos

  • [ ] Copias de seguridad de la base de datos cada noche, copiadas fuera del servidor, y una restauración probada.
  • [ ] La API de administración de Shop se puede alcanzar solo desde el servidor o a través de un túnel SSH.
