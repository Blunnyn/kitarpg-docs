Servidores y despliegue

Builds

Cómo compilar cada parte de un juego KitARPG en línea: el cliente que instalan los jugadores, los servidores de mapa para tu computadora y para Linux, el juego de un jugador y los servicios .NET. También cubre las revisiones por las que pasa cada build y lo que puede llevar cada una.

#Los menús de build

Todos están bajo KitARPG > Starter. Cada uno toma sus escenas de los mapas de tu Game Database, así que un mapa nuevo entra en cada build sin pasos extra. Las builds van a una carpeta Builds/Starter junto a la carpeta de tu proyecto de Unity (el servidor Linux va a Deploy/builds/starter).

Menú Qué hace Salida Backend de scripting Defines extra
Build Mac Client El cliente MMO para macOS Builds/Starter/MacClient/KitARPG.app IL2CPP (lo pone el menú) Ninguno
Build Windows Client El cliente MMO para Windows Builds/Starter/WindowsClient/KitARPG.exe IL2CPP (lo pone el menú) Ninguno
Build Mac Server Un servidor de mapa que el lanzador corre en una Mac Builds/Starter/MacServer/KitARPGServer.app Opción del proyecto KITARPG_SERVER
Build Windows Server Un servidor de mapa que el lanzador corre en Windows Builds/Starter/WindowsServer/KitARPGServer.exe Opción del proyecto KITARPG_SERVER
Build Linux Server El servidor de mapa para Docker y hosts Linux (Dedicated Server) Deploy/builds/starter/KitARPGServer.x86_64 IL2CPP (lo pone el menú) Ninguno (Unity agrega UNITY_SERVER)
Build Mac Single Player Un juego de un jugador para macOS Builds/Starter/MacSinglePlayer/KitARPG.app Opción del proyecto KITARPG_SERVER, KITARPG_SINGLEPLAYER
Build Windows Single Player Un juego de un jugador para Windows Builds/Starter/WindowsSinglePlayer/KitARPG.exe Opción del proyecto KITARPG_SERVER, KITARPG_SINGLEPLAYER
Build Mac Test Client Un cliente con las herramientas de prueba, para tus propias revisiones Builds/Starter/MacTestClient/KitARPGTest.app Mono (se restaura después) KITARPG_DEV

Junto a cada build el menú escribe KitARPGScenes.txt con las escenas que lleva. Play & Servers lo lee para avisarte cuando a un servidor de mapa le falta la escena de un mapa.

Los servidores de Mac y Windows son builds de jugador normales con el código del servidor compilado dentro, arrancadas con -batchmode -nographics. No necesitan el módulo Dedicated Server. El servidor Linux es una build Dedicated Server de verdad: más chica, sin gráficos en absoluto.

#Lo que revisa primero cada build

  1. Escenas. Cada mapa de la Game Database nombra su escena. Si falta un archivo de escena, la build se detiene y dice cuál. La escena Title siempre va primero.
  2. Project Check. El validador corre antes de cada build y la detiene si hay errores. Puedes desactivar eso en Project Check con Stop builds on errors. Consulta Project Check.
  3. Separación de builds. El kit revisa qué ensamblados compilaría la build y la detiene cuando uno no corresponde. Esta revisión corre en cada build, desde los menús del kit, desde File > Build Profiles o desde un script, y no se puede desactivar.
  4. Modo. La build lleva KitARPGSettings con el modo para el que se compila (en línea o un jugador). El menú vuelve a poner el modo de tu editor después.
  5. Versión de red. Se escribe en la build un hash de todo lo que envía Mirror. Consulta Versión de red.

#Defines y qué va dónde

Define Qué compila Lo usa
KITARPG_SERVER (o el UNITY_SERVER de Unity) KitARPG.Server, cada KitARPG.Modes.*.Server y cada ensamblado cuyo nombre termina en .Server: el servidor de mapa, el enlace con Central, los comandos de GM, las reglas del lado del servidor Servidores de mapa y un jugador
KITARPG_SINGLEPLAYER KitARPG.Local: el guardado SQLite local Solo un jugador
KITARPG_DEV Herramientas de prueba: inicio de sesión automático, la prueba de humo, -save, -mode, -login, -centralUrl Solo el editor y el cliente de prueba
KITARPG_LOADTEST Herramientas de prueba de carga Solo builds de prueba de carga
Build Lleva Nunca lleva
Cliente MMO Juego, interfaz, red Código de servidor, comandos de GM, el guardado local, herramientas de prueba, claves, cadenas de conexión
Servidor de mapa Código de servidor El guardado local
Un jugador Código de servidor y el guardado local Herramientas de prueba

La separación de builds detiene una build cuando:

  • un cliente MMO llevaría código de servidor o el guardado local, o se compila con KITARPG_SERVER o KITARPG_SINGLEPLAYER;
  • un ensamblado que va en un cliente MMO referencia un ensamblado de servidor;
  • un servidor de mapa llevaría KitARPG.Local;
  • una build de release llevaría herramientas de prueba;
  • un ensamblado de editor o de prueba iría en cualquier build;
  • a una build de un jugador le falta el código de servidor o el guardado local;
  • un cliente MMO de release se compila con Mono;
  • un cliente MMO de release apunta a Login o Central por HTTP simple en algo que no es esta computadora.

Advierte (y sigue) para un cliente de desarrollo o un cliente compilado con Mono en desarrollo.

KitARPG > Check Build Separation muestra la tabla de tu proyecto: qué ensamblados entran en cada tipo de build.

Tu propio código solo de servidor va en un ensamblado cuyo nombre termina en .Server, con la restricción de define UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER (Create > KitARPG > Scripts > Game Server Assembly crea uno). Consulta Ensamblados.

#Compilar el cliente MMO

  1. Pon Login Url y Central Url en Assets/Settings/Resources/KitARPGSettings.asset con tus direcciones HTTPS públicas, por ejemplo https://login.mygame.com y https://central.mygame.com. Consulta Configuración.
  2. Elige el mismo modo de control con el que se compilan los servidores de mapa (Game Settings). Un cliente en otro modo se rechaza con mode_mismatch.
  3. KitARPG > Starter > Build Mac Client o Build Windows Client.
  4. Compila los servidores de mapa a partir del mismo código, para que coincidan las versiones de red.

Los clientes de release son siempre IL2CPP: su código viaja como código nativo en vez de DLLs que cualquiera puede leer y cambiar. Unity compila un reproductor IL2CPP de Windows solo en Windows, y uno de Mac solo en una Mac.

Un cliente de release ignora los argumentos -login, -centralUrl y -mode, y habla con Login y Central solo por HTTPS.

#Compilar el servidor de mapa Linux

El servidor de mapa que corre en Docker o en un host Linux.

Antes de la primera build, instala en Unity Hub para tu editor:

  • Linux Dedicated Server Build Support;
  • IL2CPP para Linux;
  • en una Mac, el paquete com.unity.toolchain.macos-arm64-linux (Package Manager), que permite a una Mac compilar para Linux.

Luego:

  1. Guarda tus escenas y aplica cualquier actualización del kit pendiente (Overview las lista), para que el servidor las tenga.
  2. KitARPG > Starter > Build Linux Server.
  3. La build queda en Deploy/builds/starter/: KitARPGServer.x86_64, KitARPGServer_Data, GameAssembly.so, UnityPlayer.so y una carpeta KitARPGServer_BackUpThisFolder_ButDontShipItWithYourGame con los símbolos de depuración de IL2CPP. Guarda los símbolos para leer reportes de fallos; la imagen de Docker los deja fuera.

La imagen pesa unos 72 MB. El servidor corre sin pantalla y lee su mapa, puerto y la dirección de Central de la línea de comandos (consulta Configuración). Una build sirve para todos los mapas; cada contenedor la corre con un -map distinto.

#Compilar para tu propia computadora

Build Mac Server o Build Windows Server hace el servidor de mapa que arrancan el lanzador y Play & Servers. Vuelve a compilarlo después de cambiar escenas, código de servidor o cualquier cosa que viaje por la red. Play & Servers te avisa cuando es más viejo que los servicios en marcha.

#Builds de un jugador

Build Mac Single Player y Build Windows Single Player hacen un juego que aloja su propio mundo y guarda en un archivo en la computadora del jugador. No necesitan servicios. Consulta Inicio rápido: un jugador.

#El cliente de prueba

Build Mac Test Client hace un cliente con las herramientas de prueba del kit: inicio de sesión automático, la prueba de humo y -smoketest systems, donde dos clientes juegan los sistemas sociales y de economía contra servidores reales. Usa Mono para compilar rápido y su propia carpeta para que no pueda confundirse con el cliente de release.

KITARPG_DEV es la única forma en que las herramientas de prueba entran en una build: una build de desarrollo común no las lleva. Nunca les des el cliente de prueba a los jugadores.

#Versión de red

Cada build lleva un hash corto de todo lo que viaja por Mirror: campos sincronizados, listas y diccionarios sincronizados, y mensajes de red, con los campos de los tipos que contienen. El cliente lo envía con su ticket, y un servidor de mapa compilado con código distinto lo rechaza con version_mismatch ("The game and the server are different versions") en vez de fallar a mitad de la lectura de un componente.

  • El valor se calcula cuando empieza la build y se guarda como recurso temporal en Assets/KitARPGBuild, que se borra después de la build.
  • El editor lo calcula a partir de su propio código.
  • Si alguno de los dos lados no tiene valor, no se comparan. Los serializadores escritos a mano no son parte del hash.

Cuando cambias un campo sincronizado o un mensaje, vuelve a compilar tanto el cliente como los servidores de mapa.

#Compilar desde la línea de comandos

Cada menú es un método estático que puedes llamar desde una máquina de builds:

Unity -batchmode -quit -projectPath MyGame \
  -executeMethod Blunnyn.KitARPG.Editor.StarterBuilder.BuildLinuxServer
Menú Método
Build Mac Client Blunnyn.KitARPG.Editor.StarterBuilder.BuildMacClient
Build Windows Client Blunnyn.KitARPG.Editor.StarterBuilder.BuildWindowsClient
Build Mac Server Blunnyn.KitARPG.Editor.StarterBuilder.BuildMacServer
Build Windows Server Blunnyn.KitARPG.Editor.StarterBuilder.BuildWindowsServer
Build Linux Server Blunnyn.KitARPG.Editor.StarterBuilder.BuildLinuxServer

En modo batch una build fallida lanza una excepción, así que Unity sale con un código de error y tu máquina de builds ve la falla.

#Compilar los servicios

Los servicios .NET se compilan con el SDK de .NET 10.

Objetivo Comando (desde la carpeta Services)
Compilar todo para el lanzador dotnet build
Correr las pruebas dotnet test
Publicar un servicio para un servidor dotnet publish Login -c Release -o out/Login
Imágenes de Docker docker compose build desde Deploy (consulta Docker)

Antes de publicar Login o compilar su imagen, ejecuta KitARPG > Export Game Data for Services. Escribe Services/Login/gamedata.json, que la build copia junto al servicio. Sin él Login no puede crear personajes.

#Errores comunes

  • "KitARPG stopped the OnlineClient build." La Console lista cada problema con su arreglo. Normalmente es código de servidor en un ensamblado de cliente, o un Login Url con HTTP simple.
  • "The game and the server are different versions." El cliente y el servidor de mapa se compilaron con código distinto. Vuelve a compilar el que sea más viejo.
  • Los jugadores que cambian de mapa vuelven al login. Al servidor de mapa le falta la escena de ese mapa. Vuelve a compilarlo; Play & Servers nombra la escena que falta.
  • La build Linux falla en una Mac. Falta el paquete de toolchain de Linux o el módulo Linux Dedicated Server.
  • El cliente de Windows no compila en una Mac. IL2CPP para Windows solo compila en Windows. Compílalo en una máquina Windows.
