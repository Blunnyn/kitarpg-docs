Servidores y despliegue

Servicio Shop

Shop es un servicio .NET opcional que lleva la tienda premium del juego: el catálogo, los saldos premium de cada cuenta, las compras y los regalos, y los pagos con dinero real. Esta página cubre cómo encaja con el resto, su archivo de catálogo, cada endpoint y opción, los pagos y cómo correrlo en local y en producción.

Para el lado del jugador (la ventana de la tienda, las monedas premium) consulta Tienda del juego. Para editar ofertas en el editor consulta Página Shop.

#Cómo encaja

  • Aparte y opcional. Central no sabe nada de Shop. Sin él el juego corre con normalidad y el botón de la tienda no aparece.
  • Solo en línea. Los juegos de un jugador no tienen tienda.
  • Los jugadores nunca llegan a él. La ventana de la tienda le pide al servidor de mapa; el servidor de mapa llama a la API interna de Shop con su clave (X-Shop-Key). Solo los webhooks de pago vienen de afuera, a través de Caddy.
  • Misma base de datos. Usa la base de datos que usan Login y Central. Login debe haber arrancado una vez para que el catálogo items esté lleno.
  • Las compras viajan por correo. Una compra escribe el cargo y una carta con los objetos comprados en una sola transacción. Los servidores de mapa pasan las cartas de la tienda a la bolsa al instante (salvo que Shop Auto Take (shopAutoTake) esté desactivado en Game Settings); si la bolsa y el banco están llenos, la carta espera en el buzón y se le avisa al jugador.
Quién Habla con Shop con Por
Servidores de mapa API interna, X-Shop-Key HTTP en la red privada, puerto 5300
Proveedores de pago Webhooks, firmados HTTPS a través de Caddy en el dominio de Login
Tú y el editor API de administración, X-Admin-Key HTTP en 127.0.0.1:5300, o un túnel SSH

#Correrlo

#En tu computadora, desde el editor

Abre la página Shop de la ventana KitARPG, activa la tienda y presiona Start the shop. El editor corre el lanzador con --headless --shop-only, con claves creadas para esta computadora y el catálogo en UserSettings/KitARPG/shop-conf.json. Los mapas en Play lo encuentran solos. Consulta Página Shop.

#Con el lanzador

Marca Premium shop en la ventana del lanzador, o pon ShopEnabled y ShopAutoStart en launcher.json. Shop arranca con Login y Central en el puerto ShopPort (5300), y los mapas que arranca Central reciben su dirección y su clave. Consulta Lanzador.

#A mano, para desarrollo

cd Services
ASPNETCORE_ENVIRONMENT=Development \
Database__ConnectionString="Data Source=/full/path/to/kitarpg.db" \
dotnet run --project Shop          # http://localhost:5300

En Development la clave del mapa es dev-shop-key y la clave de administración dev-shop-admin-key (appsettings.Development.json). Apúntalo al mismo archivo SQLite que Login y Central.

#En Docker Compose

docker compose --profile shop up --build -d

Pon primero KITARPG_SHOP_KEY y KITARPG_SHOP_ADMIN_KEY en Deploy/.env. Consulta Docker.

#Cómo lo encuentran los servidores de mapa

El servidor de mapa lee Qué es
-shop <url> o KITARPG_SHOP_URL La dirección de Shop, por ejemplo http://shop:5300
-shopKey <key> o KITARPG_SHOP_KEY Una de las claves de mapa de Shop

En el editor, un mapa en Play sin estos usa las opciones de la página Shop (UserSettings/KitARPG/launcher.json). Un servidor de mapa compilado rechaza una dirección http:// simple en una IP pública, porque la clave cruzaría internet legible: usa https:// o una dirección privada.

#El archivo de catálogo

shop-conf.json, en Shop:CatalogPath (relativo a la carpeta del servicio salvo que sea absoluto). Junto al servicio viene una muestra; si falta el archivo configurado, el primer arranque copia la muestra ahí.

{
  "mailSender": "Shop",
  "mailDays": 30,
  "products": [ { "id": "gems_500", "currency": "gems", "amount": 550 } ],
  "offers": [
    {
      "id": "potion_bundle", "name": "Potion Bundle", "description": "Twenty of each.",
      "category": "Supplies", "icon": "", "image": "", "banner": "", "badge": "Sale", "order": 0,
      "currency": "gems", "price": 60,
      "items": [ { "itemId": "health_potion", "amount": 20 }, { "itemId": "mana_potion", "amount": 20 } ],
      "startsAt": "", "endsAt": "2026-12-31T23:59:59Z", "perAccount": 0, "giftable": true, "hidden": false
    }
  ]
}

#Nivel superior

Campo Qué hace Predeterminado
mailSender Nombre del remitente en las cartas de compra Shop
mailDays Días que una carta de compra queda en el buzón 30
products Lo que da cada producto de dinero real (abajo) Vacío
offers Lo que vende la tienda por moneda premium (abajo) Vacío

#Ofertas

Campo Qué hace Predeterminado
id Id único, hasta 64 caracteres. Nunca lo cambies una vez vendida: los límites de compra y el historial lo usan Obligatorio
name, description Lo que leen los jugadores Vacío
category La entrada bajo la que aparece en el lado izquierdo de la tienda Featured
icon Objeto cuyo ícono muestra la tarjeta. Vacío usa el del primer objeto Vacío
image Clave de la imagen de la tarjeta y el detalle en el Shop Art del juego. Vacío dibuja el ícono Vacío
banner Clave de una imagen ancha. Las ofertas que tienen una se turnan arriba de la tienda Vacío
badge Cinta en la tarjeta, como New o Sale, hasta 24 caracteres Vacío
order Menor va primero al ordenar por relevancia 0
currency La moneda premium que cuesta Obligatorio
price Precio, mayor que 0 y hasta 1.000.000.000.000 Obligatorio
items itemId y amount de cada objeto que da. Al menos uno Obligatorio
startsAt, endsAt UTC, ISO 8601 (2026-12-01T00:00:00Z). Vacío es siempre Vacío
perAccount Veces que una cuenta puede comprarla. 0 es sin límite 0
giftable Se puede comprar como regalo para otro personaje true
hidden Se conserva para el historial pero ya no se vende false

#Productos

Cada id de producto de dinero real (el que envía tu proveedor de pagos) da una cantidad de una moneda.

Campo Qué hace
id Id de producto, único, hasta 64 caracteres
currency La moneda premium que da
amount Cuánto, de 1 a 1.000.000.000.000

#Revisiones y recarga

  • Cada oferta y producto se revisa: id, moneda, precio, fechas (ISO 8601, con el fin después del inicio), largos de la insignia y de la clave de imagen, al menos un objeto con cantidad, sin ids repetidos, y cada objeto presente y no retirado en la tabla items.
  • Una oferta o un producto inválido se registra y se deja fuera. Nunca detiene el servicio. Si la tabla items está vacía, la revisión de objetos se salta con una advertencia.
  • El archivo se vuelve a leer medio segundo después de cambiar, y con POST /api/shop/admin/reload. Un archivo que no se puede leer conserva el último catálogo bueno.
  • El catálogo tiene una version, un hash corto de las ofertas a la venta, para que los mapas sepan cuándo volver a pedirlo.

#Cómo funciona la compra

  1. El jugador elige una oferta en la ventana de la tienda. El servidor de mapa crea las copias de los objetos (con sus bonificaciones aleatorias) y las envía con el id de la oferta a /api/shop/internal/buy.
  2. Shop cobra el precio de su propio catálogo, nunca uno del mapa, y revisa las copias contra la oferta: los mismos objetos, las mismas cantidades, ids únicos, conocidos por el catálogo de objetos.
  3. Revisa que la oferta esté a la venta, el límite por cuenta y el saldo.
  4. En una transacción, una compra a la vez, escribe el cargo en currency_ledger y una carta con las copias, de mailSender, marcada Kind = shop, con el asunto From the shop: <offer> (o A gift from <buyer>).
  5. El mapa pasa la carta a la bolsa; Central borra una carta de la tienda una vez tomada.
  6. La compra se escribe en game_logs como shop.premium_buy o shop.premium_gift.

Los rechazos (moneda insuficiente, límite alcanzado, no está a la venta, copias incorrectas) vuelven como una respuesta normal con ok: false y un mensaje para el jugador.

  • Regalos. La oferta debe ser giftable. El destinatario se encuentra por nombre de personaje y no puede ser el comprador.
  • Entregas. Los comandos de GM (/currency gems 100 Name) y las recompensas del juego usan la entrega interna. Una referencia enviada por un mapa se guarda como map:<reference>; sin una se convierte en grant:<guid>, así las entregas nunca chocan con los pagos.

#El registro

Cada cambio a un saldo es una fila de currency_ledger: cuenta, moneda, cambio, motivo, oferta, detalle y una referencia única. El saldo es la suma de las filas. La referencia única hace que un pago, una entrega o un webhook reintentado cuente una vez.

Motivo Cuándo
shop.buy Una compra o un regalo
premium.topup Un webhook de pago
premium.refund Un webhook de reembolso
gm.grant Una entrega de GM o una entrega de administración
game.reward Una recompensa del juego, como una misión

#API interna

Para los servidores de mapa. Cabecera X-Shop-Key con una de Shop:MapKeys o KITARPG_SHOP_KEY. Los cuerpos y las respuestas son las clases compartidas de ShopMessages.cs.

Método Ruta Cuerpo → respuesta
GET /api/shop/internal/catalog ShopCatalog: la versión y cada oferta que no está oculta. El cliente filtra por fecha
POST /api/shop/internal/state ShopStateRequest (characterId) → ShopState: saldos de cada moneda del catálogo y de cualquiera que tenga la cuenta, compras por oferta, versión del catálogo. 404 para un personaje desconocido
POST /api/shop/internal/buy ShopBuyRequest (characterId, offerId, items, giftTo) → ShopResult (mailedTo es el personaje que recibió la carta, state el del comprador)
POST /api/shop/internal/grant ShopGrantRequest → ShopResult (changed es el personaje destinatario)

#API de administración

Cabecera X-Admin-Key con Shop:AdminKey. Un AdminKey vacío desactiva la API de administración. Caddy no la reenvía: llámala desde el servidor mismo (127.0.0.1:5300) o a través de un túnel SSH.

Método Ruta Qué hace
GET /api/shop/admin/catalog El archivo entero como un ShopConfig, incluidas las ofertas ocultas y las que no pasan las revisiones. 409 si no se puede leer
PUT /api/shop/admin/catalog Publica un ShopConfig entero (como máximo 2 MB, 2.000 ofertas y 500 productos). Todo o nada: con cualquier problema no se escribe nada y la respuesta es 400 con una línea por problema (Offer witch_hat: gives no items). Si no, 200 con ok, la nueva version y la cantidad de offers
GET /api/shop/admin/offers Cada oferta en uso, también las ocultas, y los productos
PUT /api/shop/admin/offers/{id} Agrega o reemplaza una oferta, revisada como el archivo. El resto del archivo queda; los comentarios que tenga se pierden
DELETE /api/shop/admin/offers/{id} Quita la oferta del archivo. Sus compras quedan en el registro
POST /api/shop/admin/reload Vuelve a leer el archivo. 409 si no se puede leer
POST /api/shop/admin/grant { username or accountId, currency, amount, reason?, reference?, detail? }. Una cantidad negativa quita. La misma reference dos veces se aplica una vez. Responde applied y el nuevo balance
GET /api/shop/admin/balance/{username} Cada moneda que tiene la cuenta
GET /api/shop/admin/history/{username}?take=50 Las últimas filas del registro, como máximo 500

Publish to server y Pull from server del editor usan las rutas del catálogo. Desde una terminal:

curl -H "X-Admin-Key: $KEY" http://127.0.0.1:5300/api/shop/admin/balance/alice
curl -X POST -H "X-Admin-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"username":"alice","currency":"gems","amount":500,"reason":"support","reference":"ticket-1234"}' \
  http://127.0.0.1:5300/api/shop/admin/grant

Las escrituras reemplazan el archivo escribiéndolo aparte y renombrándolo sobre el viejo. En Docker la carpeta Deploy/shop debe poder escribirla el usuario del contenedor (sudo chown 1654 shop).

#Pagos

Los webhooks llegan a POST /api/shop/webhooks/{provider}, que Caddy reenvía desde https://<login domain>/api/shop/webhooks/....

  • Un evento pagado suma amount × quantity de su producto (premium.topup). Un reembolso lo quita (premium.refund). Un saldo puede quedar bajo cero; el jugador entonces no puede comprar hasta que vuelva a estar por encima del precio.
  • Un evento ya aplicado responde 200 con "status": "duplicate". Una cuenta o un producto desconocido responde 422 y se registra. Una firma incorrecta responde 400.
  • Como máximo Shop:MaxQuantity (100) unidades de un producto por pago.

#Stripe

Pon en Shop:Stripe:WebhookSecret (KITARPG_STRIPE_WEBHOOK_SECRET) el secreto de firma del endpoint del panel de Stripe. Shop revisa Stripe-Signature por sí mismo (HMAC-SHA256 de {t}.{body}, de como máximo ToleranceSeconds de antigüedad), sin el SDK de Stripe.

  1. En Stripe, agrega un endpoint de webhook https://login.mygame.com/api/shop/webhooks/stripe para checkout.session.completed, checkout.session.async_payment_succeeded y charge.refunded.
  2. Crea Checkout Sessions desde tu sitio web con client_reference_id (el id de la cuenta o el nombre de usuario), o metadata.account_id / metadata.username, más metadata.product (un id de producto del catálogo) y metadata.quantity cuando no es 1.
  3. Las sesiones completadas cuentan una vez pagadas. La referencia es stripe:<payment_intent>.
  4. charge.refunded cuenta una vez que el cargo se reembolsa por completo y quita exactamente lo que dio ese pago. Atiende los reembolsos parciales con la entrega de administración.

#Tu propia tienda web

Pon Shop:Signed:Secret (KITARPG_SHOP_SIGNED_SECRET) y haz que tu tienda envíe a /api/shop/webhooks/signed:

  • Cabecera X-KitARPG-Signature: sha256=<hex HMAC-SHA256 of the raw body with the secret>.
  • Cuerpo { "id", "kind": "paid" | "refunded", "accountId" or "username", "product", "quantity", "refundOf" }. Un reembolso con refundOf (el id del pedido pagado) quita exactamente lo que dio ese pedido.

#Otro proveedor

Implementa IPaymentProvider en el proyecto Shop:

  • Name es el {provider} de la URL.
  • Read revisa la firma y devuelve un PaymentEvent, null para los eventos que se ignoran, o lanza PaymentRejectedException para los falsificados.
  • Regístralo en Shop/Program.cs: builder.Services.AddSingleton<IPaymentProvider, MyProvider>();.

Las consolas y las tiendas móviles necesitan sus propios sistemas de pago.

#Opciones

Opción Qué hace Predeterminado
Shop:CatalogPath El archivo de catálogo shop-conf.json
Shop:MapKeys Claves que envían los servidores de mapa como X-Shop-Key. KITARPG_SHOP_KEY agrega una más. Tener varias permite rotarlas Vacío (dev-shop-key en Development)
Shop:AdminKey Clave para la API de administración. Vacío la desactiva Vacío (dev-shop-admin-key en Development)
Shop:Stripe:WebhookSecret Secreto del endpoint de Stripe (whsec_...). Vacío desactiva Stripe Vacío
Shop:Stripe:ToleranceSeconds Qué antigüedad puede tener un evento de Stripe 300
Shop:Signed:Secret Secreto compartido con tu tienda web. Vacío lo desactiva Vacío
Shop:InternalPerMinute Peticiones a la API interna por dirección de cliente y minuto 1.200
Shop:WebhooksPerMinute Peticiones de webhooks por dirección de cliente y minuto 120
Shop:AdminPerMinute Peticiones a la API de administración por dirección de cliente y minuto 30

#Seguridad

  • Fuera de Development Shop se niega a arrancar sin una clave de mapa, o con una clave de mapa, una clave de administración o un secreto de proveedor vacío, corto o de ejemplo. Un secreto de proveedor vacío solo desactiva ese proveedor.
  • Las claves y las firmas se comparan en tiempo constante. Cada grupo de endpoints tiene su propio límite de ritmo por dirección de cliente.
  • Las API interna y de administración quedan fuera de internet. Los servidores de mapa en otras máquinas alcanzan a Shop por una red privada o un túnel WireGuard.
  • Corre un solo Shop por base de datos: las compras se ordenan con un bloqueo en su proceso. Shop solo agrega filas de objetos nuevas dentro de cartas nuevas; mover copias sigue siendo cosa de Central.

#Errores comunes

  • El botón de la tienda no aparece. Shop no está corriendo, el mapa no tiene -shop/-shopKey, o el módulo de tienda del juego está desactivado.
  • Falta una oferta en el juego. No pasó una revisión (el registro de Shop la nombra), está oculta o sus fechas excluyen el día de hoy.
  • Publicar desde el editor falla con 401. La clave de administración de la página Shop no coincide con Shop:AdminKey.
  • Las ediciones de administración fallan en Docker. El uid 1654 no puede escribir la carpeta shop.
  • Un pago no llegó. Busca el webhook en el registro de Shop: 400 es un secreto incorrecto, 422 una cuenta o un id de producto desconocido.
