Servidores y despliegue

Base de datos

Dónde guarda un juego KitARPG en línea las cuentas, los personajes y los objetos: SQLite o PostgreSQL, cómo se crea y actualiza el esquema, cada tabla, cómo pasar a PostgreSQL y cómo hacer copias de seguridad y restaurarlas.

#SQLite o PostgreSQL

Login, Central y Shop comparten una base de datos. Los servidores de mapa nunca se conectan a ella; cargan y guardan a través de Central.

SQLite PostgreSQL
Qué es Un archivo en disco Un servidor de base de datos
Configuración Ninguna Un servidor, una base de datos y un usuario (el editor puede crearlos)
Sirve para Desarrollar, probar, servidores privados pequeños en una máquina Producción, cualquier cosa pública, mapas en varias máquinas
Dónde UserSettings/KitARPG/data/kitarpg.db desde el editor, data/kitarpg.db junto a launcher.json desde el lanzador Donde corra tu servidor. En Docker Compose, el volumen pgdata
Columnas JSON Texto jsonb
Versiones Incluida con los servicios PostgreSQL 16 o más nuevo. El archivo compose usa postgres:17-alpine

El mismo código y las mismas migraciones corren en ambos. Cada proveedor tiene su propio contexto de base de datos (SqliteGameDbContext, PostgresGameDbContext) y su propia carpeta de migraciones.

Un juego de un jugador no usa ninguno de los dos: guarda en su propio archivo SQLite en la carpeta de datos persistentes del jugador (savegame.db por defecto, definido en KitARPGSettings como Save File (saveFile)). Ese archivo es del jugador y no se cubre aquí.

#Opciones

Todos los servicios leen la misma sección Database. Las variables de entorno usan __ entre niveles.

Opción Variable de entorno Qué hace Predeterminado
Database:Provider Database__Provider Sqlite o Postgres Sqlite
Database:ConnectionString Database__ConnectionString La conexión. SQLite: Data Source=<file>. PostgreSQL: Host=...;Port=5432;Database=...;Username=...;Password=... Data Source=kitarpg.db
Database:MigrateOnStartup Database__MigrateOnStartup Actualiza el esquema cuando arranca el servicio, luego migra las tablas de los módulos true

Una ruta de SQLite relativa es relativa a la carpeta propia del servicio. Cuando corres los servicios a mano, dales a todos la misma ruta absoluta, o cada uno crea su propio archivo.

Todas las opciones de cadena de conexión de Npgsql funcionan, por ejemplo SSL Mode=Require para servidores alojados y Maximum Pool Size=... para el pool de conexiones.

#Migraciones

  • Con MigrateOnStartup activado, cada servicio aplica al arrancar las migraciones que falten. El lanzador arranca Login primero y espera un momento, así que normalmente lo hace Login.
  • Las migraciones aplicadas se registran en __EFMigrationsHistory. Las de un módulo van en __ModuleMigrations_<module name>.
  • Una actualización del kit que cambia el esquema trae migraciones nuevas para ambos proveedores. Reiniciar los servicios las aplica.
  • Las migraciones solo van hacia adelante. Algunas mueven datos de formas que no se pueden deshacer (por ejemplo ItemOwnersAndCatalog, que pasó a filas los objetos guardados como JSON). Haz una copia de seguridad antes de actualizar el kit en un servidor en vivo.

Para crear tus propias tablas, escribe un módulo de servicio con su propio contexto y migraciones; nunca cambies las tablas del kit. Consulta Módulos de servicio. Si igual cambias las entidades del kit (para tu propio fork), genera una migración para ambos proveedores:

cd Services/Data
dotnet ef migrations add <Name> --context SqliteGameDbContext --output-dir Migrations/Sqlite
dotnet ef migrations add <Name> --context PostgresGameDbContext --output-dir Migrations/Postgres

#Tablas

Tabla Qué contiene La escribe
accounts Nombre de usuario (único, hasta 32), email, hash de contraseña Argon2id, nivel de GM (Role: 1 Player, 2 Moderator, 3 Game Master, 4 Admin), BannedUntil, oro del banco, fecha de creación Login, Central (baneos, roles, banco)
characters Nombre (único), clase, nivel, experiencia, oro, mapa y posición, vida, maná, puntos libres, y columnas JSON para monedas, atributos, habilidades, barra rápida, apariencia y Extra (misiones, progreso, tu propio PlayerData bajo game). Version rechaza guardados viejos; Deliveries cuenta lo que entregó Central Login la crea, Central guarda
item_instances Cada copia de cada objeto: uid, id de objeto, exactamente un dueño (CharacterId, AccountId, GuildId, MailId, CollectorId o ListingId), contenedor, casilla, cantidad, ligado, JSON Extra (tiradas aleatorias, mejora, gemas) Central, Shop (copias nuevas en cartas)
items El catálogo de objetos: id, nombre, categoría y el resto de lo que exportan los datos del juego, más Retired Login, en cada arranque
skills El catálogo de habilidades: id, nombre, clases, Retired Login, en cada arranque
friends Pares de personajes Central
guilds, guild_members Gremios (nombre único, aviso, nivel, mejoras, emblema, alianza) y sus miembros con roles Central
guild_events Líneas del historial del gremio, descartadas después de Central:GuildHistoryDays Central
alliances Alianzas (nombre y sigla únicos, aviso) Central
mails Cartas: destinatario, nombre del remitente, asunto, cuerpo, oro, vencimiento, Kind (shop para entregas de la tienda) Central, Shop
market_listings Lotes en el mercado: vendedor, objeto, precio por unidad, vencimiento Central
collectors Recaudadores: gremio, mapa, puesto Central
game_logs El registro del juego: tipo, hora, cuenta, personaje, mapa, objeto, oro, detalle. Se recorta después de Logs:Days Login, Central, Shop
gm_audit Cada comando de GM de nivel 2 o más, con la línea, el objetivo y el resultado Central
reports Reportes de jugadores, con el chat que los rodea Central
remember_tokens SHA-256 de cada token de "Remember me", su familia, cuenta, dirección, vencimiento y uso Login
currency_ledger Cada cambio a un saldo premium, con una referencia única Shop

La base de datos impone por sí misma las reglas importantes:

  • item_instances tiene una restricción check: exactamente un dueño y una cantidad mayor que cero. Su id de objeto es una clave foránea a items, así que una copia no puede apuntar a un objeto que el catálogo nunca tuvo.
  • Borrar un personaje, cuenta, gremio, carta, recaudador o lote del mercado borra las copias que contiene.
  • Los nombres de usuario, de personaje, de gremio y los nombres y siglas de alianza son únicos, comparados en una forma normalizada.
  • currency_ledger.Reference es única, así que un pago o una entrega cuenta una vez.

No edites items ni skills a mano: Login los sobrescribe desde gamedata.json en cada arranque.

#Pasar a PostgreSQL

#Desde el editor

  1. Abre KitARPG > Play and Servers, elige MMO y detén los servicios si están corriendo.
  2. En el paso de la base de datos elige PostgreSQL: for production y presiona Set up PostgreSQL... (compila los servicios primero; ellos hacen la comunicación).
  3. Elige una:
    • A server I run: llena Host, Port y SSL (Prefer, Require o Disable; los servidores alojados normalmente necesitan Require). Luego Create the database for me con un usuario administrador (usado una vez, nunca guardado) y Create and use, o Use a database I have y Test and use.
    • Docker on this computer: Create and use arranca PostgreSQL 17 en un contenedor llamado kitarpg-postgres, publicado en 127.0.0.1 desde el puerto 5432 (o el siguiente libre), con sus datos en el volumen kitarpg-pgdata y una contraseña aleatoria.
  4. Arranca los servicios. Las tablas se crean en el primer arranque.

La conexión se guarda para esta computadora en UserSettings/KitARPG/launcher.json. Consulta Play & Servers.

#Con el lanzador

Pon dos campos en launcher.json:

{
  "DatabaseProvider": "Postgres",
  "ConnectionString": "Host=localhost;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>"
}

Para crear la base de datos y el usuario primero, dotnet run --project Launcher -- --postgres con una petición create hace lo mismo que el editor. Consulta Lanzador.

#A mano

Como superusuario de PostgreSQL:

CREATE ROLE kitarpg LOGIN PASSWORD '<long random password>';
CREATE DATABASE kitarpg OWNER kitarpg ENCODING 'UTF8';

Luego dale a cada servicio:

Database__Provider=Postgres
Database__ConnectionString="Host=db.example.com;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>;SSL Mode=Require"

#En Docker Compose

El archivo compose ya usa PostgreSQL con la contraseña de POSTGRES_PASSWORD en Deploy/.env. Consulta Docker.

Nota

Cambiar de proveedor empieza con una base de datos vacía. El kit no copia datos de SQLite a PostgreSQL. Cambia antes de tener jugadores.

#Copias de seguridad

Haz copia de toda la base de datos: los personajes, los objetos, los gremios, el correo y el registro de la tienda solo tienen sentido juntos.

#PostgreSQL en Docker Compose

Desde la carpeta Deploy:

docker compose exec -T postgres pg_dump -U kitarpg -d kitarpg -Fc > kitarpg-$(date +%F).dump

pg_dump toma una instantánea coherente mientras el juego corre. Copia el archivo fuera del servidor. Para correrlo cada noche, pon la línea en el crontab del servidor con la ruta completa a la carpeta Deploy.

#PostgreSQL en otro lugar

pg_dump "host=db.example.com dbname=kitarpg user=kitarpg sslmode=require" -Fc > kitarpg.dump

Los servicios de PostgreSQL alojados también guardan sus propias copias; revisa cuánto tiempo las conservan.

#SQLite

Detén los servicios, luego copia kitarpg.db junto con kitarpg.db-wal y kitarpg.db-shm si existen. Copiar el archivo mientras los servicios corren puede darte una copia rota.

#Restaurar

  1. Detén Login, Central, Shop y los servidores de mapa (docker compose stop login central shop map-town map-forest map-crypt map-guild-hall).

  2. Restaura en una base de datos vacía:

    docker compose exec -T postgres dropdb -U kitarpg kitarpg
docker compose exec -T postgres createdb -U kitarpg -O kitarpg kitarpg
docker compose exec -T postgres pg_restore -U kitarpg -d kitarpg < kitarpg-2026-11-10.dump

  3. Arranca todo de nuevo. Si la copia es más vieja que los servicios, las migraciones que faltan corren al arrancar.

Atención

Restaurar lleva a cada jugador de vuelta al momento de la copia, incluida la moneda premium comprada desde entonces. Los pagos hechos después de la copia siguen en tu proveedor de pagos; vuelve a entregarlos con la API de administración de Shop antes de reabrir.

#Consultas de todos los días

Nombra al primer admin después de crear tu cuenta:

UPDATE accounts SET "Role" = 4 WHERE "Username" = 'yourname';

Los nombres de columna conservan sus mayúsculas, así que necesitan comillas dobles en PostgreSQL. Después de eso, los admins cambian niveles dentro del juego con /role. Consulta Herramientas de GM.

Otras lecturas útiles:

-- Who is banned
SELECT "Username", "BannedUntil" FROM accounts WHERE "BannedUntil" > now();
-- The latest GM commands
SELECT "At", "Character", "Line", "Result" FROM gm_audit ORDER BY "At" DESC LIMIT 50;

Para moderar, prefiere las herramientas propias del juego (/logs, /reports, el panel de GM). Nunca muevas objetos ni oro con SQL mientras el juego corre: Central y los mapas tienen su propia vista y sobrescribirían o duplicarían tu cambio.

#Retención de registros

Opción Qué hace Predeterminado
Logs:Days Días que se guardan las líneas de game_logs. Se revisa una vez por hora. 0 las guarda para siempre 180
Central:GuildHistoryDays Días que se guardan las líneas del historial del gremio 90

Ponlas en cada servicio que escribe el registro (Login, Central y Shop).

#Errores comunes

  • Dos archivos SQLite. Los servicios corridos a mano desde carpetas distintas con la cadena de conexión predeterminada crean cada uno su propio kitarpg.db. Usa una sola ruta absoluta.
  • "The database password in Database:ConnectionString is empty or a sample value." Fuera de Development los servicios rechazan contraseñas como kitarpg, postgres, password o cualquiera con change-me. Usa una larga y aleatoria.
  • El usuario no puede crear tablas. El usuario del juego debe ser dueño de la base de datos (o tener CREATE sobre ella y sobre el esquema public). Test and use del editor lo revisa.
  • Editar items a mano. Login lo sobrescribe en el próximo arranque. Cambia el objeto en la Game Database y exporta de nuevo.
