Servidores y despliegue

Servicios

Login, Central y Shop son servicios web .NET 10 que corren junto a tus servidores de mapa. Esta página cubre lo que hace cada uno, cada endpoint, los mensajes del enlace del mapa y las piezas compartidas sobre las que están construidos.

#Dónde están

Los servicios son una solución .NET, KitARPG.Services.slnx, con estos proyectos:

Proyecto Qué hace
Shared Compila los contratos y las reglas de Assets/Blunnyn/KitARPG/Runtime/Shared/, así los servicios y Unity usan el mismo código
Data EF Core: las tablas, un contexto de base de datos por proveedor (SQLite y PostgreSQL) y sus migraciones. Consulta Base de datos
Hosting Lo que comparten todos los servicios: revisión de tokens, JSON, límites de tamaño de las peticiones, cabeceras del proxy, rechazo de secretos de ejemplo, el escritor del registro del juego, revisión de baneos
Modules El contrato y el cargador para tus propios módulos de Login y Central. Consulta Módulos de servicio
Login Cuentas y personajes
Central Sesiones, tickets, el enlace del mapa y todo lo que se comparte entre mapas
Shop La tienda premium opcional. Consulta Servicio Shop
Launcher Arranca todo con un botón o un comando. Consulta Lanzador
Examples/Bounties Un módulo de Central de ejemplo con su propia tabla
Tests Pruebas para las reglas, Login, Central (con un servidor de mapa falso), Shop y los módulos, sobre SQLite

En el paquete de la Asset Store vienen como Assets/Blunnyn/KitARPG/Services.zip. El editor los descomprime en Assets/Blunnyn/KitARPG/Services~ la primera vez que se abre, y otra vez cuando una actualización del kit trae un zip nuevo. Unity no importa carpetas cuyo nombre termina en ~. KitARPG > Play and Servers los compila por ti; desde una terminal:

cd Assets/Blunnyn/KitARPG/Services~
dotnet build
dotnet test

#Lo que comparten todos los servicios

  • JSON. Las peticiones y respuestas son JSON con nombres en camelCase. Los contratos compartidos usan campos públicos para que el JsonUtility de Unity también los lea.
  • Errores. Una petición rechazada responde { "code": "...", "message": "..." }. Los códigos están en ErrorCodes en el código compartido, por ejemplo wrong_credentials, login_locked, account_banned, session_busy, map_unavailable, character_limit.
  • Tamaño del cuerpo. Las peticiones de más de 64 KB se rechazan. La publicación del catálogo de Shop tiene su propio límite de 2 MB.
  • Salud. GET /health responde ok en Login, Central y Shop. Úsalo para balanceadores de carga y monitoreo.
  • Migraciones. Con Database:MigrateOnStartup activado (lo predeterminado), cada servicio actualiza el esquema de la base de datos cuando arranca.
  • Secretos de ejemplo. Fuera del entorno Development un servicio se niega a arrancar mientras una clave o la contraseña de la base de datos esté vacía, sea corta o sea un valor de ejemplo. Consulta Seguridad.
  • Registro del juego. Cada servicio escribe sus propias líneas en game_logs por lotes, fuera del camino de la petición. Las líneas más viejas que Logs:Days (180) se borran una vez por hora; 0 las guarda.

#Login

Login es dueño de las cuentas y los personajes. Los clientes lo alcanzan por HTTPS en producción.

#Endpoints

Método Ruta Necesita Qué hace
POST /api/auth/register Nada Crea una cuenta: username, password, email (opcional). 201, o 409 username_taken
POST /api/auth/login Nada username, password, remember. Responde token, expiresAt (segundos Unix), accountId, username y, con remember, un rememberToken
POST /api/auth/resume Un token de recordar Cambia el token de recordar por un nuevo token de acceso y el siguiente token de recordar
POST /api/auth/forget Un token de recordar Borra la familia de ese token (cerrar sesión en esta computadora)
POST /api/auth/forget-all Token de acceso Borra cada token de recordar de la cuenta (cerrar sesión en todos lados)
GET /api/characters Token de acceso Los personajes de la cuenta y maxCharacters
POST /api/characters Token de acceso Crea un personaje: name, classId, appearance
DELETE /api/characters/{id} Token de acceso Borra uno de los personajes de la cuenta y todo lo que contiene
GET /health Nada ok

Cada ruta /api/auth/* cuenta contra el límite de ritmo de abajo.

#Contraseñas

Las contraseñas se hashean con Argon2id: 19 MiB de memoria, 2 pasadas, sal de 16 bytes, hash de 32 bytes. Los parámetros se guardan dentro de cada hash, así que pueden subirse después sin romper las cuentas existentes. Cuando un nombre de usuario no existe, Login igual hashea una contraseña ficticia, así un nombre de usuario incorrecto tarda lo mismo que una contraseña incorrecta.

#Tokens de acceso

  • Un JWT firmado con HMAC-SHA256 con la primera clave de Auth:SigningKeys (o Auth:SigningKey).
  • Vive Auth:TokenMinutes (30). El emisor y la audiencia son Auth:Issuer (kitarpg).
  • Lleva el id de la cuenta (sub), el nombre de usuario y el nivel de GM.
  • Central lo valida con las mismas claves. Una cuenta baneada o borrada pierde el acceso dentro de Auth:BanCheckSeconds (5), con HTTP 403 account_banned.

#Remember me

  • Con remember: true, el inicio de sesión devuelve un token aleatorio de 32 bytes. La base de datos guarda solo su SHA-256 en remember_tokens, con la cuenta, la dirección y un vencimiento de Auth:RememberDays (30).
  • POST /api/auth/resume usa el token una vez y devuelve el siguiente de la misma familia.
  • Un token gastado que vuelve significa que alguien lo copió. Login borra toda la familia, así tanto el dueño como quien lo copió deben volver a iniciar sesión con la contraseña. La línea remember token reused va al registro del juego.
  • Una cuenta conserva como máximo 10 computadoras recordadas; iniciar sesión en una más descarta la más vieja.
  • El cliente guarda el nombre de usuario, las casillas y el token, nunca la contraseña.

#Límites de ritmo

Límite Opción Predeterminado
Peticiones a /api/auth/* por cliente y minuto Auth:AttemptsPerMinute 10
Contraseñas incorrectas por nombre de usuario antes de que se bloquee Auth:FailedLoginsPerAccount 5
Duración del bloqueo, en minutos Auth:FailedLoginMinutes 15
  • Los clientes se cuentan por dirección IPv4, o por el /64 de una dirección IPv6.
  • Un nombre de usuario bloqueado responde HTTP 429 login_locked. Los nombres de usuario desconocidos se cuentan de la misma forma, así la respuesta nunca dice si una cuenta existe. Una contraseña correcta borra la cuenta.
  • Los contadores viven en memoria: un reinicio los olvida, y cada copia de Login cuenta por su lado.
  • Detrás de un proxy inverso, activa las opciones Proxy, o cada jugador parecerá la dirección del proxy. Consulta Seguridad.

#Personajes y gamedata.json

Login crea los personajes a partir de gamedata.json, un archivo exportado de tu Game Database: los modelos de jugador, las clases que puede tomar cada modelo, el mapa inicial, la posición, la vida, el maná y los objetos iniciales de cada clase, el catálogo de objetos y habilidades, y la mayor cantidad de personajes por cuenta (maxCharactersPerAccount en la Game Database, 6 por defecto).

  • Characters:GameDataFile dice dónde está (gamedata.json junto al servicio por defecto).
  • KitARPG > Play and Servers lo exporta cada vez que arranca los servicios, a UserSettings/KitARPG/gamedata.json.
  • KitARPG > Export Game Data for Services lo escribe en Services/Login/gamedata.json, así una build o una imagen de Docker de Login lo lleva. Ejecútalo antes de compilar Login para un servidor.
  • Sin el archivo, Login registra un error y nadie puede crear personajes.
  • Un personaje solo puede tomar una clase que ofrezca su modelo. Los nombres son únicos en todo el juego.

En cada arranque Login copia los objetos y las habilidades del archivo a las tablas items y skills. Un objeto quitado no se borra: se marca como retirado, ya que puede haber copias que todavía apunten a él. Si el archivo no tiene objetos, el catálogo queda como estaba.

#Central

Central es el centro del mundo en línea. Los clientes lo llaman una vez por entrada a un mapa; los servidores de mapa se quedan conectados a él todo el tiempo.

#Endpoints HTTP

Método Ruta Necesita Qué hace
POST /api/play Token de acceso characterId. Responde mapId, address, port y un ticket de un solo uso. 404 character_not_found, 403 account_banned, 503 map_unavailable o session_busy
GET /api/maps Nada Los mapas registrados y los jugadores en cada uno: [{ "mapId": "town", "players": 3 }]
GET /health Nada ok

Los módulos agregan sus propios endpoints. Consulta Hablar con Central.

#Tickets y sesiones

  • /api/play abre una sesión para la cuenta en el estado Pending con un ticket aleatorio de 24 bytes. Vence después de Central:TicketSeconds (30).
  • El servidor de mapa envía el ticket a Central; Central lo canjea una vez, solo para ese mapa, y la sesión pasa a InMap.
  • Solo el mapa que tiene la sesión puede guardar al personaje o pedir moverlo.
  • Volver a iniciar sesión mientras juegas expulsa primero la sesión vieja. Consulta Iniciar sesión dos veces.

#Arrancar servidores de mapa

Central conoce los mapas por Central:Maps. Para cada mapa:

  • Con un Executable, Central lo arranca con Arguments cuando un jugador lo necesita, o al inicio con AutoStart, y espera hasta Central:LaunchTimeoutSeconds (60) a que se registre. La clave del mapa va al proceso en la variable de entorno KITARPG_CENTRAL_KEY.
  • Sin uno, el mapa lo arranca otro (Docker, el editor en Play, un gestor de servicios). Central espera 3 segundos a que se registre.
  • Un mapa que se registra pero no está listado igual funciona mientras corre; listarlo permite que Central lo espere.
  • Detener Central mata los servidores de mapa que arrancó.

Consulta Configuración para cada campo.

#El enlace del mapa

Los servidores de mapa se conectan a Central por UDP en Central:MapLinkPort (7700) con LiteNetLib. La petición de conexión debe llevar Central:MapKey, y la dirección del remitente debe estar en Central:MapNetworks cuando esa lista no está vacía. Cada mensaje es su nombre de clase seguido de un cuerpo JSON, enviado de forma fiable y ordenada.

Mensaje del mapa Lo que hace Central
MapRegister Agrega el mapa con su id, dirección pública y puerto. Se rechaza si otro servidor ya tiene ese id de mapa
MapHeartbeat Actualiza la cantidad de jugadores (cada 5 segundos)
TicketCheck Canjea un ticket y envía el personaje
CharacterSave Guarda al personaje si este mapa lo tiene y la versión coincide; termina la sesión cuando el jugador se va
TransferRequest Guarda la nueva posición, arranca el mapa de destino si hace falta y devuelve un ticket para él
ChatRelay, FriendCommand, PartyCommand, CharacterLevel Chat entre mapas, amigos, grupos, cambios de nivel
GuildCommand, AllianceCommand, GuildExperience, GuildStorageCommand Gremios, alianzas, niveles de gremio y el banco del gremio
MailSend, MailCommand Correo
MarketCommand El mercado entre jugadores
CollectorCommand Recaudadores
BanRequest, RoleChange, GmAuditBatch, RatesChange Acciones de GM; las líneas de auditoría se confirman solo una vez guardadas
PlayerReport, ReportCommand Reportes de jugadores
GameLogBatch Líneas del registro del juego, marcadas con el id del mapa del remitente
Cualquier otro nombre de clase Se entrega a un módulo que lo registró, o se registra como desconocido

Central revisa que un mensaje sobre un jugador venga del mapa en el que está ese jugador, así un mapa solo puede hablar por sus propios jugadores.

#Los objetos se mueven por un solo registro

Cada copia de un objeto es una fila de item_instances con exactamente un dueño: un personaje, el banco de una cuenta, un gremio, una carta, un recaudador o un lote del mercado. El ItemLedger de Central cambia los dueños de a un movimiento, dentro de una transacción:

  • Un movimiento solo ocurre si la copia está donde dice el remitente. Una copia en manos de otro se rechaza y se registra.
  • Un objeto que el catálogo no conoce nunca llega a la base de datos. El mapa lo conserva y lo intenta de nuevo cuando Login tiene la nueva exportación.
  • El mercado, el correo, el almacén del gremio y los recaudadores suben el contador Deliveries del personaje en la misma transacción. El mapa registra la última entrega que aplicó, así un guardado hecho antes de una entrega no puede borrarla.

Por eso debe haber exactamente un Central por base de datos: el bloqueo vive en su proceso.

#Límites que impone Central

Las opciones propias de Central (tamaños de amigos, grupos y gremios, reglas de correo y mercado) están listadas en Configuración. Algunos límites están fijos en el código:

Límite Valor
Oro o franqueo en una carta 1.000.000.000.000.000
Precio de un lote del mercado 1.000.000.000.000
Reportes que un jugador puede enviar por día 10
Líneas de auditoría de GM por lote desde un mapa 500

#Shop

Shop es opcional y aparte: Central no sabe que existe. Los servidores de mapa llaman a su API interna con una clave; los proveedores de pago llaman a sus webhooks; tú lo administras con la API de administración. Todo sobre él está en Servicio Shop.

#Correr un servicio a mano

El lanzador es la forma fácil. Para correr un servicio solo, para depurar:

cd Services
ASPNETCORE_ENVIRONMENT=Development \
ASPNETCORE_URLS=http://127.0.0.1:5100 \
Database__ConnectionString="Data Source=$PWD/kitarpg.db" \
dotnet run --project Login
  • Development usa las claves de prueba de appsettings.Development.json. Nunca lo uses en un servidor.
  • Sin ASPNETCORE_URLS, dotnet run usa los puertos de Properties/launchSettings.json del proyecto (5022 para Login, 5091 para Central, 5300 para Shop), no los 5100 y 5200 que espera el cliente.
  • Con SQLite, dale a cada servicio el mismo archivo absoluto. El Data Source=kitarpg.db predeterminado es relativo a la carpeta de cada servicio, así que Login y Central crearían cada uno su propia base de datos.
  • Central arrancado así tiene los mapas de appsettings.json sin ejecutables: arranca tú los servidores de mapa con -central 127.0.0.1:7700 y la clave de mapa de desarrollo.

#Errores comunes

  • Nadie puede crear personajes. Login no encontró gamedata.json. Su registro dice dónde buscó. Expórtalo y reinicia Login.
  • "Map ... is not running." El mapa no está registrado: falta la build del servidor de mapa, la ruta de su ejecutable es incorrecta, se cayó (mira su registro), o su clave o dirección no están permitidas. Central registra Refused a map link y Map registration refused con el motivo.
  • Los jugadores reciben session_busy. El mapa viejo no confirmó el guardado dentro de KickWaitSeconds. Normalmente se resuelve en unos segundos. Si sigue pasando, mira el registro de ese mapa.
  • Los tokens fallan entre Login y Central. Ambos deben tener las mismas claves de firma y el mismo emisor.
