安全规则

这些规则让基于 KitARPG 构建的在线游戏免受被修改的客户端攻击，本页也说明如何在你自己的代码中遵守它们：服务器权威、请求限速、身份、校验、物品和货币、客户端能收到什么、构建中包含什么，以及服务。

#假定客户端是恶意的

在线时，玩家在自己的机器上运行你的客户端。任何人都可以修改它，或者编写一个使用你的网络协议通信的程序。这样的客户端可以：

  • 调用任何 [Command] 并发送任何网络消息，携带任意参数，频率只受连接本身限制，
  • 读取你的服务器发给它的每一个值，
  • 跳过你的客户端代码所做的每一项检查，
  • 修改自己的内存：生命条、冷却计时器、原本隐藏的按钮。

它无法改变服务器的决定。整个模型就是这样：客户端请求，服务器决定。 下面的每条规则都由此而来。

单人模式中没有其他玩家需要保护，但同一份代码也在那里运行，所以遵守这些规则没有任何代价。

#1. 服务器决定一切重要的事情

伤害、治疗、物品、金币、经验、任务进度、冷却、位置、谁能看到什么：所有这些都由服务器代码决定（在线时是地图服务器，单人模式中是主机）。客户端代码显示结果并发送请求。

属于服务器 属于客户端
Server... 方法、[Command] 方法体、NetworkServer 上的消息处理函数 窗口、菜单、相机、输入、声音、特效
技能效果的 Apply、物品效果的 Use、动作的 Run、NPC 选项的 Run 提示（Describe）、标签
公式 PlayerPrefs 中的设置

客户端所做的检查（把按钮变灰、范围圈）只是对玩家的方便。在服务器上要再检查一次。

#2. 为每个请求限速

CommandPacing（命名空间 Blunnyn.KitARPG.Net）为每个连接提供一个由所有组件和处理函数共享的额度：每秒 30 个请求，突发上限 60。远超额度的连接会以 KickReasons.Flooding 断开。会给 Central 带来工作的请求（邮件、公会、好友、举报，以及你自己任何最终调用 CentralMessages.Send 的请求）还会消耗一个更严格的额度：每秒 2 个，突发上限 10。

[Command]
void CmdDoThing(int value)
{
    if (!CommandPacing.Allow(connectionToClient)) return;
    ...
}

static void OnRequest(NetworkConnectionToClient conn, MyRequest message)
{
    if (!CommandPacing.AllowCentral(conn)) return;   // this one reaches Central
    ...
}

被拒绝的请求同样计数，所以持续发送的客户端会越陷越深，直到被踢出。单人模式中主机自己的连接永远不受限制。

#3. 身份来自连接

服务器知道是谁发送了请求：连接的玩家对象（conn.identity，或在 [Command] 中组件所属的玩家）。永远不要把"我是谁"放进请求里。

// Wrong: any client can claim any id.
public struct GiftRequest : NetworkMessage { public long fromCharacterId; public string toName; }

// Right: the sender is the connection's player.
public struct GiftRequest : NetworkMessage { public string toName; }

static void OnGift(NetworkConnectionToClient conn, GiftRequest message)
{
    if (conn.identity == null || !conn.identity.TryGetComponent(out PlayerCharacter from)) return;
    ...
}

Central 模块也是如此：消息携带角色 id，模块检查 m.Hosts(characterId)，这样一张地图只能代表它所持有的玩家发言。

#4. 校验每个参数

参数 检查
字符串 不为 null、长度限制，存储或展示给其他人之前使用 PlayerText.Clean
整数 范围，在没有意义的地方绝不为负，long.MinValue 和溢出（先与上限比较，不要先相加）
浮点数和向量 对每个分量使用 float.IsFinite，限制距离
游戏数据的 id 存在于数据库中（GameInstance.Database.TryGet）
栏位和索引 在容器范围内；栏位中确实是客户端所说的东西
世界中的事物 在服务器上解析并且在可及范围内（见下文）
数组 循环之前先限制长度

溢出是真实的风险：套件曾有一个 bug，一笔很大的金币数额加上邮费后回绕成一个很小的数字。要比较 amount > limit - fee，而不是 amount + fee > limit。

#5. 在服务器上解析世界

客户端指定的是 解析方式 然后检查
怪物或玩家（通过 netId） Fighters.TargetFor(conn, player, netId)：对于该客户端视野之外的任何东西、隐身的敌人、为别人生成的事件怪物，返回 null Fighters.Enemies、距离、Sight.Clear
NPC（通过 id） Npc.TryFind(id, out npc) npc.InReach(player.transform.position)
掉落物 Rewards.Instance.Pickup(player, id)（自己会检查可及范围）
按名称指定的玩家 PlayerCharacter.ServerFind(name)（本地图） 距离、同意、规则
地面上的一个点 限制距离、NavMesh.SamplePosition、Sight.Clear

#6. 通过套件转移物品和货币

物品在任何时候都只有一个所有者，所有者之间的每次转移都是 Central 中的一笔事务。你的代码通过套件来保持这一点：

  • 背包和装备：PlayerInventory（Give、GiveOrBank、ServerReceive、ServerReceiveGold、AddGold、AddCurrency），或 IPlayerActor（GiveItem、TakeItem、AddCurrency）。
  • 玩家之间：使用套件的交易、邮件和市场。不要用两次独立的保存自己实现转移；两次保存之间如果崩溃，就会复制或丢失物品。
  • 高级货币属于账号，只能在游戏内商店中花费，由商店服务检查余额。对高级货币调用 AddCurrency 会通过商店服务发放；扣除则会被拒绝。
  • 用 GameLog.Write("mygame.kind", player, ...) 记录客服会需要的信息。记录会写入 game_logs 表，管理员用 /logs 读取。

#7. 只发送客户端可以知道的内容

  • Sync Mode 为 Observers 的 NetworkBehaviour 会把它的同步值发送给每个能看到该玩家的客户端。私有数据（背包、任务、标记、你自己的系统）使用 Owner。
  • [ClientRpc] 发给每个观察者；[TargetRpc] 只发给所有者。
  • PlayerData 永远不会离开服务器。只同步界面需要的内容。
  • 不要发送客户端看不到的事物的位置、生命值或属性；套件的兴趣管理已经限制了每个客户端收到的内容。
  • 玩家写的文字用 PlayerText.NoTags 显示（或在服务器上用 PlayerText.Clean 清理），这样就没人能把 TextMeshPro 标签注入到其他玩家的屏幕上。

#8. 让服务器代码远离客户端构建

仅服务器代码放在带有 UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER 约束的程序集中（Game.Server）。这样在线客户端就不会携带 GM 命令、Central 消息或你的服务器规则，因此它们无法被读取或调用。

每次构建之前，BuildSeparation 会阻止携带服务器代码、单人模式存档或测试工具的客户端构建。正式发布的客户端使用 IL2CPP 构建（该检查要求如此），这让它们更难被读懂。永远不要把密钥、密码或连接字符串放进客户端构建包含的任何内容中：地图服务器从 KITARPG_CENTRAL_KEY 读取 Central 密钥，从 KITARPG_SHOP_KEY 读取商店密钥。

参见程序集和构建。

#9. 管理人员命令会被审计

GM 命令位于仅服务器程序集中，在运行前检查玩家的等级，每一次管理人员级别（等级 2 或以上）的使用都会写入 GM 审计和游戏日志。当审计无法写入时，管理人员命令会暂停。你的命令通过 GmCommands.Register 获得以上所有功能。用 GmCommands.MaxItems、MaxGold 以及其他上限限制它们能发放的数量。参见代码中的 GM 命令。

#10. 服务

  • Central 模块处理地图为其玩家发送的内容：校验每个字段，检查 m.Hosts(characterId)，并带上地图 id 记录拒绝。
  • 模块中的 HTTP 端点是公开的，除非它们调用 RequireAuthorization()。从令牌的 sub 声明中读取账号，永远不要从参数中读取。
  • 模块以服务的全部权限运行。 只有服务器运维人员会安装它们；Modules:Allow 限制哪些 dll 可以加载。参见服务模块。
  • 永远不要在模块中修改套件的表。

#审查清单

在发布一个功能之前，逐一检查客户端能发送的每个请求：

  • [ ] 它用 CommandPacing.Allow（或 AllowCentral）限速。
  • [ ] 发送者来自连接，而不是消息。
  • [ ] 每个字符串、数字、向量和数组都经过检查。
  • [ ] 每个 id 都在服务器上查找；每个世界对象都用套件的辅助方法解析，并检查可及范围和视线。
  • [ ] 物品、金币和货币通过 PlayerInventory 或 IPlayerActor 转移。
  • [ ] 回应和任何同步值都不会泄露玩家不该知道的东西。
  • [ ] 仅服务器代码位于 .Server 程序集中。
  • [ ] 客服会问到的任何事情都记录在游戏日志中。
