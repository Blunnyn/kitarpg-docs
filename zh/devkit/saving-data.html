保存数据

把你游戏自己的数据放在哪里，才能在单人模式和在线模式中随角色一起保存：角色标记、PlayerData、实现 IPlayerSave 的组件、Central 模块中的表，以及数据资源。

#选择存放位置

你要保存的内容 放在哪里 客户端能否看到 保存方式
每个角色的小整数：剧情标记、计数器、日期戳 角色标记 所有者可见，会同步 随角色保存
每个角色的结构化数值：列表、带属性的宠物、历史记录 PlayerData 永远看不到 随角色保存
同上，但由你自己的组件负责加载和写入 IPlayerSave + PlayerData 你自己同步的部分 随角色保存
需要跨角色查询的数据：排行榜、世界事件、整个服务器的计数器 Central 模块中的一张表 你发送的部分 存在你自己的表中
由内容设计者编辑的内容：配方、任务板、掉落列表 ScriptableObject 或 GameData 资源 两种构建都会加载 它是一个资源

永远不要把游戏状态放进 PlayerPrefs：它存在玩家的电脑上，从不会到达服务器，并且玩家可以修改它。PlayerPrefs 用于客户端设置（见菜单和设置选项）。

#角色标记

标记是角色身上带名字的整数，由 PlayerProgress 保存。设计者已经通过 SetFlagAction 和 FlagCondition 使用它们，你也可以。

位置 读取 写入
条件和动作 facts.Flag(key) actor.SetFlag(key, value)（服务器）
服务器代码 player.Facts.Flag(key) 或 progress.Flag(key) player.Facts.SetFlag(key, value) 或 progress.SetFlag(key, value)
所有者的客户端 PlayerProgress.Local.Flag(key) 永远不能
  • 值为 0 会删除该标记。对从未设置过的标记，Flag 返回 0。
  • 标记会同步给所有者（PlayerProgress 使用 Owner 同步），因此所有者的界面和条件可以读取它们。其他玩家永远看不到。
  • 标记变化时，服务器上会触发 PlayerProgress.ServerFlagChanged（PlayerCharacter, string key, int value）。
  • 在线时，Central 把它们保存在 characters.extra 的 flags 下；在单人模式中它们进入本地存档。

悬赏示例把狩猎进度保存在标记中（bounty.board、bounty.index、bounty.kills、bounty.day、bounty.done）。每个角色最近几次狩猎的记录是一串名字，放不进标记，所以存放在 PlayerData 中（见下文）。

标记保存的是 int。天数、计数或 id 的哈希放得下；文本和列表放不下。

#PlayerData

PlayerData（命名空间 Blunnyn.KitARPG.Net）在角色上以你自己的键保存 JSON。仅限服务器。

成员 作用
T Get<T>(PlayerCharacter player, string key) 返回该值；没有值或无法读取时返回一个新的 T。
bool Set<T>(PlayerCharacter player, string key, T value) 保存它。null 会删除该键。会超出限制时返回 false，此时什么都不改变。
bool Has(PlayerCharacter player, string key) 该键是否有值。
void Remove(PlayerCharacter player, string key) 删除它。
string GetJson(...)、bool SetJson(...) 同上，但使用原始 JSON。

值是 [Serializable] 类，用 Unity 的 JsonUtility 读写：

[Serializable]
public class PetSave
{
    public string petId;
    public int level = 1;
    public long experience;
    public List<string> tricks = new List<string>();
}

// On the server:
PetSave pet = PlayerData.Get<PetSave>(player, "mygame.pet");
pet.experience += 50;
if (!PlayerData.Set(player, "mygame.pet", pet)) Debug.LogWarning("Pet data too big.");

#限制

CharacterDataRules（命名空间 Blunnyn.KitARPG.Shared.Characters）在地图、Central 和本地存档中应用相同的限制：

限制 值
每个角色的键数（MaxKeys） 64
键的长度（MaxKeyLength） 64 个字符
键可用的字符 字母、数字、.、- 和 _
所有值合计（MaxBytes） 32 KB 的 UTF-8

给每个键加上你游戏名字的前缀（mygame.pet），这样它永远不会与其他包的键冲突。

#存放在哪里

在线时，Central 把这些值保存在 characters.extra 的 game 下，作为一个 JSON 对象（{ "mygame.pet": { ... } }），可以在数据库中直接读取，也不需要表迁移。如果一次保存的数据超出限制，或包含不是有效 JSON 的值，就会保留已存储的数据、记录一条警告，并保存角色的其余部分。在单人模式中，同样的数据进入本地存档（玩家持久数据文件夹下的 savegame.db，由 KitSettings 中的 Save File 设置）。

#JsonUtility 能做什么、不能做什么

  • 公共字段和 [SerializeField] 私有字段。不支持属性。
  • int、long、float、bool、string、枚举、数组、List<T>、嵌套的 [Serializable] 类。
  • 不支持字典。 改为保存两个平行列表，或一个键值类的列表。
  • 不支持多态，嵌套类不会是 null（它们读回来是空的）。

#实现 IPlayerSave 的组件

当你自己的某个组件拥有它的数据时，实现 IPlayerSave，让套件来调用你：

方法 何时调用
void ServerLoad(PlayerCharacter player, CharacterState state) 角色进入地图时，在套件的系统加载之后、玩家生成之前。
void WriteTo(PlayerCharacter player, CharacterState state) 每次保存之前。 
[RequireComponent(typeof(PlayerCharacter))]
public class PlayerPet : NetworkBehaviour, IPlayerSave
{
    const string Key = "mygame.pet";

    PetSave pet = new PetSave();

    [SyncVar] public string petId;
    [SyncVar] public int petLevel;

    public void ServerLoad(PlayerCharacter player, CharacterState state)
    {
        pet = PlayerData.Get<PetSave>(player, Key);
        petId = pet.petId;
        petLevel = pet.level;
    }

    public void WriteTo(PlayerCharacter player, CharacterState state) => PlayerData.Set(player, Key, pet);
}

Saved Player Data 模板会生成一个这样的组件（见模板）。

警告

在 ServerLoad 中玩家还没有生成，所以 isServer 为 false，PlayerData.Set 会拒绝写入。在那里只读取；在 WriteTo 或之后再写入。

#何时保存

在地图服务器上，角色会在以下时机保存：

  • 每隔 Save Interval Seconds（地图服务器上的 saveIntervalSeconds，60），
  • 玩家断开连接或切换地图时，
  • 服务器停止时。

每次保存都会对每个 IPlayerSave 调用 WriteTo。在线时状态发往 Central，由 Central 写入数据库；在单人模式中它进入本地存档。在两次保存之间用 PlayerData.Set 设置的值保存在内存中的角色上，并随下一次保存一起写入。两次保存之间如果崩溃，会丢失上次保存以来的变化，套件自己的数据也是如此。

在角色之间转移的物品和金币（交易、邮件、市场、公会仓库）使用 Central 中的事务，而不是定期保存；永远不要用 PlayerData 实现玩家之间的交换。

#以后修改格式

保存的 JSON 比你的代码活得更久。要为旧数据做好准备：

  • 读取旧数据时，新字段取它们的默认值；给它们合理的默认值。
  • 已删除的字段会被忽略。
  • 改动较大时，在类中放一个版本号，并在 ServerLoad 中转换。
  • 重命名键会丢失旧数据。读取一次旧键，写入新键，然后 Remove 旧键。

#Central 模块中的表

对于需要跨角色查询的数据（最佳猎人、全服计数器、你自己的拍卖历史），模块会在套件的数据库中、在套件自己的表旁边添加表，并带有自己的迁移。地图服务器通过 CentralMessages 访问它。见与 Central 通信和服务模块。单人模式没有 Central：保留一个按角色保存的后备方案，就像悬赏示例用它的 PlayerData 历史记录所做的那样。

#数据资源

内容（配方、掉落列表、任务板定义）属于资源，而不是存档：

  • 只有你的代码引用它时，使用带 [CreateAssetMenu] 的普通 ScriptableObject。悬赏示例的 BountyBoardData 就是这样。
  • 当存档或消息必须通过 id 引用它时，使用 GameData 的子类。GameData 有一个 Id（由它的名字生成，随角色保存）、一个显示名称、一段描述和一个图标，GameInstance.Database.TryGet<T>(id, out T) 可以找到它。它必须能从游戏数据库访问到：列在数据库的某个数组中，或者由某个能访问到的对象的 Visit 方法交出。Project Check 会列出数据库访问不到的 GameData 资源。

#常见错误

  • 保存在 PlayerPrefs 中。 它永远不会到达服务器。
  • 在客户端读取 PlayerData。 它从不会被发送。界面需要什么就同步什么。
  • 键没有前缀。 其他包可能会覆盖它们。
  • 在保存的类中使用字典。 JsonUtility 会悄悄丢掉它们。
  • 忽略 Set 的返回值。 超出限制时什么都不会保存。
  • 修改 GameData 的 id。 存档指向的是旧 id。
