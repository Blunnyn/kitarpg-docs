服务器与部署

架构

一款在线 KitARPG 游戏是如何组成的：客户端、Login、Central 和 Shop 服务、地图服务器和数据库，每一部分负责什么，它们之间的端口和协议，以及从登录到切换地图的整个过程。

#组成部分

一款在线（MMO）游戏由五类程序组成。单人模式游戏只有一个：客户端自己托管地图，并保存到本地文件（见单人模式）。

部分 是什么 用什么做的 负责
客户端 玩家安装的游戏 Unity、Mirror 什么都不负责。它只发出请求，由服务器决定
Login 管理账号和角色的 Web 服务 .NET 10、ASP.NET Core 账号、密码、访问令牌、"Remember me" 令牌、角色的创建和删除、数据库中的物品和技能目录
Central Web 服务，外加一条连接地图服务器的 UDP 链路 .NET 10、ASP.NET Core、LiteNetLib 会话（每个账号一个）、地图票据、正在运行的地图列表、角色存档、跨地图聊天、好友、队伍、公会、联盟、邮件、市场、收税官、举报、GM 审计、物品在所有者之间的每一次转移
地图服务器 每张地图一个无图形界面的 Unity 服务器 Unity、使用 KCP 的 Mirror 所在地图的实时世界：玩家、怪物、战斗、掉落、NPC、地下城副本。它从不接触数据库
Shop（可选） 高级商店的 Web 服务 .NET 10、ASP.NET Core 商店目录、高级货币余额、高级购买和赠礼、真实货币支付的 webhook
数据库 SQLite 文件或 PostgreSQL EF Core 所有需要持久保存的数据。Login、Central 和 Shop 共用一个数据库

三个服务和各个地图服务器都是独立的进程。在你的电脑上由启动器替你启动它们（启动器）；在服务器上由 Docker Compose 启动（Docker）。

#它们如何通信

从 到 协议 默认端口 传输什么 谁能访问
客户端 Login HTTP（生产环境为 HTTPS） 本地 5100，Caddy 之后为 443 注册、登录、"Remember me"、角色列表、创建、删除 所有人
客户端 Central HTTP（生产环境为 HTTPS） 本地 5200，Caddy 之后为 443 POST /api/play：哪张地图、它的地址和一次性票据 所有人
客户端 地图服务器 基于 KCP（UDP）的 Mirror 7777 town、7778 forest、7779 crypt、7780 guild_hall 游戏本身：先是票据，然后是输入、世界状态、聊天、窗口 所有人
地图服务器 Central LiteNetLib（UDP），密钥放在连接请求中 7700 注册、心跳、票据校验、角色存档、切换地图、聊天、社交、公会、邮件、市场、GM 审计、游戏日志 只有地图服务器。绝不对互联网开放
地图服务器 Shop 带 X-Shop-Key 请求头的 HTTP 5300 目录、余额、购买、发放 只有地图服务器。绝不对互联网开放
支付服务商 Shop 经过 Caddy 的 HTTPS 443 发往 /api/shop/webhooks/{provider} 的签名 webhook 所有人，通过签名校验
编辑器或运维人员 Shop 带 X-Admin-Key 请求头的 HTTP 5300 管理 API：发布目录、发放、余额、历史 只有服务器本机（127.0.0.1）
Login、Central、Shop 数据库 SQLite 文件或 PostgreSQL 协议 PostgreSQL 为 5432 所有持久数据 只有这些服务

游戏过程中客户端只保持一条网络连接：与其地图服务器的连接。聊天、好友、队伍和公会消息都经过地图，由地图通过地图链路转发给 Central。客户端从不与 Shop 通信：商店窗口向地图请求，再由地图向 Shop 请求。

#用文字描述的示意图

从上往下读：

  1. 最上方是客户端。它有两条 HTTPS 线向左上连到 Login 和 Central，还有一条 UDP 线向右连到它的地图服务器。
  2. 中间一排是 Login、Central 和各个地图服务器。Central 和每个地图服务器之间由一条双向 UDP 线相连，即端口 7700 上的地图链路。地图服务器还有一条 HTTP 线连到 Shop，Shop 位于 Central 旁边。
  3. 最下方是一个数据库。Login、Central 和 Shop 各有一条线向下连到它。地图服务器没有。
  4. 在生产环境中，一个 Caddy 方框位于 Login、Central 和 Shop 的 webhook 路由前面，把来自互联网的 HTTPS 转换为私有网络上的普通 HTTP。

#每一部分负责什么

每类数据只有一个所有者，因此两个程序永远不会争夺同一份数据。

数据 所有者 说明
账号和密码 Login Argon2id 哈希。每个服务在每次请求时都会读取封禁状态
访问令牌（JWT） Login 签发，Central 校验 两者使用相同的签名密钥。默认 30 分钟
角色（创建、删除） Login 初始值来自 gamedata.json，从你的 Game Database 导出
角色（创建之后的一切） Central 由持有该角色的地图通过 Central 保存。版本号会拒绝旧的存档
会话和票据 Central，在内存中 每个账号一个会话。Central 重启后，每张地图会报告其上的玩家，这些会话随之恢复
队伍 Central，在内存中 Central 重启后由玩家重新组建
更换所有者的物品副本 Central（ItemLedger） 背包、银行、公会仓库、信件、收税官和市场拍品都是同一张表中的行，每行恰好有一个所有者
物品和技能目录 Login 每次启动时从 gamedata.json 复制。手动修改会被覆盖
实时世界状态 地图服务器 怪物、位置、战斗、增益、地下城副本。只有保存的角色会持久保存
高级货币和商店购买 Shop currency_ledger 中的一条条记录；余额是它们的总和
游戏日志、GM 审计、举报 Central（Login 和 Shop 负责各自的记录） 表 game_logs、gm_audit、reports

各表的详细信息见数据库。

#从登录到开始游戏

  1. 登录。 客户端通过 HTTPS 把用户名和密码发给 Login（POST /api/auth/login）。Login 校验 Argon2id 哈希，返回一个有效期为 Auth:TokenMinutes（30）的访问令牌，勾选 "Remember me" 时还会返回一个一次性的记住令牌。
  2. 选择角色。 客户端列出角色（GET /api/characters），也可以创建角色（POST /api/characters）。Login 用 gamedata.json 中的职业、初始地图、位置、生命、法力和初始物品创建角色。
  3. 请求进入游戏。 客户端把访问令牌和角色 id 发给 Central（POST /api/play）。Central 会：
    • 检查该角色属于这个账号，并且账号没有被封禁；
    • 如果账号已经在某张地图中，通知那张地图保存并移除该角色，并最多等待 Central:KickWaitSeconds（5）秒等存档到达（见重复登录）；
    • 确保角色所在的地图正在运行：正在运行的地图直接使用，有可执行文件的地图会被启动并最多等待 Central:LaunchTimeoutSeconds（60）秒，没有可执行文件的地图（Docker、编辑器）有 3 秒时间完成注册；
    • 打开一个会话，返回地图的地址、端口和一个随机票据，票据在 Central:TicketSeconds（30）秒后过期。
  4. 加入地图。 客户端用 Mirror 连接地图服务器，并出示票据、网络版本和控制模式。地图服务器通过地图链路把票据发给 Central。Central 只兑现一次票据，从数据库加载角色并发回。地图会拒绝由不同网络代码构建的客户端（version_mismatch）或使用其他控制模式的客户端（mode_mismatch）。
  5. 游戏。 客户端发送请求；地图服务器校验并执行。地图每 60 秒（MapServer.saveIntervalSeconds）、在角色离开时以及切换地图时保存每个角色。每个角色同一时间只有一个存档在途，Central 会拒绝来自不持有该角色的地图的存档，或版本过旧的存档。
  6. 切换地图。 玩家进入传送门时，地图保存角色及其目的地，并向 Central 发送转移请求。Central 检查会话，必要时启动目标地图，保存新位置，并返回目标地图的票据。客户端显示加载画面，并用该票据加入新地图。
  7. 离开。 地图在设置 leaving 的情况下保存角色，Central 关闭会话。如果地图服务器停止或与 Central 断开，其上的所有会话都会结束，玩家回到标题画面。

#重复登录

每个账号只有一个会话。当一个账号请求进入游戏而它的角色仍在某张地图中时：

  • Central 向那张地图发送一个原因为 logged_in_elsewhere 的踢出指令。地图保存角色并将其移除。
  • Central 最多等待 Central:KickWaitSeconds（5）秒等存档到达。
  • 如果存档到达，Central 重新读取角色并发放新票据。
  • 如果没有到达，/api/play 返回 HTTP 503 和 session_busy，不发放票据。客户端稍后重试。如果在存档落地之前就发放票据，加载的会是存档之前的角色，旧会话转移过的任何东西（金币、物品）都会重复存在。
  • 如果旧地图已经不在，会话会立即被移除。

#扩展模型

  • 每张地图一个进程。 每个地图 id 恰好在一个地图服务器中运行。当第一个注册者仍连接时，Central 拒绝同一地图 id 的第二次注册。玩家更多意味着更多地图（或为繁忙的地图配更强的硬件），而不是同一地图的多个副本。
  • 地下城在其地图服务器内运行。 实例化地图（MapData.instanced）为每个队伍或每个单独的玩家提供场景的独立副本，在同一进程中再次加载，并与其他副本相隔 instanceSpacing（1000）米。空副本在 emptyMinutes（5）分钟后卸载。见地下城。
  • 地图服务器可以运行在其他机器上。 它们可以从 Central 允许的任何位置（Central:MapNetworks）通过地图链路向 Central 注册。该链路没有加密，因此其他机器要通过私有网络或 WireGuard 隧道访问。见 Docker。
  • 每个数据库恰好一个 Central。 会话、票据、队伍和物品锁都在它的内存中。同一数据库上的两个 Central 可能把同一件物品发放两次。
  • 每个数据库恰好一个 Shop。 购买由其进程内的锁串行处理。
  • Login 可以在代理之后运行多个实例，但每个实例有各自的速率限制和登录失败计数。

目标和调优见性能。

#当某部分停止时

停止的部分 玩家看到什么 会发生什么
一个地图服务器 其上的所有人都断开连接 Central 结束他们的会话。最后一次存档有效（默认最多 60 秒前，如果他们交易过、切换过地图或做过 Central 处理的事情则更新）。如果该地图有可执行文件，Central 会在下一个需要它的玩家到来时再次启动它
Central 玩家留在自己的地图上，但没有新玩家能获得票据，切换地图、存档、跨地图聊天、邮件、公会和市场都会失败 地图每 3 秒重试一次链路（CentralLink.retrySeconds）。当 Central 无法记录时，2 级及以上的 GM 命令不会执行。游戏日志记录在地图中等待（最多 5,000 条）。链路恢复后，每张地图会报告正在其上游戏的玩家，Central 会恢复这些会话，存档随之恢复正常。队伍只保存在 Central 的内存中，重启后会结束
Login 没有人能登录或创建角色 已经在地图中的玩家继续游戏
Shop 商店窗口提示无法连接服务 其他一切照常运行
数据库 服务返回错误 地图服务器继续运行世界，但在数据库恢复之前存档会失败

#单人模式

单人模式游戏使用同样的地图代码，但不使用任何服务：

  • 客户端为地图启动一个不接受外部连接的 Mirror 主机（MapServer.Host）。
  • KitARPG.Local 程序集用一个本地后端取代 Login 和 Central，保存到玩家持久数据文件夹中的 SQLite 文件（KitSettings.saveFile，默认为 savegame.db）。
  • 每次切换地图都会用新地图重启主机，使用与 MMO 相同的票据和转移流程。
  • 没有商店、没有玩家之间的邮件、没有跨玩家的公会，也没有市场。

模式在 KitARPG > Play and Servers 中选择，并保存在 Assets/Settings/Resources/KitARPGSettings.asset 中。见 Play & Servers。
