服务器与部署

Shop 服务

Shop 是一个可选的 .NET 服务，负责运行游戏内的高级商店：目录、每个账号的高级货币余额、购买和赠礼，以及真实货币支付。本页介绍它如何与其他部分配合、它的目录文件、每个端点和设置、支付，以及如何在本地和生产环境中运行它。

玩家一侧（商店窗口、高级货币）见商城。在编辑器中编辑商品见 Shop 页面。

#它如何配合

  • 独立且可选。 Central 对 Shop 一无所知。没有它游戏照常运行，只是不显示商店按钮。
  • 仅限在线模式。 单人模式游戏没有商店。
  • 玩家从不直接访问它。 商店窗口向地图服务器请求；地图服务器用它的密钥（X-Shop-Key）调用 Shop 的内部 API。只有支付 webhook 从外部经 Caddy 进入。
  • 同一个数据库。 它使用 Login 和 Central 使用的数据库。Login 必须至少启动过一次，使 items 目录被填充。
  • 购买的物品通过邮件送达。 一次购买在同一个事务中写入扣款和一封装有所购物品的信件。地图服务器会立即把商店信件收进背包（除非在 Game Settings 中关闭了 Shop Auto Take（shopAutoTake））；如果背包和银行都满了，信件会留在邮箱中并通知玩家。
谁 用什么与 Shop 通信 通过什么
地图服务器 内部 API，X-Shop-Key 私有网络上的 HTTP，端口 5300
支付服务商 Webhook，带签名 经 Caddy 的 HTTPS，位于 Login 域名上
你和编辑器 管理 API，X-Admin-Key 127.0.0.1:5300 上的 HTTP，或 SSH 隧道

#运行它

#在你的电脑上，从编辑器

打开 KitARPG 窗口的 Shop 页面，开启商店并按 Start the shop。编辑器以 --headless --shop-only 运行启动器，使用为这台电脑生成的密钥，目录位于 UserSettings/KitARPG/shop-conf.json。处于 Play 中的地图会自行找到它。见 Shop 页面。

#使用启动器

在启动器窗口中勾选 Premium shop，或在 launcher.json 中设置 ShopEnabled 和 ShopAutoStart。Shop 随 Login 和 Central 一起在端口 ShopPort（5300）上启动，Central 启动的地图会获得它的地址和密钥。见启动器。

#手动运行，用于开发

cd Services
ASPNETCORE_ENVIRONMENT=Development \
Database__ConnectionString="Data Source=/full/path/to/kitarpg.db" \
dotnet run --project Shop          # http://localhost:5300

在 Development 中，地图密钥为 dev-shop-key，管理密钥为 dev-shop-admin-key（appsettings.Development.json）。让它指向与 Login 和 Central 相同的 SQLite 文件。

#在 Docker Compose 中

docker compose --profile shop up --build -d

先在 Deploy/.env 中设置 KITARPG_SHOP_KEY 和 KITARPG_SHOP_ADMIN_KEY。见 Docker。

#地图服务器如何找到它

地图服务器读取 是什么
-shop <url> 或 KITARPG_SHOP_URL Shop 的地址，例如 http://shop:5300
-shopKey <key> 或 KITARPG_SHOP_KEY Shop 的地图密钥之一

在编辑器中，处于 Play 中且没有这些参数的地图使用 Shop 页面的设置（UserSettings/KitARPG/launcher.json）。构建好的地图服务器会拒绝公网 IP 上的普通 http:// 地址，因为密钥会以可读的形式穿过互联网：请使用 https:// 或私有地址。

#目录文件

shop-conf.json，位于 Shop:CatalogPath（除非是绝对路径，否则相对于服务所在的文件夹）。服务旁边附带一个示例；如果配置的文件不存在，首次启动时会把示例复制过去。

{
  "mailSender": "Shop",
  "mailDays": 30,
  "products": [ { "id": "gems_500", "currency": "gems", "amount": 550 } ],
  "offers": [
    {
      "id": "potion_bundle", "name": "Potion Bundle", "description": "Twenty of each.",
      "category": "Supplies", "icon": "", "image": "", "banner": "", "badge": "Sale", "order": 0,
      "currency": "gems", "price": 60,
      "items": [ { "itemId": "health_potion", "amount": 20 }, { "itemId": "mana_potion", "amount": 20 } ],
      "startsAt": "", "endsAt": "2026-12-31T23:59:59Z", "perAccount": 0, "giftable": true, "hidden": false
    }
  ]
}

#顶层

字段 作用 默认值
mailSender 购买信件上的发件人名称 Shop
mailDays 购买信件在邮箱中保留的天数 30
products 每个真实货币产品提供什么（见下文） 空
offers 商店以高级货币出售什么（见下文） 空

#商品

字段 作用 默认值
id 唯一 id，最多 64 个字符。一旦售出就不要再修改：购买限制和历史记录都使用它 必填
name、description 玩家看到的内容 空
category 它显示在商店左侧哪个条目下 Featured
icon 卡片显示其图标的物品。为空则使用第一个物品的图标 空
image 游戏 Shop Art 中卡片和详情图片的键。为空则绘制图标 空
banner 一张宽图的键。设置了横幅的商品会轮流显示在商店顶部 空
badge 卡片上的角标，例如 New 或 Sale，最多 24 个字符 空
order 按相关性排序时，值越小越靠前 0
currency 它花费的高级货币 必填
price 价格，大于 0 且最多 1,000,000,000,000 必填
items 它提供的每个物品的 itemId 和 amount。至少一个 必填
startsAt、endsAt UTC，ISO 8601（2026-12-01T00:00:00Z）。为空表示始终 空
perAccount 一个账号可以购买的次数。0 表示不限 0
giftable 可以作为礼物为其他角色购买 true
hidden 为历史记录保留，但不再出售 false

#产品

每个真实货币产品 id（即你的支付服务商发送的 id）提供一定数量的一种货币。

字段 作用
id 产品 id，唯一，最多 64 个字符
currency 它提供的高级货币
amount 数量，从 1 到 1,000,000,000,000

#检查和重新加载

  • 每个商品和产品都会被检查：id、货币、价格、日期（ISO 8601，结束时间晚于开始时间）、角标和图片键的长度、至少一个带数量的物品、没有重复的 id，以及每个物品都存在于 items 表中且未退役。
  • 有问题的商品或产品会被记录并排除。它从不会让服务停止。如果 items 表为空，会跳过物品检查并给出警告。
  • 文件修改半秒后会被重新读取，调用 POST /api/shop/admin/reload 时也会。无法解析的文件会保留上一个正确的目录。
  • 目录有一个 version，即在售商品的简短哈希，这样地图就知道何时需要重新获取。

#购买如何进行

  1. 玩家在商店窗口中选择一个商品。地图服务器生成物品副本（带有其随机加成），并把它们和商品 id 一起发送到 /api/shop/internal/buy。
  2. Shop 按它自己目录中的价格扣款，从不使用地图给出的价格，并对照商品检查这些副本：相同的物品、相同的数量、唯一的 id、物品目录中已知。
  3. 它检查商品是否在售、每账号限制和余额。
  4. 在一个事务中、一次处理一笔购买，它把扣款写入 currency_ledger，并写入一封装有副本的信件，发件人为 mailSender，标记为 Kind = shop，主题为 From the shop: <offer>（或 A gift from <buyer>）。
  5. 地图把信件收进背包；商店信件被收取后，Central 会删除它。
  6. 这次购买以 shop.premium_buy 或 shop.premium_gift 写入 game_logs。

拒绝（货币不足、达到限制、不在售、副本不正确）会以普通回答返回，带有 ok: false 和一条给玩家的消息。

  • 赠礼。 商品必须是 giftable。收礼人按角色名查找，不能是购买者本人。
  • 发放。 GM 命令（/currency gems 100 Name）和游戏奖励使用内部发放接口。地图发送的引用保存为 map:<reference>；没有引用时变为 grant:<guid>，因此发放永远不会与付款冲突。

#账本

余额的每一次变动都是 currency_ledger 中的一行：账号、货币、变动量、原因、商品、详情和一个唯一的引用。余额是这些行的总和。唯一引用使重试的付款、发放或 webhook 只计算一次。

原因 何时
shop.buy 购买或赠礼
premium.topup 已付款的 webhook
premium.refund 退款的 webhook
gm.grant GM 发放或管理员发放
game.reward 游戏奖励，例如任务

#内部 API

供地图服务器使用。请求头 X-Shop-Key 为 Shop:MapKeys 或 KITARPG_SHOP_KEY 中的一个。请求体和回答是 ShopMessages.cs 中的共享类。

方法 路由 请求体 → 回答
GET /api/shop/internal/catalog ShopCatalog：版本以及所有未隐藏的商品。由客户端按日期筛选
POST /api/shop/internal/state ShopStateRequest（characterId）→ ShopState：目录中每种货币以及账号持有的任何货币的余额、每个商品的购买次数、目录版本。未知角色返回 404
POST /api/shop/internal/buy ShopBuyRequest（characterId、offerId、items、giftTo）→ ShopResult（mailedTo 是收到信件的角色，state 是购买者的状态）
POST /api/shop/internal/grant ShopGrantRequest → ShopResult（changed 是目标角色）

#管理 API

请求头 X-Admin-Key 为 Shop:AdminKey。AdminKey 为空则关闭管理 API。Caddy 不转发它：请从服务器本机（127.0.0.1:5300）或通过 SSH 隧道调用。

方法 路由 作用
GET /api/shop/admin/catalog 以 ShopConfig 形式返回整个文件，包括隐藏的商品和未通过检查的商品。无法解析时返回 409
PUT /api/shop/admin/catalog 发布一个完整的 ShopConfig（最多 2 MB、2,000 个商品和 500 个产品）。要么全部成功要么全部失败：有任何问题时不写入任何内容，回答为 400，每个问题一行（Offer witch_hat: gives no items）。否则返回 200，带有 ok、新的 version 和 offers 的数量
GET /api/shop/admin/offers 所有正在使用的商品（包括隐藏的）以及产品
PUT /api/shop/admin/offers/{id} 添加或替换一个商品，检查方式与文件相同。文件的其余部分保持不变；其中的注释会丢失
DELETE /api/shop/admin/offers/{id} 从文件中移除该商品。它的购买记录保留在账本中
POST /api/shop/admin/reload 重新读取文件。无法解析时返回 409
POST /api/shop/admin/grant { username or accountId, currency, amount, reason?, reference?, detail? }。负数表示扣除。同一个 reference 发送两次只应用一次。返回 applied 和新的 balance
GET /api/shop/admin/balance/{username} 该账号拥有的每种货币
GET /api/shop/admin/history/{username}?take=50 最新的账本记录，最多 500 条

编辑器的 Publish to server 和 Pull from server 使用目录路由。在终端中：

curl -H "X-Admin-Key: $KEY" http://127.0.0.1:5300/api/shop/admin/balance/alice
curl -X POST -H "X-Admin-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"username":"alice","currency":"gems","amount":500,"reason":"support","reference":"ticket-1234"}' \
  http://127.0.0.1:5300/api/shop/admin/grant

写入操作先把文件写到旁边，再通过重命名覆盖旧文件来替换它。在 Docker 中，Deploy/shop 文件夹必须可以被容器用户写入（sudo chown 1654 shop）。

#支付

Webhook 到达 POST /api/shop/webhooks/{provider}，由 Caddy 从 https://<login domain>/api/shop/webhooks/... 转发而来。

  • 已付款事件会增加其产品的 amount × quantity（premium.topup）。退款会把它收回（premium.refund）。余额可以低于零；此时玩家在余额重新高于价格之前无法购买。
  • 已经应用过的事件返回 200 和 "status": "duplicate"。未知的账号或产品返回 422 并被记录。签名错误返回 400。
  • 每笔付款中一个产品最多 Shop:MaxQuantity（100）个单位。

#Stripe

把 Shop:Stripe:WebhookSecret（KITARPG_STRIPE_WEBHOOK_SECRET）设为 Stripe 控制台中该端点的签名密钥。Shop 自己检查 Stripe-Signature（对 {t}.{body} 的 HMAC-SHA256，时间不超过 ToleranceSeconds），不使用 Stripe SDK。

  1. 在 Stripe 中添加一个 webhook 端点 https://login.mygame.com/api/shop/webhooks/stripe，订阅 checkout.session.completed、checkout.session.async_payment_succeeded 和 charge.refunded。
  2. 在你的网站上创建 Checkout Session，带上 client_reference_id（账号 id 或用户名），或 metadata.account_id / metadata.username，以及 metadata.product（目录中的一个产品 id），数量不为 1 时还要带上 metadata.quantity。
  3. 完成的会话在付款后计入一次。引用为 stripe:<payment_intent>。
  4. charge.refunded 在这笔费用全额退款后计入一次，并准确收回该笔付款给予的内容。部分退款请用管理员发放来处理。

#你自己的网上商店

设置 Shop:Signed:Secret（KITARPG_SHOP_SIGNED_SECRET），并让你的商店向 /api/shop/webhooks/signed 发送请求：

  • 请求头 X-KitARPG-Signature: sha256=<hex HMAC-SHA256 of the raw body with the secret>。
  • 请求体 { "id", "kind": "paid" | "refunded", "accountId" or "username", "product", "quantity", "refundOf" }。带有 refundOf（已付款订单的 id）的退款会准确收回该订单给予的内容。

#其他服务商

在 Shop 项目中实现 IPaymentProvider：

  • Name 是 URL 中的 {provider}。
  • Read 检查签名并返回一个 PaymentEvent，对于要忽略的事件返回 null，对于伪造的事件抛出 PaymentRejectedException。
  • 在 Shop/Program.cs 中注册它：builder.Services.AddSingleton<IPaymentProvider, MyProvider>();。

主机和移动应用商店需要它们自己的支付系统。

#设置

设置 作用 默认值
Shop:CatalogPath 目录文件 shop-conf.json
Shop:MapKeys 地图服务器以 X-Shop-Key 发送的密钥。KITARPG_SHOP_KEY 会再增加一个。多个密钥便于轮换 空（Development 中为 dev-shop-key）
Shop:AdminKey 管理 API 的密钥。为空则关闭 空（Development 中为 dev-shop-admin-key）
Shop:Stripe:WebhookSecret Stripe 端点密钥（whsec_...）。为空则关闭 Stripe 空
Shop:Stripe:ToleranceSeconds Stripe 事件允许的最长时间 300
Shop:Signed:Secret 与你的网上商店共享的密钥。为空则关闭 空
Shop:InternalPerMinute 每个客户端地址每分钟的内部 API 请求数 1200
Shop:WebhooksPerMinute 每个客户端地址每分钟的 webhook 请求数 120
Shop:AdminPerMinute 每个客户端地址每分钟的管理 API 请求数 30
Shop:MaxQuantity 一笔付款中一个产品的最多单位数 100
Shop:MaxItemsPerBuy 一次购买最多可以携带的物品副本数 100

它也像其他服务一样读取 Database、Proxy 和 Logs。见配置。

#安全

  • 在 Development 之外，没有地图密钥时，或者地图密钥、管理密钥或服务商密钥为空、过短或为示例值时，Shop 拒绝启动。服务商密钥为空只会关闭该服务商。
  • 密钥和签名以常量时间比较。每组端点都有各自的按客户端地址的速率限制。
  • 内部 API 和管理 API 不对互联网开放。其他机器上的地图服务器通过私有网络或 WireGuard 隧道访问 Shop。
  • 每个数据库只运行一个 Shop：购买由其进程内的锁串行处理。Shop 只在新信件中添加新的物品行；移动副本仍由 Central 负责。

#常见错误

  • 商店按钮不显示。 Shop 没有运行、地图没有 -shop/-shopKey，或者 In-game shop 模块已关闭。
  • 游戏中缺少某个商品。 它没有通过检查（Shop 的日志会指出它）、它被隐藏，或者它的日期不包括今天。
  • 从编辑器发布时失败并返回 401。 Shop 页面上的管理密钥与 Shop:AdminKey 不一致。
  • 在 Docker 中管理编辑失败。 shop 文件夹无法被 uid 1654 写入。
  • 一笔付款没有到账。 在 Shop 的日志中查找该 webhook：400 表示密钥错误，422 表示未知的账号或产品 id。
