Database

此页面尚未翻译，以英文显示。

Where an online KitARPG game keeps accounts, characters and items: SQLite or PostgreSQL, how the schema is created and updated, every table, how to switch to PostgreSQL, and how to back up and restore.

#SQLite or PostgreSQL

Login, Central and the Shop share one database. Map servers never connect to it; they load and save through Central.

SQLite PostgreSQL
What it is One file on disk A database server
Setup None A server, a database and a user (the editor can make them)
Good for Developing, testing, small private servers on one machine Production, anything public, maps on several machines
Where UserSettings/KitARPG/data/kitarpg.db from the editor, data/kitarpg.db next to launcher.json from the launcher Wherever your server runs. In Docker Compose, the pgdata volume
JSON columns Text jsonb
Versions Bundled with the services PostgreSQL 16 or newer. The compose file uses postgres:17-alpine

The same code and the same migrations run on both. Each provider has its own database context (SqliteGameDbContext, PostgresGameDbContext) and its own migration folder.

A single player game uses neither: it saves to its own SQLite file in the player's persistent data folder (savegame.db by default, set in KitARPGSettings as Save File (saveFile)). That file belongs to the player and isn't covered here.

#Settings

Every service reads the same Database section. Environment variables use __ between levels.

Setting Environment variable What it does Default
Database:Provider Database__Provider Sqlite or Postgres Sqlite
Database:ConnectionString Database__ConnectionString The connection. SQLite: Data Source=<file>. PostgreSQL: Host=...;Port=5432;Database=...;Username=...;Password=... Data Source=kitarpg.db
Database:MigrateOnStartup Database__MigrateOnStartup Bring the schema up to date when the service starts, then migrate the modules' tables true

A relative SQLite path is relative to the service's own folder. When you run services by hand, give them all the same absolute path, or each makes its own file.

Npgsql connection string options all work, for example SSL Mode=Require for hosted servers and Maximum Pool Size=... for the connection pool.

#Migrations

  • With MigrateOnStartup on, each service applies any missing migrations at start. The launcher starts Login first and waits a moment, so Login usually does it.
  • The applied migrations are recorded in __EFMigrationsHistory. A module's go in __ModuleMigrations_<module name>.
  • A kit update that changes the schema ships new migrations for both providers. Restarting the services applies them.
  • Migrations go forward only. Some move data in ways that can't be undone (for example ItemOwnersAndCatalog, which moved items stored as JSON into rows). Back up before updating the kit on a live server.

To make your own tables, write a service module with its own context and migrations; never change the kit's tables. See Service modules. If you change the kit's entities anyway (for your own fork), generate a migration for both providers:

cd Services/Data
dotnet ef migrations add <Name> --context SqliteGameDbContext --output-dir Migrations/Sqlite
dotnet ef migrations add <Name> --context PostgresGameDbContext --output-dir Migrations/Postgres

#Tables

Table What it holds Written by
accounts Username (unique, up to 32), email, Argon2id password hash, GM level (Role: 1 Player, 2 Moderator, 3 Game Master, 4 Admin), BannedUntil, bank gold, creation date Login, Central (bans, roles, bank)
characters Name (unique), class, level, experience, gold, map and position, health, mana, free points, and JSON columns for currencies, attributes, skills, hotbar, appearance and Extra (quests, progress, your own PlayerData under game). Version refuses old saves; Deliveries counts what Central handed over Login creates, Central saves
item_instances Every copy of every item: uid, item id, exactly one owner (CharacterId, AccountId, GuildId, MailId, CollectorId or ListingId), container, slot, amount, bound, Extra JSON (random rolls, upgrade, gems) Central, the Shop (new copies in letters)
items The item catalog: id, name, category and the rest of what the game data exports, plus Retired Login, at every start
skills The skill catalog: id, name, classes, Retired Login, at every start
friends Pairs of characters Central
guilds, guild_members Guilds (unique name, notice, level, upgrades, emblem, alliance) and their members with roles Central
guild_events Guild history lines, dropped after Central:GuildHistoryDays Central
alliances Alliances (unique name and tag, notice) Central
mails Letters: recipient, sender name, subject, body, gold, expiry, Kind (shop for shop deliveries) Central, the Shop
market_listings Lots on the market: seller, item, unit price, expiry Central
collectors Tax collectors: guild, map, spot Central
game_logs The game log: kind, time, account, character, map, item, gold, detail. Trimmed after Logs:Days Login, Central, the Shop
gm_audit Every GM command of level 2 or more, with the line, target and result Central
reports Player reports, with the chat around them Central
remember_tokens SHA-256 of each "Remember me" token, its family, account, address, expiry and use Login
currency_ledger Every change to a premium balance, with a unique reference The Shop

The database enforces the important rules itself:

  • item_instances has a check constraint: exactly one owner and an amount above zero. Its item id is a foreign key to items, so a copy can't point to an item the catalog never had.
  • Deleting a character, account, guild, letter, collector or market lot deletes the copies it holds.
  • Usernames, character names, guild names and alliance names and tags are unique, compared in a normalized form.
  • currency_ledger.Reference is unique, so a payment or grant counts once.

Don't edit items or skills by hand: Login overwrites them from gamedata.json at every start.

#Switching to PostgreSQL

#From the editor

  1. Open KitARPG > Play and Servers, pick MMO, and stop the services if they run.
  2. In the database step pick PostgreSQL: for production and press Set up PostgreSQL... (build the services first; they do the talking).
  3. Pick one:
    • A server I run: fill Host, Port and SSL (Prefer, Require or Disable; hosted servers usually need Require). Then Create the database for me with an admin login (used once, never saved) and Create and use, or Use a database I have and Test and use.
    • Docker on this computer: Create and use starts PostgreSQL 17 in a container named kitarpg-postgres, published on 127.0.0.1 from port 5432 (or the next free one), with its data in the kitarpg-pgdata volume and a random password.
  4. Start the services. The tables are created on the first start.

The connection is saved for this computer in UserSettings/KitARPG/launcher.json. See Play & Servers.

#With the launcher

Set two fields in launcher.json:

{
  "DatabaseProvider": "Postgres",
  "ConnectionString": "Host=localhost;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>"
}

To create the database and user first, dotnet run --project Launcher -- --postgres with a create request does what the editor does. See Launcher.

#By hand

As a PostgreSQL superuser:

CREATE ROLE kitarpg LOGIN PASSWORD '<long random password>';
CREATE DATABASE kitarpg OWNER kitarpg ENCODING 'UTF8';

Then give every service:

Database__Provider=Postgres
Database__ConnectionString="Host=db.example.com;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>;SSL Mode=Require"

#In Docker Compose

The compose file already uses PostgreSQL with the password from POSTGRES_PASSWORD in Deploy/.env. See Docker.

注意

Switching providers starts an empty database. The kit doesn't copy data from SQLite to PostgreSQL. Switch before you have players.

#Backups

Back up the whole database: characters, items, guilds, mail and the shop ledger only make sense together.

#PostgreSQL in Docker Compose

From the Deploy folder:

docker compose exec -T postgres pg_dump -U kitarpg -d kitarpg -Fc > kitarpg-$(date +%F).dump

pg_dump takes a consistent snapshot while the game runs. Copy the file off the server. To run it every night, put the line in the server's crontab with the full path to the Deploy folder.

#PostgreSQL elsewhere

pg_dump "host=db.example.com dbname=kitarpg user=kitarpg sslmode=require" -Fc > kitarpg.dump

Hosted PostgreSQL services also keep their own backups; check how long they keep them.

#SQLite

Stop the services, then copy kitarpg.db together with kitarpg.db-wal and kitarpg.db-shm if they exist. Copying the file while the services run can give you a broken copy.

#Restoring

  1. Stop Login, Central, the Shop and the map servers (docker compose stop login central shop map-town map-forest map-crypt).

  2. Restore into an empty database:

    docker compose exec -T postgres dropdb -U kitarpg kitarpg
docker compose exec -T postgres createdb -U kitarpg -O kitarpg kitarpg
docker compose exec -T postgres pg_restore -U kitarpg -d kitarpg < kitarpg-2026-11-10.dump

  3. Start everything again. If the backup is older than the services, the missing migrations run on start.

警告

Restoring rolls back every player to the time of the backup, including premium currency bought since. Payments made after the backup are still in your payment provider; grant them again with the Shop's admin API before reopening.

#Everyday queries

Name the first admin after creating your account:

UPDATE accounts SET "Role" = 4 WHERE "Username" = 'yourname';

Column names keep their capitals, so they need double quotes in PostgreSQL. After that, admins change levels in game with /role. See GM tools.

Other useful reads:

-- Who is banned
SELECT "Username", "BannedUntil" FROM accounts WHERE "BannedUntil" > now();
-- The latest GM commands
SELECT "At", "Character", "Line", "Result" FROM gm_audit ORDER BY "At" DESC LIMIT 50;

Prefer the game's own tools (/logs, /reports, the GM panel) for moderation. Never move items or gold with SQL while the game runs: Central and the maps hold their own view and would overwrite or duplicate your change.

#Log retention

Setting What it does Default
Logs:Days Days game_logs lines are kept. Checked once an hour. 0 keeps them forever 180
Central:GuildHistoryDays Days guild history lines are kept 90

Set them on every service that writes the log (Login, Central and the Shop).

#Common mistakes

  • Two SQLite files. Services run by hand from different folders with the default connection string each make their own kitarpg.db. Use one absolute path.
  • "The database password in Database:ConnectionString is empty or a sample value." Outside Development the services refuse passwords like kitarpg, postgres, password or anything with change-me. Use a long random one.
  • The user can't create tables. The game's user must own the database (or have CREATE on it and on the public schema). The editor's Test and use checks this.
  • Editing items by hand. Login overwrites it at the next start. Change the item in the Game Database and export again.
