服务器与部署

数据库

在线 KitARPG 游戏在哪里保存账号、角色和物品：SQLite 或 PostgreSQL，数据库结构如何创建和更新，每张表的内容，如何切换到 PostgreSQL，以及如何备份和恢复。

#SQLite 还是 PostgreSQL

Login、Central 和 Shop 共用一个数据库。地图服务器从不连接它；它们通过 Central 加载和保存。

SQLite PostgreSQL
是什么 磁盘上的一个文件 一个数据库服务器
安装 无 一个服务器、一个数据库和一个用户（编辑器可以创建它们）
适合 开发、测试、单台机器上的小型私人服务器 生产环境、任何公开服务、分布在多台机器上的地图
位置 从编辑器运行时为 UserSettings/KitARPG/data/kitarpg.db，从启动器运行时为 launcher.json 旁边的 data/kitarpg.db 你的服务器运行的任何地方。在 Docker Compose 中为 pgdata 卷
JSON 列 文本 jsonb
版本 随服务一起打包 PostgreSQL 16 或更新版本。compose 文件使用 postgres:17-alpine

两者运行相同的代码和相同的迁移。每个提供程序有自己的数据库上下文（SqliteGameDbContext、PostgresGameDbContext）和自己的迁移文件夹。

单人模式游戏两者都不用：它保存到玩家持久数据文件夹中自己的 SQLite 文件（默认为 savegame.db，在 KitARPGSettings 中以 Save File（saveFile）设置）。这个文件属于玩家，本页不涉及。

#设置

每个服务都读取同一个 Database 节。环境变量在层级之间使用 __。

设置 环境变量 作用 默认值
Database:Provider Database__Provider Sqlite 或 Postgres Sqlite
Database:ConnectionString Database__ConnectionString 连接。SQLite：Data Source=<file>。PostgreSQL：Host=...;Port=5432;Database=...;Username=...;Password=... Data Source=kitarpg.db
Database:MigrateOnStartup Database__MigrateOnStartup 服务启动时把数据库结构更新到最新，然后迁移模块的表 true

SQLite 的相对路径是相对于服务自己的文件夹。手动运行服务时，要给它们全部相同的绝对路径，否则每个服务都会创建自己的文件。

Npgsql 连接字符串的选项都可以使用，例如托管服务器用的 SSL Mode=Require，以及连接池用的 Maximum Pool Size=...。

#迁移

  • 开启 MigrateOnStartup 时，每个服务在启动时应用所有缺失的迁移。启动器先启动 Login 并稍等片刻，所以通常由 Login 完成迁移。
  • 已应用的迁移记录在 __EFMigrationsHistory 中。模块的迁移记录在 __ModuleMigrations_<module name> 中。
  • 修改数据库结构的套件更新会为两种提供程序都附带新的迁移。重启服务即可应用。
  • 迁移只能向前。有些迁移移动数据的方式无法撤销（例如 ItemOwnersAndCatalog，它把以 JSON 存储的物品移到了行中）。在正式服务器上更新套件之前先备份。

要创建你自己的表，请编写一个带有自己上下文和迁移的服务模块；绝不要修改套件的表。见服务模块。如果你仍然修改了套件的实体（用于你自己的分支），请为两种提供程序都生成迁移：

cd Services/Data
dotnet ef migrations add <Name> --context SqliteGameDbContext --output-dir Migrations/Sqlite
dotnet ef migrations add <Name> --context PostgresGameDbContext --output-dir Migrations/Postgres

#表

表 保存什么 由谁写入
accounts 用户名（唯一，最多 32 个字符）、电子邮件、Argon2id 密码哈希、GM 等级（Role：1 Player、2 Moderator、3 Game Master、4 Admin）、BannedUntil、银行金币、创建日期 Login、Central（封禁、角色等级、银行）
characters 名称（唯一）、职业、等级、经验、金币、地图和位置、生命、法力、自由点数，以及货币、属性、技能、快捷栏、外观和 Extra（任务、进度、game 下你自己的 PlayerData）的 JSON 列。Version 拒绝旧存档；Deliveries 统计 Central 交付过的内容 Login 创建，Central 保存
item_instances 每件物品的每一个副本：uid、物品 id、恰好一个所有者（CharacterId、AccountId、GuildId、MailId、CollectorId 或 ListingId）、容器、格子、数量、绑定、Extra JSON（随机属性、强化、宝石） Central、Shop（信件中的新副本）
items 物品目录：id、名称、类别以及游戏数据导出的其余内容，外加 Retired Login，每次启动时
skills 技能目录：id、名称、职业、Retired Login，每次启动时
friends 成对的角色 Central
guilds、guild_members 公会（唯一名称、公告、等级、升级、徽章、联盟）及其带职位的成员 Central
guild_events 公会历史记录，在 Central:GuildHistoryDays 之后删除 Central
alliances 联盟（唯一名称和标签、公告） Central
mails 信件：收件人、发件人名称、主题、正文、金币、过期时间、Kind（商店交付为 shop） Central、Shop
market_listings 市场上的拍品：卖家、物品、单价、过期时间 Central
collectors 收税官：公会、地图、位置 Central
game_logs 游戏日志：类型、时间、账号、角色、地图、物品、金币、详情。在 Logs:Days 之后清理 Login、Central、Shop
gm_audit 每条 2 级及以上的 GM 命令，包括命令行、目标和结果 Central
reports 玩家举报，以及前后的聊天内容 Central
remember_tokens 每个 "Remember me" 令牌的 SHA-256、其令牌族、账号、地址、过期时间和使用情况 Login
currency_ledger 高级货币余额的每一次变动，带有唯一的引用 Shop

数据库自身会强制执行重要规则：

  • item_instances 有一个检查约束：恰好一个所有者，并且数量大于零。它的物品 id 是指向 items 的外键，所以副本不能指向目录中从未有过的物品。
  • 删除角色、账号、公会、信件、收税官或市场拍品时，会删除其持有的副本。
  • 用户名、角色名、公会名以及联盟名称和标签都是唯一的，以规范化形式比较。
  • currency_ledger.Reference 是唯一的，所以一笔支付或发放只计算一次。

不要手动编辑 items 或 skills：Login 每次启动时都会用 gamedata.json 覆盖它们。

#切换到 PostgreSQL

#在编辑器中

  1. 打开 KitARPG > Play and Servers，选择 MMO，如果服务正在运行则停止它们。
  2. 在数据库步骤中选择 PostgreSQL: for production，然后按 Set up PostgreSQL...（先构建服务；由它们负责与数据库通信）。
  3. 选择其一：
    • A server I run：填写 Host、Port 和 SSL（Prefer、Require 或 Disable；托管服务器通常需要 Require）。然后用管理员登录信息（只使用一次，从不保存）选择 Create the database for me 并按 Create and use，或者选择 Use a database I have 并按 Test and use。
    • Docker on this computer：Create and use 会在名为 kitarpg-postgres 的容器中启动 PostgreSQL 17，在 127.0.0.1 上从端口 5432（或下一个空闲端口）发布，数据放在 kitarpg-pgdata 卷中，并使用随机密码。
  4. 启动服务。首次启动时会创建表。

连接信息会为这台电脑保存在 UserSettings/KitARPG/launcher.json 中。见 Play & Servers。

#使用启动器

在 launcher.json 中设置两个字段：

{
  "DatabaseProvider": "Postgres",
  "ConnectionString": "Host=localhost;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>"
}

要先创建数据库和用户，用 dotnet run --project Launcher -- --postgres 加一个 create 请求，它会做与编辑器相同的事。见启动器。

#手动

以 PostgreSQL 超级用户身份执行：

CREATE ROLE kitarpg LOGIN PASSWORD '<long random password>';
CREATE DATABASE kitarpg OWNER kitarpg ENCODING 'UTF8';

然后给每个服务设置：

Database__Provider=Postgres
Database__ConnectionString="Host=db.example.com;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>;SSL Mode=Require"

#在 Docker Compose 中

compose 文件已经使用 PostgreSQL，密码来自 Deploy/.env 中的 POSTGRES_PASSWORD。见 Docker。

注意

切换提供程序会从一个空数据库开始。套件不会把数据从 SQLite 复制到 PostgreSQL。请在有玩家之前切换。

#备份

备份整个数据库：角色、物品、公会、邮件和商店账本只有放在一起才有意义。

#Docker Compose 中的 PostgreSQL

在 Deploy 文件夹中执行：

docker compose exec -T postgres pg_dump -U kitarpg -d kitarpg -Fc > kitarpg-$(date +%F).dump

pg_dump 在游戏运行时也能获取一致的快照。把文件复制到服务器以外。要每晚运行，把这行命令连同 Deploy 文件夹的完整路径放进服务器的 crontab。

#其他地方的 PostgreSQL

pg_dump "host=db.example.com dbname=kitarpg user=kitarpg sslmode=require" -Fc > kitarpg.dump

托管的 PostgreSQL 服务也会保留自己的备份；请确认它们保留多长时间。

#SQLite

停止服务，然后复制 kitarpg.db，如果存在 kitarpg.db-wal 和 kitarpg.db-shm，也一并复制。在服务运行时复制文件可能会得到损坏的副本。

#恢复

  1. 停止 Login、Central、Shop 和地图服务器（docker compose stop login central shop map-town map-forest map-crypt map-guild-hall）。

  2. 恢复到一个空数据库：

    docker compose exec -T postgres dropdb -U kitarpg kitarpg
docker compose exec -T postgres createdb -U kitarpg -O kitarpg kitarpg
docker compose exec -T postgres pg_restore -U kitarpg -d kitarpg < kitarpg-2026-11-10.dump

  3. 重新启动所有内容。如果备份比服务旧，缺失的迁移会在启动时运行。

警告

恢复会把每个玩家回滚到备份时的状态，包括之后购买的高级货币。备份之后的付款仍记录在你的支付服务商中；重新开放之前，用 Shop 的管理 API 再次发放它们。

#日常查询

创建账号后，将第一个管理员设为你自己：

UPDATE accounts SET "Role" = 4 WHERE "Username" = 'yourname';

列名保留大写字母，所以在 PostgreSQL 中需要加双引号。之后，管理员可以在游戏中用 /role 修改等级。见 GM 工具。

其他有用的查询：

-- Who is banned
SELECT "Username", "BannedUntil" FROM accounts WHERE "BannedUntil" > now();
-- The latest GM commands
SELECT "At", "Character", "Line", "Result" FROM gm_audit ORDER BY "At" DESC LIMIT 50;

管理时优先使用游戏自带的工具（/logs、/reports、GM 面板）。绝不要在游戏运行时用 SQL 移动物品或金币：Central 和各地图持有自己的视图，会覆盖或复制你的修改。

#日志保留

设置 作用 默认值
Logs:Days game_logs 记录保留的天数。每小时检查一次。0 表示永久保留 180
Central:GuildHistoryDays 公会历史记录保留的天数 90

在每个写入日志的服务（Login、Central 和 Shop）上设置它们。

#常见错误

  • 两个 SQLite 文件。 从不同文件夹手动运行、使用默认连接字符串的服务，会各自创建自己的 kitarpg.db。请使用同一个绝对路径。
  • "The database password in Database:ConnectionString is empty or a sample value." 在 Development 之外，服务会拒绝 kitarpg、postgres、password 或任何包含 change-me 的密码。请使用一个长的随机密码。
  • 用户无法创建表。 游戏使用的用户必须拥有该数据库（或在数据库和 public 模式上有 CREATE 权限）。编辑器的 Test and use 会检查这一点。
  • 手动编辑 items。 Login 会在下次启动时覆盖它。请在 Game Database 中修改物品并重新导出。
