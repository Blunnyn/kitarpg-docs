Sistemas do jogador

Como adicionar um sistema seu a todos os jogadores: um NetworkBehaviour nos prefabs dos modelos de jogador com estado sincronizado, comandos que o dono envia, respostas, salvamento e as regras que o mantêm correto online.

#Quando você precisa de um

Os recursos do jogador do kit são componentes no prefab do jogador: PlayerInventory, PlayerSkills, PlayerQuests, PlayerProgress, PlayerChat, PlayerGuild, PlayerMail e os demais. Adicione um componente seu quando o seu recurso precisar de:

  • estado que outro código lê com frequência, no servidor ou no cliente (um valor de reputação, um mascote, uma fila de criação),
  • valores sincronizados que a interface mostra, ou que outros jogadores veem,
  • pedidos do dono com regras próprias.

Se você só precisa de um pedido e uma resposta, sem estado no jogador, mensagens de rede são mais leves e não exigem mudar o prefab. Se você só precisa salvar alguns números, marcas do personagem não exigem código nenhum.

Onde o arquivo fica: no assembly Game. O mesmo componente roda no servidor e nos clientes.

#Comece pelo template

Create > KitARPG > Scripts > Player System cria PlayerNewSystem. O código completo está em Templates. Ele mostra as peças que todo sistema do jogador tem:

Peça Para que serve
[RequireComponent(typeof(PlayerCharacter))] Só faz sentido em um jogador.
[SyncVar] public int points Um valor que o servidor define e os clientes recebem.
static event Action<int> Changed Avisa a interface do dono quando o valor muda.
static PlayerNewSystem Local A cópia do jogador local, para as janelas. Definida em OnStartAuthority.
ResetStatics em SubsystemRegistration Limpa os estáticos entre Plays sem domain reload.
OnStartServer Carrega o estado salvo quando o jogador aparece no servidor.
public void Earn() => CmdEarn() O método do lado do cliente que as janelas chamam.
[Command] void CmdEarn() O pedido, executado no servidor. Gasta do orçamento da conexão com CommandPacing.Allow e depois verifica tudo.
[TargetRpc] void TargetTold(string) Uma resposta só para o dono.
Hook OnPointsChanged Dispara Changed no cliente do dono.

#Adicionando aos prefabs do jogador

Cada modelo de jogador tem seu próprio prefab, listado no banco de dados do jogo (KitARPG > Game Database > Models, campo GameDatabase.playerModels). Adicione o seu componente a cada um deles:

  1. Abra KitARPG > Game Database > Models e escolha um modelo. A página dele tem o link do prefab.
  2. Abra o prefab e adicione o seu componente.
  3. Repita para cada modelo.

Um modelo adicionado depois com + New player model recebe os sistemas do kit, mas não o seu. Para adicionar o seu componente a todos os modelos automaticamente, inclusive aos criados depois, distribua uma atualização do kit que o adiciona onde falta. Essa página tem o código completo para isso.

Atenção

O Mirror associa os componentes de rede pela ordem deles no objeto. As builds de cliente e de servidor devem ter exatamente os mesmos NetworkBehaviours em cada prefab de jogador. Nunca adicione o seu componente em tempo de execução, nem só em um tipo de build.

#Estado sincronizado

Ferramenta Chega a Use para
[SyncVar] em um campo Clientes que veem o jogador (ou só o dono, veja abaixo) Valores únicos
SyncList<T>, SyncDictionary<K,V>, SyncHashSet<T> (como campos readonly) Os mesmos Coleções
[TargetRpc] Só o dono Respostas e eventos pontuais
[ClientRpc] Todo cliente que vê o jogador Efeitos que os outros precisam ver

Cada NetworkBehaviour tem um Sync Mode: Observers (todos que veem o jogador recebem os valores) ou Owner (só o dono recebe). Os sistemas privados do kit (PlayerQuests, PlayerProgress, o conteúdo da bolsa em PlayerInventory) definem Owner em Reset():

void Reset() => syncMode = SyncMode.Owner;

Reset roda quando você adiciona o componente no editor. Escolha Owner para tudo o que outros jogadores não devem ler: um cliente hackeado consegue ler todo valor que recebe.

Quem vê um jogador é decidido pelo interest management do kit (uma grade espacial). Jogadores distantes, ou em outra cópia de uma masmorra, não recebem os seus valores nem os seus [ClientRpc]s.

#Comandos: o dono pede

Um [Command] roda no servidor com a identidade de quem chamou conhecida: só o cliente do dono pode chamar comandos no próprio jogador. Dentro de um comando:

  1. Gaste do orçamento da conexão. CommandPacing.Allow(connectionToClient) dá a cada conexão 30 comandos por segundo com rajada de 60, compartilhados por todos os componentes, e desconecta inundações. Use CommandPacing.AllowCentral para comandos que viram trabalho para o Central (2 por segundo, rajada de 10).
  2. Valide todo argumento. Comprimentos, intervalos, números finitos, ids que existem no banco de dados.
  3. Verifique o estado do jogador. Vivo, carregado (player.State != null), não ocupado, ao alcance daquilo sobre o que age.
  4. Mude o estado pelos sistemas do kit. Itens e ouro por PlayerInventory, marcas por PlayerProgress, missões por PlayerQuests.

#Um exemplo completo: reputação

Um valor de reputação por facção, ganho com abates, mostrado em uma janela e gasto em um NPC. Ele se salva com PlayerData através de IPlayerSave e sincroniza só com o dono.

using System;
using System.Collections.Generic;
using Blunnyn.KitARPG.Data;
using Blunnyn.KitARPG.Net;
using Blunnyn.KitARPG.Shared.Characters;
using Mirror;
using UnityEngine;

namespace Game
{
    [RequireComponent(typeof(PlayerCharacter))]
    public class PlayerReputation : NetworkBehaviour, IPlayerSave
    {
        const string Key = "mygame.reputation";
        public const int Max = 100000;

        [Serializable]
        class Saved
        {
            public List<string> factions = new List<string>();
            public List<int> values = new List<int>();
        }

        /// <summary>Faction id to reputation. Owner only.</summary>
        public readonly SyncDictionary<string, int> standing = new SyncDictionary<string, int>();

        /// <summary>Owner's client: something changed.</summary>
        public event Action Changed;

        /// <summary>Owner's client: a message for the reputation window.</summary>
        public static event Action<string> Told;

        public static PlayerReputation Local { get; private set; }

        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            Local = null;
            Told = null;
        }

        void Reset() => syncMode = SyncMode.Owner;

        PlayerCharacter player;

        protected virtual void Awake()
        {
            player = GetComponent<PlayerCharacter>();
            standing.OnChange += (_, __, ___) => Changed?.Invoke();
        }

        public override void OnStartAuthority() => Local = this;

        public override void OnStopAuthority()
        {
            if (Local == this) Local = null;
        }

        public int Of(string faction) => standing.TryGetValue(faction, out int v) ? v : 0;

        // Saving: loaded as the character enters a map, written before every save.

        public void ServerLoad(PlayerCharacter owner, CharacterState state)
        {
            standing.Clear();
            Saved saved = PlayerData.Get<Saved>(owner, Key);
            for (int i = 0; i < saved.factions.Count && i < saved.values.Count; i++)
                standing[saved.factions[i]] = saved.values[i];
        }

        public void WriteTo(PlayerCharacter owner, CharacterState state)
        {
            var saved = new Saved();
            foreach (KeyValuePair<string, int> pair in standing)
            {
                saved.factions.Add(pair.Key);
                saved.values.Add(pair.Value);
            }
            PlayerData.Set(owner, Key, saved);
        }

        /// <summary>Server only. Called by your own rules, never from a client's word.</summary>
        [Server]
        public void ServerAdd(string faction, int amount)
        {
            if (string.IsNullOrEmpty(faction) || amount == 0) return;
            standing[faction] = Mathf.Clamp(Of(faction) + amount, -Max, Max);
        }

        // Spending: the owner asks, the server checks everything.

        public void Spend(string npcId, string faction, int amount) => CmdSpend(npcId, faction, amount);

        [Command]
        void CmdSpend(string npcId, string faction, int amount)
        {
            if (!CommandPacing.Allow(connectionToClient)) return;
            if (player.State == null || player.IsDead) return;
            if (string.IsNullOrEmpty(faction) || faction.Length > 32 || amount <= 0 || amount > Max) return;
            if (!Npc.TryFind(npcId, out Npc npc) || !npc.InReach(transform.position)) return;
            if (Of(faction) < amount)
            {
                TargetTold("Not enough reputation.");
                return;
            }
            standing[faction] = Of(faction) - amount;
            GameLog.Write("mygame.reputation_spent", player, amount: amount, detail: $"{faction} at {npc.Id}");
            TargetTold($"Spent {amount} reputation with {faction}.");
        }

        // Runs on the owner's client: hand it to the interface.
        [TargetRpc]
        void TargetTold(string text) => Told?.Invoke(text);
    }
}

Uma janela sua se inscreve em PlayerReputation.Told e em PlayerReputation.Local.Changed, e chama PlayerReputation.Local.Spend(...) pelo botão dela.

E a regra do servidor que dá reputação, em qualquer lugar do assembly Game:

public static class ReputationRules
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]
    static void Hook()
    {
        Monster.ServerKilled -= OnKilled;
        Monster.ServerKilled += OnKilled;
    }

    static void OnKilled(Monster monster, PlayerCharacter killer)
    {
        if (killer == null || monster.Data == null) return;
        if (killer.TryGetComponent(out PlayerReputation reputation)) reputation.ServerAdd("forest_wardens", 5);
    }
}

#Carregando e salvando

Forma Como carrega Quando salva Visto pelos clientes
Marcas do personagem (PlayerProgress.SetFlag, IPlayerActor.SetFlag) Com o personagem, antes de aparecer Com o personagem O dono, sincronizado
PlayerData com IPlayerSave O seu ServerLoad, antes de aparecer O seu WriteTo, antes de cada salvamento Nunca; sincronize o que precisar

A ordem no servidor de mapa quando um personagem entra:

  1. O prefab do jogador é instanciado.
  2. PlayerCharacter.ServerSetup carrega os sistemas do kit (inventário, banco, habilidades, progresso com suas marcas, missões) e depois chama ServerLoad em todo componente IPlayerSave.
  3. O jogador aparece na rede: OnStartServer roda em todo componente e depois PlayerCharacter.ServerSpawned é disparado.

Por isso OnStartServer pode ler marcas, como o template faz. Em ServerLoad o objeto ainda não apareceu na rede: isServer ainda é false, então PlayerData.Set recusa e os métodos [Server] registram um aviso ali. Leia em ServerLoad; escreva depois.

Os salvamentos acontecem a cada Save Interval Seconds (saveIntervalSeconds, 60 no servidor de mapa), quando o jogador sai ou troca de mapa e quando o servidor para. Veja Salvando dados.

#Desligando o seu sistema com um módulo

GameInstance.Has(KitModule.X) diz se um dos módulos do kit está ligado. Para um interruptor seu, adicione um campo a um asset seu e verifique-o no servidor em todo comando. Nunca remova o componente no lugar disso: o prefab precisa manter os mesmos componentes de rede em todas as builds.

#Sobrescrever em vez de adicionar

Para mudar um dos sistemas do jogador do kit em vez de adicionar um novo, crie uma subclasse dele e troque o componente nos prefabs. Veja Sobrescrevendo o comportamento do kit.

#Servidor e cliente

Servidor Cliente do dono Outros clientes
Corpo do [Command] Roda Chama Não
Corpo do [TargetRpc] Chama Roda Não
Corpo do [ClientRpc] Chama Roda Roda se veem o jogador
[SyncVar] (Observers) Define Recebe Recebem
[SyncVar] (Owner) Define Recebe Não
OnStartServer, IPlayerSave Roda Não Não
OnStartAuthority, OnStartLocalPlayer Não Roda Não

Em um jogador, o host é servidor e dono ao mesmo tempo: os comandos rodam no mesmo processo, CommandPacing deixa passar a conexão do próprio host, e tanto OnStartServer quanto OnStartAuthority rodam no mesmo objeto.

#Erros comuns

  • Sem CommandPacing em um [Command]. Um cliente modificado pode chamá-lo milhares de vezes por segundo.
  • Confiar em um argumento porque o botão que o envia está escondido. Os clientes podem enviar qualquer coisa.
  • Componentes diferentes nas builds de cliente e de servidor. O Mirror lê o componente errado e a conexão quebra.
  • Estáticos sem reset. Local do último Play aponta para um objeto destruído. Veja Play sem domain reload.
  • Sync mode Observers para dados privados. Todo cliente próximo os recebe.
  • Escrever PlayerData em ServerLoad. O jogador ainda não apareceu na rede; a escrita é recusada.
