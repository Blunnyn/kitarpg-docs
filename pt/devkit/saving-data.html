Salvando dados

Onde guardar os dados próprios do seu jogo para que sejam salvos com o personagem em um jogador e online: flags do personagem, PlayerData, componentes com IPlayerSave, tabelas em um módulo do Central e assets de dados.

#Escolha um lugar

O que você guarda Onde Visto pelo cliente Salvo
Números inteiros pequenos por personagem: marcas de história, contadores, um carimbo de dia Flags do personagem O dono, sincronizado Com o personagem
Valores estruturados por personagem: uma lista, um mascote com stats, um histórico PlayerData Nunca Com o personagem
O mesmo, mantido por um componente seu que carrega e grava os dados IPlayerSave + PlayerData O que você mesmo sincronizar Com o personagem
Dados que você consulta entre personagens: rankings, eventos do mundo, contadores do servidor inteiro Uma tabela em um módulo do Central O que você enviar Na sua própria tabela
Conteúdo que os designers editam: receitas, quadros, listas de drop Um asset ScriptableObject ou GameData As duas builds o carregam É um asset

Nunca coloque estado do jogo em PlayerPrefs: ele fica no computador do jogador, nunca chega ao servidor e pode ser editado pelo jogador. PlayerPrefs é para configurações do cliente (veja Menus e opções de configuração).

#Flags do personagem

Flags são inteiros com nome no personagem, mantidos por PlayerProgress. Os designers já os usam por meio de SetFlagAction e FlagCondition, e você também pode.

Onde Ler Gravar
Condições e ações facts.Flag(key) actor.SetFlag(key, value) (servidor)
Código do servidor player.Facts.Flag(key) ou progress.Flag(key) player.Facts.SetFlag(key, value) ou progress.SetFlag(key, value)
Cliente do dono PlayerProgress.Local.Flag(key) Nunca
  • Um valor 0 remove a flag. Flag retorna 0 para flags nunca definidas.
  • As flags são sincronizadas com o dono (PlayerProgress usa sincronização Owner), então a interface e as condições do dono podem lê-las. Os outros jogadores nunca as veem.
  • PlayerProgress.ServerFlagChanged (PlayerCharacter, string key, int value) é disparado no servidor quando uma muda.
  • Online, o Central as guarda em characters.extra sob flags; em um jogador elas vão para o save local.

O exemplo de recompensas guarda o progresso da caçada em flags (bounty.board, bounty.index, bounty.kills, bounty.day, bounty.done). As últimas caçadas de cada personagem são uma lista de nomes, que não cabe em uma flag, então vão em PlayerData (veja abaixo).

As flags guardam int. Um número de dia, uma contagem ou o hash de um id cabem; texto e listas não.

#PlayerData

PlayerData (namespace Blunnyn.KitARPG.Net) guarda JSON no personagem sob chaves suas. Só no servidor.

Membro O que faz
T Get<T>(PlayerCharacter player, string key) O valor, ou um T novo quando não há nenhum ou ele não pode ser lido.
bool Set<T>(PlayerCharacter player, string key, T value) Guarda o valor. Null remove a chave. False quando um limite seria ultrapassado; nesse caso nada muda.
bool Has(PlayerCharacter player, string key) Se a chave tem valor.
void Remove(PlayerCharacter player, string key) Remove a chave.
string GetJson(...), bool SetJson(...) O mesmo, com JSON bruto.

Os valores são classes [Serializable] lidas e gravadas com o JsonUtility do Unity:

[Serializable]
public class PetSave
{
    public string petId;
    public int level = 1;
    public long experience;
    public List<string> tricks = new List<string>();
}

// On the server:
PetSave pet = PlayerData.Get<PetSave>(player, "mygame.pet");
pet.experience += 50;
if (!PlayerData.Set(player, "mygame.pet", pet)) Debug.LogWarning("Pet data too big.");

#Limites

CharacterDataRules (namespace Blunnyn.KitARPG.Shared.Characters) aplica os mesmos limites no mapa, no Central e no save local:

Limite Valor
Chaves por personagem (MaxKeys) 64
Tamanho da chave (MaxKeyLength) 64 caracteres
Caracteres da chave Letras, dígitos, ., - e _
Todos os valores juntos (MaxBytes) 32 KB de UTF-8

Comece cada chave com o nome do seu jogo (mygame.pet), para que nunca se encontre com a de outro pacote.

#Onde fica guardado

Online, o Central guarda os valores em characters.extra sob game, como um único objeto JSON ({ "mygame.pet": { ... } }), legível no banco de dados e sem migração de tabela. Um save cujos dados ultrapassam os limites, ou que tem um valor que não é JSON válido, mantém os dados guardados, registra um aviso no log e salva o resto do personagem. Em um jogador, os mesmos dados vão para o save local (savegame.db na pasta de dados persistentes do jogador, definido por Save File em KitSettings).

#O que o JsonUtility pode e não pode fazer

  • Campos públicos e campos privados com [SerializeField]. Propriedades não.
  • int, long, float, bool, string, enums, arrays, List<T>, classes [Serializable] aninhadas.
  • Nada de dicionários. Guarde duas listas paralelas, ou uma lista de classes chave-valor.
  • Sem polimorfismo, sem null em classes aninhadas (elas voltam vazias).

#Componentes com IPlayerSave

Quando um componente seu é dono dos próprios dados, implemente IPlayerSave e deixe o kit chamar você:

Método Quando
void ServerLoad(PlayerCharacter player, CharacterState state) Quando o personagem entra em um mapa, depois que os sistemas do kit carregaram, antes de o jogador surgir.
void WriteTo(PlayerCharacter player, CharacterState state) Antes de cada save. 
[RequireComponent(typeof(PlayerCharacter))]
public class PlayerPet : NetworkBehaviour, IPlayerSave
{
    const string Key = "mygame.pet";

    PetSave pet = new PetSave();

    [SyncVar] public string petId;
    [SyncVar] public int petLevel;

    public void ServerLoad(PlayerCharacter player, CharacterState state)
    {
        pet = PlayerData.Get<PetSave>(player, Key);
        petId = pet.petId;
        petLevel = pet.level;
    }

    public void WriteTo(PlayerCharacter player, CharacterState state) => PlayerData.Set(player, Key, pet);
}

O template Saved Player Data cria um desses (veja Templates).

Atenção

Em ServerLoad o jogador ainda não surgiu, então isServer é false e PlayerData.Set recusa. Leia ali; grave a partir de WriteTo ou depois.

#Quando os saves acontecem

No servidor de mapa, um personagem é salvo:

  • a cada Save Interval Seconds (saveIntervalSeconds no servidor de mapa, 60),
  • quando o jogador se desconecta ou troca de mapa,
  • quando o servidor para.

Cada save chama WriteTo em todo IPlayerSave. Online, o estado vai para o Central, que o grava no banco de dados; em um jogador, vai para o save local. Valores definidos com PlayerData.Set entre saves ficam no personagem em memória e vão com o próximo save. Uma queda entre dois saves perde o que mudou desde o último, como acontece com os próprios dados do kit.

Itens e ouro que passam entre personagens (trocas, correio, mercado, banco da guilda) usam transações no Central em vez do save periódico; nunca modele uma troca entre jogadores com PlayerData.

#Mudando o formato depois

O JSON salvo dura mais que o seu código. Planeje para os dados antigos:

  • Campos novos recebem seu valor padrão quando dados antigos são lidos; dê a eles padrões sensatos.
  • Campos removidos são ignorados.
  • Para mudanças maiores, coloque um número de versão na classe e converta em ServerLoad.
  • Renomear uma chave perde os dados antigos. Leia a chave antiga uma vez, grave a nova e faça Remove da antiga.

#Tabelas em um módulo do Central

Para dados que você consulta entre personagens (os melhores caçadores, um contador do servidor inteiro, um histórico de leilões próprio), um módulo adiciona tabelas ao banco de dados do kit ao lado das do kit, com suas próprias migrações. Os servidores de mapa chegam a ele com CentralMessages. Veja Falando com o Central e Módulos de serviço. Em um jogador não há Central: mantenha uma alternativa por personagem, como o exemplo de recompensas faz com seu histórico em PlayerData.

#Assets de dados

Conteúdo (receitas, listas de drop, definições de quadros) pertence a assets, não a saves:

  • Um ScriptableObject simples com [CreateAssetMenu] quando só o seu código aponta para ele. O BountyBoardData do exemplo de recompensas é um deles.
  • Uma subclasse de GameData quando saves ou mensagens precisam apontar para ele por id. Um GameData tem um Id (feito a partir do nome, salvo com os personagens), um nome de exibição, uma descrição e um ícone, e GameInstance.Database.TryGet<T>(id, out T) o encontra. Ele precisa ser alcançável a partir do game database: listado em um dos seus arrays, ou entregue pelo método Visit de algo que seja. Project Check lista os assets GameData que o banco de dados não alcança.

#Erros comuns

  • Salvar em PlayerPrefs. Nunca chega ao servidor.
  • Ler PlayerData no cliente. Nunca é enviado. Sincronize o que a interface precisa.
  • Chaves sem prefixo. Outro pacote pode sobrescrevê-las.
  • Dicionários em classes salvas. O JsonUtility os descarta sem avisar.
  • Ignorar a resposta de Set. Acima dos limites, nada é guardado.
  • Mudar o id de um GameData. Os saves apontam para o id antigo.
