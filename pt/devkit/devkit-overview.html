DevKit

Visão geral do DevKit

O DevKit é o conjunto de pontos de extensão, templates e exemplos que permite criar qualquer recurso sobre o KitARPG sem editar o código do kit. Esta página explica as regras, onde o seu código roda e qual página ler para cada tipo de mudança.

#Por que você nunca edita o kit

Tudo o que fica em Assets/Blunnyn/KitARPG/ pertence ao kit. Quando você instala uma versão nova, esses arquivos são substituídos. Qualquer linha que você tenha mudado ali se perde, e juntar a sua mudança com a versão nova é um problema que você resolve à mão.

O kit foi feito para que você nunca precise mexer nele:

  • Os assets de dados (itens, habilidades, monstros, missões) são seus. Ficam onde você os salvar e o kit nunca os reconstrói.
  • O comportamento vem em peças polimórficas pequenas (efeitos de habilidade, efeitos de item, condições, ações, objetivos de missão, opções de NPC). Você adiciona tipos novos escrevendo uma classe; o inspector a lista ao lado das do kit.
  • Os sistemas disparam eventos estáticos e expõem métodos virtual, então você pode reagir a eles ou substituí-los a partir do seu próprio assembly.
  • As regras que decidem números (dano, experiência, stats) são objetos que você pode trocar na inicialização.
  • Os serviços (Login e Central) carregam os seus próprios módulos .NET, com as suas próprias tabelas no banco de dados.

O seu código vai em assemblies seus, em uma pasta sua, por exemplo Assets/Game. As atualizações do kit nunca tocam essa pasta.

#As camadas do kit

O kit é organizado em camadas. Cada camada só conhece as que estão abaixo dela.

Camada Assembly O que fica ali
Regras compartilhadas KitARPG.Shared C# puro sem referências ao Unity: regras de inventário, estado do personagem, mensagens para o Central, o formato do registro. Os serviços .NET compilam os mesmos arquivos.
Dados KitARPG.Data Assets ScriptableObject e regras puras: itens, habilidades, monstros, missões, condições, ações, fórmulas, GameInstance.
Entidades em rede KitARPG.Net Tudo o que vive na rede com o Mirror: jogadores, monstros, NPCs, chat, guildas, o registro do jogo. A lógica de servidor dessas entidades roda aqui.
Só servidor KitARPG.Server O servidor de mapa: pagamento de saque, a ligação com o Central, comandos de GM. Nunca vai em um build de cliente online.
Cliente KitARPG.Client HUD, janelas, auxiliares de câmera, tela de título, configurações, input.
Modos de jogo KitARPG.Modes.* Como cada modo de controle se move e luta. Cada um tem uma metade de cliente e uma metade .Server.
Editor KitARPG.Editor A janela KitARPG, o validador, os templates.

A página Assemblies lista cada assembly, o que ele referencia e quais builds o levam.

#Onde o seu código roda

O KitARPG tem duas formas de jogar, e o mesmo código de jogo roda nas duas:

Um jogador MMO
Quem é o servidor O próprio jogo é o host: roda o servidor de mapa e o cliente em um só processo. Um processo separado de servidor de mapa (um build Linux sem tela, ou o editor em Play) roda cada mapa.
Salvamento Um save local no computador do jogador (KitARPG.Local). O Central salva os personagens em PostgreSQL ou SQLite.
Central Nenhum. CentralMessages.Online é false. O Central liga todos os servidores de mapa; o Login cuida das contas.
Assemblies só de servidor Incluídos (o build define KITARPG_SERVER). Só no build do servidor de mapa.
Comandos de GM Todo jogador é admin quando Single Player Commands (singlePlayerCommands) está ligado em Game Settings. O papel da conta decide.

Por isso, cada pedaço de código que você escreve pertence a um de três lugares:

  • Código de servidor decide o que acontece: dano, itens, ouro, progresso de missões, salvamento. Roda no servidor de mapa online e no host em um jogador. Métodos chamados Server... e handlers [Command] são código de servidor.
  • Código de cliente mostra coisas e pede ao servidor: janelas, menus, sons, a câmera, o input. Roda na máquina de cada jogador e, em um jogador, na mesma máquina do servidor.
  • Código compartilhado roda nos dois, como o Met de uma condição, que o servidor confere e o cliente usa para deixar cinza uma linha bloqueada.

A página Regras de segurança explica por que o servidor sempre confere de novo o que um cliente pede.

Efeitos, condições, ações, objetivos e opções de NPC não precisam de registro. São classes [Serializable] guardadas em campos [SerializeReference] marcados com [PickType]: assim que a sua classe compila, ela aparece no menu de tipos de toda lista desse tipo no inspector.

#Os seus primeiros cinco minutos

  1. Na janela Project, crie uma pasta Assets/Game.
  2. Clique nela com o botão direito e escolha Create > KitARPG > Scripts > Game Assembly. Aparece um Game.asmdef. Os scripts dessa pasta agora enxergam o kit e recebem o namespace Game.
  3. Clique na pasta com o botão direito de novo e escolha Create > KitARPG > Scripts > Skill Effect. Dê ao arquivo o nome PoisonDart.cs.
  4. Abra qualquer habilidade em KitARPG > Game Database > Skills. Na lista de efeitos, aperte + e escolha PoisonDart no menu de tipos.
  5. Aperte Play e lance a habilidade.

A página Templates documenta cada template com o código completo.

#O exemplo

Assets/Blunnyn/KitARPG/DevKit/Example/Bounties é um recurso completo feito só com essas ferramentas: um quadro de recompensas que entrega uma caçada por dia, conta abates, mostra o progresso no HUD, paga recompensas e mantém um ranking no Central. A página Exemplo: quadro de recompensas percorre o exemplo arquivo por arquivo. Leia uma vez antes de começar um recurso grande.

#Regras que valem em todo lugar

  • Nunca edite arquivos em Assets/Blunnyn/KitARPG/. Crie subclasses, assine eventos ou troque componentes.
  • O servidor decide. Os clientes pedem. Confira de novo cada pedido no servidor. Veja Regras de segurança.
  • Código só de servidor vai em um assembly só de servidor (Game.Server), para que os clientes online nunca o levem. Veja Assemblies.
  • O estado estático é você quem reinicia. O projeto do kit dá Play sem recarga de domínio, então os campos estáticos mantêm os valores entre um Play e outro. Veja Play sem recarga de domínio.
  • Use um prefixo nas suas chaves e nomes com o nome do seu jogo (mygame.pets, mygame.bounty_done), para que nunca se cruzem com os do kit ou de outro pacote.

#Referência da API

Todo tipo e membro público do kit está na referência da API que vem com o pacote, em Assets/Blunnyn/KitARPG/Documentation/API/, um arquivo por assembly. Ela é gerada a partir do código, então sempre corresponde à versão que você tem instalada.
