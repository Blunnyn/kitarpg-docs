DevKit

Assemblies

Como o código do kit é dividido em assemblies, quais builds levam cada um e como configurar os assemblies do seu próprio código (Game, Game.Server e Game.Editor).

#O que é um assembly aqui

A Unity compila os scripts em assemblies definidos por arquivos .asmdef. Um script pertence ao assembly cujo .asmdef está na pasta dele ou na pasta pai mais próxima. Um assembly só enxerga os assemblies que lista nas suas referências.

Os assemblies do kit não são referenciados automaticamente. Scripts em Assets que não têm um .asmdef próprio (o Assembly-CSharp padrão) não enxergam o kit. Isso é proposital: o seu código ganha um assembly próprio, o que mantém o tempo de compilação curto e mantém o seu código separado do kit.

#Os assemblies do kit

Assembly Referências Restrição de define Em quais builds
KitARPG.Shared nada (sem referências da engine) nenhuma Todos. Os serviços .NET compilam os mesmos arquivos.
KitARPG.Data Shared nenhuma Todos
KitARPG.Net Shared, Data, Mirror nenhuma Todos
KitARPG.Client Shared, Data, Net, Mirror, UI, TextMeshPro, URP, Input System nenhuma Todos (os servidores de mapa o levam, mas não o mostram)
KitARPG.Server Shared, Data, Net, Mirror, KCP, AI Navigation UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER Servidores de mapa, modo um jogador, editor
KitARPG.Local Shared, Data, Net, Server, Client UNITY_EDITOR || KITARPG_SINGLEPLAYER Só modo um jogador e editor
KitARPG.Modes.TopDown, KitARPG.Modes.ThirdPerson Shared, Data, Net, Client nenhuma Todos
KitARPG.Modes.TopDown.Server, KitARPG.Modes.ThirdPerson.Server Shared, Data, Net, Server, o modo UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER Servidores de mapa, modo um jogador, editor
KitARPG.Editor tudo acima Só a plataforma Editor Nunca em um build

KitARPG.Shared também é o contrato com os serviços: Services/Shared/KitARPG.Shared.csproj compila todos os arquivos dentro de Runtime/Shared, então uma classe de mensagem definida ali é lida igual na Unity e no Central.

#Símbolos de build

Quais assemblies um build leva depende dos seus scripting define symbols. Os menus de build do kit os definem para você.

Símbolo Compila Builds
KITARPG_SERVER (ou UNITY_SERVER) KitARPG.Server, todo KitARPG.Modes.*.Server e todo assembly cujo nome termina em .Server Servidor de mapa e modo um jogador
KITARPG_SINGLEPLAYER KitARPG.Local (o save local) Só modo um jogador
KITARPG_DEV ou um development build Ferramentas de teste (login automático, smoke test, sandbox) Editor e development builds
KITARPG_LOADTEST Bots de teste de carga Só builds de teste de carga; os menus do kit o adicionam e removem

Um build de cliente online não tem nenhum dos símbolos de servidor, então não leva código de servidor nenhum. Um build de um jogador é um cliente e um servidor em um só, então tem KITARPG_SERVER e KITARPG_SINGLEPLAYER.

#A verificação de separação de builds

Antes de todo build, de qualquer menu ou Build Profile, o kit roda BuildSeparation. Ele lê todos os assemblies do projeto, avalia as restrições de define de cada um com os símbolos daquele build e para o build quando:

  • um cliente online levaria código de servidor (qualquer assembly .Server, KitARPG.Server) ou o save local,
  • um servidor de mapa levaria o save local,
  • um build de release levaria ferramentas de teste,
  • um build de um jogador ficaria sem o servidor,
  • um cliente online de release seria compilado com Mono em vez de IL2CPP (o código dele iria em DLLs legíveis).

Um cliente de desenvolvimento compilado com Mono recebe um aviso em vez disso. KitARPG > Check Build Separation mostra o que vai em cada tipo de build. A verificação não pode ser desligada. Os seus próprios assemblies são verificados do mesmo jeito: um assembly chamado Something.Server sem a restrição de define de servidor para os builds de cliente online.

#Os seus assemblies

Crie-os em Create > KitARPG > Scripts com a pasta selecionada na janela Project.

Menu Arquivo Para
Game Assembly Game.asmdef Tudo o que roda em todo build: efeitos, condições, ações, objetivos, opções de NPC, sistemas do jogador, mensagens, janelas, fórmulas, linhas de menu, ajustes.
Game Server Assembly Game.Server.asmdef Código que só servidores de mapa e o modo um jogador podem levar: comandos de GM, CentralMessages, qualquer coisa que use KitARPG.Server.
Game Editor Assembly Game.Editor.asmdef Ferramentas do editor: páginas da janela KitARPG, verificações do validador, atualizações do kit, menus de configuração.

#Game

O menu escreve este arquivo:

{
    "name": "Game",
    "rootNamespace": "Game",
    "references": [
        "KitARPG.Shared",
        "KitARPG.Data",
        "KitARPG.Net",
        "KitARPG.Client",
        "Mirror",
        "Unity.TextMeshPro",
        "UnityEngine.UI"
    ],
    "autoReferenced": true
}

rootNamespace é Game, então os scripts criados a partir dos templates nesta pasta recebem namespace Game. Adicione referências quando precisar: KitARPG.Modes.TopDown para usar as classes de input do top-down, Unity.InputSystem para o Input System, Unity.AI.Navigation para os componentes de NavMesh.

#Game.Server

{
    "name": "Game.Server",
    "rootNamespace": "Game",
    "references": [
        "Game",
        "KitARPG.Shared",
        "KitARPG.Data",
        "KitARPG.Net",
        "KitARPG.Server",
        "Mirror"
    ],
    "defineConstraints": [
        "UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER"
    ],
    "autoReferenced": false
}

A restrição de define o mantém fora dos builds de cliente online. Ele compila no editor, nos servidores de mapa e no modo um jogador. Coloque-o em uma pasta própria, por exemplo Assets/Game/Server, para que os scripts dele não caiam em Game.

#Game.Editor

{
    "name": "Game.Editor",
    "rootNamespace": "Game",
    "references": [
        "Game",
        "KitARPG.Shared",
        "KitARPG.Data",
        "KitARPG.Net",
        "KitARPG.Editor"
    ],
    "includePlatforms": [ "Editor" ]
}

A Unity também trata de forma especial qualquer pasta chamada Editor, mas com assembly definitions é a linha includePlatforms que o mantém fora dos builds. Coloque-o em Assets/Game/Editor.

#Em que sentido vão as referências

Game.Server referencia Game, nunca o contrário. Os clientes online têm Game, mas não Game.Server, então Game não pode depender de nada que só os servidores têm.

Quando o código em Game precisa passar algo para código só de servidor, dispare um evento em Game e inscreva-se nele a partir de Game.Server. O exemplo de recompensas faz exatamente isso:

// In Game.Bounties (every build): raised when a bounty is paid.
public static event Action<PlayerCharacter, MonsterData> ServerTurnedIn;

// In Game.Bounties.Server (server builds): forwards it to Central.
Bounties.ServerTurnedIn += OnTurnedIn;

O mesmo vale para os tipos de KitARPG.Server, como GmCommands e CentralMessages: só código em um assembly exclusivo de servidor pode usá-los.

#Um assembly de C# puro para mensagens

As mensagens que os seus servidores de mapa trocam com um módulo do Central são compiladas duas vezes: pela Unity e pelo módulo .NET. Mantenha-as em um assembly sem referências da engine, para que nada exclusivo da Unity escape para dentro:

{
    "name": "Game.Shared",
    "rootNamespace": "Game",
    "references": [],
    "noEngineReferences": true,
    "autoReferenced": false
}

Referencie Game.Shared a partir de Game.Server (e de Game se o cliente precisar dos tipos), e vincule o mesmo arquivo .cs no .csproj do módulo. Veja Conversar com o Central e Módulos de serviço.

#Vários assemblies de recursos

Um jogo grande pode dividir recursos em assemblies próprios, como o exemplo faz com Game.Bounties, Game.Bounties.Server, Game.Bounties.Shared e Game.Bounties.Editor. Assim cada recurso compila sozinho e pode ser apagado removendo a pasta dele. Siga a mesma nomenclatura: sufixo .Server e a restrição de define de servidor para as metades de servidor, includePlatforms: Editor para as metades de editor.

#O Mirror e os seus assemblies

O weaver do Mirror processa todo assembly que referencia Mirror, então NetworkBehaviours, [SyncVar]s, [Command]s e structs NetworkMessage em Game funcionam como os do kit. Daí vêm duas coisas:

  • Versão de rede. O kit calcula um hash de todo campo sincronizado e todo tipo de mensagem (NetworkVersion), incluindo os seus. Um cliente e um servidor de mapa compilados de código diferente têm valores diferentes, e o mapa recusa o cliente com version_mismatch. Recompile os dois depois de mudar qualquer coisa que passe pela rede.
  • Ordem dos componentes. O Mirror associa os NetworkBehaviours pelo índice deles no objeto. Cliente e servidor precisam ter os mesmos componentes na mesma ordem em todo prefab de rede. Nunca adicione ou remova um NetworkBehaviour só em um tipo de build.

#Problemas comuns

Sintoma Causa Solução
The type or namespace 'Blunnyn' could not be found O script não está dentro de uma pasta com o seu assembly, então compila em Assembly-CSharp. Mova-o para dentro da pasta com Game.asmdef, ou crie o assembly ali.
GmCommands ou CentralMessages não encontrados O script está em Game, que não referencia KitARPG.Server. Mova-o para a pasta de Game.Server.
O build de cliente para com um erro de separação de builds que cita o seu assembly Um assembly .Server não tem a restrição de define, ou um assembly de cliente referencia um de servidor. Adicione UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER e faça a referência ir do assembly de servidor para o de cliente.
A sua classe de template não aparece no menu de tipos do inspector Ela não compila, é abstrata ou não é [Serializable]. Corrija os erros do Console; mantenha a classe pública, concreta e [Serializable].
version_mismatch ao entrar Cliente e servidor de mapa foram compilados de código diferente. Recompile os dois.
