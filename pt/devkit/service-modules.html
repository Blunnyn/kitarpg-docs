Módulos de serviço

Como estender os serviços Login e Central com módulos .NET seus: as interfaces de módulo, mensagens de mapa, endpoints HTTP, tabelas e migrações próprias no banco de dados, compilação e instalação, e as regras de segurança para módulos.

#O que é um módulo

Login e Central são serviços ASP.NET Core (.NET 10). Você não os edita: um jogo adiciona código a eles como módulos, bibliotecas de classes que os serviços carregam de uma pasta ao iniciar. Um módulo pode:

  • tratar mensagens dos servidores de mapa e respondê-las (Central),
  • manter as próprias tabelas no banco de dados do kit, com as próprias migrações,
  • adicionar endpoints HTTP (Login ou Central),
  • registrar serviços no contêiner de injeção de dependências.

Atualizar o kit substitui o código dos serviços, mas nunca toca os seus módulos.

Escreva um módulo do Central para dados que abrangem mapas ou personagens (rankings, eventos do mundo). Escreva um módulo do Login para recursos do lado da conta acessados por HTTP. Para o lado Unity das mensagens de mapa, veja Falar com o Central.

#O contrato

Os módulos referenciam um projeto pequeno, Services/Modules/KitARPG.Services.Modules.csproj (namespace Blunnyn.KitARPG.Services.Modules). Ele é mantido pequeno para que os módulos continuem compilando entre atualizações do kit. No pacote da Asset Store, os serviços ficam em Assets/Blunnyn/KitARPG/Services~ (descompactados pelo kit a partir de Services.zip), então o caminho é Services~/Modules/....

#IKitModule

Membro O que faz
string Name Único entre os módulos do serviço: letras, dígitos e sublinhados, até 40.
void ConfigureServices(IServiceCollection services, IConfiguration configuration) Registra serviços e o banco de dados do módulo. Roda antes de o serviço ser construído. Opcional.
void MapEndpoints(IEndpointRouteBuilder endpoints) Adiciona endpoints HTTP. Ficam abertos a qualquer um, a menos que chamem RequireAuthorization(). Opcional.

Um módulo é uma classe pública com um construtor público sem parâmetros que implementa uma destas:

Interface Serviço
ILoginModule Login
ICentralModule Central. Adiciona void OnMapLink(IMapLink link), chamado uma vez ao iniciar: registre ali todos os handlers de mensagens de mapa.

#IMapLink

Membro O que faz
IServiceProvider Services Os serviços do Central: escopos, loggers, o seu DbContext.
void On<T>(Func<MapMessage<T>, Task> handler) Trata todo T que um mapa envia, pelo nome da classe. Nomes do kit e nomes que outro módulo já pegou são recusados ao iniciar.
bool Send(string mapId, object message) Envia para um mapa. False quando ele não está conectado.
bool SendToCharacter(long characterId, object message) Envia para o mapa em que o personagem está jogando. False quando ele não está jogando.
void Broadcast(object message) Envia para todos os mapas conectados.

#MapMessage<T>

Membro O que é
string MapId O mapa que enviou.
T Message A mensagem.
void Reply(object message) Envia uma mensagem de volta para esse mapa.
bool Hosts(long characterId) True só quando esse personagem está jogando no mapa que enviou a mensagem.

Um mapa é autenticado, mas fala pelos seus jogadores. Confira Hosts(characterId) antes de agir por um personagem, para que um mapa comprometido não possa agir por jogadores que ele não tem.

#AddModuleDatabase

services.AddModuleDatabase<TContext>(configuration, name);

Registra o seu DbContext no banco de dados e no provedor do kit (Database:Provider, Database:ConnectionString), com a própria tabela de histórico de migrações __ModuleMigrations_<name>. As suas migrações rodam ao iniciar, depois das do kit, quando Database:MigrateOnStartup está ligado (o padrão).

#Criar um módulo do Central, passo a passo

#1. O projeto

Crie uma biblioteca de classes ao lado do seu projeto Unity, por exemplo Services/MyGame.Central/MyGame.Central.csproj. O arquivo de projeto do exemplo de recompensas:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <RootNamespace>Game.Bounties</RootNamespace>
    <EnableDynamicLoading>true</EnableDynamicLoading>
    <!-- The linked messages are Unity code, written without nullable annotations. -->
    <NoWarn>$(NoWarn);CS8618</NoWarn>
  </PropertyGroup>

  <ItemGroup>
    <!-- Central already has these; Private and ExcludeAssets keep copies out of the module folder. -->
    <ProjectReference Include="..\..\Modules\KitARPG.Services.Modules.csproj">
      <Private>false</Private>
      <ExcludeAssets>runtime;native</ExcludeAssets>
    </ProjectReference>
  </ItemGroup>

  <ItemGroup>
    <!-- The same message file Unity compiles. -->
    <Compile Include="$(KitFolder)DevKit/Example/Bounties/Shared/BountyBoardMessages.cs" Link="Shared/BountyBoardMessages.cs" />
  </ItemGroup>

  <Target Name="CopyToKitModules" AfterTargets="Build" Condition="'$(KitModulesDir)' != ''">
    <PropertyGroup>
      <KitModuleFolder>$([System.IO.Path]::GetFullPath('$(KitModulesDir)', '$(MSBuildStartupDirectory)'))/$(AssemblyName)</KitModuleFolder>
    </PropertyGroup>
    <ItemGroup>
      <ModuleFiles Include="$(OutDir)**/*" />
    </ItemGroup>
    <Copy SourceFiles="@(ModuleFiles)" DestinationFolder="$(KitModuleFolder)/%(RecursiveDir)" SkipUnchangedFiles="true" />
    <Message Importance="high" Text="Module copied to $(KitModuleFolder)" />
  </Target>
</Project>
  • EnableDynamicLoading faz a saída do build levar o que um plugin precisa.
  • Private=false mantém a DLL do próprio contrato fora da pasta do seu módulo, e ExcludeAssets=runtime;native mantém fora os arquivos de runtime e nativos dos pacotes que vêm por ele (EF Core, Npgsql). O seu código continua compilando contra eles; na execução, são usadas as cópias do próprio serviço.
  • $(KitFolder) vem de Services/Directory.Build.props: a pasta do kit no projeto Unity. Ligue o seu próprio arquivo de mensagens da pasta do seu jogo da mesma forma, com um caminho relativo.
  • O target CopyToKitModules copia o build para <KitModulesDir>/<AssemblyName>/ quando você passa -p:KitModulesDir=....

Adicione os pacotes de que o seu módulo precisa. Microsoft.EntityFrameworkCore e os provedores de SQLite e PostgreSQL vêm pelo contrato, só para compilar, como descrito acima.

#2. A classe do módulo

O módulo do exemplo de recompensas, que mantém um ranking de recompensas concluídas:

using Blunnyn.KitARPG.Services.Modules;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Logging;

namespace Game.Bounties;

/// <summary>Counts finished bounties per character and answers the board's ranking.</summary>
public class BountiesModule : ICentralModule
{
    public const int TopCount = 10;
    public const int MaxNameLength = 32;

    // One writer at a time, so two bounties finished together can't both insert the same row.
    readonly SemaphoreSlim writing = new(1, 1);
    IServiceScopeFactory scopes = null!;
    ILogger log = null!;

    public string Name => "Bounties";

    public void ConfigureServices(IServiceCollection services, IConfiguration configuration) =>
        services.AddModuleDatabase<BountyContext>(configuration, Name);

    public void OnMapLink(IMapLink link)
    {
        scopes = link.Services.GetRequiredService<IServiceScopeFactory>();
        log = link.Services.GetRequiredService<ILoggerFactory>().CreateLogger<BountiesModule>();
        link.On<BountyFinished>(Finished);
        link.On<BountyBoardAsk>(Ask);
    }

    async Task Finished(MapMessage<BountyFinished> m)
    {
        BountyFinished b = m.Message;
        string name = b.name?.Trim() ?? "";
        if (name.Length == 0 || name.Length > MaxNameLength || !m.Hosts(b.characterId))
        {
            log.LogWarning("Ignored a bounty from {Map} for character {Character}", m.MapId, b.characterId);
            return;
        }
        await writing.WaitAsync();
        try
        {
            using var scope = scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<BountyContext>();
            var row = await db.Hunters.FindAsync(b.characterId);
            if (row == null) db.Hunters.Add(new BountyHunterRow { CharacterId = b.characterId, Name = name, Count = 1 });
            else
            {
                row.Count++;
                row.Name = name;
            }
            await db.SaveChangesAsync();
        }
        finally
        {
            writing.Release();
        }
    }

    async Task Ask(MapMessage<BountyBoardAsk> m)
    {
        long id = m.Message.characterId;
        if (!m.Hosts(id)) return;
        using var scope = scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<BountyContext>();
        var top = await db.Hunters.AsNoTracking()
            .OrderByDescending(h => h.Count).ThenBy(h => h.CharacterId)
            .Take(TopCount)
            .Select(h => new BountyHunter { name = h.Name, bounties = h.Count })
            .ToArrayAsync();
        int mine = await db.Hunters.Where(h => h.CharacterId == id).Select(h => h.Count).FirstOrDefaultAsync();
        m.Reply(new BountyBoardList { characterId = id, top = top, mine = mine });
    }
}

Pontos para copiar:

  • Uma instância do módulo atende todos os mapas. DbContext tem escopo, então cada handler cria o próprio escopo com IServiceScopeFactory.
  • Os handlers rodam fora da thread de rede e lado a lado. Duas mensagens podem terminar em qualquer ordem, e dois handlers podem rodar ao mesmo tempo. O exemplo serializa as escritas com um SemaphoreSlim; um índice único e uma nova tentativa também funcionariam.
  • Valide cada campo (tamanhos, faixas) e confira Hosts antes de agir.
  • Registre no log as recusas com o id do mapa, para que um mapa que se comporta mal apareça no log do Central.

#3. As suas tabelas

using Microsoft.EntityFrameworkCore;

namespace Game.Bounties;

public class BountyHunterRow
{
    public long CharacterId { get; set; }
    public string Name { get; set; } = "";
    public int Count { get; set; }
}

/// <summary>The module's own table, next to the kit's in the same database.</summary>
public class BountyContext : DbContext
{
    public BountyContext(DbContextOptions<BountyContext> options) : base(options) { }

    public DbSet<BountyHunterRow> Hunters => Set<BountyHunterRow>();

    protected override void OnModelCreating(ModelBuilder model)
    {
        model.Entity<BountyHunterRow>(e =>
        {
            e.ToTable("bounty_hunters");
            e.HasKey(h => h.CharacterId);
            e.Property(h => h.CharacterId).HasColumnName("character_id").ValueGeneratedNever();
            e.Property(h => h.Name).HasColumnName("name").HasMaxLength(BountiesModule.MaxNameLength);
            e.Property(h => h.Count).HasColumnName("count");
            e.HasIndex(h => h.Count);
        });
    }
}

Regras para tabelas de módulo:

  • Nunca crie, altere nem apague as tabelas do kit. Isso é trabalho das migrações do kit, e uma atualização quebraria por causa das suas mudanças. Leia os dados do kit por mensagens dos mapas, não pelas tabelas dele.
  • Use um prefixo nas suas tabelas com o nome do seu recurso (bounty_hunters).
  • Os ids de personagem são estáveis. Use character_id como chave das linhas por personagem, como faz o exemplo. As linhas de personagens apagados ficam até você removê-las.

#4. Migrações

Gere as migrações com as ferramentas do EF Core. Elas precisam de Microsoft.EntityFrameworkCore.Design e de uma factory de tempo de design enquanto você as roda:

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;

namespace Game.Bounties;

public class BountyContextFactory : IDesignTimeDbContextFactory<BountyContext>
{
    public BountyContext CreateDbContext(string[] args) =>
        new(new DbContextOptionsBuilder<BountyContext>().UseSqlite("Data Source=design.db").Options);
}

cd Services
dotnet ef migrations add BountyHunters --project Examples/Bounties

Um único conjunto de migrações serve SQLite e PostgreSQL quando os tipos de coluna ficam por conta do provedor. Remova todo argumento type: e toda chamada HasColumnType da migração gerada, como faz o exemplo:

character_id = table.Column<long>(nullable: false),
name = table.Column<string>(maxLength: 32, nullable: false),
count = table.Column<int>(nullable: false)

AddModuleDatabase registra no log o aviso de "pending model changes" em vez de falhar por causa dele, porque os tipos do snapshot mudam entre provedores. Se você precisa de tipos específicos de um provedor, mantenha um contexto por provedor.

#5. Compilar e instalar

Cada serviço carrega os módulos do seu Modules Path (Modules:Path, padrão modules, relativo à raiz de conteúdo do serviço): uma pasta por módulo, com o mesmo nome da dll.

modules/
    Game.Bounties.Central/
        Game.Bounties.Central.dll
        (its own dependencies)
Como você roda os serviços Pasta do Login Pasta do Central
O lançador (e Play & Servers) modules/login ao lado de launcher.json (ModulesFolder em launcher.json) modules/central
Docker Compose Deploy/modules/login, montada como somente leitura Deploy/modules/central, montada como somente leitura

Compile direto na pasta:

cd Services
dotnet build Examples/Bounties -c Release -p:KitModulesDir=<launcher folder>/modules/central
dotnet build Examples/Bounties -c Release -p:KitModulesDir=../Deploy/modules/central   # Docker

No editor, launcher.json fica em UserSettings/KitARPG, então a pasta do lançador é UserSettings/KitARPG e os módulos vão em UserSettings/KitARPG/modules/central.

Reinicie o serviço. O log dele lista cada módulo: Module Bounties loaded from .../Game.Bounties.Central.dll (SHA-256 ...). Os módulos carregam uma vez, ao iniciar; para atualizar um, substitua a pasta dele e reinicie.

#Endpoints

MapEndpoints adiciona endpoints de API mínima ao serviço. Eles são públicos, a menos que chamem RequireAuthorization(), que confere o token de Login do jogador (um JWT de vida curta). O id da conta é a claim sub do token:

using System.Security.Claims;
using Blunnyn.KitARPG.Services.Modules;
using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Routing;

public class NewsModule : ILoginModule
{
    public string Name => "News";

    public void MapEndpoints(IEndpointRouteBuilder endpoints)
    {
        // Anyone, for the title screen.
        endpoints.MapGet("/api/news", () => Results.Ok(new[] { "Welcome to the open beta." }));

        // Only logged-in players.
        endpoints.MapGet("/api/news/mine", (ClaimsPrincipal user) =>
        {
            if (!long.TryParse(user.FindFirstValue("sub"), out long accountId)) return Results.Unauthorized();
            return Results.Ok(new { accountId });
        }).RequireAuthorization();
    }
}

Use o nome do seu jogo como prefixo das suas rotas para ficar longe das do kit. Valide cada entrada e limite o que cada chamada pode fazer ou ler: os endpoints ficam expostos à internet.

#Carregamento e segurança

Um módulo roda dentro do serviço com todos os direitos dele, como o próprio código do kit. Só o operador do servidor instala módulos.

  • Só a pasta configurada é lida, nunca um caminho vindo de uma requisição ou de um mapa.
  • Modules Allow (Modules:Allow, ou Modules__Allow__0, Modules__Allow__1 como variáveis de ambiente) lista os nomes de dll permitidos. Com ele definido, qualquer outro módulo para o serviço.
  • O log nomeia cada módulo com o arquivo e o SHA-256. O assembly é carregado dos mesmos bytes que foram usados no hash.
  • Falha fechada: um módulo que falha ao carregar, configurar os serviços, registrar os handlers de mensagens, mapear os endpoints ou migrar para o serviço com o erro. Uma dll solta na pasta de módulos, ou uma pasta sem a sua dll, também o para.
  • No Docker, as pastas de módulos são montadas como somente leitura.
  • Cada módulo recebe o próprio contexto de carregamento. Os assemblies que o serviço já tem (o kit, ASP.NET Core, EF Core, Npgsql) sempre vêm do serviço, então as interfaces e entidades do seu módulo são os mesmos tipos que o serviço vê; todo o resto vem da pasta do módulo.

#Testes

AddKitModule registra um módulo criado em código, sem pasta, para testes ou para um host seu:

services.AddKitModule<ICentralModule>(new BountiesModule(), configuration);

Os próprios testes do kit (Services/Tests/ModuleTests.cs) rodam o Central com módulos de teste dessa forma.

#Erros comuns

  • Copiar o contrato ou o EF Core para a pasta do módulo. Use Private=false e ExcludeAssets na referência.
  • Uma classe de módulo sem construtor público sem parâmetros. Ela não pode ser criada.
  • Tratar um nome de mensagem do kit. O Central se recusa a iniciar.
  • Agir sem Hosts. Um mapa poderia agir por jogadores que ele não tem.
  • Tipos de coluna nas migrações. Quebram no outro provedor.
  • Endpoints sem RequireAuthorization() que devolvem dados privados.
  • Trabalho longo em um handler sem escopo, ou um mesmo DbContext compartilhado entre handlers.
