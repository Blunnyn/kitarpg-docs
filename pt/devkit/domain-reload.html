Play sem domain reload

Por que o estado estático no seu código precisa ser reiniciado à mão, quando roda cada método de inicialização e os padrões que o kit usa para que todo Play comece limpo.

#O que é o domain reload

Quando você aperta Play, o Unity pode recarregar o domínio de scripts: descartar todos os assemblies carregados e todos os valores estáticos e carregá-los de novo. Isso faz cada Play começar limpo, e leva muitos segundos em um projeto do tamanho do KitARPG.

O projeto do kit desliga isso: Project Settings > Editor > Enter Play Mode Settings tem Reload Domain desligado (as cenas continuam sendo recarregadas). O Play então começa em um ou dois segundos. O preço é que campos estáticos mantêm os valores do último Play:

  • uma lista estática ainda guarda as entradas adicionadas da última vez,
  • um evento estático ainda tem os inscritos do último Play, que apontam para objetos destruídos,
  • um Local estático ainda aponta para o jogador local anterior,
  • um contador estático continua contando.

As builds sempre começam limpas. Esses problemas só aparecem no editor, e só a partir do segundo Play, o que os torna fáceis de deixar passar. Seu projeto pode ter Reload Domain ligado; escreva seu código para que funcione de qualquer jeito.

#Os momentos de inicialização

[RuntimeInitializeOnLoadMethod] roda um método estático em um momento fixo de cada Play (e de cada inicialização de build):

Tipo de carga Quando Use para
SubsystemRegistration Primeiro, antes de tudo Limpar seus próprios estáticos.
AfterAssembliesLoaded Depois que todos os assemblies foram carregados Se inscrever em eventos estáticos de outras classes; adicionar entradas de menu e opções.
BeforeSplashScreen Antes da tela de abertura (raramente necessário)
BeforeSceneLoad Antes de a primeira cena carregar Instalar fórmulas e outras substituições.
AfterSceneLoad Depois que a primeira cena carregou Coisas que precisam de objetos da cena: KitNetworkManager.Instance, comandos de GM.

Dentro de um mesmo tipo de carga, o Unity não define a ordem entre métodos de classes diferentes. As regras do kit vêm disso.

#As regras do kit

  1. Toda classe limpa seus próprios estáticos em SubsystemRegistration. Campos, eventos, coleções e caches que guardam estado voltam aos valores iniciais em um método normalmente chamado ResetStatics.
  2. Inscreva-se nos eventos estáticos de outra classe em AfterAssembliesLoaded ou depois. Essa classe os limpa em SubsystemRegistration; se você se inscrevesse na mesma fase, sua inscrição poderia ser apagada depois de feita.
  3. As listas que o kit preenche com suas próprias entradas são refeitas em SubsystemRegistration (ItemMenu.Entries, PlayerMenu.Entries, ClientOptions.All, os comandos de GM). Adicione as suas depois.
  4. As fórmulas do kit voltam às dele em SubsystemRegistration (GameInstance.Formula, GameInstance.Combat). Instale as suas em BeforeSceneLoad.
  5. Uma classe que registra algo próprio em SubsystemRegistration limpa e registra no mesmo método, para que a ordem com as outras classes não importe (GmCommands).
  6. Buffers de trabalho esvaziados a cada uso e caches que continuam válidos não são limpos. Uma List estática usada como espaço de rascunho, ou um valor calculado que não pode mudar durante a sessão, pode ficar.

As tabelas dos modos de jogo (GameModes) são uma exceção: nunca são limpas, então os assemblies de modo podem se registrar a partir de SubsystemRegistration em qualquer ordem.

#O padrão para o seu código

using System;
using System.Collections.Generic;
using Blunnyn.KitARPG.Net;
using UnityEngine;

namespace Game
{
    public static class Kills
    {
        // State of this class.
        static readonly Dictionary<long, int> counts = new Dictionary<long, int>();
        public static event Action<PlayerCharacter, int> ServerCounted;

        // 1. Clear own state first.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
        static void ResetStatics()
        {
            counts.Clear();
            ServerCounted = null;
        }

        // 2. Subscribe to the kit's events after the kit cleared them.
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]
        static void Hook()
        {
            Monster.ServerKilled -= OnKilled;
            Monster.ServerKilled += OnKilled;
        }

        static void OnKilled(Monster monster, PlayerCharacter killer)
        {
            if (killer == null || killer.State == null) return;
            counts.TryGetValue(killer.State.id, out int n);
            counts[killer.State.id] = ++n;
            ServerCounted?.Invoke(killer, n);
        }
    }
}

-= antes de += torna a inscrição segura mesmo que o método rode duas vezes. Métodos com nome (não lambdas) tornam o -= possível.

#Estáticos em componentes

Um NetworkBehaviour ou MonoBehaviour com membros estáticos segue a mesma regra:

public class PlayerPet : NetworkBehaviour
{
    public static PlayerPet Local { get; private set; }
    public static event Action<string> Told;

    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    static void ResetStatics()
    {
        Local = null;
        Told = null;
    }

    public override void OnStartAuthority() => Local = this;

    public override void OnStopAuthority()
    {
        if (Local == this) Local = null;
    }
}

Os templates de sistemas do jogador e de dados salvos já fazem isso.

#Coisas que vivem em objetos da cena

Eventos em objetos que são criados de novo a cada Play (o gerenciador de rede, uma janela no HUD) não precisam ser limpos: o objeto antigo some junto com seus inscritos. Por isso os templates do kit se inscrevem em KitNetworkManager.ServerStarted em AfterSceneLoad sem cancelar a inscrição.

#Caches preguiçosos

static AttributeData toughness;

public static AttributeData Toughness
{
    get
    {
        if (toughness == null && GameInstance.Database != null) GameInstance.Database.TryGet("toughness", out toughness);
        return toughness;
    }
}

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
static void ResetStatics() => toughness = null;

Um cache de um asset sobrevive ao Play sem problema se o asset não pode mudar, mas limpá-lo não custa nada e cobre edições feitas entre um Play e outro.

#Lista de verificação

Para cada static no seu código, pergunte:

Ele é Faça
Um valor que muda durante o jogo (um contador, um Local, um dicionário de jogadores) Reinicie em SubsystemRegistration.
Um evento estático da sua classe Defina como null em SubsystemRegistration.
Uma inscrição no evento estático de outra classe Faça em AfterAssembliesLoaded ou depois, com -= antes.
Uma entrada em uma lista do kit (menus, opções, comandos, verificações do validador no editor) Adicione depois que o kit preencheu a lista.
Um valor const ou static readonly que nunca muda Nada.
Um buffer de rascunho limpo antes de cada uso Nada.

Os estáticos só de editor (verificações do validador, páginas) seguem o ciclo de vida do próprio editor, não o Play: registre-os a partir de [InitializeOnLoadMethod] e remova antes de adicionar (veja Extensões do editor).

#Testando

  1. Aperte Play, faça o que sua funcionalidade faz, pare.
  2. Aperte Play de novo e faça de novo.
  3. Fique atento a mensagens duplicadas, eventos disparando duas vezes, contagens que não começaram em zero e MissingReferenceException vindos de objetos destruídos.

O próprio kit foi testado assim: dois Plays seguidos em um jogador dão os mesmos inscritos, comandos e entradas de menu.

#Erros comuns

  • Se inscrever em SubsystemRegistration. O kit pode limpar o evento depois de você. Inscreva-se em AfterAssembliesLoaded ou depois.
  • Limpar o evento de outra classe. Cada classe limpa só os seus.
  • Limpar seu evento em um método de inicialização e se inscrever nele em outro do mesmo tipo. A ordem não é definida: limpe em SubsystemRegistration e se inscreva em uma fase posterior.
  • Lambdas em += que rodam a cada Play em um evento que não é limpo.
  • Referências estáticas a objetos da cena sem reinício: viram objetos destruídos que se comparam como iguais a null, mas ainda ocupam memória.
