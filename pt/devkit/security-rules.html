Regras de segurança

As regras que protegem um jogo online feito com KitARPG contra clientes modificados, e como segui-las no seu próprio código: autoridade do servidor, ritmo de pedidos, identidade, validação, itens e moedas, o que os clientes recebem, o que as builds levam e os serviços.

#Considere o cliente hostil

Online, os jogadores rodam o seu cliente nas próprias máquinas. Qualquer um pode modificá-lo ou escrever um programa que fale o seu protocolo de rede. Um cliente assim pode:

  • chamar qualquer [Command] e enviar qualquer mensagem de rede, com quaisquer argumentos, tantas vezes quanto a conexão permitir,
  • ler todo valor que o seu servidor envia a ele,
  • pular toda verificação que o seu código de cliente faz,
  • alterar a própria memória: barras de vida, timers de recarga, botões que estavam ocultos.

Ele não pode mudar o que o servidor decide. Esse é o modelo inteiro: o cliente pede, o servidor decide. Todas as regras abaixo vêm disso.

No modo um jogador não há outros jogadores para proteger, mas o mesmo código roda ali, então seguir as regras não custa nada.

#1. O servidor decide tudo o que importa

Dano, cura, itens, ouro, experiência, progresso de missões, recargas, posições, quem pode ver o quê: tudo isso é decidido por código de servidor (o servidor de mapa online, o host no modo um jogador). O código de cliente mostra resultados e envia pedidos.

Fica no servidor Fica no cliente
Métodos Server..., corpos de [Command], handlers de mensagens no NetworkServer Janelas, menus, câmera, input, sons, efeitos
Apply dos efeitos de habilidade, Use dos efeitos de item, Run das ações, Run das opções de NPC Tooltips (Describe), rótulos
Fórmulas Configurações em PlayerPrefs

Uma verificação feita pelo cliente (deixar um botão cinza, um círculo de alcance) é uma cortesia ao jogador. Faça-a de novo no servidor.

#2. Limite o ritmo de todo pedido

CommandPacing (namespace Blunnyn.KitARPG.Net) dá a cada conexão um orçamento compartilhado por todos os componentes e handlers: 30 pedidos por segundo com rajada de 60. Uma conexão muito acima disso é desconectada com KickReasons.Flooding. Pedidos que geram trabalho para o Central (correio, guilda, amigos, denúncias e qualquer coisa sua que termine em CentralMessages.Send) também gastam de um orçamento mais rígido: 2 por segundo, rajada de 10.

[Command]
void CmdDoThing(int value)
{
    if (!CommandPacing.Allow(connectionToClient)) return;
    ...
}

static void OnRequest(NetworkConnectionToClient conn, MyRequest message)
{
    if (!CommandPacing.AllowCentral(conn)) return;   // this one reaches Central
    ...
}

Pedidos recusados também contam, então um cliente que continua insistindo afunda até ser expulso. A conexão do próprio host no modo um jogador nunca é limitada.

#3. A identidade vem da conexão

O servidor sabe quem enviou um pedido: o objeto de jogador da conexão (conn.identity, ou o próprio jogador do componente dentro de um [Command]). Nunca coloque "quem eu sou" em um pedido.

// Wrong: any client can claim any id.
public struct GiftRequest : NetworkMessage { public long fromCharacterId; public string toName; }

// Right: the sender is the connection's player.
public struct GiftRequest : NetworkMessage { public string toName; }

static void OnGift(NetworkConnectionToClient conn, GiftRequest message)
{
    if (conn.identity == null || !conn.identity.TryGetComponent(out PlayerCharacter from)) return;
    ...
}

O mesmo vale para os módulos do Central: uma mensagem leva um id de personagem, e o módulo verifica m.Hosts(characterId) para que um mapa só possa falar pelos jogadores que ele hospeda.

#4. Valide todo argumento

Argumento Verificação
Strings Não nulas, limites de tamanho, PlayerText.Clean antes de guardar ou mostrar a outros
Inteiros Faixas, nunca negativos onde não faz sentido, long.MinValue e overflow (compare com os limites sem somar antes)
Floats e vetores float.IsFinite em cada componente, distâncias limitadas
Ids de dados do jogo Existem no banco de dados (GameInstance.Database.TryGet)
Casas e índices Dentro do contêiner; a casa contém o que o cliente diz
Coisas no mundo Resolvidas no servidor e ao alcance (veja abaixo)
Arrays Limites de tamanho antes de percorrer

Overflow é um risco real: o kit já teve um bug em que uma quantia grande de ouro mais a postagem dava a volta e virava um número pequeno. Compare amount > limit - fee, não amount + fee > limit.

#5. Resolva o mundo no servidor

O cliente nomeia Resolva com Depois verifique
Um monstro ou jogador (por netId) Fighters.TargetFor(conn, player, netId): null para qualquer coisa fora da visão desse cliente, inimigos invisíveis, monstros de evento gerados para outra pessoa Fighters.Enemies, distância, Sight.Clear
Um NPC (por id) Npc.TryFind(id, out npc) npc.InReach(player.transform.position)
Um drop Rewards.Instance.Pickup(player, id) (verifica o alcance sozinho)
Um jogador pelo nome PlayerCharacter.ServerFind(name) (este mapa) Distância, consentimento, regras
Um ponto no chão Limite a distância, NavMesh.SamplePosition, Sight.Clear

#6. Mova itens e moedas pelo kit

Os itens têm um único dono o tempo todo, e toda movimentação entre donos é uma transação no Central. O seu código mantém isso verdadeiro passando pelo kit:

  • Bolsa e equipamento: PlayerInventory (Give, GiveOrBank, ServerReceive, ServerReceiveGold, AddGold, AddCurrency), ou IPlayerActor (GiveItem, TakeItem, AddCurrency).
  • Entre jogadores: a troca, o correio e o mercado do kit. Não construa sua própria transferência com dois salvamentos separados; uma queda entre eles duplica ou perde itens.
  • Moedas premium pertencem à conta e só são gastas na loja do jogo, cujo serviço verifica o saldo. AddCurrency com uma moeda premium a concede pelo serviço da loja; retirá-la é recusado.
  • Registre o que o suporte vai precisar com GameLog.Write("mygame.kind", player, ...). As linhas vão para a tabela game_logs e os moderadores as leem com /logs.

#7. Envie aos clientes só o que eles podem saber

  • Um NetworkBehaviour com Sync Mode Observers envia seus valores sincronizados a todo cliente que vê o jogador. Use Owner para dados privados (bolsas, missões, marcas, seus próprios sistemas).
  • [ClientRpc] chega a todo observador; [TargetRpc] só ao dono.
  • PlayerData nunca sai do servidor. Sincronize só o que a interface precisa.
  • Não envie posições, vida ou stats de coisas que um cliente não pode ver; o gerenciamento de interesse do kit já limita o que cada cliente recebe.
  • Texto escrito por jogadores é mostrado com PlayerText.NoTags (ou limpo com PlayerText.Clean no servidor), para que ninguém injete tags de TextMeshPro na tela de outros jogadores.

#8. Mantenha o código de servidor fora das builds de cliente

Código só de servidor vai em assemblies com a restrição UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER (Game.Server). Assim os clientes online não levam comandos de GM, mensagens do Central nem as suas regras de servidor, e por isso não podem lê-los nem chamá-los.

Antes de cada build, BuildSeparation para uma build de cliente que levaria código de servidor, o salvamento do modo um jogador ou ferramentas de teste. Os clientes de release são compilados com IL2CPP (a verificação exige isso), o que os torna muito mais difíceis de ler. Nunca coloque chaves, senhas ou strings de conexão em nada que uma build de cliente inclua: o servidor de mapa lê a chave do Central de KITARPG_CENTRAL_KEY, e a chave da loja de KITARPG_SHOP_KEY.

Veja Assemblies e Builds.

#9. Os comandos da equipe são auditados

Os comandos de GM ficam em assemblies só de servidor, verificam o nível do jogador antes de rodar, e todo uso de nível de equipe (nível 2 ou mais) é gravado na auditoria de GM e no registro do jogo. Quando a auditoria não pode ser gravada, os comandos da equipe ficam em pausa. Os seus comandos ganham tudo isso de GmCommands.Register. Limite o que eles distribuem com GmCommands.MaxItems, MaxGold e os outros limites. Veja Comandos de GM em código.

#10. Os serviços

  • Módulos do Central tratam o que os mapas enviam por seus jogadores: valide todo campo, verifique m.Hosts(characterId) e registre as recusas com o id do mapa.
  • Endpoints HTTP em módulos são públicos a menos que chamem RequireAuthorization(). Leia a conta da claim sub do token, nunca de um parâmetro.
  • Os módulos rodam com todos os direitos do serviço. Só o operador do servidor os instala; Modules:Allow limita quais dlls podem carregar. Veja Módulos de serviço.
  • Nunca altere as tabelas do kit a partir de um módulo.

#Uma lista de revisão

Antes de lançar um recurso, passe por cada pedido que um cliente pode enviar:

  • [ ] O ritmo é limitado com CommandPacing.Allow (ou AllowCentral).
  • [ ] O remetente vem da conexão, não da mensagem.
  • [ ] Toda string, número, vetor e array é verificado.
  • [ ] Todo id é buscado no servidor; todo objeto do mundo é resolvido com os helpers do kit e verificado quanto a alcance e visão.
  • [ ] Itens, ouro e moedas passam por PlayerInventory ou IPlayerActor.
  • [ ] A resposta e qualquer valor sincronizado não revelam nada que o jogador não deveria saber.
  • [ ] O código só de servidor está em um assembly .Server.
  • [ ] Tudo o que o suporte vai perguntar está no registro do jogo.
