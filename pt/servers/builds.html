Servidores e implantação

Builds

Como gerar a build de cada parte de um jogo online do KitARPG: o cliente que os jogadores instalam, os servidores de mapa para o seu computador e para Linux, o jogo de um jogador (single player) e os serviços .NET. Também cobre as verificações pelas quais toda build passa e o que cada build pode levar.

#Os menus de build

Todos ficam em KitARPG > Starter. Cada um pega as cenas dos mapas do seu Game Database, então um mapa novo entra em todas as builds sem passos extras. As builds vão para uma pasta Builds/Starter ao lado da pasta do seu projeto Unity (o servidor Linux vai para Deploy/builds/starter).

Build Windows Client O cliente MMO para Windows Builds/Starter/WindowsClient/KitARPG.exe IL2CPP (definido pelo menu) Nenhum
Build Mac Server Um servidor de mapa que o lançador roda em um Mac Builds/Starter/MacServer/KitARPGServer.app Configuração do projeto KITARPG_SERVER
Build Windows Server Um servidor de mapa que o lançador roda no Windows Builds/Starter/WindowsServer/KitARPGServer.exe Configuração do projeto KITARPG_SERVER

Ao lado de cada build, o menu escreve KitARPGScenes.txt com as cenas que ela leva. O Play & Servers o lê para avisar quando falta a cena de um mapa em um servidor de mapa.

Os servidores de Mac e Windows são builds normais de jogador com o código de servidor compilado, iniciadas com -batchmode -nographics. Elas não precisam do módulo Dedicated Server. O servidor Linux é uma build Dedicated Server de verdade: menor, sem gráficos nenhum.

#O que toda build verifica primeiro

  1. Cenas. Cada mapa do Game Database indica sua cena. Se faltar um arquivo de cena, a build para e diz qual. A cena Title é sempre a primeira.
  2. Project Check. O validador roda antes de cada build e a interrompe se houver erros. Você pode desligar isso no Project Check com Stop builds on errors. Veja Project Check.
  3. Separação de builds. O kit verifica quais assemblies a build compilaria e a interrompe quando algum não pertence a ela. Essa verificação roda em toda build, seja pelos menus do kit, por File > Build Profiles ou por um script, e não pode ser desligada.
  4. Modo. A build leva KitARPGSettings com o modo para o qual foi gerada (online ou um jogador). Depois, o menu devolve o modo do seu editor.
  5. Versão de rede. Um hash de tudo o que o Mirror envia é gravado na build. Veja Versão de rede.

A separação de builds interrompe uma build quando:

  • um cliente MMO levaria código de servidor ou o save local, ou é gerado com KITARPG_SERVER ou KITARPG_SINGLEPLAYER;
  • um assembly que vai em um cliente MMO referencia um assembly de servidor;
  • um servidor de mapa levaria KitARPG.Local;
  • uma build de release levaria ferramentas de teste;
  • um assembly de editor ou de teste entraria em qualquer build;
  • uma build de um jogador não tem o código de servidor ou o save local;
  • um cliente MMO de release é gerado com Mono;
  • um cliente MMO de release aponta para o Login ou a Central por HTTP simples em qualquer lugar que não seja este computador.

Ela avisa (e segue em frente) para um cliente de desenvolvimento ou um cliente gerado com Mono em desenvolvimento.

KitARPG > Check Build Separation mostra a tabela do seu projeto: quais assemblies entram em cada tipo de build.

O seu próprio código só de servidor vai em um assembly cujo nome termina em .Server, com a restrição de define UNITY_SERVER || UNITY_EDITOR || KITARPG_SERVER (Create > KitARPG > Scripts > Game Server Assembly cria um). Veja Assemblies.

#Gerar o cliente MMO

  1. Defina Login Url e Central Url em Assets/Settings/Resources/KitARPGSettings.asset com os seus endereços HTTPS públicos, por exemplo https://login.mygame.com e https://central.mygame.com. Veja Configuração.
  2. Escolha o mesmo modo de controle com que os servidores de mapa são gerados (Game Settings). Um cliente em outro modo é recusado com mode_mismatch.
  3. KitARPG > Starter > Build Mac Client ou Build Windows Client.
  4. Gere os servidores de mapa a partir do mesmo código, para que as versões de rede coincidam.

Os clientes de release são sempre IL2CPP: o código deles vai como código nativo em vez de DLLs que qualquer um pode ler e alterar. A Unity gera um player IL2CPP de Windows só no Windows, e um de Mac só em um Mac.

Um cliente de release ignora os argumentos -login, -centralUrl e -mode, e fala com o Login e a Central somente por HTTPS.

#Gerar o servidor de mapa Linux

O servidor de mapa que roda no Docker ou em um host Linux.

Antes da primeira build, instale no Unity Hub para o seu editor:

  • Linux Dedicated Server Build Support;
  • IL2CPP para Linux;
  • em um Mac, o pacote com.unity.toolchain.macos-arm64-linux (Package Manager), que permite a um Mac compilar para Linux.

Depois:

  1. Salve as suas cenas e aplique as atualizações do kit pendentes (o Overview as lista), para que o servidor as tenha.
  2. KitARPG > Starter > Build Linux Server.
  3. A build fica em Deploy/builds/starter/: KitARPGServer.x86_64, KitARPGServer_Data, GameAssembly.so, UnityPlayer.so e uma pasta KitARPGServer_BackUpThisFolder_ButDontShipItWithYourGame com os símbolos de depuração do IL2CPP. Guarde os símbolos para ler relatórios de falhas; a imagem Docker os deixa de fora.

A imagem tem cerca de 72 MB. O servidor roda sem tela e lê o mapa, a porta e o endereço da Central da linha de comando (veja Configuração). Uma build atende todos os mapas; cada contêiner a roda com um -map diferente.

#Gerar para o seu próprio computador

Build Mac Server ou Build Windows Server gera o servidor de mapa que o lançador e o Play & Servers iniciam. Gere de novo depois de mudar cenas, código de servidor ou qualquer coisa que trafegue pela rede. O Play & Servers avisa quando ele é mais antigo que os serviços em execução.

#Builds de um jogador

Build Mac Single Player e Build Windows Single Player geram um jogo que hospeda o próprio mundo e salva em um arquivo no computador do jogador. Não precisam de serviços. Veja Início rápido: um jogador.

#O cliente de teste

Build Mac Test Client gera um cliente com as ferramentas de teste do kit: login automático, o smoke test e -smoketest systems, em que dois clientes jogam os sistemas sociais e de economia contra servidores reais. Ele usa Mono para uma build rápida e uma pasta própria, para não ser confundido com o cliente de release.

KITARPG_DEV é a única forma de as ferramentas de teste entrarem em uma build: uma build de desenvolvimento comum não as leva. Nunca entregue o cliente de teste aos jogadores.

#Versão de rede

Toda build leva um hash curto de tudo o que trafega pelo Mirror: campos sincronizados, listas e dicionários sincronizados e mensagens de rede, com os campos dos tipos dentro deles. O cliente o envia com o ticket, e um servidor de mapa gerado a partir de outro código o recusa com version_mismatch ("The game and the server are different versions") em vez de falhar no meio da leitura de um componente.

  • O valor é calculado quando a build começa e guardado como um recurso temporário em Assets/KitARPGBuild, que é apagado depois da build.
  • O editor o calcula a partir do próprio código.
  • Se um dos lados não tiver valor, eles não são comparados. Serializadores escritos à mão não fazem parte do hash.

Quando você mudar um campo sincronizado ou uma mensagem, gere de novo tanto o cliente quanto os servidores de mapa.

#Gerar pela linha de comando

Cada menu é um método estático que você pode chamar de uma máquina de build:

Unity -batchmode -quit -projectPath MyGame \
  -executeMethod Blunnyn.KitARPG.Editor.StarterBuilder.BuildLinuxServer

#Gerar os serviços

Os serviços .NET são compilados com o SDK do .NET 10.

Objetivo Comando (a partir da pasta Services)
Compilar tudo para o lançador dotnet build
Rodar os testes dotnet test
Publicar um serviço para um servidor dotnet publish Login -c Release -o out/Login
Imagens Docker docker compose build a partir de Deploy (veja Docker)

Antes de publicar o Login ou gerar a imagem dele, rode KitARPG > Export Game Data for Services. Ele escreve Services/Login/gamedata.json, que a build copia para junto do serviço. Sem ele, o Login não consegue criar personagens.

#Erros comuns

  • "KitARPG stopped the OnlineClient build." O Console lista cada problema com a sua correção. Geralmente é código de servidor em um assembly de cliente, ou uma Login Url em HTTP simples.
  • "The game and the server are different versions." O cliente e o servidor de mapa foram gerados a partir de códigos diferentes. Gere de novo o que for mais antigo.
  • Jogadores que trocam de mapa voltam para o login. Falta a cena desse mapa no servidor de mapa. Gere-o de novo; o Play & Servers diz qual cena falta.
  • A build Linux falha em um Mac. Falta o pacote de toolchain do Linux ou o módulo Linux Dedicated Server.
  • O cliente Windows não compila em um Mac. O IL2CPP para Windows só compila no Windows. Gere-o em uma máquina Windows.
