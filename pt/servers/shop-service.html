Servidores e implantação

Serviço Shop

O Shop é um serviço .NET opcional que roda a loja premium do jogo: o catálogo, os saldos premium de cada conta, as compras e os presentes, e os pagamentos com dinheiro real. Esta página cobre como ele se encaixa no resto, o arquivo de catálogo, cada endpoint e configuração, os pagamentos, e como rodá-lo localmente e em produção.

Para o lado do jogador (a janela da loja, as moedas premium), veja Loja premium. Para editar ofertas no editor, veja Página Shop.

#Como ele se encaixa

  • Separado e opcional. A Central não sabe nada do Shop. Sem ele, o jogo roda normalmente e o botão da loja não aparece.
  • Só online. Jogos de um jogador não têm loja.
  • Os jogadores nunca chegam a ele. A janela da loja pede ao servidor de mapa; o servidor de mapa chama a API interna do Shop com a sua chave (X-Shop-Key). Só os webhooks de pagamento vêm de fora, pelo Caddy.
  • Mesmo banco de dados. Ele usa o banco de dados que o Login e a Central usam. O Login precisa ter iniciado uma vez para que o catálogo items esteja preenchido.
  • As compras viajam pelo correio. Uma compra grava a cobrança e uma carta com os itens comprados em uma única transação. Os servidores de mapa levam as cartas da loja para a bolsa na hora (a menos que Shop Auto Take (shopAutoTake) esteja desligado em Game Settings); se a bolsa e o banco estiverem cheios, a carta espera na caixa de correio e o jogador é avisado.
Quem Fala com o Shop com Por
Servidores de mapa API interna, X-Shop-Key HTTP na rede privada, porta 5300
Provedores de pagamento Webhooks, assinados HTTPS pelo Caddy no domínio do Login
Você e o editor API de administração, X-Admin-Key HTTP em 127.0.0.1:5300, ou um túnel SSH

#Rodar o Shop

#No seu computador, pelo editor

Abra a página Shop da janela KitARPG, ligue a loja e pressione Start the shop. O editor roda o lançador com --headless --shop-only, com chaves criadas para este computador e o catálogo em UserSettings/KitARPG/shop-conf.json. Os mapas em Play o encontram sozinhos. Veja Página Shop.

#Com o lançador

Marque Premium shop na janela do lançador, ou defina ShopEnabled e ShopAutoStart no launcher.json. O Shop inicia com o Login e a Central na porta ShopPort (5300), e os mapas que a Central inicia recebem o endereço e a chave dele. Veja Lançador.

#À mão, para desenvolvimento

cd Services
ASPNETCORE_ENVIRONMENT=Development \
Database__ConnectionString="Data Source=/full/path/to/kitarpg.db" \
dotnet run --project Shop          # http://localhost:5300

Em Development, a chave dos mapas é dev-shop-key e a chave de administração é dev-shop-admin-key (appsettings.Development.json). Aponte-o para o mesmo arquivo SQLite do Login e da Central.

#No Docker Compose

docker compose --profile shop up --build -d

Defina primeiro KITARPG_SHOP_KEY e KITARPG_SHOP_ADMIN_KEY em Deploy/.env. Veja Docker.

#Como os servidores de mapa o encontram

O servidor de mapa lê O que é
-shop <url> ou KITARPG_SHOP_URL O endereço do Shop, por exemplo http://shop:5300
-shopKey <key> ou KITARPG_SHOP_KEY Uma das chaves dos mapas do Shop

No editor, um mapa em Play sem esses valores usa as configurações da página Shop (UserSettings/KitARPG/launcher.json). Um servidor de mapa compilado recusa um endereço http:// simples em um IP público, já que a chave cruzaria a internet legível: use https:// ou um endereço privado.

#O arquivo de catálogo

shop-conf.json, em Shop:CatalogPath (relativo à pasta do serviço, a menos que seja absoluto). Um exemplo vem ao lado do serviço; se o arquivo configurado não existir, o primeiro início copia o exemplo para lá.

{
  "mailSender": "Shop",
  "mailDays": 30,
  "products": [ { "id": "gems_500", "currency": "gems", "amount": 550 } ],
  "offers": [
    {
      "id": "potion_bundle", "name": "Potion Bundle", "description": "Twenty of each.",
      "category": "Supplies", "icon": "", "image": "", "banner": "", "badge": "Sale", "order": 0,
      "currency": "gems", "price": 60,
      "items": [ { "itemId": "health_potion", "amount": 20 }, { "itemId": "mana_potion", "amount": 20 } ],
      "startsAt": "", "endsAt": "2026-12-31T23:59:59Z", "perAccount": 0, "giftable": true, "hidden": false
    }
  ]
}

#Nível superior

Campo O que faz Padrão
mailSender Nome do remetente nas cartas de compra Shop
mailDays Dias que uma carta de compra fica na caixa de correio 30
products O que cada produto pago com dinheiro real dá (abaixo) Vazio
offers O que a loja vende por moeda premium (abaixo) Vazio

#Ofertas

Campo O que faz Padrão
id Id único, de até 64 caracteres. Nunca o mude depois de vendido: os limites de compra e o histórico o usam Obrigatório
name, description O que os jogadores leem Vazio
category A entrada sob a qual aparece no lado esquerdo da loja Featured
icon Item cujo ícone o cartão mostra. Vazio usa o do primeiro item Vazio
image Chave da imagem do cartão e do detalhe no Shop Art do jogo. Vazio desenha o ícone Vazio
banner Chave de uma imagem larga. As ofertas que têm uma se revezam no topo da loja Vazio
badge Fita no cartão, como New ou Sale, de até 24 caracteres Vazio
order Menor vem primeiro quando ordenado por relevância 0
currency A moeda premium que ela custa Obrigatório
price Preço, acima de 0 e até 1.000.000.000.000 Obrigatório
items itemId e amount de cada item que ela dá. Pelo menos um Obrigatório
startsAt, endsAt UTC, ISO 8601 (2026-12-01T00:00:00Z). Vazio é sempre Vazio
perAccount Vezes que uma conta pode comprá-la. 0 é sem limite 0
giftable Pode ser comprada como presente para outro personagem true
hidden Mantida para o histórico, mas não é mais vendida false

#Produtos

Cada id de produto pago com dinheiro real (o que o seu provedor de pagamentos envia) dá uma quantidade de uma moeda.

Campo O que faz
id Id do produto, único, de até 64 caracteres
currency A moeda premium que ele dá
amount Quanto, de 1 a 1.000.000.000.000

#Verificações e recarga

  • Cada oferta e produto é verificado: id, moeda, preço, datas (ISO 8601, terminando depois de começar), tamanho da fita e das chaves de imagem, pelo menos um item com quantidade, sem ids repetidos, e cada item presente e não aposentado na tabela items.
  • Uma oferta ou produto inválido é registrado no log e deixado de fora. Isso nunca para o serviço. Se a tabela items estiver vazia, a verificação de itens é pulada com um aviso.
  • O arquivo é lido de novo meio segundo depois de mudar, e com POST /api/shop/admin/reload. Um arquivo que não pode ser interpretado mantém o último catálogo válido.
  • O catálogo tem uma version, um hash curto das ofertas à venda, para que os mapas saibam quando buscá-lo de novo.

#Como funciona a compra

  1. O jogador escolhe uma oferta na janela da loja. O servidor de mapa cria as cópias dos itens (com os bônus aleatórios delas) e as envia com o id da oferta para /api/shop/internal/buy.
  2. O Shop cobra o preço do próprio catálogo, nunca um vindo do mapa, e confere as cópias com a oferta: mesmos itens, mesmas quantidades, ids únicos, conhecidos pelo catálogo de itens.
  3. Ele verifica se a oferta está à venda, o limite por conta e o saldo.
  4. Em uma única transação, uma compra por vez, ele grava a cobrança em currency_ledger e uma carta com as cópias, de mailSender, marcada com Kind = shop, com o assunto From the shop: <offer> (ou A gift from <buyer>).
  5. O mapa leva a carta para a bolsa; a Central apaga uma carta da loja assim que ela é retirada.
  6. A compra é gravada em game_logs como shop.premium_buy ou shop.premium_gift.

As recusas (moeda insuficiente, limite atingido, fora de venda, cópias erradas) voltam como uma resposta normal com ok: false e uma mensagem para o jogador.

  • Presentes. A oferta precisa ser giftable. O destinatário é encontrado pelo nome do personagem e não pode ser o comprador.
  • Concessões. Os comandos de GM (/currency gems 100 Name) e as recompensas do jogo usam a concessão interna. Uma referência enviada por um mapa é guardada como map:<reference>; sem uma, vira grant:<guid>, para que as concessões nunca colidam com pagamentos.

#O livro-razão

Cada mudança em um saldo é uma linha de currency_ledger: conta, moeda, variação, motivo, oferta, detalhe e uma referência única. O saldo é a soma das linhas. A referência única faz com que um pagamento, uma concessão ou um webhook repetido conte uma vez só.

Motivo Quando
shop.buy Uma compra ou um presente
premium.topup Um webhook de pagamento
premium.refund Um webhook de reembolso
gm.grant Uma concessão de GM ou de administração
game.reward Uma recompensa do jogo, como uma missão

#API interna

Para os servidores de mapa. Cabeçalho X-Shop-Key com uma de Shop:MapKeys ou KITARPG_SHOP_KEY. Os corpos e as respostas são as classes compartilhadas em ShopMessages.cs.

Método Rota Corpo → resposta
GET /api/shop/internal/catalog ShopCatalog: a versão e todas as ofertas que não estão ocultas. O cliente filtra por data
POST /api/shop/internal/state ShopStateRequest (characterId) → ShopState: saldos de todas as moedas do catálogo e de qualquer outra que a conta tenha, compras por oferta, versão do catálogo. 404 para um personagem desconhecido
POST /api/shop/internal/buy ShopBuyRequest (characterId, offerId, items, giftTo) → ShopResult (mailedTo é o personagem que recebeu a carta, state o do comprador)
POST /api/shop/internal/grant ShopGrantRequest → ShopResult (changed é o personagem de destino)

#API de administração

Cabeçalho X-Admin-Key com Shop:AdminKey. AdminKey vazio desliga a API de administração. O Caddy não a encaminha: chame-a a partir do próprio servidor (127.0.0.1:5300) ou por um túnel SSH.

Método Rota O que faz
GET /api/shop/admin/catalog O arquivo inteiro como um ShopConfig, incluindo ofertas ocultas e as que falham nas verificações. 409 se não puder ser interpretado
PUT /api/shop/admin/catalog Publica um ShopConfig inteiro (no máximo 2 MB, 2.000 ofertas e 500 produtos). Tudo ou nada: com qualquer problema nada é gravado e a resposta é 400 com uma linha por problema (Offer witch_hat: gives no items). Caso contrário, 200 com ok, a nova version e o número de offers
GET /api/shop/admin/offers Todas as ofertas em uso, as ocultas também, e os produtos
PUT /api/shop/admin/offers/{id} Adiciona ou substitui uma oferta, verificada como no arquivo. O resto do arquivo continua; os comentários nele se perdem
DELETE /api/shop/admin/offers/{id} Remove a oferta do arquivo. As compras dela continuam no livro-razão
POST /api/shop/admin/reload Lê o arquivo de novo. 409 se não puder ser interpretado
POST /api/shop/admin/grant { username or accountId, currency, amount, reason?, reference?, detail? }. Uma quantidade negativa retira. A mesma reference duas vezes se aplica uma vez. Responde applied e o novo balance
GET /api/shop/admin/balance/{username} Todas as moedas que a conta tem
GET /api/shop/admin/history/{username}?take=50 As linhas mais recentes do livro-razão, no máximo 500

Publish to server e Pull from server do editor usam as rotas do catálogo. Em um terminal:

curl -H "X-Admin-Key: $KEY" http://127.0.0.1:5300/api/shop/admin/balance/alice
curl -X POST -H "X-Admin-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"username":"alice","currency":"gems","amount":500,"reason":"support","reference":"ticket-1234"}' \
  http://127.0.0.1:5300/api/shop/admin/grant

As gravações substituem o arquivo escrevendo-o ao lado e renomeando-o por cima do antigo. No Docker, a pasta Deploy/shop precisa ter permissão de escrita para o usuário do contêiner (sudo chown 1654 shop).

#Pagamentos

Os webhooks chegam em POST /api/shop/webhooks/{provider}, que o Caddy encaminha a partir de https://<login domain>/api/shop/webhooks/....

  • Um evento de pagamento adiciona amount × quantity do seu produto (premium.topup). Um reembolso o retira (premium.refund). Um saldo pode ficar abaixo de zero; o jogador então não pode comprar até ele voltar a ficar acima do preço.
  • Um evento já aplicado responde 200 com "status": "duplicate". Uma conta ou um produto desconhecido responde 422 e é registrado no log. Uma assinatura inválida responde 400.
  • No máximo Shop:MaxQuantity (100) unidades de um produto por pagamento.

#Stripe

Defina Shop:Stripe:WebhookSecret (KITARPG_STRIPE_WEBHOOK_SECRET) com o segredo de assinatura do endpoint, do painel da Stripe. O próprio Shop verifica Stripe-Signature (HMAC-SHA256 de {t}.{body}, com no máximo ToleranceSeconds de idade), sem o SDK da Stripe.

  1. Na Stripe, adicione um endpoint de webhook https://login.mygame.com/api/shop/webhooks/stripe para checkout.session.completed, checkout.session.async_payment_succeeded e charge.refunded.
  2. Crie Checkout Sessions no seu site com client_reference_id (o id da conta ou o nome de usuário), ou metadata.account_id / metadata.username, mais metadata.product (um id de produto do catálogo) e metadata.quantity quando não for 1.
  3. As sessões concluídas contam assim que forem pagas. A referência é stripe:<payment_intent>.
  4. charge.refunded conta assim que a cobrança é reembolsada por inteiro e retira exatamente o que aquele pagamento deu. Trate reembolsos parciais com a concessão de administração.

#A sua própria loja web

Defina Shop:Signed:Secret (KITARPG_SHOP_SIGNED_SECRET) e faça a sua loja enviar para /api/shop/webhooks/signed:

  • Cabeçalho X-KitARPG-Signature: sha256=<hex HMAC-SHA256 of the raw body with the secret>.
  • Corpo { "id", "kind": "paid" | "refunded", "accountId" or "username", "product", "quantity", "refundOf" }. Um reembolso com refundOf (o id do pedido pago) retira exatamente o que aquele pedido deu.

#Outro provedor

Implemente IPaymentProvider no projeto Shop:

  • Name é o {provider} na URL.
  • Read verifica a assinatura e devolve um PaymentEvent, null para eventos a ignorar, ou lança PaymentRejectedException para os forjados.
  • Registre-o em Shop/Program.cs: builder.Services.AddSingleton<IPaymentProvider, MyProvider>();.

Consoles e lojas de celular precisam dos próprios sistemas de pagamento.

#Configurações

Configuração O que faz Padrão
Shop:CatalogPath O arquivo de catálogo shop-conf.json
Shop:MapKeys Chaves que os servidores de mapa enviam como X-Shop-Key. KITARPG_SHOP_KEY adiciona mais uma. Ter várias permite trocá-las Vazio (dev-shop-key em Development)
Shop:AdminKey Chave da API de administração. Vazio a desliga Vazio (dev-shop-admin-key em Development)
Shop:Stripe:WebhookSecret Segredo do endpoint da Stripe (whsec_...). Vazio desliga a Stripe Vazio
Shop:Stripe:ToleranceSeconds Idade máxima de um evento da Stripe 300
Shop:Signed:Secret Segredo compartilhado com a sua loja web. Vazio o desliga Vazio
Shop:InternalPerMinute Requisições à API interna por endereço do cliente e por minuto 1200
Shop:WebhooksPerMinute Requisições de webhook por endereço do cliente e por minuto 120
Shop:AdminPerMinute Requisições à API de administração por endereço do cliente e por minuto 30
Shop:MaxQuantity Máximo de unidades de um produto em um pagamento 100
Shop:MaxItemsPerBuy Máximo de cópias de itens que uma compra pode levar 100

Ele também lê Database, Proxy e Logs como os outros serviços. Veja Configuração.

#Segurança

  • Fora de Development, o Shop se recusa a iniciar sem uma chave dos mapas, ou com uma chave dos mapas, chave de administração ou segredo de provedor que esteja vazio, curto ou seja um valor de exemplo. Um segredo de provedor vazio só desliga aquele provedor.
  • Chaves e assinaturas são comparadas em tempo constante. Cada grupo de endpoints tem o próprio limite de requisições por endereço do cliente.
  • As APIs interna e de administração ficam fora da internet. Servidores de mapa em outras máquinas chegam ao Shop por uma rede privada ou um túnel WireGuard.
  • Rode um único Shop por banco de dados: as compras são serializadas por um bloqueio no processo dele. O Shop só adiciona novas linhas de itens dentro de cartas novas; mover cópias continua com a Central.

#Erros comuns

  • O botão da loja não aparece. O Shop não está rodando, o mapa não tem -shop/-shopKey, ou o módulo In-game shop está desligado.
  • Uma oferta não aparece no jogo. Ela falhou em uma verificação (o log do Shop diz qual), está oculta, ou as datas dela excluem o dia de hoje.
  • Publicar pelo editor falha com 401. A chave de administração na página Shop não bate com Shop:AdminKey.
  • As edições de administração falham no Docker. A pasta shop não tem permissão de escrita para o uid 1654.
  • Um pagamento não chegou. Procure o webhook no log do Shop: 400 é um segredo errado, 422 uma conta ou um id de produto desconhecido.
