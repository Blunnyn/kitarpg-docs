Security

Esta página ainda não foi traduzida. Ela aparece em inglês.

How KitARPG keeps an online game safe, what you must set up before opening it to players, how to rotate keys, and a checklist to go through before launch.

#The model

  • The server decides. The client only asks. Movement, combat, loot, trades, the bank, the forge, the shop: the map server checks every request and applies it. A modified client can send anything; it can't make the server accept it.
  • Players never reach the database. Map servers don't either: they load and save through Central.
  • Tickets. A client enters a map only with a one-use ticket from Central, valid 30 seconds, for that map only. Nobody skips the login or plays someone else's character.
  • One session per account. Signing in again closes the old session first, after its map saves.
  • Items have one owner. Every copy is one database row with exactly one owner, and every move goes through one lock and one transaction. See Services.
  • Clients carry no server code. Build separation keeps server logic, GM commands, keys and connection strings out of the client you ship. See Builds.

The rest of this page is what you set up so that model holds on your servers.

#Secrets

Secret Where it lives Who must have it
Token signing key Auth:SigningKey / KITARPG_SIGNING_KEY Login and Central
Map key Central:MapKey / KITARPG_MAP_KEY, KITARPG_CENTRAL_KEY on maps Central and every map server
Shop map key Shop:MapKeys / KITARPG_SHOP_KEY The Shop and every map server
Shop admin key Shop:AdminKey / KITARPG_SHOP_ADMIN_KEY The Shop and whoever publishes the catalog
Payment secrets Shop:Stripe:WebhookSecret, Shop:Signed:Secret The Shop and your payment provider
Database password Database:ConnectionString / POSTGRES_PASSWORD Login, Central, the Shop, PostgreSQL

Outside Development, the services refuse to start while any of these is empty, shorter than 16 characters, or a sample value from the repository (anything containing change-me or kitarpg-dev, or starting with development- or dev-). The signing key must also be at least 32 bytes. The database password may not be kitarpg, postgres, password, admin, root or secret. A connection string with no password at all is allowed, for passfiles and trusted local connections.

The launcher and Play & Servers generate random keys per computer and keep them in launcher.json (UserSettings/KitARPG/ from the editor). Docker reads them from Deploy/.env. Keep both out of version control and never put a secret in a client build.

Importante

Anyone with the map key can pose as a map server and save any character. Anyone with the signing key can sign in as any account. Treat both like the database password.

#TLS and the reverse proxy

Login, Central and the Shop speak plain HTTP. In production, Caddy sits in front of them (the compose file starts it):

  • Caddy serves https://<login domain> and https://<central domain> and forwards to the services on the private compose network. It gets and renews the certificates by itself once the domains point at the server and ports 80 and 443 are open.
  • Ports 5100, 5200 and 5300 are published on 127.0.0.1 only, for health checks and the Shop's admin API from the server itself. Don't publish them on other interfaces.
  • Of the Shop, Caddy forwards only /api/shop/webhooks/*, on the Login domain.
  • Release clients refuse to build with plain HTTP addresses for Login or Central (except this computer), and ignore -login, -centralUrl and -mode, so a malicious shortcut can't send a password elsewhere.

#Reverse proxy

Behind a proxy, every request comes from the proxy's address, so per-address rate limits would lump all players together. The services read X-Forwarded-For and X-Forwarded-Proto only when allowed:

Setting What it does Default
Proxy:Enabled Believe forwarded headers at all false
Proxy:KnownProxies Proxy addresses whose headers are believed (loopback always is) Empty
Proxy:KnownNetworks Networks in CIDR form, for proxies without a fixed address Empty
Proxy:ForwardLimit Proxies in the chain 1

The compose file gives Caddy a fixed address (KITARPG_PROXY_ADDRESS, 172.28.0.10) and trusts only that one.

Atenção

Never turn Proxy:Enabled on without a known proxy in front. Clients could then write their own X-Forwarded-For and dodge the rate limits.

#Accounts and tokens

  • Passwords are hashed with Argon2id (19 MiB, 2 passes). Unknown usernames take as long as wrong passwords.
  • Rate limits. /api/auth/* allows Auth:AttemptsPerMinute (10) requests per client and minute, counting IPv4 addresses one by one and IPv6 addresses by /64.
  • Account lock. Auth:FailedLoginsPerAccount (5) wrong passwords lock that username for Auth:FailedLoginMinutes (15) with login_locked, whether the account exists or not.
  • Access tokens live Auth:TokenMinutes (30). A banned or deleted account loses access within Auth:BanCheckSeconds (5).
  • Remember me tokens are stored as SHA-256 only, used once and traded for the next of their family. A reused token deletes the whole family. POST /api/auth/forget-all signs an account out everywhere.

These counters live in memory, per Login process: a restart forgets them, and several Login copies each count on their own.

#The map link

  • Map servers connect to Central on UDP Central:MapLinkPort (7700) and must present Central:MapKey.
  • Central:MapNetworks lists the addresses or networks allowed to open the link. Empty allows any. The compose file allows only its own network.
  • Central passes the key to the maps it launches in the KITARPG_CENTRAL_KEY environment variable, which other users of the machine can't read the way they can a command line.
  • A map can only speak for players on that map: Central checks the sender of every message about a player.
  • The link isn't encrypted. Maps on other machines reach Central over a private network or a WireGuard tunnel. Publish UDP 7700 only on that interface's address and add the network to Central:MapNetworks. Never publish it on the internet.

#The Shop

  • Map servers authenticate with X-Shop-Key, the admin API with X-Admin-Key. Both are compared in constant time.
  • The internal and admin APIs stay off the internet: only webhooks go through Caddy, and port 5300 is published on loopback only.
  • Each endpoint group has its own rate limit per client address.
  • Webhooks are accepted only with a valid signature; each payment counts once.
  • A map server refuses a plain http:// Shop address on a public IP, since its key would cross the internet readable.

See Shop service.

#What the map server checks

A short list of what protects you from modified clients, all in the kit's server code:

  • Command pacing. Every client command counts against 30 per second with bursts of 60; far above that the connection is dropped as flooding. Commands that reach Central (mail, guild, friends, party, reports) get 2 per second with bursts of 10. Trade and duel requests are limited to one every 2 seconds.
  • Targets. A player can only target what their connection sees, never an invisible enemy.
  • Player text. Chat, mail, notes, guild names and roles are cleaned so they can't open TextMeshPro tags.
  • Amounts. Negative, huge or overflowing gold and item amounts are refused in the bank, mail, trade and market.
  • Deliveries. A save made before Central delivered an item (market, mail, guild bank, collectors) can't erase the delivery.
  • GM commands run only for accounts with the right level, and every command of level 2 or more is written to gm_audit first. If Central can't record it, the command doesn't run. See GM tools.

Your own code follows the same rules. See Security rules for your code.

#Builds

  • Release clients are IL2CPP only. The build stops if a release client uses Mono.
  • An MMO client never carries server assemblies, the local save, test tools, keys or connection strings. The build stops if it would.
  • Test tools (KITARPG_DEV) are only in the test client. Never give the test client to players.
  • Keep the IL2CPP symbol folder (*_BackUpThisFolder_ButDontShipItWithYourGame) for crash reports and out of what you ship.

#Running the services

  • Exactly one Central per database. Sessions, tickets, parties and the item lock live in its memory. Two would hand out the same items twice.
  • Exactly one Shop per database. Buys are serialized by a lock in its process.
  • Login may run several times behind the proxy, but each copy adds its own rate limit allowance.
  • Modules run with the service's full rights. Only install modules you trust, list them in Modules:Allow, and keep the module folders read-only (the compose file mounts them that way). Each module's file and SHA-256 are logged at start.
  • Run as non-root. The Docker images run the services as the app user and the map servers as kit.

#Rotating keys

Rotate a key when someone who knew it leaves, when it may have leaked, or on a schedule.

#Token signing key (no downtime)

Auth:SigningKeys is a list. The first key signs; every key in it, plus Auth:SigningKey, is accepted.

  1. Make a new key: openssl rand -hex 32.

  2. On both Login and Central, set the new key first and keep the old one:

    Auth__SigningKeys__0=<new key>
Auth__SigningKeys__1=<old key>

    In Docker Compose, add both lines to the &service-env block of the login service, which Central shares, and run docker compose up -d login central.

  3. Wait at least Auth:TokenMinutes (30 minutes), so every token signed with the old key has expired.

  4. Remove the old key: set KITARPG_SIGNING_KEY to the new key and drop the SigningKeys lines, then restart again.

"Remember me" tokens aren't signed with this key, so players stay remembered.

#Map key (short maintenance)

Central accepts one map key at a time.

  1. Make a new key and put it in KITARPG_MAP_KEY (or Central__MapKey and each map's KITARPG_CENTRAL_KEY).
  2. With players out, restart Central and every map server together: docker compose up -d central map-town map-forest map-crypt.

Maps still on the old key are refused until they restart with the new one.

#Shop map key (no downtime)

The Shop accepts every key in Shop:MapKeys plus KITARPG_SHOP_KEY.

  1. Add the new key to the Shop as Shop__MapKeys__0 next to the old one and restart the Shop.
  2. Give the map servers the new KITARPG_SHOP_KEY and restart them.
  3. Remove the old key from the Shop and restart it.

#Shop admin key

Change KITARPG_SHOP_ADMIN_KEY, restart the Shop, and update the admin key on the editor's Shop page.

#Payment secrets

Roll the webhook secret in your provider's dashboard (Stripe) or in your web shop, put the new value in .env and restart the Shop. Webhooks signed with the old secret are refused from then on.

#Database password

  1. In PostgreSQL: ALTER USER kitarpg PASSWORD '<new password>';
  2. Change POSTGRES_PASSWORD in .env (the compose file builds the connection strings from it).
  3. docker compose up -d login central shop.

POSTGRES_PASSWORD only sets the password when the pgdata volume is first created; afterwards, only ALTER USER changes it.

#Checklist before launch

Secrets

  • [ ] Every value in .env changed from the sample, each made with openssl rand -hex 32.
  • [ ] .env and launcher.json are out of version control and backups are stored safely.
  • [ ] No service runs with ASPNETCORE_ENVIRONMENT=Development.

Network

  • [ ] Firewall open only for 22/tcp, 80/tcp, 443/tcp and udp, and the map UDP ports.
  • [ ] 5100, 5200, 5300, 5432 and 7700 not reachable from the internet.
  • [ ] Both domains resolve and serve HTTPS with a valid certificate.
  • [ ] KITARPG_PUBLIC_ADDRESS is the server's public address.
  • [ ] Map servers on other machines use a private network or WireGuard, listed in Central:MapNetworks.

Builds

  • [ ] The client was built with Build Mac Client or Build Windows Client (IL2CPP), with HTTPS Login Url and Central Url.
  • [ ] KitARPG > Check Build Separation shows no server code in the client.
  • [ ] The test client is nowhere players can get it.
  • [ ] Client and map servers built from the same code.

Services

  • [ ] One Central and at most one Shop per database.
  • [ ] Proxy settings trust only Caddy's address.
  • [ ] Modules:Allow lists your modules, if you use any.
  • [ ] The first admin is named, and GM levels in Game Settings > Commands are what you want.

Data

  • [ ] Nightly database backups, copied off the server, and one restore tested.
  • [ ] The Shop's admin API reachable only from the server or through an SSH tunnel.
