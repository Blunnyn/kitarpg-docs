Servidores e implantação

Segurança

Como o KitARPG mantém um jogo online seguro, o que você precisa configurar antes de abri-lo aos jogadores, como trocar as chaves e uma lista de verificação para revisar antes do lançamento.

#O modelo

  • O servidor decide. O cliente só pede. Movimento, combate, espólio, trocas, banco, forja, loja: o servidor de mapa verifica cada pedido e o aplica. Um cliente modificado pode enviar qualquer coisa; não consegue fazer o servidor aceitar.
  • Os jogadores nunca chegam ao banco de dados. Os servidores de mapa também não: eles carregam e salvam pela Central.
  • Tickets. Um cliente entra em um mapa só com um ticket de uso único da Central, válido por 30 segundos, só para aquele mapa. Ninguém pula o login nem joga com o personagem de outra pessoa.
  • Uma sessão por conta. Entrar de novo fecha primeiro a sessão antiga, depois que o mapa dela salva.
  • Os itens têm um único dono. Cada cópia é uma linha do banco de dados com exatamente um dono, e cada movimento passa por um único bloqueio e uma única transação. Veja Serviços.
  • Os clientes não levam código de servidor. A separação de builds mantém a lógica do servidor, os comandos de GM, as chaves e as strings de conexão fora do cliente que você distribui. Veja Builds.

O resto desta página é o que você configura para que esse modelo se mantenha nos seus servidores.

#Segredos

Segredo Onde fica Quem precisa tê-lo
Chave de assinatura de tokens Auth:SigningKey / KITARPG_SIGNING_KEY Login e Central
Chave dos mapas Central:MapKey / KITARPG_MAP_KEY, KITARPG_CENTRAL_KEY nos mapas A Central e cada servidor de mapa
Chave dos mapas para o Shop Shop:MapKeys / KITARPG_SHOP_KEY O Shop e cada servidor de mapa
Chave de administração do Shop Shop:AdminKey / KITARPG_SHOP_ADMIN_KEY O Shop e quem publica o catálogo
Segredos de pagamento Shop:Stripe:WebhookSecret, Shop:Signed:Secret O Shop e o seu provedor de pagamentos
Senha do banco de dados Database:ConnectionString / POSTGRES_PASSWORD Login, Central, Shop, PostgreSQL

Fora de Development, os serviços se recusam a iniciar enquanto qualquer um desses estiver vazio, tiver menos de 16 caracteres ou for um valor de exemplo do repositório (qualquer coisa que contenha change-me ou kitarpg-dev, ou que comece com development- ou dev-). A chave de assinatura também precisa ter pelo menos 32 bytes. A senha do banco de dados não pode ser kitarpg, postgres, password, admin, root nem secret. Uma string de conexão sem nenhuma senha é permitida, para passfiles e conexões locais confiáveis.

O lançador e Play & Servers geram chaves aleatórias por computador e as guardam no launcher.json (UserSettings/KitARPG/ a partir do editor). O Docker as lê de Deploy/.env. Mantenha os dois fora do controle de versão e nunca coloque um segredo em uma build de cliente.

Importante

Quem tiver a chave dos mapas pode se passar por um servidor de mapa e salvar qualquer personagem. Quem tiver a chave de assinatura pode entrar como qualquer conta. Trate as duas como a senha do banco de dados.

#TLS e o proxy reverso

Login, Central e Shop falam HTTP simples. Em produção, o Caddy fica na frente deles (o arquivo compose o inicia):

  • O Caddy serve https://<login domain> e https://<central domain> e encaminha para os serviços na rede privada do compose. Ele obtém e renova os certificados sozinho assim que os domínios apontam para o servidor e as portas 80 e 443 estão abertas.
  • As portas 5100, 5200 e 5300 são publicadas só em 127.0.0.1, para verificações de saúde e para a API de administração do Shop a partir do próprio servidor. Não as publique em outras interfaces.
  • Do Shop, o Caddy encaminha só /api/shop/webhooks/*, no domínio do Login.
  • Os clientes de release se recusam a ser gerados com endereços HTTP simples para o Login ou a Central (exceto este computador) e ignoram -login, -centralUrl e -mode, para que um atalho malicioso não consiga mandar uma senha para outro lugar.

#Proxy reverso

Atrás de um proxy, cada requisição vem do endereço do proxy, então os limites por endereço juntariam todos os jogadores. Os serviços leem X-Forwarded-For e X-Forwarded-Proto só quando permitido:

Configuração O que faz Padrão
Proxy:Enabled Confiar em cabeçalhos encaminhados false
Proxy:KnownProxies Endereços de proxy cujos cabeçalhos são aceitos (o loopback sempre é) Vazio
Proxy:KnownNetworks Redes em formato CIDR, para proxies sem endereço fixo Vazio
Proxy:ForwardLimit Proxies na cadeia 1

O arquivo compose dá ao Caddy um endereço fixo (KITARPG_PROXY_ADDRESS, 172.28.0.10) e confia só nele.

Atenção

Nunca ligue Proxy:Enabled sem um proxy conhecido na frente. Os clientes poderiam então escrever o próprio X-Forwarded-For e escapar dos limites.

#Contas e tokens

  • Senhas são transformadas em hash com Argon2id (19 MiB, 2 passadas). Nomes de usuário desconhecidos demoram tanto quanto senhas erradas.
  • Limites de requisições. /api/auth/* permite Auth:AttemptsPerMinute (10) requisições por cliente e por minuto, contando endereços IPv4 um a um e endereços IPv6 por /64.
  • Bloqueio de conta. Auth:FailedLoginsPerAccount (5) senhas erradas bloqueiam aquele nome de usuário por Auth:FailedLoginMinutes (15) com login_locked, exista a conta ou não.
  • Tokens de acesso duram Auth:TokenMinutes (30). Uma conta banida ou excluída perde o acesso em até Auth:BanCheckSeconds (5).
  • Os tokens de Remember me são guardados só como SHA-256, usados uma vez e trocados pelo próximo da sua família. Um token reutilizado apaga a família inteira. POST /api/auth/forget-all desconecta uma conta em todos os lugares.

Esses contadores ficam na memória, por processo do Login: um reinício os esquece, e várias cópias do Login contam cada uma por conta própria.

#O link dos mapas

  • Os servidores de mapa se conectam à Central por UDP em Central:MapLinkPort (7700) e precisam apresentar Central:MapKey.
  • Central:MapNetworks lista os endereços ou redes que podem abrir o link. Vazio permite qualquer um. O arquivo compose permite só a própria rede.
  • A Central passa a chave aos mapas que inicia na variável de ambiente KITARPG_CENTRAL_KEY, que outros usuários da máquina não conseguem ler como leriam uma linha de comando.
  • Um mapa só pode falar pelos jogadores daquele mapa: a Central verifica o remetente de cada mensagem sobre um jogador.
  • O link não é criptografado. Mapas em outras máquinas chegam à Central por uma rede privada ou um túnel WireGuard. Publique a UDP 7700 só no endereço dessa interface e adicione a rede a Central:MapNetworks. Nunca a publique na internet.

#O Shop

  • Os servidores de mapa se autenticam com X-Shop-Key, a API de administração com X-Admin-Key. As duas são comparadas em tempo constante.
  • As APIs interna e de administração ficam fora da internet: só os webhooks passam pelo Caddy, e a porta 5300 é publicada só no loopback.
  • Cada grupo de endpoints tem o próprio limite de requisições por endereço do cliente.
  • Os webhooks são aceitos só com uma assinatura válida; cada pagamento conta uma vez.
  • Um servidor de mapa recusa um endereço http:// simples do Shop em um IP público, já que a chave dele cruzaria a internet legível.

Veja Serviço Shop.

#O que o servidor de mapa verifica

Uma lista curta do que protege você de clientes modificados, tudo no código de servidor do kit:

  • Ritmo de comandos. Cada comando do cliente conta contra 30 por segundo com rajadas de 60; muito acima disso, a conexão cai por inundação. Os comandos que chegam à Central (correio, guilda, amigos, grupo, denúncias) têm 2 por segundo com rajadas de 10. Pedidos de troca e de duelo ficam limitados a um a cada 2 segundos.
  • Alvos. Um jogador só pode mirar o que a conexão dele vê, nunca um inimigo invisível.
  • Texto dos jogadores. Chat, correio, notas, nomes de guilda e cargos são limpos para que não possam abrir tags do TextMeshPro.
  • Quantidades. Quantidades de ouro e de itens negativas, enormes ou que estouram são recusadas no banco, no correio, nas trocas e no mercado.
  • Entregas. Um salvamento feito antes de a Central entregar um item (mercado, correio, banco da guilda, coletores) não consegue apagar a entrega.
  • Comandos de GM rodam só para contas com o nível certo, e cada comando de nível 2 ou mais é gravado primeiro em gm_audit. Se a Central não conseguir registrá-lo, o comando não roda. Veja Ferramentas de GM.

O seu próprio código segue as mesmas regras. Veja Regras de segurança para o seu código.

#Builds

  • Os clientes de release são só IL2CPP. A build para se um cliente de release usar Mono.
  • Um cliente MMO nunca leva assemblies de servidor, o salvamento local, ferramentas de teste, chaves ou strings de conexão. A build para se fosse levar.
  • As ferramentas de teste (KITARPG_DEV) estão só no cliente de teste. Nunca dê o cliente de teste aos jogadores.
  • Guarde a pasta de símbolos do IL2CPP (*_BackUpThisFolder_ButDontShipItWithYourGame) para relatórios de falhas e fora do que você distribui.

#Rodar os serviços

  • Exatamente uma Central por banco de dados. Sessões, tickets, grupos e o bloqueio de itens ficam na memória dela. Duas entregariam os mesmos itens duas vezes.
  • Exatamente um Shop por banco de dados. As compras são serializadas por um bloqueio no processo dele.
  • O Login pode rodar várias vezes atrás do proxy, mas cada cópia soma a própria cota de limite de requisições.
  • Os módulos rodam com todos os direitos do serviço. Instale só módulos em que você confia, liste-os em Modules:Allow e mantenha as pastas de módulos somente leitura (o arquivo compose as monta assim). O arquivo e o SHA-256 de cada módulo são registrados no log ao iniciar.
  • Rode sem root. As imagens Docker rodam os serviços como o usuário app e os servidores de mapa como kit.

#Trocar as chaves

Troque uma chave quando alguém que a conhecia sair, quando ela puder ter vazado, ou em uma agenda fixa.

#Chave de assinatura de tokens (sem parada)

Auth:SigningKeys é uma lista. A primeira chave assina; todas as chaves da lista, mais Auth:SigningKey, são aceitas.

  1. Crie uma chave nova: openssl rand -hex 32.

  2. Tanto no Login quanto na Central, coloque a chave nova primeiro e mantenha a antiga:

    Auth__SigningKeys__0=<new key>
Auth__SigningKeys__1=<old key>

    No Docker Compose, adicione as duas linhas ao bloco &service-env do serviço login, que a Central compartilha, e rode docker compose up -d login central.

  3. Espere pelo menos Auth:TokenMinutes (30 minutos), para que todo token assinado com a chave antiga tenha expirado.

  4. Remova a chave antiga: defina KITARPG_SIGNING_KEY com a chave nova e tire as linhas de SigningKeys, depois reinicie de novo.

Os tokens de "Remember me" não são assinados com essa chave, então os jogadores continuam lembrados.

#Chave dos mapas (manutenção curta)

A Central aceita uma chave dos mapas por vez.

  1. Crie uma chave nova e coloque-a em KITARPG_MAP_KEY (ou em Central__MapKey e no KITARPG_CENTRAL_KEY de cada mapa).
  2. Com os jogadores fora, reinicie a Central e todos os servidores de mapa juntos: docker compose up -d central map-town map-forest map-crypt map-guild-hall.

Os mapas que ainda estiverem com a chave antiga são recusados até reiniciarem com a nova.

#Chave dos mapas para o Shop (sem parada)

O Shop aceita todas as chaves em Shop:MapKeys mais KITARPG_SHOP_KEY.

  1. Adicione a chave nova ao Shop como Shop__MapKeys__0 ao lado da antiga e reinicie o Shop.
  2. Dê aos servidores de mapa o novo KITARPG_SHOP_KEY e reinicie-os.
  3. Remova a chave antiga do Shop e reinicie-o.

#Chave de administração do Shop

Mude KITARPG_SHOP_ADMIN_KEY, reinicie o Shop e atualize a chave de administração na página Shop do editor.

#Segredos de pagamento

Gere um novo segredo de webhook no painel do seu provedor (Stripe) ou na sua loja web, coloque o novo valor no .env e reinicie o Shop. Os webhooks assinados com o segredo antigo passam a ser recusados.

#Senha do banco de dados

  1. No PostgreSQL: ALTER USER kitarpg PASSWORD '<new password>';
  2. Mude POSTGRES_PASSWORD no .env (o arquivo compose monta as strings de conexão a partir dela).
  3. docker compose up -d login central shop.

POSTGRES_PASSWORD só define a senha quando o volume pgdata é criado pela primeira vez; depois disso, só ALTER USER a muda.

#Lista de verificação antes do lançamento

Segredos

  • [ ] Todos os valores do .env trocados em relação ao exemplo, cada um criado com openssl rand -hex 32.
  • [ ] .env e launcher.json estão fora do controle de versão e as cópias de segurança estão guardadas com segurança.
  • [ ] Nenhum serviço roda com ASPNETCORE_ENVIRONMENT=Development.

Rede

  • [ ] Firewall aberto só para 22/tcp, 80/tcp, 443/tcp e udp, e as portas UDP dos mapas.
  • [ ] 5100, 5200, 5300, 5432 e 7700 inacessíveis pela internet.
  • [ ] Os dois domínios resolvem e servem HTTPS com um certificado válido.
  • [ ] KITARPG_PUBLIC_ADDRESS é o endereço público do servidor.
  • [ ] Servidores de mapa em outras máquinas usam uma rede privada ou WireGuard, listada em Central:MapNetworks.

Builds

  • [ ] O cliente foi gerado com Build Mac Client ou Build Windows Client (IL2CPP), com Login Url e Central Url em HTTPS.
  • [ ] KitARPG > Check Build Separation não mostra código de servidor no cliente.
  • [ ] O cliente de teste não está em nenhum lugar onde os jogadores possam pegá-lo.
  • [ ] Cliente e servidores de mapa gerados a partir do mesmo código.

Serviços

  • [ ] Uma Central e no máximo um Shop por banco de dados.
  • [ ] As configurações de Proxy confiam só no endereço do Caddy.
  • [ ] Modules:Allow lista os seus módulos, se você usar algum.
  • [ ] O primeiro administrador está definido, e os níveis de GM em Game Settings > Commands são os que você quer.

Dados

  • [ ] Cópias de segurança noturnas do banco de dados, copiadas para fora do servidor, e uma restauração testada.
  • [ ] A API de administração do Shop acessível só a partir do servidor ou por um túnel SSH.
