Servidores e implantação

Banco de dados

Onde um jogo online do KitARPG guarda contas, personagens e itens: SQLite ou PostgreSQL, como o esquema é criado e atualizado, cada tabela, como mudar para PostgreSQL e como fazer backup e restaurar.

#SQLite ou PostgreSQL

Login, Central e o Shop compartilham um banco de dados. Os servidores de mapa nunca se conectam a ele; eles carregam e salvam através da Central.

SQLite PostgreSQL
O que é Um arquivo no disco Um servidor de banco de dados
Configuração Nenhuma Um servidor, um banco de dados e um usuário (o editor pode criá-los)
Bom para Desenvolvimento, testes, servidores privados pequenos em uma máquina Produção, qualquer coisa pública, mapas em várias máquinas
Onde UserSettings/KitARPG/data/kitarpg.db pelo editor, data/kitarpg.db ao lado de launcher.json pelo lançador Onde o seu servidor rodar. No Docker Compose, o volume pgdata
Colunas JSON Texto jsonb
Versões Incluído nos serviços PostgreSQL 16 ou mais recente. O arquivo compose usa postgres:17-alpine

O mesmo código e as mesmas migrações rodam nos dois. Cada provedor tem o próprio contexto de banco de dados (SqliteGameDbContext, PostgresGameDbContext) e a própria pasta de migrações.

Um jogo de um jogador (single player) não usa nenhum dos dois: ele salva no próprio arquivo SQLite, na pasta de dados persistentes do jogador (savegame.db por padrão, definido em KitARPGSettings como Save File (saveFile)). Esse arquivo pertence ao jogador e não é tratado aqui.

#Configurações

Todo serviço lê a mesma seção Database. As variáveis de ambiente usam __ entre os níveis.

Configuração Variável de ambiente O que faz Padrão
Database:Provider Database__Provider Sqlite ou Postgres Sqlite
Database:ConnectionString Database__ConnectionString A conexão. SQLite: Data Source=<file>. PostgreSQL: Host=...;Port=5432;Database=...;Username=...;Password=... Data Source=kitarpg.db
Database:MigrateOnStartup Database__MigrateOnStartup Atualiza o esquema quando o serviço inicia e depois migra as tabelas dos módulos true

Um caminho relativo do SQLite é relativo à pasta do próprio serviço. Quando você roda os serviços à mão, dê a todos o mesmo caminho absoluto, ou cada um cria o próprio arquivo.

Todas as opções de connection string do Npgsql funcionam, por exemplo SSL Mode=Require para servidores hospedados e Maximum Pool Size=... para o pool de conexões.

#Migrações

  • Com MigrateOnStartup ligado, cada serviço aplica as migrações que faltam ao iniciar. O lançador inicia o Login primeiro e espera um momento, então geralmente é o Login que faz isso.
  • As migrações aplicadas são registradas em __EFMigrationsHistory. As de um módulo vão em __ModuleMigrations_<module name>.
  • Uma atualização do kit que muda o esquema traz migrações novas para os dois provedores. Reiniciar os serviços as aplica.
  • As migrações só vão para frente. Algumas movem dados de formas que não podem ser desfeitas (por exemplo ItemOwnersAndCatalog, que transformou em linhas os itens guardados como JSON). Faça backup antes de atualizar o kit em um servidor ativo.

Para criar as suas próprias tabelas, escreva um módulo de serviço com o próprio contexto e as próprias migrações; nunca altere as tabelas do kit. Veja Módulos de serviço. Se mesmo assim você alterar as entidades do kit (no seu próprio fork), gere uma migração para os dois provedores:

cd Services/Data
dotnet ef migrations add <Name> --context SqliteGameDbContext --output-dir Migrations/Sqlite
dotnet ef migrations add <Name> --context PostgresGameDbContext --output-dir Migrations/Postgres

#Tabelas

Tabela O que guarda Escrita por
accounts Nome de usuário (único, até 32), e-mail, hash Argon2id da senha, nível de GM (Role: 1 Player, 2 Moderator, 3 Game Master, 4 Admin), BannedUntil, ouro do banco, data de criação Login, Central (banimentos, níveis, banco)
characters Nome (único), classe, nível, experiência, ouro, mapa e posição, vida, mana, pontos livres, e colunas JSON para moedas, atributos, habilidades, barra rápida, aparência e Extra (missões, progresso, o seu próprio PlayerData em game). Version recusa saves antigos; Deliveries conta o que a Central entregou Login cria, Central salva
item_instances Cada cópia de cada item: uid, id do item, exatamente um dono (CharacterId, AccountId, GuildId, MailId, CollectorId ou ListingId), contêiner, espaço, quantidade, vinculado, JSON Extra (tiradas aleatórias, melhoria, gemas) Central, o Shop (cópias novas em cartas)
items O catálogo de itens: id, nome, categoria e o resto do que os dados do jogo exportam, mais Retired Login, a cada início
skills O catálogo de habilidades: id, nome, classes, Retired Login, a cada início
friends Pares de personagens Central
guilds, guild_members Guildas (nome único, aviso, nível, melhorias, emblema, aliança) e seus membros com cargos Central
guild_events Linhas do histórico da guilda, apagadas depois de Central:GuildHistoryDays Central
alliances Alianças (nome e sigla únicos, aviso) Central
mails Cartas: destinatário, nome do remetente, assunto, corpo, ouro, validade, Kind (shop para entregas da loja) Central, o Shop
market_listings Lotes no mercado: vendedor, item, preço unitário, validade Central
collectors Coletores de impostos: guilda, mapa, ponto Central
game_logs O registro do jogo: tipo, hora, conta, personagem, mapa, item, ouro, detalhe. Limpo depois de Logs:Days Login, Central, o Shop
gm_audit Cada comando de GM de nível 2 ou mais, com a linha, o alvo e o resultado Central
reports Denúncias de jogadores, com o chat ao redor delas Central
remember_tokens SHA-256 de cada token de "Remember me", sua família, conta, endereço, validade e uso Login
currency_ledger Cada mudança em um saldo premium, com uma referência única O Shop

O próprio banco de dados garante as regras importantes:

  • item_instances tem uma check constraint: exatamente um dono e uma quantidade acima de zero. O id do item é uma chave estrangeira para items, então uma cópia não pode apontar para um item que o catálogo nunca teve.
  • Excluir um personagem, conta, guilda, carta, coletor ou lote do mercado exclui as cópias que ele guarda.
  • Nomes de usuário, nomes de personagens, nomes de guildas e nomes e siglas de alianças são únicos, comparados em uma forma normalizada.
  • currency_ledger.Reference é único, então um pagamento ou uma concessão conta uma única vez.

Não edite items nem skills à mão: o Login os sobrescreve a partir do gamedata.json a cada início.

#Mudar para PostgreSQL

#Pelo editor

  1. Abra KitARPG > Play and Servers, escolha MMO e pare os serviços se estiverem rodando.
  2. Na etapa do banco de dados, escolha PostgreSQL: for production e pressione Set up PostgreSQL... (gere os serviços primeiro; são eles que fazem a comunicação).
  3. Escolha uma opção:
    • A server I run: preencha Host, Port e SSL (Prefer, Require ou Disable; servidores hospedados geralmente precisam de Require). Depois, Create the database for me com um login de administrador (usado uma vez, nunca salvo) e Create and use, ou Use a database I have e Test and use.
    • Docker on this computer: Create and use inicia o PostgreSQL 17 em um contêiner chamado kitarpg-postgres, publicado em 127.0.0.1 na porta 5432 (ou na próxima livre), com os dados no volume kitarpg-pgdata e uma senha aleatória.
  4. Inicie os serviços. As tabelas são criadas no primeiro início.

A conexão é salva para este computador em UserSettings/KitARPG/launcher.json. Veja Play & Servers.

#Com o lançador

Defina dois campos em launcher.json:

{
  "DatabaseProvider": "Postgres",
  "ConnectionString": "Host=localhost;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>"
}

Para criar o banco de dados e o usuário primeiro, dotnet run --project Launcher -- --postgres com uma requisição create faz o mesmo que o editor. Veja Lançador.

#À mão

Como superusuário do PostgreSQL:

CREATE ROLE kitarpg LOGIN PASSWORD '<long random password>';
CREATE DATABASE kitarpg OWNER kitarpg ENCODING 'UTF8';

Depois, passe para todos os serviços:

Database__Provider=Postgres
Database__ConnectionString="Host=db.example.com;Port=5432;Database=kitarpg;Username=kitarpg;Password=<password>;SSL Mode=Require"

#No Docker Compose

O arquivo compose já usa PostgreSQL com a senha de POSTGRES_PASSWORD em Deploy/.env. Veja Docker.

Nota

Trocar de provedor começa com um banco de dados vazio. O kit não copia dados do SQLite para o PostgreSQL. Faça a troca antes de ter jogadores.

#Backups

Faça backup do banco de dados inteiro: personagens, itens, guildas, correio e o livro-razão da loja só fazem sentido juntos.

#PostgreSQL no Docker Compose

A partir da pasta Deploy:

docker compose exec -T postgres pg_dump -U kitarpg -d kitarpg -Fc > kitarpg-$(date +%F).dump

O pg_dump tira um snapshot consistente enquanto o jogo roda. Copie o arquivo para fora do servidor. Para rodá-lo toda noite, coloque a linha no crontab do servidor com o caminho completo da pasta Deploy.

#PostgreSQL em outro lugar

pg_dump "host=db.example.com dbname=kitarpg user=kitarpg sslmode=require" -Fc > kitarpg.dump

Serviços de PostgreSQL hospedado também mantêm os próprios backups; verifique por quanto tempo os guardam.

#SQLite

Pare os serviços e depois copie kitarpg.db junto com kitarpg.db-wal e kitarpg.db-shm, se existirem. Copiar o arquivo enquanto os serviços rodam pode gerar uma cópia corrompida.

#Restaurar

  1. Pare o Login, a Central, o Shop e os servidores de mapa (docker compose stop login central shop map-town map-forest map-crypt map-guild-hall).

  2. Restaure em um banco de dados vazio:

    docker compose exec -T postgres dropdb -U kitarpg kitarpg
docker compose exec -T postgres createdb -U kitarpg -O kitarpg kitarpg
docker compose exec -T postgres pg_restore -U kitarpg -d kitarpg < kitarpg-2026-11-10.dump

  3. Inicie tudo de novo. Se o backup for mais antigo que os serviços, as migrações que faltam rodam no início.

Atenção

Restaurar volta todos os jogadores ao momento do backup, incluindo a moeda premium comprada desde então. Os pagamentos feitos depois do backup continuam no seu provedor de pagamento; conceda-os de novo com a API de administração do Shop antes de reabrir.

#Consultas do dia a dia

Defina o primeiro administrador depois de criar a sua conta:

UPDATE accounts SET "Role" = 4 WHERE "Username" = 'yourname';

Os nomes das colunas mantêm as maiúsculas, então precisam de aspas duplas no PostgreSQL. Depois disso, os administradores mudam os níveis no jogo com /role. Veja Ferramentas de GM.

Outras leituras úteis:

-- Who is banned
SELECT "Username", "BannedUntil" FROM accounts WHERE "BannedUntil" > now();
-- The latest GM commands
SELECT "At", "Character", "Line", "Result" FROM gm_audit ORDER BY "At" DESC LIMIT 50;

Prefira as ferramentas do próprio jogo (/logs, /reports, o painel de GM) para moderação. Nunca mova itens ou ouro com SQL enquanto o jogo roda: a Central e os mapas mantêm a própria visão e sobrescreveriam ou duplicariam a sua mudança.

#Retenção de logs

Configuração O que faz Padrão
Logs:Days Dias que as linhas de game_logs são mantidas. Verificado uma vez por hora. 0 as mantém para sempre 180
Central:GuildHistoryDays Dias que as linhas do histórico da guilda são mantidas 90

Defina-as em todos os serviços que escrevem o registro (Login, Central e o Shop).

#Erros comuns

  • Dois arquivos SQLite. Serviços rodados à mão a partir de pastas diferentes com a connection string padrão criam, cada um, o próprio kitarpg.db. Use um único caminho absoluto.
  • "The database password in Database:ConnectionString is empty or a sample value." Fora de Development, os serviços recusam senhas como kitarpg, postgres, password ou qualquer coisa com change-me. Use uma senha longa e aleatória.
  • O usuário não consegue criar tabelas. O usuário do jogo precisa ser dono do banco de dados (ou ter CREATE nele e no esquema public). O Test and use do editor verifica isso.
  • Editar items à mão. O Login o sobrescreve no próximo início. Altere o item no Game Database e exporte de novo.
