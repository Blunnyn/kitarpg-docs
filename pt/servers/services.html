Servidores e implantação

Serviços

Login, Central e Shop são serviços web .NET 10 que rodam ao lado dos seus servidores de mapa. Esta página cobre o que cada um faz, cada endpoint, as mensagens do link dos mapas e as peças compartilhadas sobre as quais eles são construídos.

#Onde estão

Os serviços são uma solução .NET, KitARPG.Services.slnx, com estes projetos:

Projeto O que faz
Shared Compila os contratos e as regras em Assets/Blunnyn/KitARPG/Runtime/Shared/, para que os serviços e o Unity usem o mesmo código
Data EF Core: as tabelas, um contexto de banco de dados por provedor (SQLite e PostgreSQL) e as migrações deles. Veja Banco de dados
Hosting O que todo serviço compartilha: verificação de tokens, JSON, limites de tamanho de requisição, cabeçalhos de proxy, recusa de segredos de exemplo, o gravador do log do jogo, verificação de banimentos
Modules O contrato e o carregador dos seus próprios módulos de Login e Central. Veja Módulos de serviço
Login Contas e personagens
Central Sessões, tickets, o link dos mapas e tudo o que é compartilhado entre mapas
Shop A loja premium opcional. Veja Serviço Shop
Launcher Inicia tudo com um botão ou um comando. Veja Lançador
Examples/Bounties Um exemplo de módulo da Central com a própria tabela
Tests Testes das regras, do Login, da Central (com um servidor de mapa falso), do Shop e dos módulos, em SQLite

No pacote da Asset Store eles vêm como Assets/Blunnyn/KitARPG/Services.zip. O editor os descompacta em Assets/Blunnyn/KitARPG/Services~ na primeira vez que abre, e de novo quando uma atualização do kit traz um zip novo. O Unity não importa pastas cujo nome termina em ~. KitARPG > Play and Servers os compila para você; em um terminal:

cd Assets/Blunnyn/KitARPG/Services~
dotnet build
dotnet test

#O que todo serviço compartilha

  • JSON. Requisições e respostas são JSON com nomes em camelCase. Os contratos compartilhados usam campos públicos para que o JsonUtility do Unity também os leia.
  • Erros. Uma requisição recusada responde { "code": "...", "message": "..." }. Os códigos estão em ErrorCodes no código compartilhado, por exemplo wrong_credentials, login_locked, account_banned, session_busy, map_unavailable, character_limit.
  • Tamanho do corpo. Requisições acima de 64 KB são recusadas. A publicação do catálogo do Shop tem o próprio limite de 2 MB.
  • Saúde. GET /health responde ok no Login, na Central e no Shop. Use-o para balanceadores de carga e monitoramento.
  • Migrações. Com Database:MigrateOnStartup ligado (o padrão), cada serviço atualiza o esquema do banco de dados ao iniciar.
  • Segredos de exemplo. Fora do ambiente Development, um serviço se recusa a iniciar enquanto uma chave ou a senha do banco de dados estiver vazia, curta ou for um valor de exemplo. Veja Segurança.
  • Log do jogo. Cada serviço grava as próprias linhas em game_logs em lotes, fora do caminho da requisição. Linhas com mais de Logs:Days (180) dias são apagadas uma vez por hora; 0 as mantém.

#Login

O Login é dono das contas e dos personagens. Os clientes chegam a ele por HTTPS em produção.

#Endpoints

Método Rota Precisa de O que faz
POST /api/auth/register Nada Cria uma conta: username, password, email (opcional). 201, ou 409 username_taken
POST /api/auth/login Nada username, password, remember. Responde token, expiresAt (segundos Unix), accountId, username e, com remember, um rememberToken
POST /api/auth/resume Um token de remember Troca o token de remember por um novo token de acesso e o próximo token de remember
POST /api/auth/forget Um token de remember Apaga a família desse token (sai neste computador)
POST /api/auth/forget-all Token de acesso Apaga todos os tokens de remember da conta (sai em todos os lugares)
GET /api/characters Token de acesso Os personagens da conta e maxCharacters
POST /api/characters Token de acesso Cria um personagem: name, classId, appearance
DELETE /api/characters/{id} Token de acesso Apaga um dos personagens da conta e tudo o que ele guarda
GET /health Nada ok

Toda rota /api/auth/* conta contra o limite de requisições abaixo.

#Senhas

As senhas são transformadas em hash com Argon2id: 19 MiB de memória, 2 passadas, salt de 16 bytes, hash de 32 bytes. Os parâmetros ficam guardados dentro de cada hash, então podem ser aumentados depois sem quebrar as contas existentes. Quando um nome de usuário não existe, o Login ainda gera o hash de uma senha fictícia, para que um nome de usuário errado demore tanto quanto uma senha errada.

#Tokens de acesso

  • Um JWT assinado com HMAC-SHA256 com a primeira chave de Auth:SigningKeys (ou Auth:SigningKey).
  • Dura Auth:TokenMinutes (30). Emissor e público são Auth:Issuer (kitarpg).
  • Leva o id da conta (sub), o nome de usuário e o nível de GM.
  • A Central o valida com as mesmas chaves. Uma conta banida ou excluída perde o acesso em até Auth:BanCheckSeconds (5), com HTTP 403 account_banned.

#Remember me

  • Com remember: true, a entrada devolve um token aleatório de 32 bytes. O banco de dados guarda só o SHA-256 dele em remember_tokens, com a conta, o endereço e uma validade de Auth:RememberDays (30).
  • POST /api/auth/resume usa o token uma vez e devolve o próximo da mesma família.
  • Um token já gasto que volta significa que alguém o copiou. O Login apaga a família inteira, então tanto o dono quanto quem copiou precisam entrar de novo com a senha. A linha remember token reused vai para o log do jogo.
  • Uma conta guarda no máximo 10 computadores lembrados; entrar em mais um descarta o mais antigo.
  • O cliente guarda o nome de usuário, as caixas de seleção e o token, nunca a senha.

#Limites de requisições

Limite Configuração Padrão
Requisições a /api/auth/* por cliente e por minuto Auth:AttemptsPerMinute 10
Senhas erradas por nome de usuário antes de ele ser bloqueado Auth:FailedLoginsPerAccount 5
Duração do bloqueio, em minutos Auth:FailedLoginMinutes 15
  • Os clientes são contados por endereço IPv4, ou pelo /64 de um endereço IPv6.
  • Um nome de usuário bloqueado responde HTTP 429 login_locked. Nomes de usuário desconhecidos são contados do mesmo jeito, então a resposta nunca diz se uma conta existe. Uma senha correta zera a contagem.
  • Os contadores ficam na memória: um reinício os esquece, e cada cópia do Login conta por conta própria.
  • Atrás de um proxy reverso, ligue as configurações de Proxy, senão todo jogador parece ter o endereço do proxy. Veja Segurança.

#Personagens e gamedata.json

O Login cria personagens a partir do gamedata.json, um arquivo exportado do seu Game Database: os modelos de jogador, as classes que cada modelo pode ter, o mapa inicial, a posição, a vida, a mana e os itens iniciais de cada classe, o catálogo de itens e habilidades, e o máximo de personagens por conta (maxCharactersPerAccount no Game Database, 6 por padrão).

  • Characters:GameDataFile diz onde ele está (gamedata.json ao lado do serviço, por padrão).
  • KitARPG > Play and Servers o exporta cada vez que inicia os serviços, para UserSettings/KitARPG/gamedata.json.
  • KitARPG > Export Game Data for Services o grava em Services/Login/gamedata.json, para que uma build ou uma imagem Docker do Login o leve junto. Rode-o antes de compilar o Login para um servidor.
  • Sem o arquivo, o Login registra um erro no log e ninguém consegue criar personagens.
  • Um personagem só pode ter uma classe que o seu modelo oferece. Os nomes são únicos no jogo inteiro.

A cada início, o Login copia os itens e as habilidades do arquivo para as tabelas items e skills. Um item removido não é apagado: é marcado como aposentado, já que ainda pode haver cópias apontando para ele. Se o arquivo não tiver itens, o catálogo fica como estava.

#Central

A Central é o centro do mundo online. Os clientes a chamam uma vez por entrada em um mapa; os servidores de mapa ficam conectados a ela o tempo todo.

#Endpoints HTTP

Método Rota Precisa de O que faz
POST /api/play Token de acesso characterId. Responde mapId, address, port e um ticket de uso único. 404 character_not_found, 403 account_banned, 503 map_unavailable ou session_busy
GET /api/maps Nada Os mapas registrados e os jogadores em cada um: [{ "mapId": "town", "players": 3 }]
GET /health Nada ok

Os módulos adicionam os próprios endpoints. Veja Falar com a Central.

#Tickets e sessões

  • /api/play abre uma sessão para a conta no estado Pending com um ticket aleatório de 24 bytes. Ele expira depois de Central:TicketSeconds (30).
  • O servidor de mapa envia o ticket à Central; a Central o resgata uma vez, só para aquele mapa, e a sessão passa a InMap.
  • Só o mapa que tem a sessão pode salvar o personagem ou pedir para movê-lo.
  • Entrar de novo enquanto joga derruba primeiro a sessão antiga. Veja Entrar duas vezes.

#Iniciar servidores de mapa

A Central conhece os mapas por Central:Maps. Para cada mapa:

  • Com um Executable, a Central o inicia com Arguments quando um jogador precisa dele, ou ao iniciar com AutoStart, e espera até Central:LaunchTimeoutSeconds (60) para ele se registrar. A chave dos mapas vai para o processo na variável de ambiente KITARPG_CENTRAL_KEY.
  • Sem um, o mapa é iniciado por outra coisa (Docker, o editor em Play, um gerenciador de serviços). A Central espera 3 segundos para ele se registrar.
  • Um mapa que se registra mas não está na lista funciona mesmo assim enquanto roda; listá-lo permite que a Central espere por ele.
  • Parar a Central encerra os servidores de mapa que ela iniciou.

Veja Configuração para todos os campos.

#O link dos mapas

Os servidores de mapa se conectam à Central por UDP em Central:MapLinkPort (7700) com LiteNetLib. O pedido de conexão precisa levar Central:MapKey, e o endereço do remetente precisa estar em Central:MapNetworks quando essa lista não está vazia. Cada mensagem é o nome da sua classe seguido de um corpo JSON, enviada de forma confiável e ordenada.

Mensagem do mapa O que a Central faz
MapRegister Adiciona o mapa com o id, o endereço público e a porta. Recusada se outro servidor já tiver esse id de mapa
MapHeartbeat Atualiza a contagem de jogadores (a cada 5 segundos)
TicketCheck Resgata um ticket e envia o personagem
CharacterSave Salva o personagem se este mapa o tiver e a versão bater; encerra a sessão quando o jogador sai
TransferRequest Salva a nova posição, inicia o mapa de destino se precisar e devolve um ticket para ele
ChatRelay, FriendCommand, PartyCommand, CharacterLevel Chat entre mapas, amigos, grupos, mudanças de nível
GuildCommand, AllianceCommand, GuildExperience, GuildStorageCommand Guildas, alianças, níveis de guilda e o banco da guilda
MailSend, MailCommand Correio
MarketCommand O mercado entre jogadores
CollectorCommand Coletores de impostos
BanRequest, RoleChange, GmAuditBatch, RatesChange Ações de GM; as linhas de auditoria só são confirmadas depois de guardadas
PlayerReport, ReportCommand Denúncias de jogadores
GameLogBatch Linhas do log do jogo, marcadas com o id do mapa remetente
Qualquer outro nome de classe Entregue a um módulo que o registrou, ou registrada no log como desconhecida

A Central verifica se uma mensagem sobre um jogador vem do mapa em que esse jogador está, então um mapa só pode falar pelos próprios jogadores.

#Os itens se movem por um único livro-razão

Cada cópia de um item é uma linha de item_instances com exatamente um dono: um personagem, um banco de conta, uma guilda, uma carta, um coletor de impostos ou um lote do mercado. O ItemLedger da Central muda os donos um movimento por vez, dentro de uma transação:

  • Um movimento só acontece se a cópia estiver onde o remetente diz que está. Uma cópia que está com outro dono é recusada e registrada no log.
  • Um item que o catálogo não conhece nunca chega ao banco de dados. O mapa o mantém e tenta de novo depois que o Login tiver a nova exportação.
  • Mercado, correio, depósito da guilda e coletores aumentam o contador Deliveries do personagem na mesma transação. O mapa registra a última entrega que aplicou, então um salvamento feito antes de uma entrega não consegue apagá-la.

É por isso que deve haver exatamente uma Central por banco de dados: o bloqueio fica no processo dela.

#Limites que a Central impõe

As configurações da própria Central (tamanhos de amigos, grupo e guilda, regras do correio e do mercado) estão listadas em Configuração. Alguns limites são fixos no código:

Limite Valor
Ouro ou porte em uma carta 1.000.000.000.000.000
Preço de um lote do mercado 1.000.000.000.000
Denúncias que um jogador pode enviar por dia 10
Linhas de auditoria de GM por lote vindo de um mapa 500

#Shop

O Shop é opcional e separado: a Central não sabe que ele existe. Os servidores de mapa chamam a API interna dele com uma chave; os provedores de pagamento chamam os webhooks dele; você o administra com a API de administração. Tudo sobre ele está em Serviço Shop.

#Rodar um serviço à mão

O lançador é o caminho fácil. Para rodar um serviço sozinho, para depurar:

cd Services
ASPNETCORE_ENVIRONMENT=Development \
ASPNETCORE_URLS=http://127.0.0.1:5100 \
Database__ConnectionString="Data Source=$PWD/kitarpg.db" \
dotnet run --project Login
  • Development usa as chaves de teste em appsettings.Development.json. Nunca o use em um servidor.
  • Sem ASPNETCORE_URLS, dotnet run usa as portas do Properties/launchSettings.json do projeto (5022 para o Login, 5091 para a Central, 5300 para o Shop), não as 5100 e 5200 que o cliente espera.
  • Com SQLite, dê a todos os serviços o mesmo arquivo com caminho absoluto. O padrão Data Source=kitarpg.db é relativo à pasta de cada serviço, então o Login e a Central criariam cada um o próprio banco de dados.
  • A Central iniciada assim tem os mapas do appsettings.json sem executáveis: inicie os servidores de mapa você mesmo com -central 127.0.0.1:7700 e a chave dos mapas de desenvolvimento.

#Erros comuns

  • Ninguém consegue criar personagens. O Login não encontrou o gamedata.json. O log dele diz onde procurou. Exporte-o e reinicie o Login.
  • "Map ... is not running." O mapa não está registrado: a build do servidor de mapa não existe, o caminho do executável está errado, ele caiu (veja o log dele), ou a chave ou o endereço dele não são permitidos. A Central registra Refused a map link e Map registration refused no log com o motivo.
  • Os jogadores recebem session_busy. O mapa antigo não confirmou o salvamento dentro de KickWaitSeconds. Normalmente se resolve em poucos segundos. Se continuar acontecendo, olhe o log desse mapa.
  • Os tokens falham entre o Login e a Central. Os dois precisam ter as mesmas chaves de assinatura e o mesmo emissor.
